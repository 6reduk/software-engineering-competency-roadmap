## Профиль A — security, technical correctness и measurement

Независимо проверить по первичным источникам и минимальному runtime-воспроизведению:

- существование, совместимость и фактический запуск CPython 3.14.0, FastAPI 0.137.1, Starlette 1.3.1 и Pydantic 2.12.5;
- осознанность pinned baseline при доступных более новых версиях: old-but-reproducible допустим только при рабочем exact stack и честной freshness note;
- exact contract `POST /orders/export`, strict JSON binding и две различимые безопасные `422 application/problem+json` semantics;
- Pydantic/FastAPI поведение для integer/string coercion, array shape, duplicate, alias, unknown, forbidden и extra fields;
- отсутствие доверия к tenant/body/header/query input и отсутствие cross-tenant данных в allowed/error/audit paths;
- корректность allowlist и построение CSV header только из нормализованных разрешённых полей;
- формулу `max_rows × unique_allowed_fields`, порядок `bind → normalize → estimate → admit/reject → execute` и отсутствие client-owned cost/weights;
- точные граничные случаи `400×4=1600`, `500×4=2000`, `501×4=2004`, `500×5=2500`;
- доказательство reject-before-work не только status code, но и нулевые delta обоих server-side indicators;
- отсутствие обхода через duplicate, type, alias, unknown, sensitive, extra либо client-tenant variants;
- корректность фактического `cells_serialized`, включая оговорку, что header не входит в unit;
- корректность и полезность recovery population после 100 bypass requests: не выдаёт ли она тривиальный результат за доказательство восстановления ресурсов;
- честность измерений: 20 последовательных requests, timings как diagnostic-only, точки измерения, TestClient warning и границы synthetic in-memory substrate;
- применимость RFC 9110/RFC 9457 и OWASP API4:2023 к конкретным claims, media types и error disclosure;
- audit record и отсутствие token, body, field values, exported rows, sensitive input и лишней cost telemetry;
- честность applicability matrix: request/cost и field exposure доказаны; quota/rate и untrusted target действительно ограничены как `not applicable` с residual risk;
- отсутствие обещаний distributed quota, aggregate fairness, SSRF protection, production storage cost, total memory/response bound или универсального threshold;
- отсутствие готовой реализации в source tree.

Runtime harness выполнять вне репозитория; fixtures и реализацию в source tree не добавлять. В отчёте указать exact environment, substitutions, выполненные cases и границы воспроизведения.

Профиль A обязан отдельно ответить:

1. Можно ли считать Gate 0 `confirmed` на exact pinned stack?
2. Действительно ли control отклоняет over-limit и shape-bypass до execution boundary?
3. Какие свойства доказывают counters/experiment, а какие остаются только design requirement будущей реализации?
4. Достаточны ли applicability matrix и residual risks для bounded Abuse L2 claim?
5. Какие security/resource свойства slice явно не доказывает?

## Профиль B — learning design, coverage и human readability

Независимо проверить:

- рабочий контекст до внутренних IDs, criteria и таблиц;
- понятное причинное различие input validation, normalization, cost estimation, admission, quota/rate, backpressure и execution boundary;
- объяснение англицизмов и контекстных терминов при первом употреблении либо в локальном glossary;
- автономность каждого файла и связный маршрут `README → learn → interview → kata → project-spec`;
- Mermaid, если есть: вопрос до схемы, объяснение после и явные упрощения;
- содержательные ответы в `<details>` для self-check, interview, follow-up, hints и defense questions;
- interview rubric по качеству reasoning, проверяемым предположениям, evidence, placement и границам обещаний, а не количеству терминов;
- kata: участник сам создаёт минимальную систему, воспроизводит один row-only/shape bypass и не получает готового handler либо решения;
- kata остаётся L1 и не изображает полную L2 applicability review;
- project: тот же endpoint, но пять populations, полная applicability matrix, threat/cost matrix, audit/error assertions, decision record и отдельное L2/L3 evidence;
- различимость наблюдаемых результатов kata и project;
- правдивость L1 как применения заданных limits/binding и negative tests;
- правдивость L2 как самостоятельной защиты типового endpoint со всеми четырьмя категориями, включая честные `not applicable` dispositions;
- правдивость L3 как проектирования multi-tenant/adversarial boundary с legitimate-use и bounded-envelope evidence;
- отсутствие Abuse L4 и supporting Identity/Load/HTTP/Verification/A3/B3/B5/B7 relationships;
- ровно 5 semantic IDs, 13 relationships и 4 unique targets;
- совпадение YAML, registrations и ролей `1 reference / 3 explain / 3 probe / 1 practice / 3 assess / 2 integrate`;
- единые versions, endpoint, allowlist, formula, threshold, populations, counters, errors и audit constraints во всех пяти материалах;
- отсутствие подмены S14 целиком cost-only половиной и явный долг SSRF/untrusted-target;
- metadata, source/freshness, ссылки, anchors, fences, `<details>`, Markdown hygiene и отсутствие готового решения.

Профиль B обязан отдельно ответить:

1. Дают ли Abuse L1/L2/L3 разные наблюдаемые evidence, а не один сценарий с тремя ярлыками?
2. Не превращается ли brief в перечень controls без причинного объяснения?
3. Достаточно ли различаются kata и project?
4. Понятна ли граница между per-operation admission, aggregate quota и общей overload protection?
5. Можно ли принимать slice после disposition findings?

## Общие anti-patterns

- Не считать один правильный `422` доказательством reject-before-work.
- Не считать client-supplied row limit полноценной cost model.
- Не требовать distributed quota, gateway или SSRF внутри этого bounded package.
- Не начислять supporting coverage за переиспользование trusted context, HTTP contract или counters.
- Не выдавать synthetic cell threshold за универсальный production limit.
- Не выдавать перечисление applicability categories за фактическое L2 evidence.
- Не считать project specification готовой реализацией.
- Не редактировать исходные материалы.

## Acceptance gate G10

M1.8.11 можно принять, когда:

- получены оба независимых профиля;
- нет открытых blocker/major по Gate 0, binding/cost/admission ordering, tenant/disclosure boundary, measurement, learning design или coverage;
- exact version baseline воспроизведён либо найденные version issues исправлены/явно adjudicated;
- Abuse L1/L2/L3 evidence признано правдивым без L4/supporting overclaim;
- все четыре категории Abuse L2 имеют подтверждённые dispositions и residual risks;
- kata и project дают разные наблюдаемые результаты;
- решения по minor/note зафиксированы оркестратором;
- после corrections пять материалов и регистрации переводятся в `accepted` отдельным acceptance-pass.

## Open questions

На review передаются два вопроса:

1. Насколько содержательно recovery после 100 запросов, которые должны быть отклонены до executor, подтверждает восстановление, а не только отсутствие выполненной работы?
2. Достаточно ли synthetic cell model и двух counters для L3 bounded resource envelope, если она намеренно не моделирует SQL scan, response bytes и peak memory?

Reviewer не расширяет пакет до общего performance benchmark, distributed quota либо SSRF. Если evidence недостаточно для конкретной relationship, finding должен предлагать минимальную коррекцию coverage или envelope, а не новый курс.
