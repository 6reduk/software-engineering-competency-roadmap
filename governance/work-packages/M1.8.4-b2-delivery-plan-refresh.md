- accepted artifacts: 22;

## Required changes

### 1. Обновить snapshot и artifact registry

- Зафиксировать snapshot 2026-08-20 и acceptance M1.8.3.
- Добавить пять S10 artifacts после существующих C/R/A entities с устойчивыми локальными кодами, kind, primary module и точным количеством relationships.
- Не менять исторические relationships первых 17 artifacts.

### 2. Пересчитать outcome audit

- Добавить все 25 YAML relationships M1.8.3 к exact targets.
- Сохранить ровно один канонический ряд на каждый из 69 outcomes.
- Не считать capability-level `reference` outcome evidence.
- Не считать `probe` proficiency evidence; отдельно пересчитать `probe-only`.
- Показать, какие ранее покрытые outcomes получили собственный Service Verification flow, не выдавая их за новое уникальное покрытие.
- Сохранить явное отсутствие L4 execution evidence в S10.

### 3. Пересчитать module states

Применять принятые определения `complete / partial / not-started / blocked` и D-044.

Обязательно проверить:

- Service Verification: `not-started → partial`, поскольку появился полный минимальный flow Verification L1–L3, но нет L4 и отдельного module-gate decision;
- ни один другой модуль не меняет состояние только из-за supporting relationships S10;
- ни один module не становится `complete` автоматически;
- conditional readiness B3 для Transactional Persistence и A3 для Identity/Security не смешивается с hard DAG и не выдаётся за уже принятое внешнее proficiency evidence.

### 4. Пересобрать очередь

Сравнить минимум:

- Transactional Persistence Integration — S07, при необходимости S15 как supporting context;
- Identity-aware Boundaries — S05, при необходимости S14 как supporting context;
- API Security & Abuse Controls — S14, если bounded action лучше отделить от identity;
- один completion-tail или другой сильный кандидат, если пересчёт показывает более высокий leverage.

Для каждого оценить prerequisite readiness, роль для двух RoleViews, пустое primary coverage, новое уникальное outcome coverage, boundedness действия, риск дублирования и готовность внешних A3/B3 baselines. Неподтверждённый внешний baseline должен стать явным authoring prerequisite/open question, а не скрытым предположением.

### 5. Выбрать один следующий package

Decision brief обязан содержать:

- один module;
- один primary scenario и не более двух supporting scenarios;
- одно центральное наблюдаемое действие;
- primary/supporting capabilities и exact outcome candidates;
- ссылки на принятое coverage, которое нельзя повторять;
- минимальный полный flow `index + learn + interview + kata + project-spec` либо явное обоснование более узкого набора;
- необходимые external baseline slices и способ не превращать B2 material в пересказ A3/B3/B5;
- non-goals, risks/open questions и минимум две сильные отвергнутые альтернативы.

Не создавать следующий authoring work package и не писать учебный content.
