## Required changes

### C-1 — развести Redis GET и SET failures

Синхронно исправить Gate 0, learn, interview и project-spec:

- initial или repeated `GET` failure до source read: `503 cache_unavailable`, `source_read=0`;
- `SET` failure после source read: `503 cache_unavailable`, fill отсутствует, но `source_read≥1`;
- для burst с неуспешным `SET` последовательные владельцы могут дать до `N` source reads; это bounded числом запросов, но не coalesced до одного чтения;
- population `32/32 503`, `source_read=0` относится только к недоступности cache с начала запроса, до PostgreSQL read.

Добавить в project-spec отдельный ожидаемый outcome для post-read `SET` failure. Не менять основную outage population и не обещать `source_read≤1` там, где fill не может завершиться.

### C-2 и C-12 — герметичная freshness bound и арифметика

В Gate 0 и learn явно зафиксировать:

1. anchor потенциально устаревшего snapshot — начало SQL statement в PostgreSQL `READ COMMITTED`;
2. перед отправкой `SET` вычисляется `remaining_ttl = max(0, 2 секунды − elapsed_since_statement_start)`;
3. при исчерпанном остатке cache fill пропускается;
4. `SET` должен завершиться внутри отдельного Redis command budget 250 мс;
5. worst case: старый statement начался непосредственно перед commit, поэтому expiry не позже `statement_start + 2 секунды + 250 мс ≤ commit + 2,25 секунды`.

Показать эту арифметику обычным языком. Не описывать границу как zero-stale/read-your-writes. Согласовать project/interview формулировки, если они сейчас подразумевают полный TTL после позднего read.

### C-3 и C-8 — retry, command budget и fault injection

В Gate 0 и релевантных материалах закрепить наблюдаемое требование:

- redis-py 8.0.1 используется с явно отключёнными автоматическими retry: `Retry(NoBackoff(), 0)` либо эквивалентная по поведению конфигурация;
- каждая Redis-команда ограничена внешним budget 250 мс, например task-level timeout; не давать готовую реализацию;
- correctness outage population воспроизводится контролируемой fault injection в точке подмены cache adapter до `GET`, а не зависит от времени остановки Docker или сетевого timeout;
- реальное выключение Redis/Docker можно оставить дополнительной диагностикой без переносимого wall-clock threshold.

Сохранить `≤350 мс` только для контролируемой acceptance population. Если в тексте оно относится к произвольному Docker/network outage, сузить формулировку. Не пересчитывать авторский эксперимент и не выдавать adapter injection за доказательство поведения реальной сети.

### C-4 — причина pinned baseline

Одной короткой фразой в Gate 0 и/или README пояснить: версии закреплены как воспроизводимый baseline, согласованный с M1.8.11; это не заявление о latest stable. Не обновлять версии.

### C-5 — нормативная опора Problem Details

Добавить RFC 9457 в Gate 0 sources и learn sources/freshness. Связать источник с `application/problem+json` и расширением `code`. Не менять wire contract.

### C-6 — человеческая терминология

При первом смыслообразующем употреблении раскрыть по-русски применимые термины:

- `evidence` — проверяемое подтверждение;
- `population` — группа/серия однотипных прогонов;
- `measurement envelope` — условия и границы измерения;
- `claim boundary` — граница применимости утверждения;
- `fixtures` — заранее подготовленные тестовые данные.

Не добавлять все слова механически в каждый файл: объяснять только реально используемые термины и сохранять связный человеческий текст.

### C-7 — место порога concurrent-miss burst

Явно обозначить `≤150 мс` как project acceptance threshold, выведенный с запасом из наблюдённого Gate 0 диапазона, либо согласовать его с общим measurement envelope. Learn и kata не обязаны наследовать этот performance threshold, если проверяют correctness; тогда различие нужно назвать одной фразой.

### C-9 — lifecycle asyncio.Lock

В learn и при необходимости kata одной фразой объяснить: освобождение lock при выходе/исключении/отмене обеспечивается корректным использованием `async with`, эквивалентным `acquire` с `try/finally release`. Не утверждать, что цитируемая страница документации отдельно гарантирует cancellation behavior.

### C-10 — leader/followers

В README рядом со схемой связать термины: `leader` — владелец текущей загрузки, `followers` — ожидающие запросы. Предпочтительна русская подпись с английским термином в скобках.
