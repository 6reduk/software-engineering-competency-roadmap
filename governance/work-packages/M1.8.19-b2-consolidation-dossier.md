# M1.8.19 — B2 consolidation/module-gate dossier

## Objective

Создать один связанный, пригодный для человека consolidation dossier по принятому B2 breadth-pass: показать маршруты через 11 accepted slices, критерии завершения десяти modules, классифицированный долг, навигацию двух RoleViews и готовность к самостоятельным реализациям. Dossier должен дать оркестратору проверяемое основание выбрать один следующий content action либо перейти к следующей вертикали.

Пакет не создаёт новый учебный slice, не начисляет proficiency coverage и не объявляет ни один module gate пройденным.

## Required artifacts

### 1. `consolidation/README.md` — точка входа и решение

README должен:

- объяснить, что завершено и что не завершено: `10/10 own content entry`, `9/10 five-genre flow`, `0/10 module completion`;
- дать минимальный маршрут выбора: роль → модуль → существующий flow → самостоятельный результат → gate/debt;
- связать остальные четыре файла dossier;
- показать, кому нужен весь B2 baseline, а кому достаточно выбранного маршрута;
- перечислить основные ограничения: HTTP Runtime debt, 11 uncovered, семь probe-only, L4 adoption и отсутствие ImplementationReference;
- в конце рекомендовать ровно одно следующее действие после dossier с обоснованием и минимум двумя отвергнутыми альтернативами;
- задать конечный trigger повторного выбора, чтобы consolidation не стал постоянной фазой.

README не должен превращаться в копию module delivery plan или длинный каталог всех links.

### 2. `routes-and-reuse.md` — карта маршрутов

Для каждого из 10 modules зафиксировать:

- человеческую цель модуля;
- собственную accepted точку входа и порядок жанров;
- какие материалы соседних modules переиспользуются и зачем;
- что reuse подтверждает и чего не подтверждает;
- практический результат, который должен получить участник;
- route status: полный пятижанровый flow, частичный собственный маршрут либо зависимость от будущего action.

Отдельно дать два среза:

- Backend / Distributed Systems;
- Architecture / Technical Leadership.

Для каждого среза различить обязательный baseline, deepening path и conditional specialization. Не копировать целиком canonical RoleViews и не превращать рекомендации в обязательный линейный курс.

HTTP Service Runtime должен быть явно показан как `learn-only own route` при наличии supporting materials, а External E0–E4 должны быть отделены от runtime R2–R5.

### 3. `module-gates.md` — критерии завершения

Для каждого module создать gate card:

- назначение gate;
- применимые primary и supporting capabilities;
- минимальное evidence по уровням и видам действия;
- принятое evidence из текущих flows;
- отсутствующее evidence;
- внешняя readiness, если она нужна;
- текущее решение только `not-ready-for-gate` либо `ready-for-orchestrator-decision`;
- точное условие, после которого оркестратор может рассматривать отдельный module-gate decision.

Нельзя ставить `complete` или `gate passed`. Полный набор жанров, coverage relationship, interview probe или project-spec без реализации не являются достаточным evidence сами по себе.

L4 card должна требовать реальный cross-team/adoption/migration result там, где это следует из outcome; не требовать L4 для каждой capability, если RoleView или module scope этого не требует.

### 4. `debt-register.md` — единый реестр долга

Каждая запись получает устойчивый локальный ID и поля:

- человеческое название;
- категория: uncovered outcome, probe-only, execution gap, navigation/genre gap, scope gap, external readiness, implementation reference либо module-gate decision;
- owner concern/module;
- влияние на две RoleViews;
- текущее evidence;
- чего именно не хватает;
- проверяемое условие закрытия;
- trigger выбора bounded package;
- disposition: `candidate-now`, `after-readiness`, `requires-real-adoption`, `conditional-specialization` либо `accepted-limitation`.

Обязательно учесть:

- 11 uncovered outcomes и семь probe-only;
- Evolution L1;
- HTTP Runtime five-genre gap и практическую самостоятельность tracing;
- S12 performance diagnosis;
- callback/SSRF и aggregate quota/rate;
- External L3/L4 и границу полного S08;
- Cache/Workflow/Delivery и другие L4 adoption/migration gaps;
- отсутствие module-gate decisions;
- отсутствие ImplementationReference для самостоятельно выполняемых проектов.

Не считать количество debt rows severity или приоритетом. Не дублировать один и тот же gap под каждым shared module без явной причины.

### 5. `implementation-readiness.md` — переход от спецификации к самостоятельной работе

Для каждого accepted project-spec либо разумной группы связанных проектов показать:

- prerequisite learning route;
- что участник реализует самостоятельно;
- минимальный reproducible environment и evidence, уже заданные спецификацией;
- какие решения остаются за участником;
- какие review artifacts нужны до появления ImplementationReference;
- какие claims запрещены без runtime, failure или adoption evidence;
- когда проект может стать примером, не превращаясь в эталонное решение для следующего участника.

Добавить общий checklist старта и завершения project repository, но не создавать repository template, scaffold, grader, CI platform или готовый код. L4 readiness описывать только как требование реального контекста и результата, а не как симуляцию межкомандной работы.

## Cross-file consistency

Пять файлов должны использовать одну систему статусов и одни определения:

- `coverage` — связь учебного artifact с capability/outcome;
- `evidence` — наблюдаемый результат выполненной деятельности;
- `proficiency` — подтверждённая способность участника;
- `readiness` — выполненные условия допуска к конкретной работе;
- `module gate` — отдельное решение по совокупности evidence;
- `ImplementationReference` — ссылка на выполненную и проверенную реализацию, а не на project-spec.

Каждый debt ID, module status и route status должен иметь одну каноническую запись и ссылки из остальных файлов. Не создавать второй параллельный outcome registry: exact outcome coverage остаётся в `module-delivery-plan.md`.

## Explicit non-goals

- новый learn/interview/kata/project-spec;
- новое proficiency coverage;
- изменение catalogs, scenarios, prerequisites, RoleViews или accepted slices;
- автоматическое принятие module gates;
- заполнение L4 текстом без execution/adoption;
- создание LMS, progress tracker, scoring system, календаря или grader;
- создание project repositories, scaffolds, reference implementations или CI templates;
- массовое копирование существующего delivery plan и coverage map.
