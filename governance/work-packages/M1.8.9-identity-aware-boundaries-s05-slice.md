# M1.8.9 — Identity-aware Boundaries: tenant-scoped Orders read S05

## Objective

Создать bounded end-to-end slice B2 для `b2.module.identity-aware-boundaries`. Материал должен научить инженера отличать authentication от object-level authorization, проводить доверенный subject/tenant context через один service flow и размещать deny-by-default enforcement так, чтобы валидная identity не давала доступа к объекту другого tenant.

Центральное действие: клиент с валидным token tenant A запрашивает `GET /orders/{order_id}`, где `order_id` принадлежит tenant B. Сервис проверяет token, формирует server-trusted identity context, загружает или проверяет resource в tenant-aware boundary и возвращает закреплённый безопасный denial result без выдачи чужих данных и без доверия к client-supplied tenant identifiers.

Primary scenario — S05. Принятые C1/C5 задают HTTP contract boundary, A1–A4 — service/application boundary, V1/V3 — выбор правдивой test boundary. S14, identity-provider implementation и общий IAM/security курс не становятся вторыми действиями slice.

## Канонический substrate S05

После Gate 0 все пять материалов используют одну историю:

- один endpoint `GET /orders/{order_id}`;
- два tenant, A и B, и минимум по одному Order fixture для каждого;
- валидный token субъекта tenant A;
- server-trusted context содержит устойчивый subject ID и tenant ID, полученные только из проверенных claims;
- route/header/query/body tenant identifiers не заменяют trusted context;
- cross-tenant запрос к Order tenant B проходит authentication, но отклоняется object authorization;
- allowed, unauthenticated, cross-tenant, forged-context и missing-object paths используют одну закреплённую HTTP/error semantics;
- audit evidence показывает decision без записи credentials, token или лишних персональных данных.

Допускается переиспользовать один Orders persistence adapter из принятого контекста либо создать минимальный deterministic fixture store. Выбор фиксируется Gate 0/материалами единообразно, но не добавляет B3 coverage и не превращает slice в database lesson.

Обязательные invariants:

1. **Trusted-context invariant:** authorization опирается только на проверенный server-side subject/tenant context, а не на client-supplied tenant identity.
2. **Object-authorization invariant:** валидная identity tenant A не получает данные Order tenant B ни через основной endpoint, ни через заявленные bypass paths.
3. **Deny-by-default invariant:** отсутствие требуемого identity/resource relationship приводит к одному закреплённому denial result; неясность или пропущенный context не открывают доступ.
4. **Disclosure invariant:** response/error/audit contract не раскрывает чужие Order fields, token/secrets или больше сведений о существовании объекта, чем допускает выбранная Gate 0 semantics.

## Граница B2 / A3 / B3

B2 владеет application integration: trusted context propagation, operation/resource enforcement point, denial/error contract и security evidence одного service flow.

A3 предоставляет token/trust/security baseline: validation requirements, trust boundary, least disclosure и безопасное обращение с security context. Slice применяет baseline, но не преподаёт криптографию, identity-provider operations, key lifecycle, IAM governance или полный threat-modeling/AppSec курс.

B3 либо fixture store предоставляет Order ownership data. Slice не преподаёт isolation, indexing, row-level security или выбор database security mechanism; authorization остаётся application-visible и проверяемой независимо от конкретного persistence pattern.

### 3. Interview

Начать с полной истории S05 и закреплённого substrate. Провести кандидата от L1 применения заданного rule через L2 trusted-context propagation к L3 placement/threat reasoning. На каждый вопрос и follow-up дать содержательный скрываемый ответ. Rubric оценивает причинное рассуждение, threat cases, ownership и границы обещаний, а не количество JWT/OAuth/RBAC терминов.

Слабые ответы включают «token валиден — доступ разрешён», доверие tenant ID из request, фильтрацию только в router при обходном application path, загрузку чужого объекта с последующим раскрывающим error, отсутствие negative cases и логирование token.

### 4. Kata

Участник сам создаёт минимальный scaffold; готового repository и решения нет. Kata исследует один cross-tenant bypass: валидный token tenant A и Order tenant B. Участник сначала записывает invariants и expected observations, затем реализует trusted context/enforcement и доказывает allowed/denied behavior. Полный token issuance, IdP, S14 controls и project-level case matrix не входят.

### 5. Project specification

Тот же Orders read path собирается в самостоятельный сервисный milestone. Обязательны allowed, unauthenticated, cross-tenant, forged tenant-input и missing-object cases, выбранная denial semantics, безопасный audit evidence, threat/bypass matrix и короткий decision record.

Project отличается от kata несколькими enforcement/bypass paths и защитой принятого решения, но остаётся одним сервисом и одной operation. Готового решения и ImplementationReference до самостоятельной реализации/review нет.

## Evidence envelope

Для каждого обязательного case зафиксировать:

- вход: token/claims fixture, route object ID и любые forged tenant inputs;
- server-trusted context после validation;
- ожидаемый HTTP status/media type/error body согласно Gate 0;
- ожидаемое отсутствие чужих Order fields;
- ожидаемый audit decision и допустимые поля;
- отсутствие token/credentials/secrets в response, log и audit record;
- точку проверки: component boundary и собранный ASGI/HTTP path.

Evidence должен отличать минимум пять populations: allowed, unauthenticated, cross-tenant, forged-context и missing-object. Это deterministic security contract, а не performance benchmark; проценты coverage и временные thresholds не вводятся.

## Non-goals

- S14: rate/quota/operation cost/SSRF/abuse controls;
- identity-provider, user login, token issuance/refresh/revocation, key rotation и IAM infrastructure;
- сравнение JWT с opaque tokens или нескольких authorization frameworks;
- универсальный RBAC/ABAC/policy engine;
- service-to-service identity, delegation и cross-service policy migration;
- row-level security как скрытая замена application enforcement;
- Identity L4, A3 proficiency, новое HTTP/Architecture/Verification coverage;
- production rollout, готовый repository, эталонная реализация или ImplementationReference.
