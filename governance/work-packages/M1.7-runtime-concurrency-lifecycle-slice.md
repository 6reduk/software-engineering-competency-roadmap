# M1.7 — runtime slice: concurrency, cancellation и lifecycle ресурсов

## Objective

Создать второй контрастный end-to-end slice B2, в котором читатель диагностирует и перерабатывает backend-сервис с fan-out к медленной зависимости: проводит deadline/cancellation через границы вызовов, ограничивает concurrency, обеспечивает bounded cleanup управляемых ресурсов и подтверждает устранение pool exhaustion тестами и telemetry.

Пакет должен доказать, что принятый human-readable формат работает не только для API design/migration, но и для runtime debugging, failure handling и performance reasoning.

## Required artifacts

### 1. Slice README

Объяснить:

- рабочий отказ и его последствия для клиента/сервиса/dependency;

- техническую freshness baseline.

### 2. Brief: cancellation, deadlines и resource lifecycle

Раскрыть одну причинную модель:

- disconnect, timeout, deadline и cancellation — разные события/механизмы;
- отмена не равна гарантированному прекращению любой работы;
- propagation через task/call boundaries;
- controlled lifecycle boundary и bounded cleanup;
- startup/shutdown/request scope;
- ограничения: process kill, blocking/uncancellable work и remote side effects.

Не превращать brief в полный курс asyncio/AnyIO. Языковую семантику B1 давать только в объёме, необходимом для service-level решения.

### 3. Brief: bounded concurrency и pool saturation

Связать:

- fan-out amplification;
- connection pool, concurrency limit и очередь ожидания;
- deadline budget и время в очереди;
- backpressure/admission/degradation;
- p50/p95/p99, active/waiting/in-flight, pool utilization и cancellation/timeout signals;
- эксперимент, отличающий причину от симптома;
- recovery после снятия нагрузки.

Все bounds/budgets должны называть workload, duration, dependency behavior и acceptance threshold. Не выдавать случайный tuning за диагностику.

### 4. Interview

Одна рабочая история S08 с последовательными follow-ups L2–L4:

- восстановление failure path;
- отличие disconnect/deadline/cancellation;
- pool exhaustion и orphan work;
- выбор limits и overload behavior;
- тесты и telemetry;
- межсервисные deadline/concurrency policies на L4.

Каждый основной и дополнительный вопрос должен иметь скрываемый содержательный ответ. Rubric различает уровни по автономности, неопределённости и масштабу, а не по числу терминов.

### 5. Kata

Минимальный substrate:

- один FastAPI endpoint;
- управляемая медленная dependency;
- fan-out из нескольких вызовов;
- ограниченный pool;
- воспроизводимый сценарий saturation/cancellation failure.

Участник должен сначала воспроизвести и измерить отказ, затем исправить его и доказать regression tests/observations. Дать контракт scaffold/test harness требования, но не готовый код решения. Подсказки — постепенные.

### 6. Project specification

Самостоятельный проект вокруг небольшого fan-out сервиса. Milestones:

1. зафиксировать исходное поведение и failure envelope;
2. построить наблюдаемость service path/pool/tasks;
3. ввести end-to-end deadline/cancellation policy;
4. ограничить concurrency/queue и определить overload response;
5. проверить cleanup, shutdown и recovery;
6. провести controlled load/failure experiment и оформить engineering decision.

Спецификация задаёт TODO, deliverables, review checklist и failure scenarios, но не диктует архитектуру и не содержит эталонного решения.

## Technical and ownership boundaries

- B1 владеет общей Python/async runtime semantics; B2 — применением на request/service/dependency boundary.
- B7 владеет общей observability/SLI/capacity methodology; B2 — конкретными signals и remediation выбранного сервиса.
- B6 владеет pod/container orchestration, autoscaling и platform enforcement; они только контекст, не предмет задания.
- B5 владеет общей теорией распределённых timeout/retry/consistency chains; здесь рассматривается один service-level fan-out.
- Не утверждать, что disconnect клиента автоматически отменяет handler/downstream work во всех ASGI/framework configurations.
- Не обещать абсолютный cleanup: формулировать controlled boundary и явно называть crash/kill/uncancellable/remote limits.
- Не добавлять retry как универсальное исправление медленной dependency; если retry упомянут, разобрать amplification и budget.
