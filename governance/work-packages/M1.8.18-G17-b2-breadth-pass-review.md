# M1.8.18 — G17 review B2 breadth-pass и следующей фазы

Независимыми профилями проверить обновлённый B2 delivery plan: coverage snapshot после M1.8.17, состояния десяти modules, узкое определение завершённого breadth-pass и выбор одного consolidation/module-gate package вместо очередного content slice.

## Профиль A — mechanical coverage, states и governance consistency

Независимо проверить:

- 57 accepted artifacts и принадлежность каждого одному primary module;
- 249 relationships как 21 capability references + 228 outcome relationships;
- role totals `21/55/57/28/30/58` для reference/explain/probe/practice/integrate/assess;
- 58 covered, 11 uncovered и семь exact probe-only outcomes из 69;
- сохранность первых 52 artifacts/240 relationships и точную дельту M1.8.17 `1/2/2/1/1/2` по ролям;
- отсутствие новых unique outcomes от External L1/L2;
- точность artifact registry, outcome audit и всех ссылок target/role;
- membership всех десяти modules по каноническим catalogs;
- переход External Service Integration `not-started → partial` и итог states `0/10/0/0`;
- отсутствие основания для automatic `complete`, особенно при External L4 и module-gate debt;
- неизменность internal hard DAG;
- раздельность hard prerequisites, external readiness и proficiency coverage;
- точность списка 11 uncovered и семи probe-only outcomes;
- отсутствие нового coverage, module-gate decision или catalog mutation в consolidation brief;
- YAML, metadata, links, anchors, fences, раскрываемые блоки, conflict markers и whitespace.

Профиль A обязан отдельно ответить:

1. Полностью ли воспроизводятся `57/249/58/11/7` и role totals?
2. Единственный ли state transition — External Service Integration в `partial`?
3. Не скрывает ли membership или полный набор жанров отсутствие module-gate evidence?
4. Точно ли hard DAG не изменился после M1.8.17?
5. Можно ли передавать plan на фазовое решение без механических corrections?

## Профиль B — phase strategy, learning navigation и boundedness

Независимо проверить:

- понятность трёх разных утверждений: own content entry `10/10`, five-genre flow `9/10`, module completion `0/10`;
- допустимость термина «breadth-pass завершён» без создания ложного ощущения готового B2 курса;
- видимость HTTP Runtime debt в executive conclusion, module table, gap map и candidate comparison;
- различение coverage links, proficiency evidence, module completion и readiness самостоятельного проекта;
- полезность gap taxonomy: uncovered outcome, probe-only, execution gap, navigation/genre gap, external readiness и L4 adoption;
- корректность утверждения, что большинство L4 нельзя честно закрыть ещё одним brief/interview/project-spec;
- соответств multiline RoleViews: обязательный L4, conditional specialization и L3 baseline не должны смешиваться;
- качество сравнения минимум шести обязательных и дополнительных кандидатов;
- содержательность отказа от Evolution L1, HTTP Runtime, callback/SSRF, aggregate quota/rate, L4 adoption и немедленного перехода к следующей вертикали;
- обоснованность consolidation именно сейчас, а не как уклонение от сложного content authoring;
- один ли у consolidation concern и наблюдаемый результат;
- не превращается ли package в новую платформу, LMS, переписывание каталогов или энциклопедический аудит;
- достаточность предложенных частей: route map, module completion criteria, debt registry, RoleView navigation, самостоятельная implementation readiness и trigger следующего выбора;
- наличие конечного выхода: после acceptance должен быть возможен один конкретный content action, bounded correction либо переход к следующей вертикали;
- отсутствие нового proficiency coverage и фиктивных ImplementationReference/module gates;
- human readability плана для tech lead, а не только для следующего агента.
Профиль B обязан отдельно ответить:

1. Не вводит ли «breadth-pass завершён» читателя в заблуждение при HTTP Runtime flow `1/5` и states `0/10 complete`?
2. Действительно ли consolidation снижает больший текущий риск, чем один HTTP Runtime либо security completion slice?
3. Можно ли выполнить выбранный package как один bounded набор артефактов с конечными acceptance criteria?
4. Достаточно ли decision brief защищает от искусственного L4 и бесконечной метаработы?
5. Какой точный факт после consolidation разрешает выбрать следующую вертикаль?
6. Можно ли принять фазовое решение после disposition findings?

## Общие anti-patterns

- Не считать `partial 10/10` завершением modules или готовностью роли.
- Не считать наличие пяти жанров доказательством исполнения outcome участником.
- Не считать количество relationships качеством маршрута.
- Не скрывать HTTP Runtime debt за формулировкой `10/10`.
- Не закрывать L4 новым текстом без adoption/migration evidence.
- Не выбирать Evolution L1 только ради изменения `58 → 59`.
- Не превращать consolidation в LMS, новый каталог competencies или переписывание принятых slices.
- Не создавать новый content package или consolidation artifacts во время review.
- Не редактировать исходный plan.

## Формат результата

Review-артефакт содержит:

1. YAML с уникальным ID, `kind: review`, `status: review`, датой, языком и `sources`;
2. профиль, модель и точный scope;
3. verdict: `accepted`, `accepted_with_changes` или `rework`;
4. счётчик `blocker / major / minor / note`;
5. findings по `authoring/workflow/review-protocol.md` с artifact, criterion, finding, evidence, impact и минимальной recommendation;
6. таблицу всех критериев профиля, включая пройденные;
7. отдельный вывод по mechanical snapshot либо по определению breadth-pass;
8. отдельный вывод по module states/DAG либо по выбору consolidation;
9. ответ, можно ли принять plan после disposition findings;
10. подтверждение независимости и отсутствия исходных правок.

## Acceptance gate G17

M1.8.18 можно принять, когда:

- получены оба независимых профиля либо владелец программы явно разрешил документированное исключение;
- нет открытых blocker/major по coverage, states, phase definition или boundedness следующего package;
- snapshot и role totals подтверждены либо исправлены;
- `10/10 own entry`, `9/10 full flow` и `0/10 complete` различаются явно;
- HTTP Runtime, L1–L3 completion gaps и L4 adoption debt не потеряны;
- consolidation имеет no-new-coverage scope, один concern, проверяемые результаты и конечный exit trigger;
- решения по minor/note зафиксированы оркестратором;
- plan переводится в `accepted` отдельным acceptance-pass.

## Open questions

На review передаётся один принципиальный вопрос: является ли риск несвязной навигации и отсутствующих module-gate criteria сейчас выше риска отложить HTTP Runtime и security completion slices ещё на один bounded package.

Ответ должен опираться на фактическое состояние 10 modules и двух RoleViews, а не на предпочтение reviewer-а к документации или к новому content.
