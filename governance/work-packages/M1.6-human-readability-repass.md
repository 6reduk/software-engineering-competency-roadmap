# M1.6 — human-readability re-pass первого slice

## Objective

Независимо проверить, воспринимается ли первый B2 slice как связная инженерная методичка для человека, а не как сжатая спецификация или след рассуждений LLM.

Reviewer должен ответить на практический вопрос: сможет ли работающий инженер открыть любой файл напрямую, понять исходную ситуацию, восстановить ментальную модель, применить материал для повторения/собеседования/практики и не угадывать локальный язык авторов проекта.

Это не повтор технического re-pass. Технические findings допустимы только если ошибка непосредственно мешает пониманию или применению материала.

## Reviewer mode

- Проверяемые материалы не редактировать.
- Не менять governance, work packages, metadata, coverage и статусы.
- Единственный разрешённый новый файл — `governance/reviews/M1.6-human-readability-<model>.md`, где `<model>`: `codex`, `glm` или `kimi`.
- Не читать отчёт другого reviewer до завершения собственного анализа.
- Читать как инженер, который не видел обсуждения создания курса.
- Не предлагать превратить материал в учебник, энциклопедию или пошаговую LMS.

## Required context

3. `authoring/standards/editorial-standard.md`;

Не нужно читать всю competency matrix или историю прежних review: каждый материал обязан объяснять необходимый контекст самостоятельно.

## Reading passes

Провести четыре прохода.

### 1. Direct-entry pass

Открыть каждый из шести документов как самостоятельную первую страницу и проверить:

- понятно ли в первых абзацах, какая рабочая проблема решается;
- названы ли участники, текущее поведение, изменение и риск;
- не начинается ли текст с критериев, локальных ID или выводов из отсутствующей первой половины разговора;
- можно ли понять назначение файла без чтения README и blueprint.

### 2. Connected-reading pass

Пройти маршрут README → briefs → interview → kata → project spec и проверить:

- сохраняется ли одна Orders API история;
- объясняют ли переходы, зачем открывать следующий документ;
- нет ли ненужного повторения или скрытых зависимостей;
- становятся ли задания естественным продолжением объяснения, а не новой задачей без контекста.

### 3. Language pass

Проверить:

- неоднозначные термины сначала объясняются обычным языком;
- английский термин в скобках помогает узнать индустриальное название, а не заменяет объяснение;
- слова вроде `target`, `shape`, `boundary`, `semantics`, `evidence`, `assumption`, `producer`, `consumer`, `contract` не остаются без конкретного объекта или пояснения;
- локальные словари действительно снимают неоднозначность;
- prose связан переходами и не превращается в чередование чек-листов и англицизмов.

### 4. Use-case pass

Проверить три сценария использования:

1. опытный backend-инженер повторяет тему перед собеседованием;
2. инженер ищет собственный пробел и хочет быстро восстановить ментальную модель;
3. инженер впервые входит в API evolution, но уже умеет разрабатывать сервисы.

Для каждого сценария указать, что работает, где читатель может потерять контекст и достаточно ли материала, чтобы перейти к самостоятельному действию.

## Artifact-specific checks

### Engineering briefs

- рабочая ситуация и причинно-следственная модель появляются раньше правил;
- схемы Mermaid имеют вводную фразу и практический вывод;
- good/bad practices объясняют последствия;
- вопросы самопроверки имеют содержательные скрываемые ответы;
- словарь помогает читать текст, а не дублирует его.

### Interview

- основной вопрос и follow-ups содержат достаточный контекст;
- скрытые ответы показывают ход сильного рассуждения, а не только список терминов;
- rubric различает уровни по автономности, масштабу и работе с неопределённостью;
- правило оценки сформулировано человеческим языком.

### Kata

- понятны система, пользователи, старое поведение, новое требование и конфликт;
- результат и критерии самопроверки наблюдаемы;
- подсказки постепенны;
- готовое решение не раскрыто.

### Project specification

- этапы объясняют назначение результатов, а не диктуют архитектуру;
- TODO/checklists помогают выполнить проект самостоятельно;
- ограничения и review criteria не требуют угадывать замысел автора;
- нет готовой эталонной реализации.

### README

- даёт карту маршрута, prerequisites, ожидаемый результат и границы;
- не пересказывает все дочерние материалы;
- позволяет выбрать нужный режим: повторение, interview или практика.

## Output artifact

Review должен содержать:

1. scope, reviewer/model и дату;
2. verdict по каждому из четырёх reading passes;
3. краткую оценку каждого из шести документов;
4. оценку трёх use cases;
5. findings в формате `authoring/workflow/review-protocol.md` с точным местом и минимальным исправлением;
6. counts blocker/major/minor/note;
7. итог `accepted`, `accepted-with-debt` или `rework`;
8. подтверждение read-only режима.

Finding должен описывать реальное препятствие для читателя, а не вкусовую замену одного корректного выражения другим. Если текст понятен, не нужно создавать замечание ради количества.

## Verdict rule

- `accepted`: каждый файл работает как самостоятельная точка входа, полный маршрут связен, blocker/major нет;
- `accepted-with-debt`: основной human-readable стандарт выполнен, но остаются локальные minor, которые можно исправить без перестройки материала;
- `rework`: хотя бы один ключевой файл требует контекста отсутствующего разговора, остаётся машиноподобным, не объясняет термины/задачу или не позволяет перейти к самостоятельному действию.

Reviewer не принимает M1.5/M1.6 и не меняет статусы материалов от имени оркестратора.
