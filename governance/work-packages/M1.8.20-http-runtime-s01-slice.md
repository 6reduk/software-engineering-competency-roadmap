# M1.8.20 — HTTP Service Runtime/S01: локализация потери request context

## Objective

Сначала подтвердить B1/A3 Gate 0 для одной собранной HTTP request pipeline, затем создать недостающие собственные жанры HTTP Service Runtime вокруг S01. Центральное действие — по неполным исходным признакам восстановить путь запроса, найти первую границу потери server-owned request context после middleware/dependency refactor, исправить причину без обхода pipeline и закрепить сохранённый публичный контракт регрессионной проверкой.

Пакет закрывает одним действием навигационный долг D19 и execution gap D20. Он не повторяет:

- C1, который объясняет порядок исполнения и формирование HTTP-контракта;
- S10 с заранее указанной ошибкой регистрации validation handler;
- R1–R5, центрированные на lifecycle, cancellation, pool saturation и fan-out;
- S05 identity/authorization context или общий observability platform.

### Итог Gate 0: `confirmed`

Readiness проверена автором 2026-09-08 до создания учебных файлов. Ниже — запись фактически исполненного опыта; это не acceptance G19.

#### G0.1 — среда и контракт

Локальный CPython 3.14.0, Windows AMD64; FastAPI 0.137.1, Starlette 1.3.1, Pydantic 2.12.5, HTTPX 0.28.1, AnyIO 4.11.0. Версии получены из `sys.version` и `importlib.metadata.version`. Один процесс, один поток event loop, стандартная task factory; все зависимости, endpoint и exception handlers асинхронные. HTTPX `ASGITransport` вызывает собранное приложение внутри процесса; сетевого ASGI-сервера, proxy, TLS, lifespan-ресурсов и thread pool в опыте нет.

Один путь: `GET /quote`, query `mode` со значениями `ok` (также default) и `unavailable`. В опыте явно передавались `ok`, `unavailable`, `bad`. Контракт проверяемых вариантов:

| mode | HTTP status | Content-Type | Полное JSON-тело | Смысл для клиента |
|---|---:|---|---|---|
| `ok` | 200 | `application/json` | `{"quote":42}` | Котировка получена |
| `unavailable` | 503 | `application/json` | `{"code":"quote_unavailable"}` | Управляемая недоступность котировки; немедленный retry не предписывается |
| `bad` | 422 | `application/json` | `{"code":"invalid_query"}` | Исправить query |

Каждый ответ также обязан иметь `X-Request-ID`: созданный сервером UUID, одинаковый с контекстом этой операции. Значение меняется между запросами; сравнивается равенство внутри операции, а не byte snapshot между прогонами. Входящий одноимённый заголовок `untrusted-client` игнорируется. ID диагностический, не authentication/authorization identity. JSON-форма сравнивается целиком, порядок ключей не закрепляется.

#### G0.2 — владелец, механизм и наблюдения

Внешний pure ASGI middleware создаёт UUID и устанавливает `ContextVar` после checkpoint `entry`; владеет token и сбрасывает его в `finally` после завершения downstream. Отдельный безопасный UUID `operation` и список наблюдений в ASGI scope позволяют связать запись даже при потере исследуемого значения. Они не используются как fallback для handler или ответа. Запись содержит только operation, stage, диагностический ID, task ID и thread ID; body, headers, credentials и персональные данные не записываются.

Контрольный dispatch непосредственно ожидает приложение. Refactor переносит тот же dispatch в дочернюю task, но запускает её с пустым `contextvars.Context()`. Первая потеря наблюдается между `created` в родительской задаче и `dispatch-enter` в дочерней. Это следствие неверного контекста запуска, а `X-Request-ID: missing` на `response-start` — поздний симптом. Исправленный профиль сохраняет дочернюю task и ожидание её завершения, но использует штатное наследование контекста при создании task. Handler, dependency и error mapping не получают ручного fallback и не меняются.

Checkpoint `dependency-exit` наблюдается на success и error paths, потому что запись выхода размещена в `finally` вокруг `yield`. Код просто после `yield`, без `finally`, может не исполниться при вбросе исключения в генератор зависимости. Поэтому отсутствие этой записи само по себе не доказывает ошибку сборки приложения: сначала проверьте instrumentation. Это условие наблюдаемого trace, а не изменение фактического порядка разворачивания dependency stack закреплённой сборки.

Порядок существенных checkpoints подтверждён для каждого запроса:

- success: `entry → created → dispatch-enter → dependency-enter → handler → response-start → dependency-exit → dispatch-exit → joined → cleaned`;
- domain error: `entry → created → dispatch-enter → dependency-enter → handler → dependency-exit → error-map → response-start → dispatch-exit → joined → cleaned`;
- invalid query: `entry → created → dispatch-enter → dependency-enter → dependency-exit → validation-map → response-start → dispatch-exit → joined → cleaned`; endpoint не вызывается.

Зависимость с `yield` имеет стандартный request scope. Обёртка добавляет заголовок на ASGI `http.response.start`; его callback исполняется в downstream task. В control наблюдалась одна task на путь; в defect/fixed — две, при неизменном thread ID. В control/fixed все checkpoints от `created` до `joined` имеют свой UUID. В defect downstream checkpoints от `dispatch-enter` до `dispatch-exit` имеют `None`, а родительский `joined` всё ещё имеет UUID. `entry` и `cleaned` всегда `None`. После `joined` дочерняя task завершена; отсутствие контекста проверено также со стороны вызывающего клиента. Это не утверждение о стирании памяти завершённой task.

Исходная карточка участника содержит только сообщение о пропавшем диагностическом ID при сохранённых status/body после refactor. Конкурирующие гипотезы: ID не создан; создан, но потерян до читателя; читатель неверно формирует заголовок. Checkpoints после создания, на входе dispatch и перед ответом различают эти причины. Участник записывает гипотезы до открытия условия посева и получает расширенный trace только после выбора instrumentation.

#### G0.3 — measurement envelope и фактические результаты

Команда финального опыта: `python <temporary-directory>/m1820-probe.py`, exit 0. Конкретный локальный путь автора удалён из публичного snapshot; сам probe в репозитории не сохранён. Три повтора каждой группы, без внешних зависимостей; `unavailable` — локальное исключение endpoint, `bad` — ошибка проверки query Pydantic. Запросы выполняются последовательно, кроме явно конкурентной группы. Наблюдение продолжается до возврата ASGI-вызова и очистки, watchdog 5 секунд на последовательный запрос или всю конкурентную волну; это защита от зависания, не latency SLO.

| Группа | В каждом повторе | Всего | Потери ID | Нарушения status/media type/body | Нарушения cleanup |
|---|---|---:|---:|---:|---:|
| control | 10 success + 10 domain error + 10 invalid | 90 | 0 | 0 | 0 |
| defect | Те же 30 запросов | 90 | 90, все на `created → dispatch-enter` | 0 | 0 |
| fixed | Те же 30 запросов | 90 | 0 | 0 | 0 |
| concurrent | Одна волна 12: 4 success + 4 domain error + 4 invalid | 36 | 0 | 0 | 0 |
| recovery | 5 последовательностей `unavailable → ok → bad → ok`, после конкурентной волны на новом экземпляре той же fixed-сборки | 60 | 0 | 0 | 0 |

Concurrent barrier удерживает все 12 операций на `dispatch-enter` до общего освобождения; проверены уникальность UUID и равенство своего ID на каждом checkpoint/ответе, смешиваний 0/36. Recovery проверяет новые независимые операции в том же процессе/event loop и чистый родительский контекст; повторное использование одной серверной task не моделируется. Во всех 366 основных операциях проверены cleanup и порядок пути. Defect нарушает полный публичный контракт именно заголовком (90/90), хотя три остальные части ответа сохранены.

Пороги: defect должен воспроизвести потерю в 100% своей группы на одной границе; control/fixed/concurrent/recovery — 0 потерь, 0 смешиваний, 0 нарушений полного ответа и cleanup. Дополнительно выполнены 3 ASGI-запроса к экспериментальному bypass: middleware возвращает верные status/body/header, пропуская dependency/handler. Все 3 отвергнуты проверкой наличия dependency checkpoints, после проверки внешнего ответа. Итого 369 HTTPX/ASGI операций, включая отрицательный контроль проверяющего механизма.

## Обязательные свойства эксперимента Gate 0

- Есть не менее двух правдоподобных исходных гипотез, например «context не создан» и «context потерян позже»; готовый ответ не зашит в исходный symptom.
- Для одной операции можно сопоставить вход, существенные checkpoints, итоговый response/error и cleanup по безопасному correlation value.
- Defect-профиль воспроизводит потерю на одной и той же границе; fixed-профиль устраняет именно её, не копируя context вручную в handler/error response.
- Публичный контракт до refactor и после исправления совпадает; defect наблюдаем, но задача не превращается в изменение API contract.
- Concurrent population доказывает отсутствие cross-request context leakage.
- После error и recovery context не остаётся в следующей независимой операции.
- Если поведение зависит от task/thread propagation, это проверяется фактически на закреплённой topology и не обобщается на другие runtime/framework versions.

## Required artifact set

После Gate 0 `confirmed` создать ровно четыре новых материала:

1. **Index** — автономная рабочая история S01, prerequisites, маршрут C1 → R1 → новый interview → kata → project-spec, границы reuse и coverage.
2. **Interview** — вопросы от L1 восстановления заданного пути к L2 самостоятельной локализации и L3 follow-up при неполной production information; все ответы в `<details>`.
3. **Kata** — один ограниченный seeded refactor defect и достаточные симптомы без готового root cause; участник строит trace, находит первую потерю, исправляет причину и добавляет regression.
4. **Project specification** — самостоятельный выбор одного request-context concern и refactor boundary в собственном минимальном сервисе, конкурирующие гипотезы, instrumentation, control/defect/fixed/concurrent/recovery evidence и decision record.

Отдельный learn не создаётся. Index обязан объяснить, зачем перед практикой прочитать два уже принятых материала и где заканчивается их supporting scope. Читатель не должен открывать work package или review, чтобы понять задачу, термины и критерии проверки.

## Coverage contract

Допустимы только следующие semantic targets:

- `b2.capability.trace-request-execution`;
- `b2.level-outcome.trace-request-execution-l1-follow-known-path`;
- `b2.level-outcome.trace-request-execution-l2-diagnose-common-failure`;
- `b2.level-outcome.trace-request-execution-l3-explain-production-path` — только `probe` в interview, без execution/assess claim этого локального пакета.

Ожидаемые роли:

- index: capability `reference`;
- interview: L1/L2/L3 `probe`;
- kata: L1/L2 `practice`, `assess`;
- project-spec: L2 `integrate`, `assess`.

Итого ожидается 10 relationships к четырём targets: 1 reference + 3 probe + 2 practice + 3 assess + 1 integrate. Если содержание не даёт наблюдаемого evidence роли, связь не добавлять и объяснить расхождение.

Lifecycle, Cancellation, Verification, HTTP Contract, B1, A3 и B7 coverage запрещены: это prerequisites/supporting context, а не результат S01. L3 остаётся interview follow-up, потому что локальная лаборатория не является production evidence.

## Content requirements

Материалы обязаны:

- объяснить `request context`, server-owned context, propagation, checkpoint, correlation, instrumentation, first-loss boundary и regression обычным языком при первом употреблении;
- показывать различие между первопричиной, первой наблюдаемой потерей и поздним внешним симптомом;
- отделять request state от client-supplied headers и не выдавать correlation ID за authentication/authorization identity;
- объяснить порядок только для закреплённой FastAPI/Starlette/ASGI сборки и назвать version-sensitive места;
- использовать минимальные checkpoints, а не совет «добавить логи везде»;
- проверять success, error, concurrency, cleanup и recovery paths;
- показывать, почему ручное протаскивание значения в конечный handler маскирует boundary defect;
- сохранять публичный HTTP contract и явно назвать его проверяемые части;
- давать частые ошибки, хорошую/плохую практику, edge cases и self-check с ответами в `<details>`;
- использовать Mermaid только если схема действительно упрощает путь запроса, и пояснить намеренные упрощения.

## Kata/project distinction

### Kata

- context concern, pipeline и seeded defect заданы;
- root cause не назван напрямую, но scope ограничен одним request path;
- участник создаёт минимальный стенд самостоятельно либо использует собственную реализацию; scaffold и готовое исправление не выдаются;
- оцениваются L1/L2: верный порядок, первая потеря, причинное исправление и regression evidence.

### Project specification

- участник самостоятельно выбирает безопасный server-owned context concern и место refactor в минимальном собранном сервисе;
- до instrumentation фиксирует минимум две конкурирующие гипотезы;
- проект требует более широкой evidence matrix, concurrency isolation и decision record;
- L3 execution не начисляется: production reconstruction остаётся отдельным фактическим результатом, а не лабораторной имитацией.

## Explicit non-goals

- S02 graceful shutdown, task leak, cancellation или resource-pool exercise;
- повтор S10 validation/error-handler registration;
- изменение публичного API/error contract, API migration или serializer design;
- identity/authentication/authorization, tenant propagation или security logging program;
- OpenTelemetry platform, collector/backend, distributed tracing, baggage across services или B7 observability governance;
- performance/load test, sampling policy, SLO или production incident simulation;
- framework-internal хрестоматия либо универсальный порядок для всех версий;
- готовая реализация, scaffold repository, grader, CI template или ImplementationReference;
- изменение consolidation dossier, canonical catalogs, module gates или program status.

## Acceptance checks

- [ ] Gate 0 заполнен первым и имеет итог `confirmed`; при `blocked` четыре материала отсутствуют.
- [ ] Один request path, context concern, refactor defect и публичный contract согласованы во всех материалах.
- [ ] Defect отличается от S10 и R1–R5 центральным действием и evidence.
- [ ] Исходный symptom не раскрывает root cause; checkpoints различают минимум две гипотезы.
- [ ] First-loss boundary подтверждена control/defect/fixed evidence, а исправление не обходит pipeline.
- [ ] Concurrent и recovery populations проверяют isolation и cleanup.
- [ ] Созданы ровно четыре новых материала; learn-переходы переиспользуют C1/R1.
- [ ] Coverage ограничено Trace L1/L2 и L3 probe; relationship totals пересчитаны по фактическому YAML.
- [ ] Kata и project требуют самостоятельной реализации и не содержат готового решения.
- [ ] Термины объяснены, interview/self-check ответы находятся в `<details>`.
- [ ] Все ссылки, anchors, YAML, Markdown, fences, Mermaid, `<details>`, UTF-8, whitespace и conflict markers проверены.
- [ ] Изменения ограничены Ownership; временный probe удалён и не зарегистрирован как ImplementationReference.
- [ ] Все новые content artifacts остаются `status: review`; G19 и program status не меняются.

## Handoff

Передать оркестратору:

1. итог и полный record Gate 0, включая pinned/current версии и первичные источники;
2. созданные файлы и две разрешённые регистрации;
3. точный request path, public contract, context owner, seeded defect и first-loss boundary;
4. control/defect/fixed/concurrent/recovery populations и измеренные результаты;
5. coverage targets, роли и фактическое число relationships;
6. доказательство отличия от C1, S10 и R1–R5, а также kata/project distinction;
7. результаты механических и human-readability проверок;
8. удаление временного probe, ограничения evidence, открытые вопросы и рекомендуемые профили G19.

Автор не принимает G19, не меняет consolidation dossier и не создаёт следующий planning package.
