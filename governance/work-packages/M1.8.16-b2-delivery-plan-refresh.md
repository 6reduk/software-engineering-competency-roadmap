## Required changes

### 1. Обновить snapshot и artifact registry

- Зафиксировать snapshot 2026-09-08 и acceptance M1.8.15.
- Добавить пять S11 artifacts после существующих entities с устойчивыми локальными кодами, kind, primary module и точным количеством relationships.
- Не менять исторические relationships первых 47 artifacts.
- Считать relationship как пару `(target, role)`.

### 2. Пересчитать outcome audit

- Добавить все 13 YAML relationships M1.8.15 к exact targets.
- Сохранить ровно один канонический ряд на каждый из 69 outcomes.
- Не считать capability-level `reference` outcome evidence.
- Не считать `probe` proficiency evidence; отдельно пересчитать `probe-only`.
- Проверить, что Delivery L1 впервые получил execution-oriented evidence, а Delivery L2/L3 получили собственное evidence модуля при существующем supporting evidence прежних slices.
- Не приписывать Evolution, Compatibility, Verification, B6 или B7 coverage за linked context, Gate 0 и переиспользованные contracts.

### 3. Пересчитать module states и DAG effects

Обязательно проверить:

- переход Safe Service Evolution из `not-started` в `partial` без automatic `complete`;
- отсутствие Delivery L4 и отдельного module-gate decision;
- B6/B7 readiness относится только к лабораторному substrate S11 и не является proficiency coverage;
- supporting relationships не завершают соседние modules автоматически;
- остался ли ровно один `not-started` module и изменилось ли prerequisite readiness downstream, не смешивая hard DAG с внешними A3/B3/B5/B6/B7 gates.

### 4. Пересобрать очередь

Сравнить минимум пять кандидатов:

- External Service Integration/S08 с новым client-side integration action, не повторяющим fan-out/deadline/pool evidence runtime slice;
- узкий HTTP Service Runtime completion вокруг S01/S02 без повторения cancellation, pool saturation, API evolution и error-contract verification;
- оставшуюся callback/untrusted-target/SSRF половину S14 с собственным A3 network/DNS/redirect readiness;
- aggregate quota/rate часть abuse control с явным coordination/store readiness и без повторения operation-cost admission;
- completion-tail Safe Service Evolution либо Transactional Persistence, только если есть локально достижимый gap без искусственного L4 и без повторения принятых flows.

Для каждого оценить hard prerequisites, external readiness, ценность двум RoleViews, новое уникальное outcome coverage, boundedness, риск повторения принятых slices и пригодность полного learning flow. Не удалять из сравнения оставшийся `not-started` module. Delivery L4 не выбирать без migration/adoption evidence, а внешний integration package не расширять до общего resilience/platform курса.

### 5. Выбрать один следующий package

Decision brief обязан содержать:

- один module;
- один primary scenario и не более двух supporting scenarios;
- одно центральное наблюдаемое действие;
- primary/supporting capabilities и exact outcome candidates;
- ссылки на принятое coverage, которое нельзя повторять;
- минимальный полный flow `index + learn + interview + kata + project-spec` либо явное обоснование более узкого набора;
- внешний readiness gate внутри будущего authoring package, если он необходим;
- non-goals, risks/open questions и минимум две сильные отвергнутые альтернативы.

Не создавать следующий authoring work package и не писать учебный content.
