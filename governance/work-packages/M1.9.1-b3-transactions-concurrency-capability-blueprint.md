# M1.9.1 — bounded capability blueprint B3 transactions/concurrency

## Objective

Создать первый канонический zoom B3 только для `b3.cluster.transactions-concurrency`: один устойчивый учебный module, небольшой набор action-oriented capabilities, применимые LevelOutcomes, внутренние и внешние prerequisites, рабочие scenarios и authoritative requirements двух первых RoleViews.

Blueprint должен позволить затем спроектировать принятый write-skew action и соседние bounded действия без превращения кластера в полный курс SQL/PostgreSQL. Пакет документальный: он не создаёт учебные artifacts, coverage, Gate 0 record, runtime evidence или реализацию.

## Required blueprint

### 1. Partial-track index

`curriculum/tracks/b3/README.md` должен:

- ясно назвать blueprint частичным zoom одного кластера, а не полным B3 track blueprint;
- связать B3 skeleton, принятый M1.9.0 intake и семь непосредственных каталогов;
- объяснить разницу cluster, module, capability, LevelOutcome и scenario человеческим языком;
- перечислить инварианты ownership и явно оставить остальные B3 clusters `not-started` без фиктивных сущностей;
- определить aggregate catalog notation и file-level defaults для B3, совместимые с метамоделью;
- запретить считать planned entities учебным coverage или proficiency.

### 2. Один module

`modules.md` содержит ровно один module, принадлежащий B3 и ограниченный transaction isolation/concurrency одного operational store.

Module обязан иметь:

- semantic ID вида `b3.module.<actionable-scope>`;
- scope, develops и non-goals;
- явное отличие от B2 application transaction, B5 distributed consistency, B6 platform и B7 production reliability;
- возможность вместить выбранный write-skew action и два отклонённых intake-кандидата без обязательства реализовать их одним content package.

Module не должен называться просто `PostgreSQL`, `SQL` или повторять cluster как список тем.

### 3. Небольшой набор capabilities

`capabilities.md` содержит от трёх до пяти B3 capabilities. Каждая:

- имеет уникальный `b3.capability.*` ID, title, primary cluster, наблюдаемое действие и primary module;
- принадлежит только `b3.cluster.transactions-concurrency`;
- описывает устойчивую профессиональную способность, а не технологию, знание термина или конкретный interview question;
- имеет различимую границу и evidence potential;
- полезна хотя бы одной из двух RoleViews;
- не копирует B2 application transaction/idempotency, B5 cross-system coordination, B6 platform operation или B7 incident/SLO ownership.

Blueprint обязан покрыть как минимум три различимых действия кластера:

1. воспроизвести и объяснить transaction anomaly по фактическому schedule и store signals;
2. выбрать и проверить ограниченный store-level concurrency-control mechanism для заданного инварианта;
3. локализовать lock/wait/deadlock либо иной transaction conflict и определить допустимую границу реакции.

Дополнительная capability допустима только при доказанной независимой ценности. Не создавать отдельную capability для каждого isolation level, SQLSTATE или PostgreSQL API.

### 4. LevelOutcomes

`level-outcomes.md` задаёт только применимые outcomes L1–L5 для каждой capability. Не заполнять все уровни механически.

Каждый outcome содержит:

- уникальный `b3.level-outcome.<capability-slug>-lN-<action>` ID;
- уровень;
- действие, контекст/масштаб и самостоятельность;
- evidence criteria, наблюдаемые отдельно от учебного artifact.

Обязательные guardrails:

- L1 не сводится к перечислению терминов: требуется воспроизвести либо объяснить наблюдаемое поведение в заданном контексте;
- L2 включает самостоятельное применение к ограниченной store-задаче;
- L3 требует выбора/диагностики при неопределённости и защиты trade-offs на уровне системы или owned store boundary;
- L4 допускается только для migration/adoption/policy across teams или нескольких workloads с реальными последствиями; локальная лаборатория L4 не доказывает;
- L5 создаётся только при действительно независимом portfolio/organizational evidence; если такого результата для bounded кластера пока нет, уровень отсутствует;
- более высокий outcome формулируется самодостаточно, но не отменяет подразумеваемую способность выполнить применимое поведение нижнего уровня.

Принятый write-skew action должен иметь естественные outcome targets, но blueprint не обязан строиться только вокруг него.

### 5. Prerequisites и DAG

`prerequisites.md` должен разделить:

- internal hard `requires` между созданными B3 capabilities;
- `related` links, не участвующие в topological order;
- external baseline/conditional context B1/B2/B5/B6/B7 без выдуманных capability IDs соседних треков;
- минимальный SQL/relational baseline, необходимый для действий, без создания полного курса;
- правило, что runtime/store readiness конкретного content package не становится hard capability edge.

Internal hard graph обязан быть ацикличным. Каждая edge получает человеческое обоснование; отсутствие edge также не должно означать отсутствие полезной последовательности обучения.

### 6. Scenarios

`scenarios.md` содержит от трёх до пяти рабочих scenarios с локальными labels и без новых глобальных сущностей вне B3 blueprint.

Обязательно включить:

- primary scenario принятого intake: два оператора и общий инвариант;
- bounded lock/wait/deadlock scenario;
- snapshot/visibility либо read-modify-write scenario.

Для каждого назвать рабочую ситуацию, центральное действие, применимые capabilities, наблюдаемый результат и non-goals. Scenario не является готовой kata/project-spec, не содержит решения или выдуманного runtime evidence.

### 7. Role requirements

`role-requirements.md` задаёт authoritative projection созданных B3 LevelOutcome IDs на:

- Backend / Distributed Systems;
- Architecture / Technical Leadership с B3 specialization.

Требования должны:

- различать required baseline, deepening и conditional L4/L5 specialization;
- не наследовать автоматически track-level target всем capabilities;
- не требовать одинаковой глубины от обеих ролей;
- объяснять, почему конкретный outcome нужен роли;
- не превращать Architecture role в DBA и Backend role в владельца production database platform;
- ссылаться только на реально созданные outcome IDs.

## Required invariants

- Созданы ровно семь файлов Ownership и один module.
- Созданы 3–5 capabilities только для `b3.cluster.transactions-concurrency`.
- Все LevelOutcome и role requirement links существуют; orphan outcomes и dangling IDs отсутствуют.
- Module develops все созданные capabilities; каждая capability имеет один primary module и cluster.
- Internal hard DAG ацикличен.
- Нет `coverage`, content artifacts, Gate 0, runtime results, implementation или ImplementationReference.
- Нет сущностей для остальных B3 clusters; они остаются явно вне текущего zoom.
- B2/B5/B6/B7 ownership не копируется.
- Все семь файлов имеют `status: review` и дату `2026-09-09`.
