# M1.8.3 — Service Verification: правдивые границы проверки вокруг S10

## Objective

Создать bounded end-to-end slice B2 для `b2.module.service-verification`. Материал должен научить инженера связывать конкретный риск с механизмом отказа, выбирать самую дешёвую границу проверки, которая действительно воспроизводит этот механизм, и явно называть остаточный риск — без догматичной пирамиды тестов и без общего курса testing practice.

Центральное наблюдаемое действие: участник получает Orders service с зелёными тестами application/domain logic, обнаруживает, что реальная HTTP error boundary нарушает обещанный клиенту контракт, и строит минимальный набор проверок, который воспроизводимо обнаруживает дефект до rollout и локализует его без хрупкого дублирования.

Primary scenario — S10. S03 даёт внешний API/error contract, S06 — разделение business/application/adapter evidence. S08 используется только как ссылка на уже принятое risk-based reasoning о failure path; runtime/cancellation material не повторяется.

## Канонический substrate S10

Все пять материалов используют один Orders API и один seeded defect.

### Обещанное внешнее поведение

Новый клиент вызывает `POST /orders` с `Accept: application/problem+json`. Для `delivery.mode="scheduled"` обязательны `window.start` и `window.end`. Если `window.end` отсутствует, API обязан вернуть:

- HTTP status `422`;
- `Content-Type: application/problem+json`;
- Problem Details с документированными `type`, `title` и `status: 422`;
- машинно читаемое указание на поле `#/delivery/window/end` в принятом расширении списка ошибок.

Стабильное значение `type` автор выбирает одно на весь slice и объясняет как часть контракта. Полный payload должен быть согласован во всех пяти материалах. Старый формат ошибки можно упомянуть только как уже решённый migration context S03; сам переход форматов не является задачей M1.8.3.

### Исходное ложное чувство уверенности

В service есть зелёные тесты:

- domain/application tests проверяют правила заказа;
- прямой тест Pydantic-модели подтверждает, что неполное окно отклоняется;
- router/handler unit test подменяет boundary слишком близким mock/fake и не запускает фактический exception handler, сериализацию и HTTP response.

### Seeded defect

При сборке приложения нужный validation exception handler не зарегистрирован либо зарегистрирован не для того типа исключения. Поэтому реальный FastAPI request проходит по default error path и возвращает `422 application/json` с framework-specific `detail`, а не обещанный `application/problem+json` payload. Локальные application/model tests остаются зелёными.

Автор не обязан давать готовый дефектный код. Он обязан описать минимальный starting scaffold так, чтобы участник мог воспроизвести именно этот разрыв между локальными тестами и фактической HTTP boundary.

### Внешний consumer contract

Представительный новый consumer ветвится по HTTP status и стабильному Problem Details `type`, а указатель поля использует для подсветки ошибки формы. Он не должен разбирать текст `detail` или внутренний Pydantic/FastAPI payload. Проверка consumer expectation должна наблюдать wire-level status, media type и body, а не только OpenAPI schema или вызов функции сериализатора.

## Capability и outcome contract

### Primary coverage

Обязательно раскрыть:

- `b2.level-outcome.verify-service-behavior-l1-test-local-behavior`;
- `b2.level-outcome.verify-service-behavior-l2-select-test-boundaries`;
- `b2.level-outcome.verify-service-behavior-l3-design-service-strategy`.

L1 — заданная проверка ловит целевую регрессию без зависимости от несущественных деталей. L2 — инженер самостоятельно сопоставляет риск, механизм и test boundary, различает confidence и false confidence. L3 — инженер перестраивает verification portfolio одного сервиса по критическим paths/failure modes и измеримо убирает медленное или хрупкое дублирование без потери значимого evidence.

### Supporting coverage

Допустимо и ожидаемо раскрыть:

- `b2.level-outcome.verify-contract-compatibility-l1-maintain-contract-check`;
- `b2.level-outcome.verify-contract-compatibility-l2-detect-breaking-change`;
- `b2.level-outcome.verify-contract-compatibility-l3-build-consumer-evidence`.

**Ожидаемое новое outcome coverage пакета — прежде всего Compatibility L1.** Verification L1–L3 и Compatibility L2/L3 уже имеют accepted relationships из других модулей; M1.8.3 создаёт для них собственный Service Verification flow, а не изображает все связи впервые появившимся покрытием.

Compatibility L3 разрешено заявлять в project-spec только если milestone действительно связывает inventory/expectations минимум двух представительных consumers с semantic checks и migration/release decision одного Orders service. Простая schema snapshot или один HTTP example L3 не доказывает.

Verification L4 и Compatibility L4 не входят в target coverage. Межкомандные expectations/process могут быть follow-up, но не считаются execution evidence.

### Coverage roles по жанрам

- index — `reference` только на capabilities;
- learn — `explain` для выбранных L1–L3 outcomes;
- interview — `probe`, не proficiency evidence;
- kata — `practice` и `assess` только для действий, наблюдаемых в acceptance criteria;
- project-spec — `integrate` и `assess` для отдельного service-level milestone.

Не добавлять relationships к Architecture, validation/error или delivery outcomes только потому, что они упомянуты как prerequisite/context. Точный набор coverage должен быть минимальным и правдивым.

## Центральная ментальная модель

Материалы должны последовательно проводить цепочку:

> риск для пользователя/системы → механизм, который может нарушить обещание → самая дешёвая граница, где механизм реально присутствует → сигнал падения и локализация → стоимость проверки → остаточный риск.

Объяснить минимум четыре разные границы на каноническом substrate:

- чистая domain/application проверка;
- проверка validation/serialization component;
- проверка собранного приложения через реальный HTTP/ASGI path;
- consumer-facing contract check.

Не объявлять одну границу универсально лучшей. Быстрая локальная проверка и более широкая HTTP check отвечают на разные вопросы; mock/fake полезен, если он не удаляет проверяемый механизм.

## Artifact requirements

### 1. Index

`README.md` — самостоятельная точка входа: рабочая история, дефект и ущерб для consumer, prerequisites, маршрут `learn → interview → kata → project-spec`, ожидаемый результат, coverage и non-goals. До внутренних ID объяснить, почему зелёный набор тестов может не подтверждать фактическое внешнее поведение.

### 2. Engineering brief

Один связный brief раскрывает:

- различие test scope, test boundary, mechanism coverage, confidence и остаточного риска;
- почему названия unit/integration/E2E без конкретного механизма мало что доказывают;
- путь ошибки от входного HTTP request через validation/exception mapping к wire response;
- как mock/fake может как помочь локализации, так и удалить проверяемый механизм;
- выбор минимального набора проверок для seeded defect;
- contract check против schema snapshot и против полного end-to-end теста;
- стоимость, скорость, стабильность, диагностичность и false positives/false confidence;
- risk-based service strategy без фиксированных процентов видов тестов;
- good/bad practice на одном substrate;
- частые ошибки: тестирование implementation detail, дублирование одной assertion на всех уровнях, чрезмерный E2E, snapshot без semantic assertions, mock реальной boundary, игнорирование negative/error paths;
- вопросы самопроверки со скрываемыми ответами;
- локальный словарь для test boundary, mechanism coverage, confidence, false confidence, contract check, critical path, residual risk, test double, mock/fake и verification portfolio.

Mermaid использовать только если схема помогает увидеть, какие механизмы присутствуют или исчезают на разных test boundaries. Перед схемой задать вопрос, после — объяснить вывод и упрощения.

### 3. Interview

Interview начинается с полной истории S10 и фактического внешнего контракта. Включить:

- основной вопрос: почему все текущие tests зелёные и какой минимальный следующий check даст правдивый сигнал;
- последовательные follow-ups о риске, механизме, boundary, локализации, стоимости и остаточном риске;
- изменение условий: дефект виден только при сборке приложения; несколько consumers зависят от разных частей error contract; HTTP check стал медленным/нестабильным;
- скрываемый ожидаемый ответ на каждый вопрос;
- rubric L1/L2/L3 по автономности и масштабу решения;
- слабые ответы и диагностируемые пробелы;
- правило: перечисление test types/frameworks или количество тестов не повышает уровень;
- L4 follow-up только как граница применимости, без L4 coverage.

### 4. Kata

Участник самостоятельно создаёт минимальную систему по описанию; готового repository, scaffold и эталонного решения нет. Kata должна дать:

- обещанный consumer contract;
- перечень зелёных, но недостаточных исходных tests;
- способ посеять ровно один описанный exception-handler/error-mapping defect;
- требование сначала объяснить false confidence, затем добавить минимальные проверки, которые падают на дефекте;
- требование локализовать failure: отделить validation rule от application assembly/HTTP mapping;
- требование сохранить полезные быстрые tests и не заменить всё одним большим E2E;
- короткий decision note: риск, механизм, выбранные boundaries, стоимость и остаточный риск.

Acceptance criteria проверяют wire-level status/media type/body, способность поймать seeded defect и качество локализации. Hints направляют рассуждение, но не дают полный test code, структуру файлов или готовую реализацию.

### 5. Project specification

Одна компактная project specification задаёт milestone, отличный от kata: участник перестраивает verification portfolio **одного небольшого Orders service**, а не только чинит обнаружение одной регрессии.

Milestone обязан включать:

- inventory критических paths и failure modes этого сервиса;
- сопоставление каждого существенного риска с механизмом, test boundary и остаточным риском;
- минимум два представительных consumers из принятой Orders истории: регулярно обновляемый новый client и legacy operations script; проверять только реально используемые ими части контракта;
- local/application, adapter/component и HTTP/contract checks там, где они дают различающееся evidence;
- измеримый до/после результат только в границах этого сервиса: например, длительность выбранного набора, повторяемость flaky failure на фиксированном числе прогонов, число дублирующих assertions или время локализации seeded failures;
- удаление либо понижение scope хотя бы одной доказанно дублирующейся медленной/хрупкой проверки без потери critical-path evidence;
- несколько seeded failures из разных механизмов для проверки локализации, но не готовое решение;
- короткий decision record: risks, alternatives, выбранный portfolio, costs, residual risks и условия пересмотра.

Порог и measurement envelope выбирает участник и обосновывает до измерения; автор не задаёт универсальные проценты или performance SLO. Общие benchmark testing frameworks, CI platform optimization и cross-team governance запрещены. Явно указать отсутствие ImplementationReference до самостоятельной реализации и review.

## Non-goals

- Общий курс test design трека A2 и каталог testing frameworks.
- Универсальная test pyramid/trophy и фиксированный процент unit/integration/E2E.
- Полный пересказ S03 API evolution, S06 service architecture или S08 runtime failures.
- Изменение бизнес-контракта Orders API; контракт в этом пакете задан.
- Production rollout, CI/CD platform, organization-wide quality gates и C1 governance.
- Performance engineering самого сервиса или общей test infrastructure.
- L4 cross-team process/adoption evidence.
- Готовый runtime-код, scaffold, эталонное решение и ImplementationReference.

## Human-readable and technical guardrails

- Каждый файл понятен инженеру, открывшему его напрямую и не читавшему blueprint discussions.
- Сначала пользовательский ущерб и рабочая ситуация, затем taxonomy и критерии.
- Не использовать `unit`, `integration`, `component`, `contract`, `E2E`, `mock`, `fake`, `confidence`, `evidence` и `boundary` как самоочевидные слова: дать русское объяснение, устойчивый термин и локальный смысл.
- Не смешивать test scope (какая часть системы запущена) с целью проверки (какой риск/механизм она подтверждает).
- Не утверждать, что ASGI in-process test полностью эквивалентен production network/deployment path; явно назвать отсутствующие механизмы.
- Не выдавать OpenAPI schema, generated client, snapshot или mock за автоматическое доказательство фактического wire behavior.
- Не дублировать одинаковые assertions механически на каждом уровне; объяснить, что именно добавляет более широкая boundary.
- Вопросы самопроверки и interview имеют содержательные ответы в `<details>`.
- Нормативные и version-sensitive утверждения о HTTP, Problem Details, FastAPI, Starlette или Pydantic проверяются по первичным источникам на дату authoring; версии и freshness фиксируются по действующему стандарту.
- Если фактическое поведение закреплённой версии отличается от substrate, автор останавливает зависимую часть и передаёт вопрос, а не переписывает контракт молча.

## Acceptance criteria

Пакет готов к независимому G6 review, если:

- создано ровно пять назначенных artifacts и изменены только разрешённые регистрации;
- во всех файлах совпадают endpoint, invalid request, status, media type, Problem Details type и field pointer;
- seeded defect воспроизводит разрыв между зелёными локальными tests и фактической HTTP boundary;
- central action остаётся risk → mechanism → truthful boundary → signal/localization → cost → residual risk;
- Primary Verification L1–L3 и Supporting Compatibility L1–L3 имеют правдивые relationships подходящих жанров;
- явно сказано, что единственное ожидаемое новое outcome coverage — Compatibility L1, а остальное получает собственный module flow;
- kata обнаруживает и локализует один defect, не выдавая готовое решение;
- project меняет portfolio одного сервиса, использует минимум два consumer expectations и измеряет удаление дублирования в локальном envelope;
- project не превращается в общую оптимизацию test infrastructure или L4 governance;
- S03/S06/S08 переиспользуются ссылками без повторения центральных тем;
- terminology, `<details>`, Mermaid и source/freshness правила соблюдены по редакционному стандарту;
- coverage targets существуют, роли соответствуют жанрам, ссылки разрешаются;
- YAML, fences и `<details>` сбалансированы; нет conflict markers и trailing whitespace;
- все новые материалы остаются в `review`.
