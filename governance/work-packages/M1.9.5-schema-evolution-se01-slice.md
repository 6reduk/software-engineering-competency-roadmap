На дату проверки [таблица поддерживаемых версий](https://www.postgresql.org/support/versioning/) указывает 18.6 как текущий minor ветки 18; проверенный baseline совпадает с ним. Это не рекомендация production deployment. Первичные источники и их конкретное использование:

- [ALTER TABLE 18](https://www.postgresql.org/docs/18/sql-altertable.html): добавление nullable-столбца, CHECK NOT VALID, VALIDATE и SET NOT NULL. NOT VALID откладывает проверку прежних строк, но не отменяет enforcement новых изменений. Фактические lock modes ниже проверены отдельно.
- [Explicit Locking 18](https://www.postgresql.org/docs/18/explicit-locking.html): конфликт RowExclusive/AccessExclusive, удержание до конца транзакции; обычный writer не назван конфликтующим с ShareUpdateExclusive validation.
- [Transaction Isolation 18](https://www.postgresql.org/docs/18/transaction-iso.html): Read Committed и повторная проверка условия UPDATE; сохранённая клиентом константа сама не становится свежей.
- [Numeric types 18](https://www.postgresql.org/docs/18/datatype-numeric.html): numeric(12,2) округляет избыточный scale, а не отвергает его. Поэтому C-7 имеет внешний входной договор.
- [Error codes 18](https://www.postgresql.org/docs/18/errcodes-appendix.html): 42703, 23514, 23502, 22003 и 55P03 классифицируют разные исходы.
- [Monitoring statistics 18](https://www.postgresql.org/docs/18/monitoring-stats.html): observer проверяет activity/wait event; [pg_locks](https://www.postgresql.org/docs/18/view-pg-locks.html) и pg_blocking_pids показывают granted/waiter/blocker.
- [psql 18](https://www.postgresql.org/docs/18/app-psql.html): `-X`, autocommit и SQLSTATE после каждой команды; маркеры связывают ответ с операцией. Дополнительно сверены [release notes 18.6](https://www.postgresql.org/docs/18/release-18-6.html), включая изменения psql; выбранная сборка выпущена 2026-08-13.
- [Trigger behavior 18](https://www.postgresql.org/docs/18/trigger-definition.html): BEFORE ROW изменяет записываемую строку в той же транзакции; роль вызывающего используется без SECURITY DEFINER.

### Topology и локальные решения C-7/C-8

Шесть одновременно открытых отдельных соединений: W-old (`se01_old`), W-new (`se01_new`), backfill (`se01_backfill`), DDL/validation, observer и lock-probe writer. Последние три используют отдельные postgres-сеансы: это совмещение DB-полномочий, не соединений. Observer — superuser только в изолированной лаборатории, поэтому видит pg_stat_activity/pg_locks и blocker PID. R-old выполняется через W-old, R-new через W-new: чтения идут на явных барьерах, не скрывают параллельную запись. PID и все параметры сохранены в полном журнале.

У всех psql autocommit включён, default isolation — Read Committed, statement_timeout=2s, lock_timeout=1500ms. W-new использует явный BEGIN/COMMIT вокруг одной SQL-записи пары; observer читает до commit и после него. DDL удерживается в явной транзакции для наблюдения уже полученного lock. Матрица проверяется диагностическими INSERT/UPDATE ID 90 с ROLLBACK; они не входят в четыре подтверждённых предметных изменения. Закрытие/повторное открытие backfill после пачки доказывает resume сохранённой таблицы.

**C-7:** допустимы точные десятичные суммы 0,00…9999999999,99, преобразуемые в целые копейки без округления. Отрицательные суммы защищены store CHECK; верхняя граница проверена также отказом numeric overflow. Избыточная точность отвергается внешним точным decimal-предикатом до SQL. Пробы `-0.01`, `1.001`, `10000000000.00` отвергнуты этим договором. Отдельная SQL-проба `1.001` действительно дала `1.00` и была откатана: store не выдан за защиту исходной точности. W-new получает целые копейки; fixtures не используют float. Обход входного договора неизвестным writer не доказан безопасным.

**C-8:** сначала nullable-столбец, затем BEFORE ROW механизм для известной роли W-old, затем CHECK согласованности NOT VALID, backfill/сверка, VALIDATE pair_ok, отдельный CHECK обязательности NOT VALID и VALIDATE, затем SET NOT NULL. Старому writer выданы только нужные column privileges; он продолжает посылать только рубли. Trigger заполняет пару для него, а W-new сам атомарно пишет оба значения. Backfill не получает бизнес-авторитет: stale константа нарушает CHECK; Fixed проверяет актуальность перед применением и дополняет только ещё пустые строки. Матрица W-old проверена до и после enforcement, а затем во всех последующих состояниях. Это выбранная модель, не универсально лучший механизм и не доказательство отсутствия обходящих writers.

### Fixtures, порядок и результат

Одна таблица orders; исходные ID 1–4: `0.00,100.00,12.34,9999999999.99`. Во время прохода W-old подтверждает UPDATE 2→120.00 и INSERT 5→7.89; W-new подтверждает INSERT 6→2501 и UPDATE 3→1300. Независимый oracle задан этими входными командами, техническая запись backfill его не меняет. Полное точное сравнение отсортированных строк проверяет ключи и значения в обе стороны, включая отсутствие лишних строк.

| ID | amount_rub | amount_minor |
|---|---:|---:|
| 1 | 0.00 | 0 |
| 2 | 120.00 | 12000 |
| 3 | 13.00 | 1300 |
| 4 | 9999999999.99 | 999999999999 |
| 5 | 7.89 | 789 |
| 6 | 25.01 | 2501 |

До полных профилей объявлена и воспроизведена сигнатура **23514**: отдельный SELECT захватывает 10000, W-old commit/readback подтверждает 12000, отдельный UPDATE пытается применить сохранённые 10000 и отвергается. Последняя подтверждённая сумма остаётся 12000; перенос не завершён.

| Профиль | Повтор 1, с | Повтор 2, с | Результат |
|---|---:|---:|---|
| Control | 0.454816 | 0.455863 | Все шесть строк, допустимые пути, обязательность, повтор пачки |
| Defect | 0.136179 | 0.154803 | 23514; stop до validation/завершения, сумма 12000 сохранена |
| Fixed | 0.445660 | 0.408949 | То же конфликтующее чередование; stale UPDATE затронул 0 строк, полный oracle, resume |

В каждом чистом профиле зафиксированный наивный список содержит только ID 1–4, полная популяция — 1–6. Проба явно обнаруживает отсутствующий в наивном списке поздний ID 5 даже при уже заполненном trigger новом поле. В Control/Fixed backfill ограничен пачками ≤2; после подтверждённой пачки соединение закрыто, снимок сохранён, новое соединение повторяет пачку без изменения результата. R-new применяет fallback только для NULL и проверяет согласованность заполненных пар.

Пять состояний проверены: исходное (новый SELECT и INSERT отвергнуты 42703), расширение (новые пути намеренно выключены), сосуществование, сверка/validation, обязательное новое поле при сохранённом старом. После завершения отрицательные записи пары/NULL/отрицательной/слишком большой суммы дали соответственно 23514/23502/23514/22003; финальная сверка после проб и повторного backfill неизменна. Пограничные 0 и максимум присутствуют в полном результате. У каждого предметного write сохранён readback; W-new до commit невидим observer, после commit видна целая пара.

### Блокировки, stop и лимиты

Полученные DDL locks наблюдались до commit: ADD COLUMN, ADD CHECK и SET NOT NULL — AccessExclusiveLock; VALIDATE — ShareUpdateExclusiveLock. Отдельная конфликтующая пара — удерживаемый UPDATE lock-probe writer и SET NOT NULL DDL. Обе повторные пробы показали:

```text
se01-ddl|Lock|relation|AccessExclusiveLock|f|{278}
se01-lockwriter|Client|ClientRead|RowExclusiveLock|t|{}
```

PID blocker=278, PID waiter есть в session record. Обе DDL попытки получили **55P03**, затем writer ROLLBACK освободил lock, отдельный разрешённый повтор DDL прошёл; незапрошенных переходов после stop нет. Ожидание доказано store-сигналами, не одной длительностью. Максимум измеренной SQL-команды с round-trip через psql: **1.502658 с**. 2 секунды на SQL-операцию и 60 секунд на профиль подтверждены в этой малой популяции; создание контейнера/загрузка клиента не входят в эти пороги. Оснастка имеет дополнительный 5-секундный предел ожидания маркера. Это лабораторные предохранители, не SLO.

Неизвестный исход отдельно проверен как ветвь управляющей логики с отсутствующим подтверждением: следующая стадия не вызывается. Это не имитация сетевого разрыва и не доказательство recovery после потери реального commit-ответа. При реальном неизвестном исходе readiness не разрешает продолжение без выяснения судьбы записи. В основном опыте все четыре записи имеют подтверждения и readback.

## Рабочая история и единый договор материалов

Все пять материалов используют одну историю Orders: старое приложение читает/пишет рубли, новое — целые копейки, существующие строки переносятся, а текущая W-old запись конкурирует с backfill. Главный результат — сохранить последнее подтверждённое приложением значение и закончить опыт с обязательным новым представлением при сохранённом старом пути.

Материалы обязаны связать:

`совместимые состояния → допустимые readers/writers → механизм совместимости → backfill и текущие writes → независимая сверка → validation/locks → stop/resume/rollback или roll-forward`.

Рецепт одного SQL-механизма не должен подменять причинную модель. Если Gate 0 использует trigger либо adapter, учебный текст объясняет класс решения, его предпосылки и обходные пути, но не объявляет его универсально лучшим.

## Required artifact set

### 1. Index

Самостоятельный маршрут: рабочая история, prerequisites, две capabilities, hard edge `plan → validate`, пять материалов, ожидаемый результат и границы с B2 application contracts, B6 deployment orchestration и B7 production stop/go. Термины раскрываются при первом употреблении.

### 2. Engineering brief

Связно объяснить:

- expand/contract как модель состояний, а не универсальный список команд;
- совместимость R-old/W-old/R-new/W-new и неизвестного consumer;
- shadow/additional column, dual representation и авторитетное значение;
- почему процент backfill, отсутствие NULL и успешный DDL по отдельности недостаточны;
- гонку текущей записи с переносом и различие «расхождение применено» / «запись отвергнута»;
- порядок mechanism-of-compatibility, backfill, data reconciliation, constraint validation и обязательности;
- блокировки DDL/validation, blocker/waiter и bounded stop;
- idempotent/resumable backfill без превращения темы в background-workflow B2;
- rollback, roll-forward и границу необратимости удаления старого пути;
- pitfalls, good/bad practice, edge cases, локальный словарь и self-check с ответами в `<details>`.

Не превращать brief в справочник синтаксиса `ALTER TABLE`, полный migration playbook или production runbook.

### 3. Interview

Одна основная история: DDL и backfill «зелёные», но concurrent W-old изменил сумму, а новое представление устарело либо перенос остановился. Вопросы L1–L3 проверяют матрицу совместимости, авторитет данных, полноту oracle, порядок ограничений, lock evidence, stop/resume и решение при неизвестном writer. Все основные и дополнительные ответы скрыты в `<details>`; rubric различает уровни по самостоятельности и работе с неопределённостью.

### 4. Kata

Дать фиксированный договор, fixtures/oracle и двухшаговый seeded defect вокруг ID 2. Участник сам создаёт минимальную SQL-среду и оснастку барьеров, воспроизводит дефект, локализует первое неверное решение и защищает результат. Готового fixed SQL, trigger/adapter, scaffold приложения или эталонного решения нет.

Kata проверяет заданную матрицу и ограниченный L1/L2 результат: ID 2 остаётся 12000, поздний ID 5 не теряется, повтор одной пачки безопасен, после stop нет автоматического перехода к следующему состоянию. Lock-профиль может быть дан как наблюдаемая диагностическая проба, но не превращает kata в L3.

### 5. Project specification

Самостоятельный проект в отдельном репозитории: участник выбирает и обосновывает механизм совместимости, строит five-state migration harness, реализует control/defect/fixed, полную сверку, interruption/resume, lock-профиль и cleanup. Он обязан сравнить минимум два допустимых механизма или порядка перехода на различающих данных и оформить decision record; готовый выбор в скрытых ответах slice отсутствует.

Проект отличается от kata: участник сам выбирает механизм и детали DDL/constraints, защищает решение при неизвестном writer и конфликтующих ограничениях доступности, задаёт обоснованные guardrails и доказывает L3 evidence обеих capabilities. Production deployment, удаление старого поля и реальный multi-team adoption не требуются. ImplementationReference появляется только после самостоятельного выполнения и независимого review.

## Coverage contract

Допустимы только:

- `b3.capability.plan-compatible-schema-transitions`;
- `b3.capability.validate-online-data-change`;
- по три принятых L1–L3 outcome каждой capability.

Ожидаемые назначения:

- index: обе capabilities — `reference`;
- learn: L1–L3 обеих capabilities — `explain`;
- interview: L1–L3 обеих capabilities — `probe`;
- kata: L1/L2 обеих capabilities — `practice`, `assess`;
- project-spec: L2/L3 обеих capabilities — `integrate`, `assess`.

При полном обоснованном наборе это 30 новых relationships к восьми targets с распределением ролей `reference 2 / explain 6 / probe 6 / practice 4 / assess 8 / integrate 4`. В coverage map сохранить отдельно принятые SQ01 totals и новые SE01 review relationships; review-материалы не прибавлять к accepted totals.

Если artifact не даёт честного evidence для роли, связь не добавлять и объяснить расхождение в handoff. L3 kata и L1 project не начислять механически. Нельзя добавлять L4/L5 или coverage для B2 application evolution, B6 deployment, B7 reliability, transaction isolation, monetary domain либо PostgreSQL operations.

## Source and freshness requirements

- Engine-dependent утверждения проверять по официальной документации закреплённой PostgreSQL версии.
- Для driver/client использовать официальную документацию и release source выбранной версии.
- Отдельно проверять фактические lock modes и различия добавления, проверки и закрепления constraints; не переносить их между версиями по памяти.
- Разделять нормативную семантику PostgreSQL, инженерный вывод и локальный контракт лаборатории.
- Stable/current versions проверить на дату выполнения, но не выдавать их за автоматическую production recommendation.
- Неиспользуемые ссылки удалить; blog posts не использовать как основание ключевых claims при наличии первичного источника.

## Explicit non-goals

- полный курс PostgreSQL DDL, migrations, SQL или денежного моделирования;
- ORM/Alembic/Django migrations как обязательный framework;
- третья версия приложения, удаление `amount_rub` или production cutover;
- large-scale backfill, partition migration, CDC, cross-store replication и migration platform;
- API evolution B2, deployment automation B6, SLO/incident response B7;
- готовый SQL, trigger/adapter, эталонный repository, scaffold или учебная платформа;
- BR01, L4/L5, module-gate decision или полное завершение B3.
