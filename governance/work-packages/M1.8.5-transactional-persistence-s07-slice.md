# M1.8.5 — Transactional Persistence: граница транзакции и неизвестный исход S07

## Objective

Создать bounded end-to-end slice B2 для `b2.module.transactional-persistence-integration`. Материал должен научить инженера очерчивать transaction boundary одной application operation, различать состояние базы и внешний side effect, перечислять failure windows и подтверждать recovery/idempotency invariants наблюдаемыми проверками.

Центральное действие: участник проектирует подтверждение заказа, при котором database commit может завершиться перед публикацией `OrderConfirmed`, а процесс — упасть в любой контрольной точке. Участник должен восстановить однозначный результат операции без удержания database transaction через внешний network I/O и без обещания exactly-once.

Primary scenario — S07. S06 задаёт application operation и dependency direction, S04 — contract context повторного command, S10 — выбор проверок по реальному механизму отказа. S15 и caching не входят.

## Канонический substrate S07

Один Orders service выполняет command `POST /orders/{order_id}/confirm`:

- draft order переводится в `confirmed`;
- в той же database transaction сохраняется намерение опубликовать `OrderConfirmed`;
- отдельный publisher читает подтверждённые намерения и отправляет событие во внешний event sink;
- повтор команды имеет явную identity и возвращает определённый result;
- процесс можно остановить до commit, во время commit, после commit до publish и после publish до фиксации результата отправки.

Конкретный HTTP payload, заголовок/поле operation identity, schema минимальных таблиц и способ локального fault injection автор выбирает один раз после Gate 0 и использует одинаково во всех пяти материалах. Механизм «transactional event record + отдельный publisher» допустимо назвать outbox, но только как выбранный для этого substrate вариант, а не универсальный рецепт.

Обязательные invariants:

1. **Transaction invariant:** подтверждённый заказ и намерение публикации либо durable вместе, либо отсутствуют вместе; внешний вызов не выполняется внутри database transaction.
2. **Recovery invariant:** после подтверждённого commit незавершённая публикация остаётся обнаружимой и может быть продолжена после рестарта.
3. **Idempotency invariant:** одна operation identity имеет определённые result/conflict/retention semantics; повторная и конкурентная обработка не создают второе бизнес-подтверждение.
4. **Delivery boundary:** повторная отправка события возможна; downstream deduplication либо другой локально выбранный механизм рассматривается как явное допущение, а не как exactly-once guarantee.

Не смешивать неизвестный исход database commit с неизвестным исходом внешней публикации: это разные контрольные точки и разные способы reconciliation.

## Граница B2 / B3 / B5

B2 владеет application operation: где начинается и заканчивается transaction, когда вызывается внешний side effect, как сервис восстанавливается и что видит вызывающая сторона.

B3 предоставляет допущения о transaction/isolation, durability, WAL/recovery и поведении driver/store. Slice применяет эти свойства, но не преподаёт MVCC, lock manager, WAL internals, anomaly taxonomy или выбор СУБД.

B5 предоставляет только ссылочный язык для описания границы. Разрешено назвать и локально пояснить:

- partial failure;
- unknown outcome;
- duplicate delivery;
- at-least-once как свойство выбранной доставки;
- reconciliation;
- consistency boundary.

Эти термины **называются и применяются к S07, но не преподаются как общая теория B5**. Запрещены обзор delivery guarantees, distributed commit/2PC, consensus, saga taxonomy, общий курс consistency models и утверждение exactly-once end to end.

## Artifact requirements

### 1. Index

Самостоятельная точка входа: рабочая история, ущерб от расхождения database state и события, Gate 0 assumptions, маршрут `learn → interview → kata → project-spec`, ожидаемый результат, coverage и non-goals. До внутренних ID объяснить человеческим языком, почему «commit прошёл» не означает «внешний эффект точно произошёл».

### 2. Engineering brief

Один связный brief раскрывает:

- application operation, transaction/unit-of-work boundary и внешний side effect;
- commit, rollback, durability и unknown commit result в рамках зафиксированного substrate;
- timeline всех обязательных fault points;
- почему network I/O внутри transaction не устраняет неопределённость и добавляет риск;
- выбранный transactional event record/publisher mechanism и его ограничения;
- отдельные transaction, recovery и idempotency invariants;
- operation identity, result/conflict/retention и concurrent duplicate behavior;
- good/bad practices, типичные ошибки и interview traps;
- вопросы самопроверки со скрываемыми ответами;
- локальный словарь для неоднозначных терминов.

Mermaid timeline или state diagram использовать только вместе с вопросом перед схемой и объяснением после неё. На схеме явно различить database commit и внешнюю publication.

### 3. Interview

Начать с полной истории S07 и заданного Orders contract. Провести кандидата от L1 success/rollback через L2 boundary choice к двум разным L3 наблюдениям:

- Transaction L3: failure-window map, recovery choice и transaction/recovery invariant;
- Idempotency L3: identity/result/conflict/retention semantics, duplicate race и replay result.

На каждый вопрос и follow-up дать содержательный скрываемый ответ. Rubric различает автономность и масштаб, а не количество терминов. Слабые ответы включают exactly-once claim, network call внутри transaction, retry без identity, outbox как магическое слово и смешение unknown commit с unknown publish.

### 4. Kata

Участник сам создаёт минимальный scaffold; готового repository и решения нет. Kata исследует один основной crash window: commit подтверждён, но процесс падает до первой публикации. Участник должен сначала записать invariants и expected observations, затем реализовать минимальный recovery path и проверить повтор команды. Fault injection обязан быть воспроизводимым. Hints направляют рассуждение, но не дают структуру файлов или полный код.

### 5. Project specification

Один Orders service и одна confirmation operation, но несколько fault points: до commit, неизвестный исход commit, после commit до publish, после publish до marking. Milestone включает реальный PostgreSQL substrate, publisher/event-sink adapter, restart/recovery checks, concurrent duplicate command и короткий decision record.

Проект шире kata по числу failure windows и проверяет оба L3 раздельно. Measurement envelope задаёт число прогонов/fault injections, точки наблюдения, ожидаемое состояние database/event sink и критерий восстановления; универсальный performance SLO не нужен. ImplementationReference отсутствует до самостоятельной реализации и review.

## Human-readable and technical guardrails

- Каждый файл понятен инженеру, открывшему его напрямую.
- Сначала рабочая ситуация и ущерб, затем термины и критерии.
- Англоязычный индустриальный термин объясняется по-русски при первом употреблении; локальный glossary используется для повторяющихся неоднозначных слов.
- Не выдавать `commit()` return за доказательство внешней публикации и не обещать автоматическое определение исхода после потери соединения.
- Не утверждать, что rollback отменяет уже выполненный внешний side effect.
- Не использовать retry без operation identity и определённой result semantics.
- Failure/measurement claims называют workload, fault point, duration/число прогонов, точки наблюдения и acceptance threshold.
- Вопросы самопроверки и interview имеют ответы в `<details>`.
- Version-sensitive claims проверяются по первичным источникам; версии и freshness фиксируются по редакционному стандарту.
- Готовая реализация, scaffold и ImplementationReference не создаются.
