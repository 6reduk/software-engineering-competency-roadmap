## Required changes

### 1. Обновить snapshot и artifact registry

- Зафиксировать snapshot 2026-08-27 и acceptance M1.8.9.
- Добавить пять S05 artifacts после существующих entities с устойчивыми локальными кодами, kind, primary module и точным количеством relationships.
- Не менять исторические relationships первых 32 artifacts.
- Явно напомнить, что relationship считается как пара `(target, role)`, поэтому один artifact может иметь две relationships к одному target.

### 2. Пересчитать outcome audit

- Добавить все 15 YAML relationships M1.8.9 к exact targets.
- Сохранить ровно один канонический ряд на каждый из 69 outcomes.
- Не считать capability-level `reference` outcome evidence.
- Не считать `probe` proficiency evidence; отдельно пересчитать `probe-only`.
- Проверить, что Identity L1–L3 впервые получили execution-oriented evidence, а Identity L4 остался пустым либо probe-only согласно фактическому реестру.
- Не приписывать Abuse Controls, A3, HTTP, Architecture или Verification coverage за linked context, Gate 0 и переиспользованные contracts.

### 3. Пересчитать module states и DAG effects

Применять принятые определения `complete / partial / not-started / blocked` и действующие governance decisions.

Обязательно проверить:

- Identity and API security boundaries: `not-started → partial` за счёт собственного S05 flow и Identity L1–L3;
- Identity L4, Abuse Controls L1–L4 и отдельный module-gate decision отсутствуют, поэтому `complete` не присваивается;
- supporting relationships других slices не создают автоматическое завершение соседних modules;
- изменилось ли prerequisite readiness downstream modules, не смешивая hard DAG с external A3/B3/B5 baseline;
- A3 readiness M1.8.9 подтверждает только token/trust/object-authorization substrate S05 и не является общим доказательством A3 proficiency либо готовностью любого S14 threat/abuse механизма.

### 4. Пересобрать очередь

Сравнить минимум четыре кандидата:

- API Security & Abuse Controls — S14;
- Application Caching — S15;
- HTTP Service Runtime completion — S01/S02 либо один более узкий primary action;
- External Service Integration — S08 либо другой строго bounded primary action этого module.

При необходимости заменить слабого кандидата одним completion-tail существующего partial module, если он даёт больше нового outcome evidence и не требует искусственного L4. Для каждого оценить hard prerequisites, external A3/B3/B5 readiness, роль для двух RoleViews, пустое primary coverage, новое уникальное outcome coverage, boundedness центрального действия, риск повторения принятых slices и пригодность полного learning flow.

Не считать Gate 0 S05 автоматической готовностью S14. Для S14 выбрать один конкретный abuse/security mechanism и отдельно определить, какие элементы A3 baseline переиспользуемы, а какие требуют нового readiness record. Для S15 отдельно проверить B3 cache-store behavior: PostgreSQL readiness S07 его не подтверждает. Для S01/S02 и S08 не повторять уже принятое runtime/cancellation/pool/degradation evidence под новым названием.

### 5. Выбрать один следующий package

Decision brief обязан содержать:

- один module;
- один primary scenario и не более двух supporting scenarios;
- одно центральное наблюдаемое действие;
- primary/supporting capabilities и exact outcome candidates;
- ссылки на принятое coverage, которое нельзя повторять;
- минимальный полный flow `index + learn + interview + kata + project-spec` либо явное обоснование более узкого набора;
- внешний readiness gate внутри будущего authoring package, если он необходим;
- non-goals, risks/open questions и минимум две сильные отвергнутые альтернативы.

Не создавать следующий authoring work package и не писать учебный content.
