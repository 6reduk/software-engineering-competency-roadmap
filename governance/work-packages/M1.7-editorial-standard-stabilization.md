# M1.7 — стабилизация редакционного стандарта

## Objective

Превратить `authoring/standards/editorial-standard.md` из provisional-набора правил в устойчивый редакционный контракт, проверенный на двух принятых B2 slices разного типа: эволюция API-контракта и runtime/concurrency/failure diagnosis. Синхронизировать с ним контракт автономного автора так, чтобы следующие пакеты M1.8 воспроизводили human-readable качество без копирования структуры пилотных материалов.

## Ownership

Автор может изменять только:

- `authoring/standards/editorial-standard.md`;
- `authoring/workflow/content-author-workflow.md`.

Запрещено изменять учебные материалы обоих slices, coverage, метамодель, `authoring/standards/content-standard.md`, reviews, decisions, work packages и program status.

Материалы внутри slices открывать точечно, когда нужно проверить формулировку правила или привести короткий пример. Не загружать все файлы автоматически и не превращать стандарт в ретроспективу конкретных Orders/Quote API.

## Required changes

### 1. Снять provisional-оговорку

- Переписать title и вводный абзац как постоянный редакционный стандарт.
- Изменить `status: drafting` на `status: review`; acceptance выполняет оркестратор только после независимого review.
- Обновить дату документа на `2026-08-16`.
- Зафиксировать область действия: учебные briefs, interview, kata, project specification и index/README; правила применяются с учётом жанра.

### 2. Зафиксировать адаптивность формы

Явно указать, что стандарт задаёт обязательные качества и движение мысли, а не одинаковый шаблон разделов. API evolution и runtime diagnosis могут иметь разную композицию. Раздел, таблица, схема или glossary появляются только тогда, когда помогают читателю решить задачу.

### 3. Добавить стандарт проверяемых условий

Для материалов о производительности, отказах, конкурентности и восстановлении определить минимальный `failure/measurement envelope`:

- исследуемая группа запросов или операций;
- нагрузка и длительность наблюдения;
- поведение зависимости или вид отказа;
- точка и сторона измерения;
- измеримый порог принятия;
- различие между профилем воспроизведения отказа, контрольным замером и состоянием системы после снятия нагрузки.

Числа, повторяющиеся в brief/interview/kata/project одного сценария, должны совпадать. Если значения намеренно отличаются, документ обязан объяснить, чем различаются контекст, группа измерений или цель проверки. Экспериментальный порог нельзя выдавать за универсальную production-гарантию.

### 4. Уточнить язык, словари и локальные обозначения

- Сохранить правило human-first первого употребления термина.
- Добавить правило для вторичных англицизмов: обычное русское слово предпочтительно, если английский термин не повышает точность; устойчивые имена протоколов, API и runtime-механизмов не переводятся искусственно.
- Локальный словарь содержит повторяющиеся или смыслообразующие термины, а не каждое единичное английское слово.
- Один термин не должен незаметно обозначать разные сущности. В частности, `baseline` следует уточнять как закреплённую версию, контрольный замер или исходное состояние; для состояния после снятия нагрузки использовать наблюдаемые признаки восстановления.
- Внутренние scenario/capability/outcome IDs не должны быть нужны читателю для понимания текста. Если ID полезен для трассировки, рядом даются человеческое название, контекст и разрешающаяся ссылка.

### 5. Уточнить правила схем и примеров

Для значимой Mermaid-схемы требовать:

1. вопрос или назначение перед схемой;
2. пояснение, что она показывает;
3. явные намеренные упрощения, если без них возможна неверная модель;
4. практический вывод после схемы.

Не требовать отдельный абзац о пропусках у тривиальной схемы, если граница очевидна и риск неверного вывода отсутствует. Примеры внутри одного slice должны сохранять согласованный substrate и обозначения либо прямо объявляться независимыми историями.

### 6. Уточнить kata и project specification

- Явно сообщать, существует ли стартовый scaffold или участник создаёт минимальную систему самостоятельно.
- Acceptance criteria предваряются рабочей историей и объяснением смысла ограничений.
- Hints разворачивают направление рассуждения, но не выдают реализацию.
- Project milestones объясняют учебную цель и наблюдаемый результат, не превращаясь в готовый план реализации.

### 7. Добавить правила источников и актуальности

- Источник должен подтверждать реально сделанное утверждение; неиспользуемые ссылки удаляются.
- Для version-sensitive утверждений используются первичные официальные источники и дата проверки.
- `versions` означает воспроизводимый baseline, на котором проверены утверждения, а не автоматически latest release.
- Если закреплённая версия заметно отстаёт от актуальной и разрыв может изменить применимость материала, автор поясняет разрыв и последствия в разделе актуальности. Новое metadata-поле без изменения метамодели не вводится.
- Нормативное требование и практическая рекомендация должны опираться на источник соответствующей силы и не подменять друг друга.

### 8. Синхронизировать контракт автономного автора

В `authoring/workflow/content-author-workflow.md` устранить расхождения с новым стандартом:

- сослаться на `authoring/standards/editorial-standard.md` как на обязательный редакционный контракт;
- компактно отразить новые правила measurement envelope, terminology/IDs, Mermaid framing, scaffold ownership, source-to-claim и pinned-version freshness;
- дополнить self-check проверками согласованности чисел и обозначений между файлами одного пакета;
- не дублировать весь редакционный стандарт и не менять роли, ownership protocol, handoff format или канонический `/goal` без необходимости.

## Constraints and non-goals

- Не переписывать стандарт как учебник по техническому письму.
- Не вводить жёсткий универсальный шаблон секций и количественные нормативы длины текста.
- Не делать Mermaid, glossary, кодовый пример или таблицу обязательными для каждого материала.
- Не переносить в стандарт конкретные thresholds, URL, версии библиотек и детали Orders/Quote API.
- Не менять semantic IDs, metadata schema, review protocol и программные gates.
- Не редактировать принятые slices и не начинать M1.8.
- Оба изменённых документа оставить в `status: review`.

## Acceptance checks

- каждое правило выведено из повторяемой проблемы или принятого решения двух slices, а не из единичной стилистической прихоти;
- стандарт остаётся human-readable и объясняет смысл правил, а не только перечисляет критерии;
- API evolution и runtime/failure material одинаково укладываются в стандарт без принудительно одинаковой структуры;
- правила терминов, Mermaid, вопросов/ответов, kata/project, измерений, источников и актуальности не противоречат друг другу;
- `docs/09` и `docs/10` согласованы, но не дублируют друг друга целиком;
- `authoring/standards/content-standard.md` и метамодель не требуют сопутствующей правки;
- YAML front matter разбирается, относительные ссылки разрешаются;
- Markdown fences, Mermaid и `<details>` сбалансированы;
- нет conflict markers и trailing whitespace;
- handoff перечисляет изменённые правила, отклонённые варианты, проверки и рекомендуемый scope независимого review.

## Open questions
