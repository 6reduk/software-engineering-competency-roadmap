# M1.8.21 — обновление B2 consolidation после HTTP Runtime/S01

## Objective

После принятого M1.8.20 синхронизировать канонический delivery plan и производное consolidation dossier с фактическим accepted-набором B2. Отделить закрытие content-action D19/D20 от отсутствующего evidence выполнения проектов участником, повторно оценить готовность десяти module gates и выбрать ровно одно следующее bounded действие либо обоснованный переход к следующей вертикали.

Пакет не создаёт учебные материалы, semantic IDs, coverage relationships, ImplementationReference или готовые реализации.

- 57 artifacts;
- 249 relationships: 21 capability-level `reference` и 228 outcome-level;
- role totals `reference 21 / explain 55 / probe 57 / practice 28 / integrate 30 / assess 58`;

M1.8.20 добавляет четыре accepted artifacts и ровно 10 relationships: `1 reference / 3 probe / 2 practice / 3 assess / 1 integrate`. Новых unique outcomes не заявлено. Ожидаемая арифметика после пересчёта — `61 artifacts / 259 relationships = 22 reference + 237 outcome-level`; role totals `22 / 55 / 60 / 30 / 31 / 61`; `58/11` outcomes и 7 probe-only. Агент обязан подтвердить эти числа по YAML, а не перенести их как данность.

## Required work

### 1. Обновить канонический snapshot

В `module-delivery-plan.md`:

- независимо пересчитать accepted artifacts, relationships, роли, covered/uncovered и probe-only;
- добавить M1.8.20 в registry и outcome audit без изменения исторических relationships;
- пересчитать membership всех 10 modules;
- проверить состояния и hard DAG;
- явно отметить, что HTTP Runtime получил собственные index/interview/kata/project-spec, но acceptance материалов не является evidence выполнения участником или module completion.

### 2. Синхронизировать навигацию

В `routes-and-reuse.md` и связанных входах досье заменить будущий HTTP Runtime action фактическим accepted-маршрутом. Маршрут должен показывать полный переход `learn → interview → kata → project-spec`, различать собственные и supporting материалы и не объявлять production Trace L3.

Оба RoleView должны приводить к обновлённому маршруту без создания второго coverage registry.

### 3. Разрешить D19/D20 без подмены proficiency

В debt register:

- пометить content/navigation часть D19 и content/exercise часть D20 закрытыми принятым M1.8.20;
- сохранить отдельным незакрытым условием фактическое выполнение project-spec участником, review реализации и возможный ImplementationReference;
- не уменьшать долг простым удалением записей без audit trail;
- не выдавать регистрацию задания за подтверждённый навык.

Проверить все ссылки на D19/D20 в module gates, implementation readiness и README досье; формулировки должны отражать их новый статус.

### 4. Повторно оценить module gates

Для каждой из 10 карточек подтвердить:

- accepted content evidence;
- чего всё ещё не хватает для gate;
- external readiness и conditional L4 границы;
- статус `not-ready-for-gate` либо обоснованный кандидат `ready-for-orchestrator-decision`.

Не принимать module gate от имени оркестратора. Если все 10 остаются `not-ready`, объяснить общий блокирующий класс конкретно: например, отсутствие выполненных самостоятельных проектов и independently reviewed ImplementationReference, а не абстрактное «нужно больше материала».

### 5. Выбрать одно следующее действие

Сравнить как минимум:

1. один bounded B2 completion-tail из актуального debt register;
2. пакет подготовки одного module gate, если он действительно близок к решению;
3. переход к следующей вертикали после завершённого breadth и полного пятижанрового content flow 10/10.

Выбрать ровно один вариант. Для выбора назвать:

- центральное инженерное действие или управленческий результат;
- какой конкретный долг/риск он закрывает;
- prerequisites/readiness;
- границы и non-goals;
- проверяемый exit trigger.

Не назначать новый пакет только ради увеличения coverage. L4 требует реального adoption/migration evidence и не закрывается дополнительным текстом.
