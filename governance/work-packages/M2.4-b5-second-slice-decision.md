# M2.4 — решение о втором B5 slice или фазовом close-out

## Objective

Создать ровно один planning artifact, который после принятого M2.3 выбирает один из двух маршрутов:

1. второй и последний контрастный B5 deep slice;
2. немедленный обязательный B5 close-out без второго slice.

Это решение о фазовом маршруте, а не Gate 0, authoring или начисление coverage.

## Ownership

Создать ровно один файл:

- `governance/planning/intakes/b5-second-slice-decision.md`.

Другие файлы не изменять. Не создавать work package следующего authoring/close-out, Gate 0 record, coverage, semantic IDs, учебные материалы, review или acceptance.

## Обязательный контекст

Прочитать полностью:

1. `governance/planning/intakes/b5-boundary-intake.md` — фазовый порядок, критерий контраста и абсолютный предел двух slices;
2. `curriculum/tracks/b5/README.md`, `modules.md`, `capabilities.md`, `level-outcomes.md`, `scenarios.md`, `role-requirements.md`;
3. `governance/reviews/M2.2-G30-b5-capability-breadth-pass-acceptance.md`;
4. `governance/reviews/M2.3-G31-stale-authority-fencing-acceptance.md`;
5. `curriculum/tracks/b5/slices/stale-authority-fencing/README.md` и `curriculum/tracks/b5/coverage-map.md`;
6. B2/B3 accepted close-out или consolidation только для проверки повторения уже созданных маршрутов.

## Обязательное сравнение

Сопоставить минимум три варианта:

1. **CA01 — старое чтение после подтверждённой записи:** visibility/consistency, capability `b5.capability.choose-read-guarantees`.
2. **Композиция доставки и бизнес-эффекта:** соответствующий сценарий messaging/events и capabilities `define-delivery-contract`, `bound-repeat-effects` или `compose-state-and-publication`; точный bounded action выбрать только для сравнения, не объединять все три.
3. **Close-out сейчас:** сохранить оставшиеся B5-кластеры blueprint-only и записать условия возвращения к ним.

Для каждого варианта указать:

- тип системного решения и защищаемую гарантию;
- одно центральное инженерное действие;
- различающие наблюдения и доступность ограниченной среды;
- новый результат для Backend и Architecture относительно TO01/CL01;
- риск повторения B2/B3 или первого B5 slice;
- стоимость Gate 0, authoring и независимого review;
- какой долг останется даже при успешном результате.

## Правило выбора

Второй slice допустим только если одновременно выполнены все условия:

1. меняется тип системного решения, а не только продукт или механизм;
2. появляется новый проверяемый результат для обеих ролей, не подтверждённый TO01/CL01;
3. defect/fixed и различающие наблюдения доступны в bounded лаборатории;
4. пакет не повторяет B2 runtime/caching/messaging/idempotency и B3 store-specific mechanics;
5. scope остаётся одним действием, максимум пятью учебными материалами и отдельным Gate 0;
6. ожидаемая ценность выше стоимости ещё одного authoring/review цикла.

Если хотя бы одно обязательное условие не выполнено, выбрать close-out. Непокрытые outcomes, отсутствие learner execution или желание «закрыть карту» сами по себе не обосновывают второй slice.

## Требования к результату

Файл `governance/planning/intakes/b5-second-slice-decision.md` должен:

- иметь уникальный `id`, `kind: plan`, `owner_track: b5`, `status: review`, `updated: 2026-09-18`, `language: ru`;
- начинаться с человеческого объяснения, какое решение принимается и почему оно нужно после первого slice;
- содержать одну сравнительную таблицу и выбрать ровно один маршрут;
- если выбран второй slice — назвать один primary scenario, один bounded action, кандидатные capabilities/outcomes, будущие Gate 0 unknowns, non-goals и конечный exit trigger;
- если выбран close-out — назвать следующий close-out artifact, обязательный recount, долг, критерии возврата и запрет третьего slice;
- явно сохранить C1 decision-record carrier как линзу решения без C1 coverage/proficiency;
- не объявлять module completion, proficiency, learner execution, production readiness или ImplementationReference;
- объяснять неоднозначные англоязычные термины при первом употреблении.

## Проверки

Проверить:

- ровно один новый файл и ноль изменённых/удалённых файлов;
- YAML и уникальность `id` в workspace;
- все относительные ссылки и anchors;
- ровно один выбранный маршрут;
- отсутствие новых coverage relationships, semantic entities, Gate 0 claims и учебных материалов;
- Markdown, UTF-8 без BOM, конечный перевод строки, отсутствие trailing whitespace и conflict markers.

SHA-256 snapshot доказывает только scope текущего запуска, а не историческую чистоту workspace.

## Handoff

Передать оркестратору:

1. выбранный маршрут и короткое обоснование;
2. сравнение трёх вариантов по обязательным критериям;
3. если выбран slice — точный bounded action и список неподтверждённых Gate 0 inputs;
4. если выбран close-out — обязательный состав close-out и условия возврата;
5. механические проверки и открытые вопросы.

Автор не запускает следующий пакет, review или acceptance.
