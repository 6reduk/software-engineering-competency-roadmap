## Профиль A — mechanical coverage, module states и DAG

Независимо, без доверия итоговым числам плана:

1. перечислить все accepted artifacts и пересчитать relationships как пары `(target, role)`;
2. подтвердить либо опровергнуть `42 artifacts / 216 relationships / 18 capability-level / 198 outcome-level`;
3. построить множество exact outcome targets, подтвердить либо опровергнуть `55 covered / 14 uncovered` из канонических 69;
4. пересчитать `probe-only`, привести exact IDs и проверить ожидаемое число 7;
5. отдельно сверить пять M1.8.11 artifacts: 13 relationships, 4 targets, новые Abuse L1–L3, отсутствие Abuse L4 и supporting claims;
6. пересчитать membership counts и состояния всех 10 modules; проверить ожидаемое `0 / 8 / 2 / 0`;
7. проверить, что Identity/API Security остаётся `partial`, а accepted flow и количество links не создают module-gate decision;
8. пройти internal hard prerequisite DAG и отдельно проверить external A3/B3/B5 readiness statements;
9. сверить artifact registry и outcome audit плана с фактическими YAML, обнаружить пропуски, дубликаты, неверные роли и битые ссылки;
10. подтвердить, что план изменяет только результат M1.8.12, не переписывая историю принятых relationships.

Профиль A не оценивает вкус выбранной cache strategy, кроме фактических противоречий catalogs/DAG.

## Профиль B — planning quality, boundedness и readiness S15

Независимо проверить:

1. честно ли сравниваются S15 caching, callback/SSRF, HTTP Runtime и External Integration, без подгонки результата только под число пустых outcomes;
2. обоснован ли приоритет S15 сейчас для обеих RoleViews и даёт ли он ровно новое Cache L2/L3 evidence;
3. является ли центральное действие одним bounded action либо скрыто объединяет stampede control, invalidation, stale policy, tenant isolation и cache outage в несколько несвязанных проектов;
4. различимы ли L2 и L3: применение известного cache pattern против самостоятельного design consistency/failure behavior;
5. достаточно ли Gate 0 требует определить cache store/client, process/worker topology, source of truth, tenant-safe key, TTL/freshness invariant, atomicity/coordination semantics, invalidation ordering, failure/fallback behavior, populations, counters, measurement points, thresholds и stop conditions;
6. не предполагает ли brief заранее Redis, distributed lock, lease или process-local lock как универсальное решение;
7. не выдаётся ли one-process evidence за distributed guarantee и ясно ли ограничивается применимость coalescing;
8. не начисляются ли повторно Transaction, Load Control, Verification, B3/B5 или Cache L4 outcomes за supporting context/readiness;
9. достаточно ли различаются будущие kata и project: один burst-miss defect против полного hit/miss/race/failure/recovery envelope;
10. сохраняются ли non-goals: write-behind/write-through, multi-region, migration, capacity program, query tuning, implementation reference и production rollout;
11. остаются ли callback/SSRF и aggregate quota/rate разными долгами, а не искусственно закрытыми operation-cost acceptance;
12. читается ли decision brief автономно человеком и позволяет ли на его основе создать следующий Gate 0 без скрытых решений.

Профиль B обязан явно ответить:

- не слишком ли широк набор `freshness + isolation + fallback + stampede` для одного slice и какая единая инварианта связывает его;
- достижимо ли честное Cache L3 evidence в локальном учебном проекте без заявления Cache L4;
- какие решения обязательно должны быть приняты в Gate 0 до написания первого материала;
- есть ли кандидат, который объективно сильнее S15 сейчас.

## Общие severity rules

- `blocker`: аудит непригоден как основа планирования либо выбранный package внутренне невыполним без смены цели;
- `major`: неверны ключевые числа/state/DAG, S15 требует несколько центральных действий, или Cache L2/L3 coverage структурно неправдив;
- `minor`: локальное расхождение, неполный readiness criterion, слабое объяснение или неверная ссылка, исправимые без смены выбора;
- `note`: улучшение либо будущий долг без дефекта текущего решения.
