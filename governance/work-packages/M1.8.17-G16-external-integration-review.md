## Профиль A — integration mechanics, technical correctness и measurement

Независимо проверить по Gate 0, первичным источникам и минимальному локальному воспроизведению:

- фактическое прохождение outbound response через HTTPX, а не готовый mock result адаптера;
- точный контракт Pricing и Quote, строгую схему, совпадение `item_id` и запрет coercion для `amount_minor`;
- порядок проверок: HTTP status до media type, decoding и schema/identity;
- корректность всех 11 matrix rows и категорий `http/media/decoding/schema/timeout/transport`;
- сохранение `200 offers=[]` как `no_offers` и невозможность получить `no_offers` из девяти failure rows;
- центральный defect failure→empty и различающую силу contract checks;
- корректность арифметики 82 входящих проверок, 79 outbound attempts, 27 failure operations и recovery 6/6;
- one-attempt evidence: retries=0, отсутствие application retry loop, redirects/auth resend и раздельные client attempts/server receipts;
- границу утверждения для transport/connect failure, где server receipt может отсутствовать;
- HTTPX timeout semantics: равные phase timeouts не являются общим deadline; timeout не доказывает remote cancellation;
- response <500 мс, drain/client/server cleanup ≤1 с как локальные experiment thresholds, а не production SLO;
- recovery на том же клиенте после снятия дефекта и корректное владение lifecycle;
- trusted configured authority и отклонение URL-подобных item IDs без заявления SSRF protection;
- отсутствие remote side effect как исходное условие операции, а не вывод только из метода GET;
- корректность и актуальность pinned/current versions и source-to-claim mapping;
- отсутствие fan-out, pool, cancellation, circuit breaker, service discovery и production-readiness overclaim;
- отсутствие External L3/L4, A3/B5 proficiency и supporting coverage overclaim.

Профиль A обязан отдельно ответить:

1. Можно ли считать текущий Gate 0 `confirmed` в его явно ограниченной модели?
2. Какие авторские runtime-наблюдения удалось независимо повторить, а какие остались непроверенными?
3. Доказывают ли 79 attempts/79 receipts отсутствие hidden retry для всех применимых строк, включая failures?
4. Есть ли хотя бы один путь, где технический отказ становится предметным отсутствием после исправления?
5. Достаточно ли Gate 0 для bounded External L1/L2 evidence без перехода к L3 или production readiness?

## Профиль B — learning design, coverage и human readability

Независимо проверить:

- наличие рабочего контекста до внутренних IDs, критериев, англицизмов и чисел;
- причинную модель: только проверенный пустой ответ доказывает отсутствие, каждый следующий technical check разрешает более сильный предметный вывод;
- понятность dependency, client adapter, business absence, integration failure, decoding, schema validation, attempt, authority, lifecycle, drain, wire contract и coercion при первом употреблении либо через локальный словарь;
- автономность каждого файла и связный маршрут `README → learn → interview → kata → project-spec`;
- содержательные скрываемые ответы для self-check, interview follow-ups, hints и defense questions;
- оценивание решений, наблюдаемых фактов и границ доказательства, а не количества терминов;
- отсутствие механического копирования Gate 0 вместо адаптации материала к жанру;
- kata как исправление одного заданного failure→empty defect по известной матрице, без scaffold/готового решения и без скрытого L2;
- project как самостоятельный выбор внутренних result/error types, mapping, owner, one-attempt decision и evidence полного client path;
- наблюдаемое различие kata и project по свободе, масштабу и результату;
- правдивость External L1 как применения заданного клиента и исходов;
- правдивость External L2 как самостоятельного проектирования типовой client boundary и resource ownership;
- отсутствие External L3/L4, Cancellation, Load Control, Verification, A3 и B5 relationships;
- ровно пять semantic IDs, 9 relationships и три unique targets;
- совпадение YAML, registrations и ролей `1 reference / 2 explain / 2 probe / 1 practice / 2 assess / 1 integrate`;
- единые endpoint, fixtures, matrix, categories, versions, populations, thresholds и limitations во всех пяти материалах;
- metadata, sources/freshness, ссылки, anchors, fences, раскрываемые блоки ответов, Markdown hygiene и отсутствие ImplementationReference;
- отсутствие готовой реализации и предписания единственного внутреннего pattern/framework.

Профиль B обязан отдельно ответить:

1. Дают ли External L1 и L2 разные наблюдаемые evidence, а не один сценарий с двумя ярлыками?
2. Объясняет ли learn причинную модель client boundary либо только пересказывает лабораторный протокол?
3. Достаточно ли различаются kata и project по свободе решения, масштабу и результату проверки?
4. Можно ли понять business absence против integration failure без чтения work package?
5. Не подавляет ли повторение measurement envelope учебную задачу отдельных жанров?
6. Можно ли принимать slice после disposition findings?

## Общие anti-patterns

- Не считать корректный Python dict доказательством проверки HTTP status, media type или transport failure.
- Не считать `.get("offers", [])`, broad exception или default-empty допустимым fallback.
- Не выдавать 503 с пустым телом или `offers=[]` за business absence.
- Не смешивать decoding, schema, HTTP и transport failure в один успешный пустой результат.
- Не считать один wrapper counter достаточным доказательством отсутствия hidden retry.
- Не считать timeout автоматической отменой удалённой работы.
- Не выдавать URL validation за полноценную SSRF protection.
- Не требовать fan-out, circuit breaker, service mesh, production benchmark или External L3/L4 внутри bounded package.
- Не начислять supporting coverage за использование runtime/verification context.
- Не считать project specification готовой реализацией.
- Не редактировать исходные материалы.

7. отдельный вывод по Gate 0 и границам runtime evidence либо по External L1/L2 и coverage;
8. отдельный вывод по failure→empty boundary либо по различию kata/project;
9. ответ, можно ли принять slice после disposition findings;
10. подтверждение независимости и отсутствия исходных правок.

## Acceptance gate G16

M1.8.17 можно принять, когда:

- получены оба независимых профиля либо оркестратор явно зафиксировал согласованное исключение из двухпрофильного gate;
- нет открытых blocker/major по Gate 0, response interpretation, one-attempt evidence, lifecycle, learning design или coverage;
- version/source issues исправлены либо явно adjudicated;
- business absence и integration failures признаны различимыми во всех применимых строках;
- External L1/L2 evidence признано различимым и правдивым без L3/L4/A3/B5/supporting overclaim;
- kata и project дают разные наблюдаемые результаты и не содержат готового решения;
- решения по minor/note зафиксированы оркестратором;
- после необходимых corrections пять материалов и регистрации переводятся в `accepted` отдельным acceptance-pass.

## Open questions

На review передаются два принципиальных вопроса:

1. Достаточен ли несохранённый авторский stdin probe при условии независимого минимального воспроизведения техническим reviewer-ом?

Ответы должны учитывать bounded scope и не подменять проверку требованием сохранить готовую реализацию либо построить production integration platform.
