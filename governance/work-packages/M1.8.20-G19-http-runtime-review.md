## Профиль A — runtime mechanics, technical correctness и traceability

Независимо проверить по Gate 0, первичным источникам и минимальному локальному воспроизведению:

- совместимость pinned FastAPI/Starlette/Pydantic/HTTPX/AnyIO с CPython и честность current-stable/freshness утверждений;
- фактический in-process ASGI путь `GET /quote` и полный контракт `200/503/422`, media type, JSON и серверного `X-Request-ID`;
- игнорирование одноимённого клиентского заголовка и отсутствие смешения diagnostic identity с authentication/authorization identity;
- корректность владельца `ContextVar`: set/token/reset во внешнем pure ASGI middleware и cleanup в `finally`;
- семантику создания asyncio task: штатное копирование текущего context и намеренно пустой `contextvars.Context()` в defect;
- воспроизводимость первой потери `created → dispatch-enter`, сохранение UUID в родительской task и отсутствие его в downstream task;
- различие первой наблюдаемой потери, уточнённой root cause и позднего `response-start: missing`;
- порядок success, domain-error и invalid-query checkpoints именно для pinned request-scoped `yield` assembly;
- достаточность safe correlation при отсутствии headers/body/secrets/credentials/избыточных персональных данных в trace;
- арифметику пяти populations: 90 control + 90 defect + 90 fixed + 36 concurrent + 60 recovery = 366, плюс три bypass-контроля;
- различающую силу control/defect/fixed, concurrent isolation, recovery cleanup и 5-second watchdog как anti-hang guard, а не SLO;
- отрицательный контроль механизма: правильный внешний ответ при bypass должен быть отклонён из-за отсутствия существенных pipeline checkpoints;
- причинность исправления: task boundary сохранена, ручной fallback в handler/response отсутствует, публичный контракт восстановлен;
- корректность ограничений: нет сети, proxy/TLS, lifespan, thread pool, worker reuse, distributed propagation, production tracing или production L3;
- отсутствие overclaim Lifecycle, Cancellation, Verification, HTTP Contract, B1/A3/B7 coverage и module completion.

Профиль A обязан отдельно ответить:

1. Можно ли считать Gate 0 `confirmed` в его явно ограниченной in-process модели?
2. Какие ключевые наблюдения удалось независимо повторить, а какие остались только авторским record?
3. Является ли `created → dispatch-enter` первой доказанной потерей и достаточно ли данных, чтобы связать её с explicit empty context?
4. Может ли proposed regression пройти при ручной подстановке правильного заголовка или обходе dependency/handler pipeline?
5. Достаточно ли evidence для Trace L1/L2 без исполнительного L3 и production-readiness claim?

## Профиль B — learning design, navigation, coverage и human readability

Независимо проверить:

- наличие рабочего контекста до внутренних IDs, checkpoints, критериев и англицизмов;
- причинную модель `symptom → competing hypotheses → distinguishing observation → first loss → root cause → regression`;
- понятность request context, server-owned context, propagation, checkpoint, instrumentation, correlation, first-loss boundary, task/thread, token/reset, scaffold, seed и bypass при первом употреблении либо через локальный словарь;
- автономность четырёх файлов и связный маршрут `README → C1/R1 learn reuse → interview → kata → project-spec`;
- достаточность переиспользованных C1/R1 без создания отсутствующего learn-файла и без требования читать весь B2;
- содержательные скрываемые ответы для self-check, interview, hints и project defense;
- оценивание гипотез, наблюдений, причинной правки и границ доказательства, а не количества терминов;
- отсутствие преждевременного раскрытия seed до фиксации гипотез и честность ограничения самостоятельной диагностики при одиночной работе;
- kata как локализацию одного заданного defect с сохранением task/pipeline, без scaffold, grader и готового решения;
- project как самостоятельный выбор diagnostic concern и refactor boundary, более широкая матрица и отдельный decision record;
- наблюдаемое различие kata/project по свободе, масштабу и результату;
- правдивость Trace L1 как прохождения известного пути и Trace L2 как самостоятельной локализации типового отказа;
- правдивость Trace L3 только как interview probe по неизвестной production topology без execution/proficiency claim;
- отсутствие Lifecycle, Cancellation, Verification, HTTP Contract, B1, A3, B7 и supporting relationships;
- ровно четыре semantic ID, 10 relationships и четыре unique targets;
- совпадение YAML, registrations и ролей `1 reference / 3 probe / 2 practice / 3 assess / 1 integrate`;
- единые endpoint, outcomes, context ownership, defect, checkpoints, populations, versions и limitations во всех четырёх материалах;
- metadata, sources/freshness, ссылки, anchors, fences, раскрываемые блоки, Markdown hygiene и отсутствие ImplementationReference;
- отсутствие готовой реализации и требования OpenTelemetry, service mesh или единственной внутренней архитектуры.

Профиль B обязан отдельно ответить:

1. Дают ли Trace L1 и L2 разные наблюдаемые evidence, а L3 остаётся честным probe?
2. Можно ли понять причинный метод диагностики без чтения work package?
3. Достаточно ли различаются kata и project по самостоятельному выбору и результату защиты?
4. Помогает ли reuse C1/R1 маршруту или создаёт контекстный разрыв из-за отсутствия собственного learn?
5. Не подавляет ли measurement envelope учебное действие каждого жанра?
6. Можно ли принять slice после disposition findings?

## Общие anti-patterns

- Не считать правильный status/body доказательством сохранения всего HTTP-контракта и request context.
- Не считать `missing` на response boundary доказанным местом первопричины.
- Не считать пару checkpoints автоматическим доказательством конкретной операции между ними без различающего опыта.
- Не исправлять дефект ручным копированием UUID в endpoint, exception handler или готовый response.
- Не считать один последовательный прогон доказательством isolation или cleanup.
- Не выдавать in-process ASGITransport за сеть, worker reuse, distributed tracing или production topology.
- Не переносить наблюдаемый порядок pinned FastAPI/Starlette assembly на другие версии и middleware stacks.
- Не требовать OpenTelemetry platform, production incident или Trace L4 внутри bounded package.
- Не начислять supporting coverage за reuse C1/R1 и B1/A3 readiness.
- Не считать project specification готовой реализацией.
- Не редактировать исходные материалы.

## Acceptance gate G19

M1.8.20 можно принять, когда:

- получены оба независимых профиля либо оркестратор явно зафиксировал согласованное исключение из двухпрофильного gate;
- нет открытых blocker/major по Gate 0, context propagation, first-loss diagnosis, cleanup/isolation, learning design или coverage;
- version/source issues исправлены либо явно adjudicated;
- причинная правка и отрицательный bypass-контроль признаны различающими root fix и маскировку;
- Trace L1/L2 evidence признано различимым и правдивым, L3 остаётся только probe без production execution claim;
- kata и project дают разные наблюдаемые результаты и не содержат готового решения;
- решения по minor/note зафиксированы оркестратором;
- после необходимых corrections четыре материала и регистрации переводятся в `accepted` отдельным acceptance-pass.
