## C-1 — different-key race для Idempotency L3

В `project-spec` добавить отдельный обязательный case: два одновременно освобождённых запроса подтверждают один draft order с **разными** UUID `Idempotency-Key` и соответствующими fingerprints.

Наблюдаемый результат:

- ровно один `draft → confirmed` transition;
- ровно один `OrderConfirmed` event record и один business result успеха;
- проигравший запрос получает определённый `409 order_not_draft` без второго event;
- authoritative PostgreSQL state, оба HTTP results и event identities входят в evidence.

Different-key race должен быть отдельной population в measurement envelope: минимум 20 trials с двумя синхронно освобождёнными requests. Не смешивать его с существующими 20 same-key trials. Обновить thresholds и краткий вывод по Idempotency L3 так, чтобы conditional `UPDATE` проверялся исполнением, а не только описанием.

## C-2 — `claim/lease` человеческим языком

В `learn` при первом употреблении объяснить: publisher instance временно помечает или блокирует pending event как взятый в работу; ограниченная аренда (`lease`) позволяет другому instance вернуть запись в обработку после сбоя владельца. Указать, что конкретный SQL/locking algorithm участник выбирает сам.

Добавить короткую строку в локальный словарь. В `project-spec` формулировка decision record должна ссылаться на этот смысл, а не предполагать знание термина.

## C-3 — обработка конфликта уникальности

В `learn` добавить точную, но не предписывающую один SQL-паттерн оговорку:

- если plain `INSERT` завершается unique violation, текущая PostgreSQL transaction становится aborted; перед чтением сохранённого результата её нужно завершить rollback и выполнить чтение в следующей transaction;
- вариант `INSERT ... ON CONFLICT DO NOTHING` может избежать exception, но код всё равно обязан явно определить последующее чтение результата и поведение при конкурентном commit.

Не утверждать, что любой unique conflict обязательно создаёт exception или что `ON CONFLICT` является универсальным рецептом.

## C-4 — граница 24-hour retention

В `project-spec` определить, что expiry оценивается отдельно для каждого запроса по авторитетному времени PostgreSQL внутри его transaction/read boundary. Запрос до границы может получить сохранённый result, запрос после границы — `409 idempotency_key_expired`; разные результаты запросов, реально оказавшихся по разные стороны границы, не нарушают same-key invariant.

Уточнить критерий «same-fingerprint responses совпадают»: он действует при одинаковом retention state. Tombstone и удаление тела должны переходить согласованно; не проектировать полный cleanup subsystem.

## C-5 — дополнительные kata cases

В kata отделить десять основных F2-прогонов от дополнительных детерминированных проверок. Задать по одному обязательному прогону для:

- same-key/different-fingerprint conflict;
- new-key/already-confirmed order;
- expiry/tombstone с управляемым clock.

Явно сказать, что эти три проверки выполняются сверх десяти основных прогонов и не превращают kata в L3 project.

## C-6 — терминология

Во всех пяти материалах заменить самостоятельные необъяснённые англицизмы связными русскими формулировками:

- `replay` при первом употреблении — «повтор с возвратом ранее сохранённого результата (`replay`)»; добавить термин в словарь learn, затем допустимо использовать короткую форму;
- `crash window` — «окно отказа (`crash window`)» либо просто «окно отказа»;
- `already confirmed order` — «уже подтверждённый заказ»;
- аналогичные правки делать только там, где термин повторяется или мешает чтению; массово переводить стандартные PostgreSQL/Psycopg/API identifiers не нужно.

Сохранить технические identifiers (`Idempotency-Key`, `event_id`, HTTP statuses, F0–F3) без перевода.
