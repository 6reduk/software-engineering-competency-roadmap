Закрыть принятые оркестратором notes N-1 и N-3 двумя локальными правками без изменения технического содержания, coverage и структуры первого slice.

## Required artifacts

Новых учебных файлов не создавать.

1. В project spec переписать фразу сценария 8 так, чтобы однозначно читалось: два формата ответа выбираются по заголовку запроса, оба ответа явно разрешены кэшированию, а общий кэш может их перепутать. Не менять следующую техническую оговорку про POST/GET, RFC 9110/9111 и `Vary`.
2. В README добавить `last_verified: 2026-08-15` и `versions` с теми же фактическими baseline, которые уже заявлены в разделе «Актуальность технической базы»: OAS 3.1.2, latest OAS 3.2.0 на дату проверки и FastAPI documented output 3.1.0. Не добавлять Pydantic baseline, если README не делает отдельного version-sensitive утверждения о семантике Pydantic.
3. Оставить оба материала в `status: review`.

## Constraints and non-goals

- Не менять остальные формулировки project spec или README.
- Не копировать полный `versions`-блок из других артефактов без проверки применимости каждого ключа.
- Не менять ID, module, coverage, ссылки, порядок прохождения и технические требования проекта.
- Не редактировать review-артефакты и не объявлять M1.6 завершённым.

## Acceptance checks

- сценарий 8 читается грамматически однозначно и сохраняет прежний технический смысл;
- metadata README соответствует prose-разделу об актуальности и `governance/architecture/metamodel/metadata.md`;
- YAML front matter обоих файлов разбирается;
- статусы, ID и coverage не изменены;
- Markdown, Mermaid, ссылки и `<details>` остаются корректными;
- diff ограничен двумя файлами из `Ownership`;
- итоговый handoff рекомендует включить обе правки в human-readability re-pass, а не запускать новый технический gate.
