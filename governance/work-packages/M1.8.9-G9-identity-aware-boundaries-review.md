## Профиль A — security и technical correctness

Независимо проверить по первичным источникам и минимальному runtime-воспроизведению:

- актуальность и совместимость Python 3.14.6, FastAPI 0.141.1, Starlette 1.3.1, PyJWT 2.13.0 и `cryptography` 50.0.0;
- обоснованность pinned Starlette 1.3.1 при доступной 1.6.0: сохранить exact baseline либо дать finding на согласованное обновление; одно лишь существование версии не считается обоснованием;
- установку и запуск точного dependency set в изолированной временной среде;
- RS256 signature verification с fixture public key и фиксированным `algorithms=["RS256"]`, без attacker-controlled algorithm selection;
- точную проверку `iss`, `aud`, `exp`, `nbf`, обязательности `sub`/`tenant_id` и отдельных type/non-empty constraints;
- rejection malformed token, wrong key/algorithm/issuer/audience, expired и not-yet-valid token до application flow;
- создание immutable минимального `IdentityContext` только после validation и отсутствие raw token/claims mapping в application/store layers;
- недоверенность route/header/query/body tenant identifiers;
- application-level object rule и deny-by-default при incomplete/missing context;
- невозможность получить Order tenant B через основной и заявленные bypass paths;
- корректность `401` challenge по RFC 6750 для missing и invalid bearer credential;
- допустимость локального `404` concealment по RFC 9110 и byte/semantic equality заявленных cross-tenant/missing wire responses;
- отсутствие overclaim, что равный response устраняет все timing/storage/traffic side channels;
- `Cache-Control: no-store`, media types и Problem Details payloads как единый wire contract;
- audit allow/deny/authentication-failure records, внутренние reason и запрет token/header/claims/key/Order fields/credentials;
- разделение внешнего response concealment и внутреннего диагностического evidence;
- пять evidence populations и две точки проверки: component boundary и собранный ASGI/HTTP path;
- отсутствие обещаний универсальной JWT/IAM/RBAC/ABAC модели, Identity L4, S14 или A3 proficiency.

Runtime harness выполнять вне репозитория; готовую реализацию или fixtures в source tree не добавлять. Явно описать substitutions, выполненные проверки и границы воспроизведения.

Профиль A обязан отдельно ответить:

1. Можно ли считать Gate 0 `confirmed` на закреплённом наборе версий?
2. Следует ли до acceptance оставить Starlette 1.3.1 или обновить baseline до 1.6.0?
3. Правдивы ли 401/404 и audit contracts относительно первичных источников и runtime?
4. Какие security свойства не доказаны данным bounded evidence envelope?

## Профиль B — learning design, coverage и human readability

Независимо проверить:

- рабочий контекст до внутренних ID, критериев и таблиц;
- понятное различие authentication, authorization, trusted context, claim, credential, object/resource boundary и deny-by-default;
- расшифровку англицизмов и неоднозначных терминов до использования либо в локальном словаре;
- автономность каждого файла и связный маршрут `README → learn → interview → kata → project-spec`;
- Mermaid, если есть: вопрос до схемы, объяснение после, явные упрощения;
- содержательные скрываемые ответы на self-check/interview/follow-up/defense questions;
- interview rubric по reasoning, threat/bypass paths, ownership и границам обещаний, а не числу JWT/IAM терминов;
- kata: участник создаёт минимальный scaffold, исследует один cross-tenant bypass и не получает готового handler/решения;
- отсутствие в kata полной project matrix, IdP/token issuance, S14, policy engine и project-level decision record;
- project: тот же один service/operation, но allowed/unauthenticated/cross-tenant/forged/missing populations, несколько enforcement paths, audit evidence и decision record;
- различимость наблюдаемых результатов kata и project;
- измеримость evidence envelope без псевдоточных процентов и performance thresholds;
- правдивость Identity L1 как заданного rule с positive/negative cases;
- правдивость Identity L2 как trusted-context propagation плюс безопасный audit context;
- правдивость Identity L3 как самостоятельный enforcement placement, threat/bypass matrix и deny-by-default reasoning;
- отсутствие Identity L4 и новых Abuse/A3/HTTP/Architecture/Verification relationships;
- ровно 5 semantic IDs, 15 relationships и 4 unique targets;
- совпадение YAML, registrations и ролей `1 reference / 3 explain / 3 probe / 2 practice / 4 assess / 2 integrate`;
- единый endpoint, fixtures, versions, token validation, 401/404, audit и evidence populations во всех пяти файлах;
- metadata, sources/freshness, ссылки, fences, `<details>`, отсутствие готовой реализации и Markdown hygiene.

Профиль B обязан отдельно ответить:

1. Дают ли L1/L2/L3 действительно разные evidence, а не один сценарий с тремя ярлыками?
2. Не превращается ли brief в JWT/IAM tutorial или security checklist без причинного объяснения?
3. Достаточно ли различаются kata и project?
4. Можно ли принимать slice после disposition findings?

## Общие anti-patterns

- Не считать валидный token достаточным authorization decision.
- Не доверять tenant ID из request вместо verified server context.
- Не выдавать L3 за перечисление терминов либо одну router dependency.
- Не считать одинаковый `404` доказательством отсутствия всех side channels.
- Не требовать production IdP/JWKS/rotation, универсальный policy engine или S14.
- Не начислять coverage соседних capabilities за упоминание HTTP/tests/architecture/security.
- Не считать project specification готовой реализацией.
- Не редактировать исходные материалы.

- получены оба независимых профиля;
