# M2.5 — фазовое закрытие первого прохода B5

## Objective

Создать компактный человеческий close-out первого прохода B5: независимо пересчитать принятую карту и coverage, показать два ролевых маршрута через единственный глубокий slice, зафиксировать оставшийся долг и условия нового фазового решения. Одновременно синхронизировать три устаревшие lifecycle-формулировки M2.3 с D-075.

Это инвентаризация и фазовое решение, а не второй slice, module gate, learner execution или попытка довести все B5-кластеры до одинаковой глубины.

## Ownership

Разрешено создать ровно один файл:

- `curriculum/tracks/b5/phase-closeout.md`.

Разрешено изменить только:

- `curriculum/tracks/b5/README.md` — добавить одну короткую навигационную ссылку на close-out и при необходимости обновить `updated`;
- `curriculum/tracks/b5/coverage-map.md` — заменить устаревшие текстовые `review`, `Итого review` и `Accepted отношений этого slice — 0` на формулировки, согласованные с D-075 и фактическим accepted YAML;
- `curriculum/tracks/b5/slices/stale-authority-fencing/README.md` — заменить устаревшую фразу «Все материалы остаются в review» на актуальную lifecycle-формулировку.

Другие файлы не изменять. Не создавать reviews, следующий selection/intake, Gate 0, semantic IDs, coverage relationships, учебные материалы, module-gate decision или ImplementationReference.

## Required result

### 1. Честный snapshot

Независимо пересчитать по текущим каталогам и accepted YAML:

- modules, capabilities, LevelOutcomes и scenarios B5;
- role links и их категории;
- accepted учебные artifacts, уникальные targets и уникальные тройки `(artifact, target, role)`;
- распределение relationships по ролям;
- capabilities и outcomes с прямым accepted coverage и без него;
- состояние каждого модуля по простой фазовой классификации `deep-slice-exists` / `blueprint-only`, не называя это module completion.

Ожидаемые ориентиры из принятых решений: 6 modules, 17 capabilities, 51 outcomes, 11 scenarios, 34 role links; 5 accepted artifacts, 11 targets и 35 relationships. Они не являются заменой пересчёта. При расхождении не подгонять числа: остановить пакет и передать его оркестратору.

### 2. Два ролевых входа

Дать компактный путь отдельно для Backend / Distributed Systems и Architecture / Technical Leadership:

- где роль входит в blueprint;
- какой результат даёт stale-authority/fencing slice;
- последовательность `index → learn → interview → kata → project-spec`;
- какие L1–L3 actions действительно адресованы;
- какой долг роли остаётся, включая Architecture leadership L3;
- почему accepted coverage не равно learner execution, proficiency или module completion.

### 3. Карта долга и возврата

Сгруппировать долг без автоматической очереди:

- blueprint-only B5-кластеры, включая кандидат чтения после записи (CA01);
- неподтверждённая среда для CA01 и ограниченного delivery-contract действия ME01;
- остаточная глубина TO01/CL01 и непроверенные partition/crash/unknown-outcome истории;
- learner execution, независимое review реализации и ImplementationReference;
- L4/L5 и реальные межкомандные последствия, которые этот проход не создавал;
- governance/module-gate decisions.

Для каждой группы назвать пример, владельца решения, наблюдаемый trigger возврата и цену дальнейшего откладывания. Uncovered outcomes и отсутствие learner execution сами по себе не запускают новый пакет.

### 4. Фазовое решение

Явно записать:

- первый B5-pass завершён после одного deep slice;
- второй неиспользованный слот не является обещанием следующего пакета;
- предел двух deep slices относится к одному фазовому проходу;
- новый проход возможен только отдельным фазовым решением после подтверждения readiness и ценности до authoring;
- close-out не объявляет завершение B5, модулей, proficiency или production readiness;
- после close-out новый track автоматически не выбирается.

### 5. C1-линза

Проверить две существующие записи `#decision-record` — blueprint и project-spec — на шесть непустых полей: заинтересованные стороны, альтернативы, ownership, стоимость риска, обратимость и передача знания. Различить авторское обоснование, учебное требование и выполненную работу. Не начислять C1 coverage/proficiency или L4/L5 evidence.

### 6. Lifecycle synchronization

Исправить только текстовые противоречия D-075:

- heading/total в `coverage-map.md` больше не называют accepted relationships `review`;
- строка accepted totals сообщает фактическое принятое состояние 5 artifacts / 35 relationships;
- slice README больше не говорит, что принятые материалы остаются в `review`.

Не менять front matter, coverage arrays, semantic IDs, targets, roles, versions или техническое содержание slice.

## Проверки

Проверить:

- создан ровно один файл и изменены не более трёх разрешённых;
- YAML и уникальность нового `id`;
- recount по исходным каталогам и accepted YAML, а не по prose totals;
- все относительные ссылки и anchors;
- отсутствие новых coverage relationships, semantic entities и Gate 0 claims;
- отсутствие второго/третьего slice и автоматического выбора следующей вертикали;
- Markdown, таблицы, UTF-8 без BOM, EOF, trailing whitespace и conflict markers.

SHA-256 snapshot доказывает только scope текущего запуска, не историческую чистоту workspace.
