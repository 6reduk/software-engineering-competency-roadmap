## Required changes

### C-1 — честная граница evidence S1

В Gate 0 и README явно разделить два утверждения:

- выполненный S1 подтвердил точное aggregate exposure и отсутствие зарегистрированных contract/server-error violations;
- поскольку interleave назначения request form на `old/new` не сохранён, этот прогон сам по себе не доказывает, что `new` в S1 наблюдался с каждой валидной и невалидной формой legacy-запроса.

В project-spec потребовать route/form evidence matrix либо эквивалентные счётчики, которые показывают наблюдение обязательных комбинаций `cohort × old/new × valid/invalid`, где комбинация применима. Не придумывать задним числом routing schedule исходного эксперимента и не менять его числовые результаты.

### C-2 — предел R-old и судьба записей new

В learn и README пояснить: возврат legacy-трафика на `old` до появления scheduled-obligation доказывает управление маршрутом, но не доказывает доступность заказов, которые до остановки принял `new`. В лаборатории они остаются в общем in-memory state `new/fixed`; непрерывность данных между раздельными хранилищами и readback этих записей — отдельная production-забота вне Gate 0.

В project-spec потребовать от участника назвать эту границу и, если его выбранная topology использует раздельное состояние, задать проверку сохранности/доступности принятых записей. Не вводить обязательную конкретную БД или схему миграции.

### C-3 — локальное определение population

При первом смыслообразующем употреблении в learn, interview и kata объяснить: `population` — число или группа однотипных запросов/наблюдений конкретной когорты в одном измерительном окне. Использовать естественный русский текст; не дублировать слово механически во всех разделах.

### C-4 — однозначный вывод о метриках

В learn заменить фразу «Здесь оба числа превышают нулевой порог» на явную: и раздельное `20/100`, и смешанное `20/200` превышают порог, но только раздельное значение показывает, ожидание какой когорты нарушено. Не менять числа и порог.

### C-5 — конвенция закрытия окна

В Gate 0 одной фразой зафиксировать: пятисекундное окно закрывается по границе расписания `t0 + 5 секунд`, а не по времени последнего полученного ответа; guard остаётся 5,25 секунды. Если материалы описывают иначе, согласовать их с этой конвенцией без пересчёта результатов.

### C-6 — размещение состояния и сила readback

В project-spec потребовать от участника:

- явно выбрать и описать размещение состояния между old/new/fixed;
- объяснить, какой отказ способен обнаружить readback в этой topology;
- назвать, чего такой readback не доказывает.

Общий state допустим, если его ограничение названо честно. Не предписывать shared database, миграцию, replication или иной конкретный механизм.

### C-7 — registration hygiene M1.8.13

В `curriculum/tracks/b2/README.md` исправить только устаревшее описание Application Caching/M1.8.13: принятые материалы не должны называться находящимися в `review`. Не менять регистрацию M1.8.15, список artifacts или coverage.

### C-8 — граница объёма kata

В kata одной короткой фразой обозначить ожидаемую границу работы: участник самостоятельно создаёт минимальный стенд, достаточный для воспроизведения одного заданного дефекта управления продвижением; готового scaffold и эталонной реализации нет. Не давать оценку времени и не превращать kata в project.

### C-9 — evidence в rubric kata

В критериях проверки kata явно указать: обязательным доказательством являются исполняемые следы исходного и исправленного прогонов, включая stop и отсутствие запросов следующей стадии. Code diff может помогать ревью, но сам по себе не заменяет evidence и не является обязательным отдельным результатом.
