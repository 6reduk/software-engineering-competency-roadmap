## Профиль A — caching, consistency, concurrency и measurement

Независимо проверить по первичным источникам и минимальному runtime-воспроизведению:

- существование, совместимость и фактический запуск pinned Python/FastAPI/Starlette/Uvicorn, PostgreSQL/Psycopg и Redis/redis-py stack;
- осознанность pinned baseline при доступных более новых версиях и честность source freshness;
- exact HTTP contract, `Cache-Control: no-store`, `503` Problem Details и применимость `Retry-After`;
- source-of-truth/cache ownership и отсутствие ложной durability/transaction guarantee;
- tenant-safe key/value schema, trusted tenant context и поведение при tenant/schema mismatch либо malformed cached JSON;
- семантику `SET ... EX 2`, TTL/expiration и отсутствие предположения о мгновенном expiration event;
- корректность вывода freshness bound 2.25 секунды для late fill: от какой точки считается 250-мс deadline, проверяется ли он перед `SET`, и существуют ли interleavings, превышающие обещание;
- commit → `DEL` ordering, rollback, invalidation error и допустимые исходы late-fill race;
- process-local per-key coalescing, повторный `GET`, scope lock registry и отсутствие глобальной блокировки независимых tenants;
- lifecycle coordination state при success, owner error, cancellation и follower cancellation;
- разделение Redis `GET` failure до PostgreSQL read и Redis `SET` failure после PostgreSQL read;
- правдивость утверждений `cache error → source_read=0`: к какой точной population и operation они относятся;
- отсутствие автоматического retry и точный budget connect/command/source paths;
- пять независимых 32-request cold bursts: очистка key, синхронный старт, корректные responses и реальный `source_read≤1` на key;
- tenant-a/tenant-b isolation, forced late-fill race, Redis outage и recovery population;
- честность временных thresholds относительно Windows/Docker host и отделение correctness gates от diagnostic timings;
- достаточность counters: правильный response/version одновременно с amplification, failure и recovery evidence;
- обоснованность fail-closed выбора и отсутствие скрытого source fallback;
- корректность решения B5 `not applicable` при строго one-process claim;
- отсутствие claims distributed coordination, read-your-writes, zero stale, linearizability, production capacity или Cache L4;
- отсутствие готовой реализации в source tree.

Runtime harness выполнять вне репозитория; fixtures и реализацию в source tree не добавлять. В отчёте указать exact environment, substitutions, cases и границы воспроизведения.

Профиль A обязан отдельно ответить:

1. Можно ли считать Gate 0 `confirmed` на exact pinned stack?
2. Математически и операционно доказан ли bound 2.25 секунды для всех заявленных late-fill interleavings?
3. Какие Redis failure points происходят до и после source read и правдив ли для каждого заявленный counter outcome?
4. Гарантирует ли coalescing lifecycle отсутствие stuck followers и unbounded re-read после error/cancellation?
5. Что доказывает локальный эксперимент, а что остаётся только требованием будущей реализации?
6. Достаточно ли evidence для Cache L3 без Cache L4/distributed overclaim?

## Общие anti-patterns

- Не считать правильные `200` доказательством ограниченного source-read amplification.
- Не считать `source_read≤1` доказательством правильной tenant/version semantics.
- Не объединять Redis `GET` и `SET` failures, если они происходят по разные стороны source read.
- Не выводить post-commit freshness только из TTL без bound для late fill.
- Не выдавать process-local lock за distributed guarantee.
- Не требовать distributed lock, multi-worker implementation или Cache L4 внутри bounded package.
- Не начислять supporting coverage за использование transaction ordering, trusted context или counters.
- Не считать project specification готовой реализацией.
- Не редактировать исходные материалы.

## Open questions

На review передаются четыре вопроса:

1. Не является ли общий тезис «ошибка `GET` или `SET` → `source_read=0`» фактически неверным для post-read `SET` failure?
2. Действительно ли source snapshot-to-fill deadline ограничивает каждый late `SET`, включая scheduling/cancellation pauses, либо 2.25-секундный bound требует более точного определения/механизма?
3. Достаточно ли `asyncio.Lock` с повторным `GET` для заявленного lifecycle при cancellation владельца или материал неявно требует single-flight/Future semantics?
4. Не слишком ли project-spec предписывает конкретную реализацию при заявленной цели самостоятельного проектирования?

Reviewer не расширяет пакет до distributed locks, Redis HA, multiple workers, production benchmark, read-your-writes или Cache L4. Если evidence недостаточно для relationship, finding предлагает минимальную коррекцию модели, coverage или envelope, а не новый курс.
