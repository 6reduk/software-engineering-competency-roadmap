#### Контракт и наблюдавшаяся матрица

Pricing выполняет одну read-only операцию `GET /v1/offers?item_id=p-7`. Успех — только `200 application/json` (параметр `charset=utf-8` допустим). Полный payload: `{"item_id":"p-7","offers":[{"offer_id":"o-1","amount_minor":12500,"currency":"RUB"}]}`; пустой: `{"item_id":"p-7","offers":[]}`. Все поля обязательны, дополнительные поля запрещены локальным контрактом; offer_id — непустая строка, amount_minor — integer ≥0 без coercion, currency — RUB. Item identity проверяется после схемы. Это учебный договор, не утверждение о vendor API.

Quote `GET /quotes?item_id=p-7` возвращает `200 application/json` с `item_id`, `outcome=offers|no_offers`, `offers`; при отказе — `application/json`, `{"error":"pricing_unavailable","reason":"<category>"}`. `rid` — лабораторный correlation-параметр, передаваемый в `X-Request-ID`, не remote operation identity. Failure response не содержит поля offers. В проекте внутренние типы выбирает участник; внешний договор сохраняется.

| Режим | Фактический Pricing response/failure | Adapter → Quote после исправления | False absence defect / fixed (из 3) |
|---|---|---|---|
| full | 200 JSON, полный payload выше | offers → 200 offers | 0 / 0 |
| empty | 200 JSON, явный offers=[] | no_offers → 200 no_offers | 0 / 0 |
| malformed | 200 JSON, bytes `{"offers":` | decoding → 502 pricing_unavailable/decoding | 3 / 0 |
| media | 200 text/html, полный JSON payload | media → 502 pricing_unavailable/media | 3 / 0 |
| schema | 200 JSON, `{"item_id":"p-7"}` | schema → 502 pricing_unavailable/schema | 3 / 0 |
| server | 503 JSON, `{"offers":[]}` | http → 502 pricing_unavailable/http | 3 / 0 |
| timeout | Pricing ждёт 350 мс до headers; ReadTimeout | timeout → 504 pricing_unavailable/timeout | 3 / 0 |
| transport | Pricing закрывает socket до ответа; RemoteProtocolError | transport → 502 pricing_unavailable/transport | 3 / 0 |
| identity | 200 JSON, `{"item_id":"p-8","offers":[]}` | schema → 502 pricing_unavailable/schema | 3 / 0 |
| null | 200 JSON, `{"item_id":"p-7","offers":null}` | schema → 502 pricing_unavailable/schema | 3 / 0 |
| coercion | 200 JSON, полный payload с amount_minor="12500" | schema → 502 pricing_unavailable/schema | 3 / 0 |

HTTP status проверяется до media/JSON: 503 с похожим на пустой результат телом остаётся HTTP failure. Любой status кроме 200 не входит в успех этого договора. Разрыв HTTP до полного ответа — transport category, а не полученный status.

В Windows PowerShell выполнен одноразовый Python probe через `@' … '@ | python -B -`: исходный текст передан только в stdin, файлы стенда/scaffold/решения не создавались, зависимости не устанавливались. Код и полные команды остаются в журнале авторской сессии; эта запись сохраняет контракт, процедуру и наблюдения, но не является executable harness. Исключение S11 для временных файлов не переносилось. Долг передачи: независимый reviewer должен повторить опыт собственным минимальным probe или получить команду из журнала сессии; готовая реализация учебного проекта в материалы не включена.

Команда проверки baseline: `python -B -c "import sys,importlib.metadata as m; print(sys.version); print({p:m.version(p) for p in ['fastapi','starlette','httpx','httpcore','pydantic','anyio']})"`.

Процедура повторения: в одном процессе открыть loopback HTTP Pricing на выделенном ОС порту; включить mode вне API caller input; запустить lifespan Quote с одним HTTPX client; вызывать собранное Quote через ASGITransport. Выполнить control full/empty, defect все 11 строк, fixed все 11 строк, recovery full/empty, по 3 последовательные операции в каждой строке. Единственная defect-мутация переводит пойманный integration failure в пустой бизнес-результат. На каждом request ID сопоставить hook клиента, приём Pricing, фактический response/failure, решение адаптера и HTTP response Quote. После каждой строки дождаться active=0 ≤1 с и проверить отсутствие незавершённой client work. Затем проверить три запрещённых item_id и игнорирование пользовательского base_url, закрыть lifespan и сервер, проверить thread/port.

Первый опыт уже показал требуемую матрицу, но при намеренном socket close HTTPServer пытался читать следующий запрос из закрытого соединения и печатал BrokenPipeError. В probe выставлен close_connection для этой ветви; смысл инъекции не изменён. Два повторных прогона завершились с exit code 0 без этой ошибки. Итоговые значения ниже взяты из последнего прогона; timings не смешиваются между прогонами.

В final fixed-профиле три timeout операции с drain заняли 591.38 мс; самая долгая Quote operation — 117.71 мс; drain после этой строки — 251.92 мс. В defect timeout профиль занял 594.66 мс, drain — 254.86 мс. Остальные строки final fixed занимали 7.20–8.67 мс за три операции. Recovery full/empty заняли 10.70/9.26 мс; весь опыт до закрытия клиента — 1769.16 мс. Общее время измерено monotonic clock на стороне harness; Quote latency — от отправки ASGI запроса до полного полученного ответа. Это не server-side p95 из R2/R5.

HTTPX phase timeouts 100 мс не объявляются общим deadline. Порог Quote <500 мс — проверенное наблюдение в конечном loopback-профиле с малыми телами, без очереди и streaming trickle; общий deadline для произвольной сети здесь не доказан. После каждого профиля active=0, дополнительных живых asyncio tasks нет. Клиент закрыт за 0.07 мс; shutdown/server_close/join и port check — 126.36 мс; server thread не жив. Не было временных данных, файлов или дочерних процессов. Задержанный Pricing заканчивает свою работу отдельно от локального timeout; drain наблюдается, а удалённая отмена не предполагается.

#### Claim → primary source; freshness

Проверка URL выполнена 2026-09-08.

- [HTTPX transports](https://www.python-httpx.org/advanced/transports/): retries задаются transport; ASGITransport сам не запускает lifespan; custom transport работает на request/response boundary.
- [HTTPX timeouts](https://www.python-httpx.org/advanced/timeouts/): connect/read/write/pool timeout различаются; read timeout ограничивает ожидание очередных данных.
- [HTTPX exceptions](https://www.python-httpx.org/exceptions/): TimeoutException и TransportError, включая RemoteProtocolError, отделены от полученного HTTP status.
- [FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/): acquire/release общего client размещены по сторонам yield.
- [Pydantic strict mode](https://docs.pydantic.dev/latest/concepts/strict_mode/): strict validation ограничивает coercion; конкретные payload rows проверены локально.
- [Python http.server](https://docs.python.org/3.14/library/http.server.html): ThreadingHTTPServer — локальный тестовый HTTP server, не production substrate.
- [RFC 9110, safe methods](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1): GET имеет read-only semantics; отсутствие бизнес-записи дополнительно подтверждено поведением probe.

### Обязательные критерии Gate 0

- Все valid-empty responses дают только предметный исход `no offers`, без integration error.
- Ни один malformed/media/schema/5xx/timeout/transport row не превращается в `no offers`.
- Для каждой операции наблюдается ровно одна HTTP attempt; автоматические retry отсутствуют.
- Timeout имеет конечный budget; после каждого профиля нет незавершённой client work и утечки управляемых ресурсов.
- После снятия отказа повторный healthy profile проходит без ручной правки данных.
- Из evidence видны входной HTTP response/failure Pricing, решение adapter и внешний результат Quote API. Unit-test готового adapter result недостаточен.
- Локальные thresholds описаны как teaching/experimental envelope, а не production defaults.

## Kata/project distinction

### Kata

- задана response/outcome matrix и один seeded defect;
- участник самостоятельно создаёт минимальный стенд либо использует свою реализацию, но не получает scaffold/готовый adapter;
- исправляет только collapse `failure → empty` и доказывает L1 execution evidence;
- не выбирает общий retry/resilience architecture.

### Project specification

- участник самостоятельно определяет внутренние result/error types и mapping полной matrix;
- реализует фактическую HTTP-client boundary и Quote API outcome;
- документирует one-attempt/no-automatic-retry решение и условия, при которых оно должно быть пересмотрено;
- показывает measurement/failure evidence и остаточные риски;
- не строит fan-out, circuit breaker, service discovery, SSRF platform или distributed tracing system.

1. созданные и изменённые файлы;
2. заполненный Gate 0, sources, pinned versions и ограничения лаборатории;
3. Pricing operation и полную response/outcome matrix;
4. measurement populations, timeout, attempt/false-absence counters, recovery и cleanup evidence;
5. coverage и раздельное evidence External L1/L2;
6. локальные решения и отвергнутые расширения;
7. результаты YAML/link/Markdown/hygiene проверок;
8. открытые вопросы и известный долг;
9. рекомендуемые два независимых review-профиля: technical/integration/measurement и learning/editorial/coverage.

Автор оставляет пять материалов в `review`, не меняет program status и не объявляет G16 пройденным.
