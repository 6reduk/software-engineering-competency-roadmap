# M1.6 — закрытие замечаний технического re-pass первого slice

## Objective

Закрыть подтверждённые findings C-1–C-11 из консолидированного технического re-pass, не меняя учебный замысел, coverage и принятую человеком структуру слайса `evolvable-api-contracts`.

Ожидаемый результат: исходные материалы согласованы между собой, содержат точные нормативные ссылки и freshness metadata, а все изменения остаются локальными редакционными поправками в статусе `review`.

## Required artifacts

Новых учебных файлов создавать не нужно. Исправить существующие документы следующим образом.

### C-1 — нормативные источники кэширования

В обоих engineering briefs развести ответственность источников:

- RFC 9110 §12.5.5 определяет смысл `Vary`;
- RFC 9111 §4.1 задаёт поведение кэша при выборе сохранённого ответа.

Добавить RFC 9111 в первичные источники. Не приписывать нормативное требование неверной спецификации.

### C-2 — единая сквозная история

Унифицировать примеры kata и project spec с основной историей: использовать `customer_id: "c-42"` и `product_id: "p-7"`, если локальный контекст не требует другого значения. Не оставлять необъяснённые параллельные варианты `c-17` и `sku: "book-1"`.

### C-3 — freshness metadata

Добавить artifact-level `last_verified` и осмысленный `versions` в interview, kata и project spec, поскольку они содержат версионно-зависимое поведение FastAPI/Pydantic/OpenAPI. Не копировать произвольный номер установленного пакета: фиксировать именно проверяемые specification/behavior baselines. Существующие overrides в двух briefs сохранить и согласовать. README не требует override, если в нём нет версионно-зависимого утверждения.

### C-4 — актуальные ссылки Pydantic

Заменить редиректящие URL `docs.pydantic.dev/...` на канонические страницы `pydantic.dev/docs/validation/latest/...` в обоих briefs и проверить доступность конечных ссылок.

### C-5 — условия кэширования POST

В сценарии project spec явно указать, что общий кэш может смешать варианты ответа только для явно кэшируемого ответа POST. Если это утяжеляет сценарий, перенести проверку на read-операцию `GET /orders/{id}`. Не создавать впечатление, что shared cache по умолчанию сохраняет любой POST response.

### C-6 — сокращённый validation response

В примере фактического ответа FastAPI добавить как минимум `"msg": "Field required"` либо прямо перед примером назвать его сокращённым и перечислить опущенные поля. Предпочтительно показать небольшой, но фактически правдоподобный ответ.

### C-7 — терминология участников API

В interview и project spec при первом употреблении `consumer`/`producer` добавить понятное русское объяснение и ссылку на выбранную в brief терминологию `API caller`/`API provider`. Не запрещать распространённые термины, а устранить впечатление, что документы используют разные модели участников.

### C-8 — формат JSON Pointer

Привести `errors[].pointer` к fragment-форме `#/delivery/window/end`, совпадающей с примером RFC 9457, либо явно зафиксировать локальное соглашение сервиса. Предпочтителен первый вариант как более простой для читателя.

### C-9 — диапазон уровней coverage

В `curriculum/tracks/b2/coverage-map.md` заменить описание interview первого slice `L1–L4` на фактическое `L2–L4`. Другие строки coverage-map не менять.

### C-10 — точность формулировки response model

В brief утвердительно указать: при `response_model_include`/`response_model_exclude` сгенерированная JSON Schema продолжает описывать полную модель. Сохранить практический вывод о расхождении документации и фактической фильтрации.

### C-11 — default dependency scope

Явно указать, что для FastAPI dependency с `yield` scope по умолчанию — `request`; очистка выполняется после отправки ответа. Сопоставить это с явно выбранным `scope="function"`.

C-12 действий не требует. Erratum E-1 уже записан в консолидированном review; исходный GLM-review не редактировать.
