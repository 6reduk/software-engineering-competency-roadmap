### Закреплённые данные и договор

Договор сводки: одна строка на каждый заказ, включая пустой. `line_count` и `payment_count` считают реальные дочерние записи; `line_total` и `paid_total` складывают их суммы. Все деньги — целые minor units (минимальные денежные единицы одной валюты). Отсутствие строк или платежей означает нулевые число и сумму; это локальное правило отчёта, а не общее равенство `NULL = 0`. Исходные суммы обязательны (`NOT NULL`): неизвестная сумма платежа не допускается. `NULL` в этом наборе возникает из отсутствующего совпадения при outer join.

`balance = line_total - paid_total`: положительное значение — недоплата, отрицательное — переплата; нулевой остаток пустого заказа не означает состоявшуюся оплату. `total_rank` ранжирует по `line_total` по убыванию без пропусков между различными суммами: равным суммам — одинаковый ранг. Выдача отдельно упорядочена по `line_total DESC, order_id ASC`; ID не входит в смысл равенства рангов.

Канонические данные: `orders = {1,2,3,4}`; строки `(line_id, order_id, amount)` — `(101,1,100)`, `(102,1,100)`, `(103,2,50)`, `(104,4,200)`; платежи `(payment_id, order_id, amount)` — `(201,1,60)`, `(202,1,40)`, `(203,4,200)`. Две строки по 100 — разные покупки, а не дубликат записи. Заказ 2 не оплачен, заказ 3 пуст, заказ 4 полностью оплачен и равен заказу 1 по стоимости.

### Исполнение и наблюдения

Каждый из трёх успешных прогонов использует новую psql-сессию: BEGIN, CREATE TEMP/fixtures, вычисление control/defect/fixed, проверки, ROLLBACK. Control считает каждое дочернее отношение отдельно коррелированными подзапросами. Fixed предварительно агрегирует каждое отношение до одной строки на order_id и соединяет эти сводки с полным набором orders. В обоих вариантах остаток и окно вычисляются над сводкой заказов. Это два разных способа композиции; независимый oracle — Python-расчёт, а не их совпадение друг с другом.

На стороне базы `DO` с `RAISE EXCEPTION` проверяет двунаправленный `EXCEPT ALL` control/expected и fixed/expected, ровно четыре строки и четыре разных order_id в fixed, а также дефектные суммы заказа 1. На стороне harness сравниваются полные JSON-массивы строк, включая порядок, все поля и диагностические результаты; любая ошибка SQL или assertion завершает запуск неуспехом. Проверены и нативные JSON null без замены строкой или нулём.

```sql
SELECT o.order_id,

LEFT JOIN order_lines l ON l.order_id = o.order_id
LEFT JOIN payments p ON p.order_id = o.order_id

ORDER BY o.order_id;
```

Технический fixed:

```sql
SELECT *, line_total-paid_total AS balance, dense_rank() OVER (ORDER BY line_total DESC) AS total_rank FROM (WITH l AS (SELECT order_id, COUNT(*) AS n, SUM(amount) AS total FROM order_lines GROUP BY order_id),
p AS (SELECT order_id, COUNT(*) AS n, SUM(amount) AS total FROM payments GROUP BY order_id)
SELECT o.order_id, COALESCE(l.n,0) AS line_count, COALESCE(l.total,0) AS line_total,
COALESCE(p.n,0) AS payment_count, COALESCE(p.total,0) AS paid_total
FROM orders o LEFT JOIN l USING(order_id) LEFT JOIN p USING(order_id)) b ORDER BY line_total DESC, order_id ASC;
```

## Рабочая история и единый договор

Orders report должен возвращать одну строку на заказ. Минимальный контракт результата включает:

- `order_id`;
- число строк заказа;
- сумму строк заказа;
- число платежей;
- сумму платежей;
- вычисляемый остаток либо состояние оплаты;
- ранг по заранее определённому показателю и отдельный стабильный порядок отображения.

Бизнес-смысл нулей, `NULL`, частичной оплаты, заказа без строк и равных значений фиксируется до написания запроса. Денежные значения представлены целыми minor units; floating-point arithmetic не вводится.

Seeded defect — попытка одновременно соединить `orders → order_lines` и `orders → payments`, а затем агрегировать уже размноженный набор. Материал обязан показать причинную цепочку `кратность отношений → гранулярность промежуточных строк → неверный агрегат`, а не только рецепт с CTE или `DISTINCT`.

- kata: L1/L2 обеих capabilities — `practice`, `assess`;
- project-spec: L2/L3 обеих capabilities — `integrate`, `assess`.

Если конкретный artifact не даёт честного evidence для роли, связь не добавлять и объяснить расхождение в handoff. L3 kata и L1 project не начислять механически. Нельзя добавлять coverage для query plans/indexes, relational schema, B2 verification, B4 analytics или любой L4/L5.

## Source and freshness requirements

- Все engine-dependent утверждения проверять по официальной документации закреплённой версии PostgreSQL.
- Stable/current version проверять на дату выполнения, но не объявлять автоматически рекомендованной production-версией.
- Разделять нормативную SQL/PostgreSQL семантику, инженерный вывод из неё и локально выбранный report contract.
- Источник должен подтверждать фактический claim; неиспользуемые ссылки удалить.
- Не использовать blog posts как основание ключевой семантики, если есть первичная документация.

## Explicit non-goals

- полный курс SQL, реляционная алгебра или перечисление всех join/window функций;
- EXPLAIN, planner estimates, индексы и performance tuning — отдельный IO01;
- проектирование общей relational schema и нормализация — RM01;
- ORM, FastAPI, HTTP API и application serialization — B2;
- Spark/BigQuery/Snowflake и analytical pipeline — B4;
- конкурентность транзакций и изоляция — TC01;
- готовый SQL-ответ, эталонный repository, scaffold или автоматическая учебная платформа;
- SE01 и BR01 в этом пакете;
- module-gate decision, L4/L5 или полное завершение B3.

- [ ] Созданы ровно пять учебных материалов и один новый coverage map; B3 README изменён только в разрешённых регистрационных местах.

- [ ] Brief содержит pitfalls, good/bad practice, edge cases, диагностику, glossary и self-check с раскрываемыми ответами.
- [ ] Interview содержит скрываемые ответы и rubric L1–L3.

- [ ] Coverage ссылается только на две capabilities и их L1–L3 outcomes; роли соответствуют фактическому evidence.
- [ ] Source/freshness claims проверены и датированы.
- [ ] YAML, IDs, ссылки/anchors, JSON/SQL snippets, Markdown fences, Mermaid и `<details>` проверены.
- [ ] Нет conflict markers, trailing whitespace и незаявленных файлов; ограничения scope proof описаны честно.

## Handoff

Передать оркестратору:

1. Gate 0 record: версии, источники, schema/fixtures, expected rows, результаты control/defect/fixed и cleanup;
2. созданные и изменённые файлы;
3. точный coverage recount по targets и roles;
4. различие kata/project и границы L1/L2/L3;
5. локальные решения по `NULL`, empty groups, ties, ordering и неоднозначному требованию;
6. результаты технических, редакционных и механических проверок;
7. открытые вопросы и долг.

Автор не проводит независимый review, не принимает G24 и не меняет program status.
