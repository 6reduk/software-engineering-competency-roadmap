# M1.9.0 — B3 boundary intake: application transaction и store isolation

## Objective

Создать один reviewable planning artifact, который разграничивает application-level transaction/side-effect ownership B2 и store-level isolation/concurrency ownership B3, сравнивает несколько bounded действий внутри `b3.cluster.transactions-concurrency` и выбирает ровно одно действие для будущего учебного execution package.

## Required work

### 1. Объяснить проблему обычным инженерным языком

Начать с рабочей ситуации: application operation в B2 уже определяет transaction boundary, но корректность при двух конкурентных транзакциях зависит от фактических правил store — isolation level, snapshot visibility, locks, constraints и conflict handling. Объяснить, почему чтение документации или успешный одиночный commit не подтверждает владение этой границей.

### 2. Зафиксировать ownership map

Явно разделить:

- B2: application operation, commit/rollback boundary, idempotency identity/result, coordination с внешними side effects;
- B3: поведение конкретного store при concurrency, MVCC/visibility, locks, anomalies, constraints и store-level recovery/error signals;
- B5: общая distributed consistency/coordination за пределами одного store;
- B7: production reliability, SLO/incident/continuity и cross-system recovery;
- B6: platform primitives только если будущая работа действительно зависит от них.

Не создавать placeholder capability IDs и не менять принятые границы track skeletons.

### 3. Сравнить bounded кандидатов

Сравнить минимум три возможных действия внутри `transactions-concurrency`, например:

- воспроизвести нарушение инварианта двумя конкурентными транзакциями и устранить его выбранным store-level механизмом;
- локализовать deadlock/lock wait, объяснить wait graph и выбрать bounded retry/ordering policy;
- объяснить различие snapshot visibility и фактической блокировки на одном read-modify-write сценарии.

Для каждого назвать инженерную ценность обеим depth-ролям, отличие от S07/S15, требуемую среду, наблюдаемый результат, риск чрезмерного scope и причину принять либо отклонить сейчас.

### 4. Выбрать ровно одно действие

Выбранное действие должно:

- проверять store behavior, а не повторять проектирование application transaction;
- содержать один бизнес-инвариант и один ограниченный concurrency mechanism;
- допускать control/defect/fixed либо эквивалентный различающий эксперимент;
- не требовать полного PostgreSQL курса, distributed database, HA, ORM framework или production incident;
- быть полезным Backend и Architecture depth без заявления одинакового ожидаемого уровня;
- иметь конечный результат, из которого можно спроектировать последующий Gate 0 и пятижанровый content package.

Точное хранилище, isolation level и механизм можно либо выбрать в intake, либо оставить как явно ограниченный вопрос будущего Gate 0 — но не оставлять центральное инженерное действие неопределённым.

### 5. Описать evidence будущего исполнения

Назвать минимально наблюдаемые результаты без выдуманных числовых thresholds:

- начальное состояние и инвариант;
- порядок или синхронизация двух конкурентных actors;
- дефектный исход и store signals;
- изменение ровно одного существенного механизма;
- исправленный исход и отрицательная проверка;
- повторяемость, cleanup и ограничения вывода.

Отделить будущий runtime evidence от текста intake. Не запускать эксперимент и не объявлять readiness confirmed.

### 6. Определить readiness будущего package

Перечислить категории Gate 0, которые должны быть закреплены до authoring материалов:

- store, точная версия и driver;
- topology и connection/transaction ownership;
- isolation/autocommit/transaction settings;
- durability settings только если они влияют на выбранное действие;
- способ детерминированно координировать actors;
- доступные store observations: transaction IDs/snapshots, locks/waits, SQLSTATE/error или иной применимый сигнал;
- cleanup/reset и запрет считать локальный опыт production adoption;
- первичные источники и freshness.

### 7. Зафиксировать non-goals и exit trigger

Non-goals должны исключать полный B3 blueprint, весь SQL/relational baseline, ORM/application repository architecture, B5 distributed consistency, B6 platform, B7 DR/SLO, performance tuning и готовую реализацию.

Exit trigger intake: один выбранный action, непротиворечивый ownership, явно отклонённые альтернативы, категории readiness и observable evidence, открытые вопросы без ownership conflict. После независимого review оркестратор может создать отдельный B3 blueprint/bounded content-planning package либо вернуть intake; автоматического authoring нет.

## Required invariants

- создаётся ровно один planning artifact;
- semantic capability/outcome/module/scenario IDs не создаются;
- `coverage` и relationships не создаются;
- B2 материалы и долг не меняются;
- ни одно readiness-условие не объявляется подтверждённым;
- не создаются учебные жанры, код, SQL-решение, scaffold или ImplementationReference;
- выбирается ровно одно центральное store-level действие;
- итог остаётся `status: review`.
