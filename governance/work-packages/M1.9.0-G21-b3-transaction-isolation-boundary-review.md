## Objective

Двумя независимыми профилями проверить один planning intake на границе B2 application transaction и B3 store isolation: техническую причинность выбранного write-skew действия, правдивость ownership, наблюдаемость будущего evidence, полезность для двух depth-ролей и достаточную конкретность следующего Gate 0 без превращения intake в B3 blueprint или учебный пакет.

## Профиль A — B3 technical correctness and experimental causality

Независимо проверить:

- корректность предметной модели: два actors принимают взаимозависимые решения, изменяя разные строки, и способны нарушить инвариант «остаётся хотя бы один дежурный»;
- справедливость утверждения о допустимой serialization anomaly/write skew при PostgreSQL `REPEATABLE READ` в указанной модели;
- справедливость ожидания, что PostgreSQL `SERIALIZABLE` сохраняет инвариант через отказ несовместимой транзакции, без обещания конкретной жертвы, blocking order или точки обнаружения;
- достаточность единственной смены механизма `REPEATABLE READ → SERIALIZABLE`; отсутствие скрытых locks, mutex, constraint, общей строки или retry, которые разрушили бы причинность сравнения;
- корректность control schedule: второй actor не должен получить исследуемый snapshot до commit первого;
- корректность defect/fixed barrier: оба actors должны завершить нужное чтение до разрешения изменений, а сбой одного actor не должен навсегда оставить другого у барьера;
- терминальные исходы commit/rollback, сохранение SQLSTATE/error и чтение committed state независимым observer;
- разделение исходного serialization conflict и отдельной новой попытки всей операции с новым чтением;
- честность negative check и отсутствие ложного вывода «SERIALIZABLE запрещает все записи»;
- достаточность repeat/reset/cleanup evidence без выдуманного числового threshold;
- границы вывода: один schedule и один store, без claims о всех interleavings, crash durability, production adoption, HA или других СУБД;
- корректность и применимость официальных источников, включая оговорку о ещё не выбранных PostgreSQL build и stable Psycopg;
- отсутствие переноса B2 S07/S15 readiness, YAML coverage или proficiency в B3.

Профиль A обязан отдельно ответить:

1. Воспроизводим ли write-skew defect в предложенной модели именно при заявленном schedule?
2. Может ли fixed дать требуемый store conflict и сохранить инвариант без второго механизма?
3. Какие минимальные observations обязательны, чтобы вывод был причинным, а не основанным только на итоговых строках?
4. Корректно ли разведены store conflict, rollback и прикладной отказ при отдельной новой попытке?
5. Достаточны ли readiness-категории для будущего Gate 0 и какие из них требуют уточнения до authoring?
6. Можно ли принять intake после disposition findings, не подтверждая Gate 0 и не выполняя эксперимент?

## Профиль B — boundary, learning value and human readability

Независимо проверить:

- начинается ли artifact с понятной рабочей ситуации и объясняет ли, зачем B3 нужен после принятого B2;
- понятны ли `store`, snapshot, MVCC, serialization anomaly, write skew, actor, observer и evidence по месту либо через локальный словарь;
- не требует ли текст знания истории M1.8.x, несмотря на traceability-ссылки;
- правдивость ownership B2/B3/B5/B6/B7 и отсутствие скрытого расширения соседних вертикалей;
- отличие выбранного действия от S07 idempotency/side-effect recovery и S15 application caching;
- сравнимость трёх кандидатов по инженерной ценности, среде, наблюдаемому результату, риску scope и решению;
- наличие ровно одного выбора и понятность причин отклонения двух альтернатив сейчас;
- ценность одного сценария для Backend и Architecture depth без заявления одинакового уровня, L4/L5 или production adoption;
- ясное разделение planning intake, capability blueprint, Gate 0, content package, runtime evidence и самостоятельной реализации;
- пригодность proposed evidence и readiness как входа следующего bounded package, но не как готовой лабораторной инструкции или скрытого SQL-решения;
- достаточность non-goals и конечность exit trigger;
- связность русского текста, оправданность англицизмов, размер таблиц, качество ссылок и отсутствие LLM-oriented метатекста, мешающего человеку;
- metadata, отсутствие `coverage` и новых semantic IDs, локальные links/anchors, Markdown, whitespace и conflict markers;
- фактическую ограниченность создания одним Ownership-файлом настолько, насколько это независимо доказуемо в доступной среде.

Профиль B обязан отдельно ответить:

1. Поймёт ли работающий backend/tech lead проблему и выбранное действие без чтения всех связанных B2 документов?
2. Помогает ли сравнение кандидатов принять решение, а не служит формальной таблицей вариантов?
3. Понятно ли, что сейчас принято только направление будущей проверки, а не сама среда, evidence, capability или учебный материал?
4. Достаточно ли сценарий полезен обеим RoleViews, сохраняя разную глубину ожиданий?
5. Есть ли фрагменты, похожие на внутреннюю нотацию LLM, необъяснённые термины или критерии без контекста?
6. Можно ли принять intake после disposition findings и перейти к отдельному B3 planning package?

## Общие anti-patterns

- Не запускать runtime experiment и не подтверждать Gate 0 за автора.
- Не требовать полный каталог isolation anomalies, SQL-курс, ORM, distributed database, HA или production incident.
- Не превращать deadlock и snapshot-visibility кандидаты во второй и третий обязательные эксперименты.
- Не переносить S07/S15 версии, readiness, coverage или module status в B3.
- Не считать изменение isolation level достаточным без проверки фактических transaction settings и schedule.
- Не считать итоговый invariant достаточным без исходов обеих транзакций и store signals.
- Не предписывать конкретную serialization victim или точку обнаружения, если это не гарантировано источником.
- Не выдавать локальный опыт за proof всех interleavings либо production adoption.
- Не создавать semantic IDs, coverage, blueprint или учебные материалы.
- Не редактировать проверяемые файлы или чужой review.

## Acceptance gate G21

M1.9.0 можно принять, когда:

- получены оба независимых профиля либо оркестратор отдельно зафиксировал исключение именно для G21;
- нет открытых blocker/major по technical causality, ownership, scope, readiness либо human readability;
- признано правдивым различие B2 application transaction и B3 store isolation без присвоения B5/B6/B7;
- один выбранный action признан конкретным, bounded и отличимым от S07/S15;
- control/defect/fixed позволяют спроектировать причинный будущий эксперимент, но не выдаются за выполненный evidence;
- Gate 0 categories достаточны для отдельного package и ни одна не объявлена подтверждённой;
- роли получают полезный depth без искусственного level/L4/L5 claim;
- decisions по minor/note зафиксированы оркестратором;
- после необходимых corrections intake переводится в `accepted` отдельным acceptance-pass.

## Open questions

На review передаются три вопроса:

1. Достаточно ли описано получение snapshot в control/defect/fixed, чтобы будущий опыт различал isolation behavior, а не случайный порядок исполнения?
2. Достаточно ли store observations для объяснения serialization conflict без ложного требования видеть полный внутренний dependency graph?
3. Следующим результатом после принятого intake должен стать B3 capability blueprint или сразу bounded content-planning package с Gate 0, и какое минимальное решение должно предшествовать authoring?

Третий вопрос не разрешает reviewer создавать следующий package; он должен оценить только необходимый тип следующего решения.
