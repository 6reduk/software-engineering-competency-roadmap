## Required changes

### C-1 — backpressure

В словаре README заменить «нижняя граница» на «нижележащая зависимость (downstream)» и согласовать смысл с brief о pool saturation. Проверить, что определения не противоречат друг другу.

### C-2 и C-6 — единый measurement profile

Синхронизировать README, brief о pool saturation, kata и project spec согласно решению в `governance/reviews/M1.7-G4b-resolution.md`:

- healthy profile: все `Pricing` calls около 80 мс; service-side p95 по всем запросам 60-секундного прогона при concurrency 12 — не более 450 мс;
- degraded profile: 25% `Pricing` calls около 700 мс; 100% запросов контролируемого прогона достигают выбранного application outcome не позднее 650 мс;
- pool wait в исправленной конфигурации — не более 100 мс;
- recovery/shutdown bounds остаются 1 с и 2 с.

В каждом месте назвать population, точку измерения, workload/duration/dependency behavior. Явно сказать, что это acceptance эксперимента, а не универсальная production-гарантия. Таблицы kata и project spec должны быть самодостаточными и не расходиться с brief.

### C-3 — происхождение kata scaffold

В начале описания исходной системы kata явно сказать: участник самостоятельно создаёт минимальную стартовую систему по контракту задания; готового scaffold repository и эталонного решения нет.

### C-4 — язык

Найти в шести материалах `guardrail`, `polling`, `runbook`, `spans` и `Median`:

- при первом употреблении дать понятное русское объяснение и при необходимости английский термин в скобках;
- добавить термин в локальный словарь только когда он используется дальше и строка реально помогает;
- `Median` заменить на «медиана»;
- не выполнять массовый перевод устойчивых названий API/framework/runtime-механизмов.

### C-5 — S08

В interview заменить заголовок `Рабочая история S08` на `Рабочая история`. В вводном тексте допустимо один раз указать, что история реализует [сценарий S08](../../curriculum/tracks/b2/scenarios.md), если относительный путь проверен. Читатель не должен знать внутренний ID для понимания вопроса.

### C-7 — источники

Из brief `cancellation-deadlines-resource-lifecycle.md` удалить ссылку на документацию synchronization primitives, если ни один claim материала на неё не опирается. Остальные первичные источники не менять без фактической причины.

### C-8 — три смысла baseline

В `bounded-concurrency-pool-saturation.md`:

- таблицу исходных условий назвать `Failure envelope`/«профиль воспроизведения отказа»;
- первый замер эксперимента назвать «контрольный замер (baseline)»;
- состояние после снятия нагрузки называть «состоянием покоя» или «возвратом счётчиков к нулю», не baseline.

По связанным файлам устранить только явно двусмысленные употребления; не запрещать термин `baseline` там, где он однозначно означает контрольную точку сравнения.

### C-9 — точка измерения latency

В interview уточнить, что p50 около 180 мс и p99 выше 4 секунд наблюдаются по service-side метрикам `Quote API`, тогда как gateway прекращает клиентское ожидание около 600 мс.

### C-10 — Mermaid

- Перед картой milestones в project spec добавить фразу с вопросом/назначением схемы.
- После схемы в brief о pool saturation явно назвать намеренные упрощения: схема не моделирует scheduler, транспортные детали и все варианты очередей либо другую эквивалентную точную границу.

Существующие выводы после схем сохранить, если они не дублируют новую фразу.

### C-12 — read-only substrate

В минимальном substrate project spec явно зафиксировать, что исходные операции `Pricing` только читают данные и не создают удалённых side effects. Сценарий 9 остаётся предостережением для самостоятельного расширения проекта.

### C-13 — prerequisites для читателя

В README переписать `Внутренние hard prerequisites` обычным языком: сначала lifecycle ресурсов, затем интеграция клиента/cancellation/pool и queue; сначала восстановление request path, затем performance diagnosis. При желании дать ссылку на `../../prerequisites.md`, проверив путь. Терминология графа не должна быть необходима для прохождения slice.
