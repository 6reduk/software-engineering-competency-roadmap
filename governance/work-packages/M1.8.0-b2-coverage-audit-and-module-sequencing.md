# M1.8.0 — аудит покрытия B2 и очередь модулей

## Objective

Установить фактическое состояние пилотного трека B2 после двух принятых thin slices и сформировать проверяемую очередь следующих bounded packages. Не считать slice завершённым модулем только из-за пересечения названий или capabilities.

Результат должен ответить на три вопроса:

1. Какие modules, capabilities и LevelOutcomes уже имеют принятое покрытие?
2. Какие части B2 остаются непокрытыми либо покрыты только частично?
3. Какой один модуль следует раскрывать следующим и почему он приоритетнее альтернатив?

Рабочая гипотеза оркестратора — первым кандидатом является `b2.module.service-architecture`, поскольку он ещё не имеет самостоятельного slice, связывает обе целевые RoleViews и является prerequisite для application transaction boundaries. Агент обязан проверить гипотезу, а не принять её без анализа.

## Ownership

Агент может создать только:

## Method

### 1. Нормализовать единицу учёта

Различать:

- наличие упоминания capability;
- coverage relationship конкретного Artifact;
- покрытие конкретного LevelOutcome;
- наличие полного artifact flow;
- прохождение module gate.

Нельзя выводить завершённость модуля только из наличия одного brief, interview probe, kata или project specification. Interview с ролью `probe` не заменяет evidence самостоятельного выполнения, а project specification не является готовой реализацией.

### 2. Построить фактическую карту

Для каждого из 10 modules указать:

- primary и supporting capabilities;
- применимые LevelOutcomes;
- outcomes, уже связанные с принятыми artifacts;
- доступные жанры: learn, interview, kata, project-spec, implementation-reference;
- использованные сценарии;
- hard и conditional prerequisites;
- оставшийся содержательный пробел.

Количество связей перепроверить по semantic IDs, а не переносить из отчётов или prose-комментариев.

### 3. Присвоить состояние модуля

Использовать только следующие состояния:

- `complete` — полный замысел модуля покрыт принятыми artifacts, module gate явно пройден;
- `partial` — существует принятое содержательное покрытие, но остаются outcomes, жанры или gate-критерии;
- `not-started` — принятого содержательного покрытия модуля нет;
- `blocked` — следующий пакет нельзя корректно спроектировать без отсутствующего решения или prerequisite.

Если формальных данных недостаточно для `complete`, выбирать `partial` и объяснять недостающее доказательство.

### 4. Сформировать очередь

Сравнить неполные модули по качественным критериям:

- prerequisite leverage: какие следующие возможности он разблокирует;
- ценность для Backend / Distributed Systems и Architecture / Technical Leadership;
- объём реально непокрытых outcomes;
- возможность выразить пакет одним центральным инженерным действием и ограниченным сценарием;
- риск дублирования двух принятых slices;
- готовность external prerequisites;
- предметная и версионная стоимость независимого review.

Не маскировать инженерное суждение псевдоточной суммой баллов. Допустима компактная сравнительная таблица с `high / medium / low` и связанным обоснованием.

### 5. Выбрать только следующий пакет

Зафиксировать:

- один рекомендуемый module;
- один primary scenario и при необходимости не более двух supporting scenarios;
- центральное наблюдаемое действие будущего пакета;
- primary capabilities и LevelOutcomes-кандидаты;
- необходимые ссылки на уже принятые материалы;
- явные non-goals;
- ожидаемый минимальный artifact set;
- риски и вопросы, которые должен решить оркестратор до authoring.

Это решение не является authoring package: не создавать briefs, вопросы интервью, kata, project specification или их черновики.

## Required result structure

`curriculum/tracks/b2/module-delivery-plan.md` должен содержать:

1. назначение и способ чтения документа;
2. executive conclusion;
3. определения состояний модулей;
4. сводную таблицу 10 modules;
5. outcome-level audit по каждому module с разрешающимися ссылками на artifacts;
6. карту оставшихся пробелов;
7. обоснованную очередь модулей;
8. decision brief для одного следующего bounded package;
9. rejected alternatives для ближайшего шага;
10. open questions и известный долг;
11. инструкции по обновлению плана после acceptance каждого следующего модуля.

Документ должен быть понятен человеку без чтения внутренних review-диалогов. Semantic IDs используются для трассировки рядом с человеческими названиями, а не вместо объяснений.

## Constraints and non-goals

- Не менять 10 modules, 19 capabilities, 69 LevelOutcomes и prerequisite DAG.
- Не придумывать отсутствующее coverage и не считать planned relationship принятым evidence.
- Не требовать ImplementationReference до самостоятельной реализации проекта; отсутствие ссылки отражать отдельно от качества project specification.
- Не превращать очередь в календарный план, оценку часов или обещание параллельной разработки.
- Не проектировать весь будущий учебный материал на уровне тем и секций.
- Не добавлять новый vertical track, module, capability, scenario или уровень.
- Не объявлять M1.8, B2 либо выбранный module завершёнными.

## Acceptance criteria

Пакет готов к review, если:

- все 10 modules классифицированы по единому правилу;
- все 69 LevelOutcomes учтены ровно один раз в базовом реестре аудита, при этом shared module membership отражена отдельно;
- каждое утверждение о принятом покрытии ведёт к существующему Artifact и coverage relationship;
- различены artifact coverage, outcome coverage и module gate;
- очередь не нарушает hard prerequisite DAG;
- выбран ровно один следующий bounded package;
- выбор сопоставлен минимум с двумя сильными альтернативами;
- scope следующего пакета реалистично ограничен одним центральным действием;
- файл имеет корректный YAML, `status: review`, уникальный ID и разрешающиеся относительные ссылки;
- исходные материалы не изменены.

## Handoff

В отчёте передать:

1. созданный файл;
2. итоговую классификацию `complete / partial / not-started / blocked`;
3. числа учтённых capabilities, LevelOutcomes и существующих coverage relationships;
4. рекомендуемый следующий module и краткое обоснование;
5. отвергнутые ближайшие альтернативы;
6. проверки целостности и ссылок;
7. открытые вопросы и рекомендуемый scope независимого review.

Агент оставляет результат в `status: review`, не меняет program gate и не объявляет собственный вывод принятым.
