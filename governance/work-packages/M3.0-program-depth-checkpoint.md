# M3.0 — программный checkpoint глубины после B2/B3/B5

## Objective

Создать ровно один planning artifact, который решает, завершать ли текущий цикл детального authoring после трёх глубоких вертикалей B2/B3/B5 или назначить ровно одну последнюю вертикаль с жёстко ограниченной фазой.

Это портфельное решение о глубине программы, а не blueprint нового track, Gate 0, учебный slice, coverage или module gate.

## Ownership

Создать ровно один файл:

- `governance/planning/intakes/program-depth-checkpoint.md`.

Другие файлы не изменять. Не создавать новый track blueprint, semantic IDs, coverage, Gate 0, learning artifacts, close-out, review, acceptance, STATUS/DECISIONS updates или ImplementationReference.

## Context manifest

Полностью прочитать:

1. `governance/decisions.md`, особенно D-016, D-071, D-072 и D-077;
2. `governance/state/STATUS.md`;
3. `curriculum/tracks/README.md`, `curriculum/roles/role-summary.md` и 15 track cards;
4. `curriculum/tracks/b2/consolidation/README.md` и актуальный B2 phase/delivery close-out источник;
5. `curriculum/tracks/b3/phase-closeout.md`;
6. `curriculum/tracks/b5/phase-closeout.md`;
7. `curriculum/roles/backend-distributed-systems.md` и `curriculum/roles/architecture-technical-leadership.md`;
8. `governance/planning/intakes/next-vertical-selection.md` только как предыдущий формат выбора;
9. `authoring/standards/editorial-standard.md` и `authoring/workflow/content-author-workflow.md`.

## Обязательное сравнение

Сопоставить минимум четыре маршрута:

1. **Остановить детальный authoring сейчас:** B2/B3/B5 остаются тремя deep verticals, остальные 12 track cards — awareness/skeleton до появления конкретной потребности.
2. **C1 Engineering Leadership & Architecture:** только если существует наблюдаемая задача межкомандного решения, ownership и передачи ответственности, которую не закрывает C1-линза B5.
3. **B7 Reliability, Observability & Production Engineering:** только если подтверждена роль с production/SLO/incident/recovery ответственностью и доступен отличимый от B2/B5 результат.
4. **B6 Platform, Cloud & Infrastructure Engineering:** только если подтверждена platform/cloud ownership и результат не сводится к application runtime или B7 operations.

Другие треки можно перечислить как отложенные, но нельзя добавлять пятого кандидата без доказанного преимущества над этими маршрутами.

## Критерии

Для каждого маршрута указать:

- связь с целевыми RoleViews и реальной задачей пользователя;
- новый проверяемый результат относительно B2/B3/B5;
- риск дублирования уже созданных маршрутов;
- readiness и доступность bounded evidence;
- стоимость intake, breadth-pass, slice, review и close-out;
- будущую стоимость сопровождения материалов;
- что потеряется при отсрочке;
- достаточность текущей модели D-016: общий core, 2–4 глубокие вертикали, awareness по остальным.

Количественный scoring не выдумывать. Не считать `12 из 15 не углублены` самостоятельным аргументом продолжать работу.

## Правило выбора

По умолчанию завершить текущий детальный authoring, потому что три глубокие вертикали уже входят в диапазон D-016.

Дополнительная вертикаль допустима только если одновременно подтверждены:

1. конкретная задача целевой роли или повторяемый пробел;
2. новый результат, не покрытый B2/B3/B5;
3. доступный bounded evidence или честный путь его подтверждения до authoring;
4. ценность выше стоимости полного цикла;
5. фаза ограничена boundary intake, одним breadth-pass, максимум одним deep slice и обязательным close-out;
6. существует конечный exit trigger без обещания пройти остальные tracks.

Если хотя бы одно условие не выполнено, выбрать остановку детального authoring и перейти к использованию/learner execution существующей программы.

## Required result

Файл должен:

- иметь уникальный `id`, `kind: plan`, `status: review`, `updated: 2026-09-18`, `language: ru`;
- начинаться с человеческого ответа, зачем нужен checkpoint после трёх вертикалей;
- содержать одну сравнительную таблицу и ровно один выбранный маршрут;
- отдельно показать, что B2/B3/B5 acceptance не означает proficiency или выполнение участником;
- если выбран stop — назвать практический следующий режим использования программы и triggers возврата к authoring;
- если выбрана вертикаль — назвать только будущий boundary intake, phase cap и неподтверждённые inputs без создания blueprint;
- сохранить 12 остальных tracks как awareness/backlog, а не провал программы;
- не объявлять весь curriculum завершённым, опубликованным или проверенным учащимся.

## Проверки

Проверить:

- создан ровно один файл и нет других изменений;
- YAML и уникальность ID;
- ссылки и anchors;
- четыре маршрута и один выбор;
- отсутствие новых semantic entities, coverage, Gate 0 и учебных материалов;
- Markdown, UTF-8 без BOM, EOF, trailing whitespace и conflict markers.

SHA-256 snapshot доказывает только scope текущего запуска, не историческую чистоту workspace.

## Handoff

Передать выбранный маршрут, сравнительную таблицу, применённое правило, открытые inputs и рекомендуемые два независимых review-профиля. Planning artifact оставить в `review`; review и acceptance не запускать.
