# M1.8.13 — S15: tenant-scoped Orders cache under concurrent miss

## Objective

Создать bounded end-to-end slice B2 для application caching внутри `b2.module.transactional-persistence-integration`.

Центральное наблюдаемое действие: инженер задаёт key/freshness invariant одного tenant-scoped Orders summary read path, ограничивает amplification чтений source-of-truth при одновременных cache misses и доказывает корректный результат при hit, miss burst, invalidation race, cache failure и recovery.

Primary scenario — S15. S07 используется только для commit/invalidation ordering, S13 — только как принятый язык bounded amplification. Они не становятся отдельными центральными действиями и не получают новое coverage.

### Правило применимости B5

B5 coordination readiness требуется, если заявленная гарантия coalescing выходит за один процесс/инстанс либо зависит от coordination semantics вне обычного контракта выбранного cache store/client. Для S15 это дополнительный conditional gate сверх списка B5 consumers в каталоге prerequisites, а не новый hard-DAG edge.

Если evidence ограничено одним процессом, достаточно подтверждённой B3 cache-store readiness и явной границы доказательства. One-process evidence нельзя выдавать за distributed guarantee.

### Обязательные классы источников

До authoring проверить и связать утверждения минимум с:

- официальной документацией выбранного cache store по key/value, TTL/expiration, atomicity, failure и persistence semantics;
- официальной документацией pinned client library по pooling, timeouts, concurrency и error behavior;
- официальной документацией выбранного framework/runtime по lifecycle и concurrency boundary;
- официальной документацией source-of-truth/driver по commit visibility, если invalidation зависит от transaction ordering;
- применимыми HTTP/RFC источниками для response/error/cache semantics.

Локальные измерения маркируются как экспериментальное evidence выбранного substrate, а не как нормативный источник или production benchmark. Версионно-чувствительные утверждения получают pinned version, прямую ссылку и дату проверки.

### Stop conditions Gate 0

Автор прекращает пакет до учебных artifacts и возвращает вопрос оркестратору, если:

- невозможно сформулировать один tenant-safe key и проверяемый freshness invariant;
- cache и source-of-truth ownership либо commit/invalidation ordering остаются неоднозначными;
- заявленная coalescing guarantee шире воспроизводимой process topology;
- B5 применим, но coordination semantics невозможно подтвердить первичным источником и экспериментом;
- failure path создаёт неограниченный fan-out к source of truth либо скрывает ошибку без согласованного bounded fallback;
- measurement envelope не различает правильный response и фактическое ограничение store-read amplification;
- для честного результата требуется multi-service migration, production rollout или Cache L4 evidence.

## Каноническая история slice

После Gate 0 все пять материалов используют одну историю:

- один tenant-scoped Orders summary read endpoint;
- source of truth остаётся авторитетным, cache хранит производное значение;
- cache key включает доверенный tenant context и identity ресурса;
- hit возвращает значение в пределах freshness invariant;
- concurrent cold misses для одного key не создают неограниченное число чтений source of truth;
- commit/invalidation race имеет заранее выбранные допустимые исходы;
- cache failure следует закреплённому bounded fallback и не раскрывает данные другого tenant;
- после снятия отказа система возвращается в объявленный контрольный диапазон.

Численные thresholds действительны только для указанного workload, topology, duration и measurement point. Они не являются универсальными production defaults.

## Обязательные invariants

1. **Tenant-key invariant:** ключ нельзя построить только из недоверенного request tenant; разные tenants не разделяют cached value.
2. **Freshness invariant:** допустимый возраст/версия ответа и поведение после подтверждённой записи сформулированы наблюдаемо.
3. **Amplification invariant:** concurrent miss population ограничивает число обращений к source of truth на key в пределах Gate 0 envelope.
4. **Failure invariant:** cache outage не превращается в неограниченный stampede и следует явному fail-open/fail-closed/degraded contract.
5. **Bounded-claim invariant:** локальная топология не выдаётся за distributed guarantee, а Cache L3 не подменяется Cache L4 adoption/migration evidence.

Обязательны hit, cold miss, concurrent miss, invalidation race, cross-tenant isolation, cache failure и recovery populations; decision record; observability; альтернативы и stop conditions. Участник реализует проект самостоятельно, готовая реализация и фиктивный ImplementationReference не создаются.

## Failure and measurement envelope

Во всех материалах согласовать:

- одинаковые fixtures, key/value contract и populations;
- process/worker topology и точную область coalescing guarantee;
- workload size, concurrency, duration и measurement points;
- source-of-truth read counter на key и признак корректного response;
- hit/miss/stale/error/fallback counters либо эквивалентные наблюдения;
- допустимые исходы invalidation race относительно commit;
- отсутствие cross-tenant value leakage;
- recovery observation после прекращения cache failure;
- threshold amplification, выведенный из Gate 0 эксперимента, а не перенесённый из другого slice.

Правильный status/response без доказательства store-read amplification недостаточен. Низкое число reads при неправильном либо stale response также недостаточно.

## Constraints и non-goals

- Не проектировать write-through, write-behind, event-driven cache invalidation как второе центральное действие или multi-region cache.
- Не создавать distributed cache migration, mixed-version rollout, capacity program либо Cache L4 evidence.
- Не навязывать Redis, distributed lock, lease или process-local lock до Gate 0.
- Не превращать материал в общий учебник по Redis, PostgreSQL, HTTP caching, CDN, ORM tuning или Kubernetes.
- Не обещать zero stale reads, exactly-once invalidation, linearizability либо universal TTL.
- Не начислять Transaction, Load Control, Identity, Verification, B3 или B5 proficiency за supporting context.
- Не создавать runtime implementation, готовое решение, project repository или ImplementationReference.

## Open questions

До запуска автора конкретные store/client, topology, TTL, coalescing mechanism, invalidation strategy и thresholds принадлежат Gate 0. Это не разрешение выбрать их произвольно: решения должны быть согласованы между собой, подтверждены первичными источниками и локальным экспериментом.

При срабатывании stop-condition автор прекращает зависимую работу и передаёт вопрос без создания учебных материалов.

Известный долг сохраняется: Cache L4 требует отдельного cross-service/migration evidence. Callback/untrusted-target/SSRF и aggregate quota/rate остаются отдельными долгами S14. ImplementationReference появится только после самостоятельной реализации и review проекта.
