# M1.8.11 — S14: operation-cost admission для tenant-scoped bulk export

## Objective

Создать bounded end-to-end slice B2 для `b2.module.identity-aware-boundaries`, который учит защищать один tenant-scoped bulk-export endpoint от чрезмерной стоимости операции.

Центральное наблюдаемое действие: инженер задаёт вычисляемую на стороне сервиса единицу стоимости, принимает решение `admit/reject` до запуска дорогой работы и доказывает на нормальных и намеренно неблагоприятных запросах, что изменение формы запроса не обходит ограничение, а допустимый export сохраняет корректное поведение.

Primary scenario — только operation-cost половина S14. S05 используется как принятый trusted tenant context, S13 — как контраст между admission и общей перегрузкой сервиса. Произвольный callback URL и SSRF остаются отдельным будущим пакетом.

### Applicability matrix Abuse L2

Каждая категория получает либо применимый threat case, control и наблюдаемое evidence, либо обоснованное `not applicable` с границей решения и residual risk. Нельзя заявлять relationship к Abuse L2, пока все четыре строки не заполнены и не подтверждены материалами.

| Категория | Threat case / применимость | Control или `not applicable` | Evidence | Residual risk |
|---|---|---|---|---|
| Request/cost bounds | Клиент увеличивает число строк или разрешённых полей одной операции; row-only check пропускает shape bypass. | Strict schema → normalize → `max_rows × unique_allowed_fields` → reject при `>2000` до executor. | normal/at-limit exact-cell checks; over-limit и `500×5` bypass дают один `422`, `export_execution_started=0`, `cells_serialized=0`. | Формула не моделирует размер строк, компрессию, SQL scan и сумму нескольких допустимых operations; production weights требуют собственной калибровки. |
| Field exposure | Клиент пытается добавить неизвестное либо чувствительное поле или client tenant selector. | Явный allowlist пяти публичных полей; `extra=forbid`; sensitive/unknown/duplicate input отклоняется до export. | Negative cases `customer_email`, `payment_token`, `debug`, duplicate field и `tenant_id` проверяют safe `422`, нулевую работу и отсутствие значений в error/audit. | Разрешённые CSV-значения всё ещё требуют защиты от spreadsheet/formula interpretation у потребителя; это не object authorization или DLP. |
| Quota/rate | Множество отдельных запросов по 2000 cells может суммарно перегрузить сервис. | `not applicable` как реализуемый control в этом per-operation slice; явно не заявлять rate/quota protection. | Project decision record и tests различают operation ceiling и отсутствие time-window/shared counter; 100 последовательных bypass используются только для recovery, не как quota test. | Distributed abuse и aggregate tenant consumption остаются; нужен отдельный rate/quota/platform package и coordination decision. |
| Untrusted target rules | В закреплённом request contract нет callback URL, host, bucket или иного адреса назначения; extra target был бы недоверенным входом. | `not applicable` для SSRF control; contract допускает только синхронный response и отклоняет extra keys. | Contract/OpenAPI и negative extra-field case показывают отсутствие target; материалы прямо запрещают считать это SSRF evidence. | Будущий callback/export destination потребует отдельного bounded package с DNS/IP/redirect policy и Gate 0. |

**Итог readiness:** `confirmed`.

## Каноническая история slice

После Gate 0 все пять материалов используют одну и ту же историю:

- один tenant-scoped Orders bulk-export endpoint;
- trusted tenant context поступает из уже проверенной S05 boundary;
- request содержит ограниченное семейство параметров, влияющих на стоимость;
- сервис нормализует request и вычисляет server-owned cost до export execution;
- допустимый request проходит, чрезмерный и обходной request получают один закреплённый rejection contract;
- rejection не запускает заявленную дорогую работу;
- fixed schema/allowlist не позволяет расширить export неизвестными или чувствительными полями;
- quota/rate и untrusted-target категории имеют честные границы и residual risks;
- после снятия adversarial workload наблюдаемые признаки возвращаются в объявленный контрольный диапазон.

Threshold не объявляется универсальным production limit. Он действителен только для явно названных workload, duration, dependency behavior и measurement point.

## Обязательные invariants

1. **Server-owned cost invariant:** решение использует нормализованную модель сервиса, а не заявленную клиентом стоимость.
2. **Reject-before-work invariant:** over-limit и shape-bypass запросы не пересекают дорогую execution boundary.
3. **Legitimate-use invariant:** допустимые и граничные запросы сохраняют согласованный результат без ложного отказа в пределах measurement envelope.
4. **Tenant/disclosure invariant:** admission, error и audit behavior не раскрывают данные другого tenant, credentials, чувствительные поля или внутреннюю cost telemetry сверх принятого контракта.
5. **Bounded-claim invariant:** материалы не обещают защиту от совокупности множества допустимых запросов, distributed abuse либо SSRF.

## Failure and measurement envelope

Во всех материалах согласовать:

- одинаковые populations и точное различие normal/at-limit/over-limit/bypass/recovery;
- workload size, duration, concurrency/dependency assumptions и точку измерения;
- cost estimate и фактический наблюдаемый work indicator;
- признак `reject-before-work`, который нельзя удовлетворить одним правильным status code;
- корректность результата допустимого export;
- отсутствие cross-tenant/disallowed-field disclosure;
- recovery observation после прекращения нагрузки;
- границу доказательства: per-operation admission не является distributed quota или общей capacity guarantee.

Численные thresholds выводятся из Gate 0 substrate и эксперимента. Они должны быть воспроизводимыми и одинаковыми в README, brief, interview, kata и project-spec.

## Constraints and non-goals

- Не добавлять arbitrary callback URL, DNS/IP validation, redirect handling или SSRF.
- Не проектировать distributed rate/quota service, shared counter, platform gateway или global fairness.
- Не создавать export-file/background workflow как второе центральное действие.
- Не превращать материал в урок по JWT, authentication, BOLA, database optimization, general performance tuning или Kubernetes autoscaling.
- Не обещать universal cost weights, zero false positives, exactly-once export либо полную защиту сервиса от overload.
- Не начислять Identity, Load Control, HTTP, Verification либо external-track proficiency за переиспользованный контекст.
- Не создавать runtime implementation, готовое решение, project repository или ImplementationReference.

## Open questions

До запуска автора открытых вопросов, требующих выбора оркестратора, нет. Конкретный substrate и thresholds принадлежат Gate 0. При срабатывании любого stop-condition автор прекращает зависимую работу и передаёт вопрос без создания учебных материалов.

Известный долг сохраняется: callback/untrusted-target/SSRF половина S14 требует отдельного будущего bounded package со своим Gate 0. ImplementationReference появится только после самостоятельной реализации и review проекта.
