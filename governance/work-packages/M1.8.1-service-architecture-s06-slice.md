# M1.8.1 — Service Architecture: change isolation вокруг S06

## Objective

Создать следующий bounded end-to-end slice B2 для `b2.module.service-architecture`. Материал должен научить инженера выделять application/domain/adapter boundaries вокруг одной изменяющейся бизнес-политики, проводить изменение по направлению зависимостей и проверяемо уменьшать coupling — без догматичного каталога архитектурных паттернов.

Центральное наблюдаемое действие: участник перестраивает одну feature так, чтобы бизнес-решение проверялось без FastAPI, ORM и сети, а реальный persistence/downstream adapter можно было заменить fake/in-memory реализацией без изменения application/domain code.

Primary scenario — S06. S10 используется только для выбора test boundaries. S07 допускается лишь как короткое объяснение будущей границы: transaction mechanics в этот пакет не входят.

## Канонический substrate S06

Все пять материалов используют одну рабочую историю Orders service.

Сервис имеет read-only operation `GET /orders/{order_id}/cancellation-eligibility`. В исходном варианте router:

- загружает ORM-модель заказа;
- сам проверяет статус и customer tier;
- напрямую вызывает Carrier API;
- собирает business decision и HTTP response;
- тестируется через mocks внутренних деталей FastAPI, ORM и HTTP client.

Исходная политика: отмена разрешена только для заказа в состоянии `CREATED`.

Изменение S06: клиент уровня `PREMIUM` может отменить заказ в состоянии `PACKED`, пока Carrier API сообщает, что передача перевозчику ещё не началась. Operation только вычисляет eligibility и ничего не записывает: нет DB commit, refund, публикации события или удалённого side effect.

Желаемая граница после изменения:

- delivery adapter преобразует HTTP request/response;
- application operation координирует use case;
- domain policy принимает бизнес-входы и возвращает решение без I/O;
- persistence и Carrier API находятся за явными ports/adapters;
- wiring остаётся composition concern и не считается само по себе доказательством change isolation.

Имена классов, папок и паттерна не каноничны. Автор может использовать функции, protocols/interfaces или небольшие objects, если dependency direction и наблюдаемое поведение остаются ясными.

## Capability и outcome contract

### Primary coverage

Обязательно раскрыть:

- `b2.level-outcome.design-service-architecture-l1-follow-existing-boundaries`;
- `b2.level-outcome.design-service-architecture-l2-structure-typical-feature`;
- `b2.level-outcome.design-service-architecture-l3-reshape-changing-service`.

L3 требует не большего количества слоёв, а evidence исходной боли, рассмотренных альтернатив, incremental migration plan и наблюдаемого уменьшения change risk.

### Supporting coverage

Допустимо и ожидаемо раскрыть:

- `b2.level-outcome.verify-service-behavior-l1-test-local-behavior`;
- `b2.level-outcome.verify-service-behavior-l2-select-test-boundaries`.

`verify-service-behavior` L3 не заявлять без полноценного изменения service-wide verification strategy. `integrate-external-services` L2 уже покрыт R2/R4: сослаться на существующие материалы и использовать downstream client только как заменяемый adapter. Не повторять timeout, retry, pool lifecycle и cancellation и не добавлять новую coverage relationship к external L2 без нового самостоятельного evidence.

L4 architecture/verification outcomes не входят в target coverage: вопрос о cross-team conventions может быть follow-up, но не выдаётся за L4 evidence.

### Coverage roles по жанрам

- index — `reference` только на capabilities;
- learn — `explain` для выбранных L1–L3 outcomes;
- interview — `probe`, не proficiency evidence;
- kata — `practice` и `assess` только там, где acceptance criteria позволяют наблюдать действие;
- project-spec — `integrate` и `assess` для отдельного интеграционного milestone.

Точный набор relationships должен быть минимальным и правдивым. Не требуется, чтобы каждый artifact ссылался на каждый target.

## Artifact requirements

### 1. Index

`README.md` должен быть самостоятельной точкой входа: рабочая история, кому полезен slice, prerequisites, маршрут `learn → interview → kata → project-spec`, ожидаемый результат, coverage и границы. Объяснить, почему это material про управляемость изменений, а не про «идеальную чистую архитектуру».

### 2. Engineering brief

Один связный brief должен раскрыть:

- как обнаружить coupling по change path, а не по внешнему виду дерева папок;
- различие business rule, application orchestration, delivery/persistence/downstream details;
- dependency direction и место composition/wiring;
- почему ORM model и HTTP schema не обязаны быть domain model;
- как выбирать boundary с учётом стоимости, а не добавлять abstraction заранее;
- failure modes: thin wrappers без смысла, service layer как god object, repository над каждым запросом, mocks implementation details, domain imports framework/ORM, protocol ради protocol;
- incremental refactoring без big-bang rewrite;
- как доказать эффект: targeted regression, tests without I/O, подмена adapter, уменьшение change surface и локализация failure;
- good/bad practice на одном substrate;
- вопросы самопроверки со скрываемыми ответами;
- локальный словарь для boundary, port, adapter, application operation, dependency direction, composition root, change surface и coupling.

Использовать Mermaid только если схема реально помогает увидеть направление зависимостей. Перед схемой сформулировать вопрос, после — объяснить вывод и существенные упрощения.

### 3. Interview

Interview artifact начинается с полной истории S06, а не с rubric. Он должен включать:

- основной вопрос;
- последовательные follow-ups от диагностики coupling до incremental migration и evidence;
- скрываемый ожидаемый ответ на каждый вопрос;
- rubric L1/L2/L3, различающий автономность и масштаб решения;
- частые слабые ответы и диагностируемые пробелы;
- явное правило: количество названных patterns не повышает уровень;
- L4 follow-up только как границу применимости, без L4 coverage.

### 4. Kata

Участник самостоятельно создаёт минимальный starting scaffold по описанию; готового repository и эталонного решения нет. Kata должна дать намеренно coupled starting state и потребовать:

- сохранить внешний HTTP behavior;
- провести policy change;
- выделить минимально достаточные boundaries;
- написать business-behavior tests без DB/network/framework runtime;
- подменить хотя бы один persistence или Carrier adapter fake/in-memory реализацией без изменения application/domain code;
- оставить короткое rationale и перечень намеренно не введённых abstractions.

Hints направляют рассуждение, но не дают структуру файлов, полный interface или реализацию. Acceptance criteria проверяют behavior и dependency direction, а не совпадение с авторской архитектурой.

### 5. Project specification

Обязательна одна компактная project specification с одним milestone, отличным от kata. Участник интегрирует application operation в небольшой FastAPI service с реальными persistence и HTTP adapters по выбранному им способу.

Наблюдаемый integration result:

- одинаковый набор business-policy tests проходит с fake/in-memory adapters и не требует FastAPI/DB/network;
- отдельные adapter/integration checks подтверждают mapping реальных границ;
- endpoint сохраняет заявленное внешнее поведение;
- повторное небольшое изменение policy локализуется в policy/application tests и не требует согласованных правок router, ORM и HTTP client;
- приложен короткий decision record: исходная боль, минимум две альтернативы, выбранная boundary, incremental migration, риски и критерии удаления лишней abstraction.

Project specification не диктует готовую реализацию, структуру репозитория или конкретный DI framework. Явно указать отсутствие ImplementationReference до самостоятельной реализации и review.

## Non-goals

- Каталог Clean/Hexagonal/Onion Architecture и design patterns.
- Обязательные layers, repository pattern, class-based use cases или DI container.
- Microservices decomposition, bounded contexts всей организации и service ownership topology — B5/C1.
- Transaction boundaries, unit of work, outbox, caching, idempotency и consistency — будущий persistence package.
- Полная testing strategy — будущий Service Verification package.
- Повторное объяснение FastAPI request lifecycle, API compatibility, HTTPX pools, timeout/retry/cancellation.
- Production code, готовый scaffold, эталонное решение и ImplementationReference.
- L4 multi-team conventions и организационная стандартизация.

## Human-readable and technical guardrails

- Каждый файл понятен без чтения внутренних blueprint/review discussions.
- Сначала рабочая ситуация и инженерная проблема, затем критерии и internal IDs.
- Русский текст не заменяется смесью необъяснённых англицизмов; устойчивые термины объясняются при первом употреблении и при необходимости входят в локальный словарь.
- Не утверждать, что одна архитектура универсально правильна. Trade-off включает стоимость indirection, boundary maintenance и тестов.
- Не выдавать fake/mock за доказательство корректности реального adapter mapping; business и adapter evidence разделяются.
- Не использовать количество файлов, классов или interfaces как метрику decoupling.
- Не придумывать измеримые проценты улучшения. Change surface описывать воспроизводимо: какие responsibilities и tests затрагиваются одинаковым policy change до и после.
- Вопросы для самопроверки и interview имеют ответы в `<details>`.
- Нормативные или version-sensitive утверждения проверяются по первичным источникам; stable engineering reasoning не обвешивается случайными ссылками.
