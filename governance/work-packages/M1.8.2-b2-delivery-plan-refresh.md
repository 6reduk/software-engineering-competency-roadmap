# M1.8.2 — обновление B2 delivery plan после Service Architecture/S06

## Objective

Обновить `curriculum/tracks/b2/module-delivery-plan.md` по фактическому acceptance M1.8.1, не переписывая исходный аудит и не предполагая автоматическое завершение `b2.module.service-architecture`.

Результат должен:

1. добавить пять принятых S06 artifacts и их 26 YAML relationships;
2. пересчитать outcome coverage и состояния десяти modules;
3. проверить, снимает ли принятое Architecture L1–L3 execution evidence блокировку Transactional Persistence;
4. заново сравнить первые кандидаты очереди;
5. выбрать ровно один следующий bounded package.

Агент может изменить только:

Запрещено изменять учебные materials, coverage map, catalogs, prerequisites, scenarios, role routes, standards, work packages, reviews, decisions и program status.

## Expected baseline to verify

Следующие числа являются контрольной гипотезой оркестратора, а не заменой независимого пересчёта:

- accepted artifacts: 17;
- relationships: 130 = 11 capability-level `reference` + 119 outcome-level;
- уникально покрытые LevelOutcomes: 41 из 69;
- непокрытые LevelOutcomes: 28;
- новых уникально покрытых outcomes относительно M1.8.0: Architecture L1–L3 и Verification L1;
- Service Architecture membership: 12 outcomes, из них 9 имеют accepted relationship;
- probe-only outcomes должны остаться отдельной категорией и не превращаться в execution evidence.

Если пересчёт не совпадает, привести точные IDs и воспроизводимую причину; не подгонять результат под гипотезу.

## Required changes

### 1. Обновить snapshot и реестр artifacts

- Зафиксировать snapshot 2026-08-19 и acceptance M1.8.1.
- Добавить к C0–C5/R0–R5 пять S06 artifacts с устойчивыми локальными кодами, kind, primary module и точным количеством relationships.
- Не менять исторические relationships первых 12 artifacts.

### 2. Обновить базовый outcome audit

- Добавить новые `explain/probe/practice/assess/integrate` ссылки к exact targets.
- Сохранить один канонический ряд на каждый из 69 outcomes.
- Не считать capability-level `reference` outcome evidence.
- Не считать `probe` proficiency evidence.
- Явно сохранить отсутствие Architecture L4, Verification L4 и External Services L4 execution evidence.

### 3. Пересчитать module states

Применять существующие определения `complete / partial / not-started / blocked` без изменения их смысла.

Контрольные ожидания, требующие проверки:

- Service Architecture переходит из `not-started` в `partial`: собственный полный artifact flow появился, но Architecture L4 и часть shared membership не покрыты, явного module-gate decision нет;
- Transactional Persistence больше не должен оставаться `blocked`, если для его следующего bounded package достаточно принятого Architecture L2/L3 evidence вокруг application operation; в таком случае состояние становится `not-started`;
- ни один module не становится `complete` автоматически;
- ожидаемая сводка после этих переходов: `complete` 0, `partial` 4, `not-started` 6, `blocked` 0.

Если hard prerequisite трактуется иначе, агент обязан показать конкретное противоречие DAG/LevelOutcome и передать open question, а не молча сохранить старый статус.

### 4. Пересобрать очередь

Качественно сравнить минимум три ближайших кандидата:

- Service Verification / S10;
- Transactional Persistence Integration / S07 или S15;
- Identity-aware Boundaries / S05 или S14.

Проверить также, не изменило ли M1.8.1 ценность остальных кандидатов. Сравнение должно учитывать prerequisite leverage, роль для двух RoleViews, пустое primary coverage, boundedness центрального действия, риск дублирования и готовность внешнего baseline.

Не сохранять прежний порядок только ради стабильности и не повышать Transactional Persistence автоматически только потому, что он разблокирован.

### 5. Выбрать один следующий package

Обновить decision brief:

- один module;
- один primary scenario и не более двух supporting;
- одно центральное наблюдаемое действие;
- primary/supporting capabilities и outcome candidates;
- links на уже принятое coverage, которое нельзя повторять;
- минимальный полный flow `index + learn + interview + kata + project-spec`;
- non-goals;
- risks/open questions до authoring;
- минимум две сильные отвергнутые альтернативы.

Не создавать work package или учебный content для победившего кандидата.

## Constraints

- Не менять 10 modules, 19 capabilities, 69 outcomes, scenarios или prerequisite DAG.
- Не считать ImplementationReference обязательным до самостоятельной реализации.
- Не пересматривать acceptance трёх slices.
- Не объявлять module gate пройденным из-за полного набора жанров.
- Не превращать обновление в полный новый документ: сохранить принятую структуру и историю M1.8.0, обновив изменившиеся данные и выводы.
- Не вводить календарь, часы, псевдоточные scoring weights или параллельный authoring.
