### Major

### Minor

#### Minor-1. Нормативное обязательство кэша приписано RFC 9110, но живёт в RFC 9111

- **Evidence:** `learn/compatible-api-change.md:188` («общий кэш обязан различать варианты, например через `Vary: Accept`»), `learn/http-contract-execution-boundary.md:175`; списки первичных источников в обоих brief (строки 340–346 и 265–273) содержат RFC 9110 и RFC 9457, но не RFC 9111.
- **Impact:** Само поле `Vary` действительно определено в RFC 9110 §12.5.5, но требование «кэш обязан» (MUST NOT использовать сохранённый ответ без совпадения номинированных заголовков) сформулировано в RFC 9111 (HTTP Caching) §4.1. Читатель, перейдя по заявленному источнику, не найдёт нормативной основы ключевого слова «обязан».
- **Recommendation:** Добавить RFC 9111 в «Первичные источники» обоих brief (или уточнить формулировку: сервер сообщает `Vary` (RFC 9110), кэш обязан учитывать его при выборе сохранённого ответа (RFC 9111 §4.1)).

#### Minor-2. Расхождение примеров данных между learn/interview и kata/project-spec

- **Evidence:** `learn/compatible-api-change.md:37-42` и `interview/api-contract-evolution.md` используют `customer_id: "c-42"` и items вида `{"product_id": "p-7", "quantity": 2}`; `kata/compatible-delivery-contract-change.md:40-44` и `project-spec/evolvable-orders-api.md:69-71` — `customer_id: "c-17"` и `{"sku": "book-1", "quantity": 1}`.
- **Impact:** Оба набора описывают «один и тот же» Orders API из сквозной ситуации README. Разные имена поля товара (`product_id` vs `sku`) в одной истории могут быть приняты за осмысленное различие или за ошибку; README это никак не комментирует.
- **Recommendation:** Либо унифицировать имена полей, либо добавить в README одну строку о том, что kata/project-spec используют собственные упрощённые примеры (по аналогии с «каждый документ содержит собственный контекст»).

#### Minor-3. Асимметрия метаданных `last_verified` / `versions`

- **Evidence:** `last_verified` и блок `versions` есть только в двух learn-документах (например, `learn/compatible-api-change.md:23-27`); README, interview, kata и project-spec их не имеют. При этом interview содержит чувствительное к версии утверждение: `interview/api-contract-evolution.md:97` («поле без default в Pydantic v2 остаётся обязательным»).
- **Impact:** Формально «проверено 2026-08-15» заявлено только для learn; версия-sensitive утверждение в interview не покрыто заявленной дисциплиной проверки.
- **Recommendation:** Добавить `last_verified: 2026-08-15` минимум в interview (и при желании в README), либо перенести все версии-sensitive утверждения в learn.

#### Minor-4. Ссылки на документацию Pydantic 301-редиректят

- **Evidence:** `learn/compatible-api-change.md:345` → `https://docs.pydantic.dev/latest/concepts/serialization/`, `learn/http-contract-execution-boundary.md:272` → `https://docs.pydantic.dev/latest/concepts/fields/`; обе возвращают 301 на `pydantic.dev/docs/...`.
- **Impact:** Ссылки работают, но домен Pydantic мигрировал; со временем редирект может исчезнуть.
- **Recommendation:** Обновить на актуальные URL `pydantic.dev/docs/validation/latest/...`.

#### Minor-5. Сценарий смешения кэша приведён без ограничения по кэшируемости метода

- **Evidence:** `project-spec/evolvable-orders-api.md:174` (сценарий 8: «Общий HTTP-кэш смешивает два формата ответа, выбранных по заголовку») и общие советы про `Vary` в обоих brief.
- **Impact:** Сквозная операция — `POST /orders`; ответы на POST сохраняются кэшем только при явной информации свежести (RFC 9111), поэтому для данного API сценарий возникает не всегда. Формулировка не неверна (совет про `Vary` общий и корректный), но без оговорки читатель может решить, что общий кэш по умолчанию хранит ответы POST.
- **Recommendation:** Одной фразой оговорить: сценарий актуален, когда ответы явно делаются кэшируемыми (Cache-Control), либо для read-операций (GET /orders/{id}).

### Notes

1. **`errors`-расширение в примере Problem Details** (`learn/http-contract-execution-boundary.md:150-153`) — RFC 9457 сам приводит пример массива `errors` для ошибок валидации; пример документа согласован со стандартом. Можно сослаться на этот раздел RFC как на прецедент.
2. **Формулировка про `response_model_include/exclude`** (`learn/http-contract-execution-boundary.md:191`: «схема может продолжить описывать полную модель») избыточно осторожна: документация FastAPI утверждает это категорически («will still be the one for the complete model»). Можно усилить до утвердительной формы.
3. **Default scope зависимостей** — в документации FastAPI default для dependencies with `yield` — `scope="request"` (очистка после отправки ответа). Схема и текст brief корректны; при желании можно указать default явно, чтобы читатель не предполагал `function`.
4. **Mermaid-схемы** — все шесть диаграмм синтаксически валидны (flowchart с текстовыми метками рёбер `-. ... .->`, sequenceDiagram с `Note over L,N`, decision-узел `{...}` и обратное ребро в project-spec). Терминальные узлы K и J в схеме `http-contract-execution-boundary.md` без слияния с основным потоком — допустимо, рядом есть явный дисклеймер «диагностическая карта, а не точная реализация».
5. **Coverage** — дубли в coverage kata и project-spec (один target с ролями practice+assess / integrate+assess) выглядят намеренными; все цели существуют в `level-outcomes.md`, роли согласуются с типами документов (reference/explain/probe/practice/integrate).
6. **Терминологическая дисциплина** — соблюдена: learn/compatible-api-change явно мотивирует отказ от producer/consumer в пользу API caller/provider; interview использует consumer/producer в собственном словаре без конфликта (контекст межкомандной миграции); «контекстно-зависимые слова» (`shape`, `assumption`, `boundary`) везде привязаны к конкретному объекту и определены в локальных словарях.
7. **Даты в примерах** (2026-08-18, 2026-08-20) согласованы с `updated: 2026-08-15` — примеры «из будущего» относительно даты проверки, что корректно для окон доставки.

## Verdict

**PASS** — слайс готов к использованию. Технически неверных утверждений не найдено: все проверяемые версии-sensitive утверждения (OAS 3.1.2/3.2.0, `openapi: 3.1.0` у FastAPI, поведение Pydantic v2 с Optional-полями, dependency scopes FastAPI, семантика полей RFC 9457, кэширование по `Vary`) подтверждены первичными источниками. Пять minor-находок носят редакционный характер (дополнение ссылки на RFC 9111, унификация примеров, метаданные `last_verified`, актуализация URL Pydantic, оговорка о кэшируемости POST) и не блокируют прохождение материалов. Рекомендуется закрыть Minor-1–Minor-4 в следующей итерации правок.
