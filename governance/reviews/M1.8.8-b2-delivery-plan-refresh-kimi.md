## Отдельный вывод по S05, A3 readiness и границам authorization slice

### 1. S05 — действительно следующий лучший bounded package

Выбор подтверждается. Решающие факторы, воспроизводимые из принятых источников:

- **Readiness:** S05 — единственный из сильных кандидатов, чей internal hard prerequisite (HTTP contract) уже подтверждён execution evidence (L2/L3 non-probe). S14 и S15 не имеют internal hard edges, но оба упираются в неподтверждённые внешние baseline (A3 threat/security + B6 context для S14; B3 cache-store для S15) — и, что важнее, оба требуют сужения scope ещё до authoring.
- **Новое уникальное coverage:** S05 открывает первый собственный flow not-started модуля и единственный путь к Identity L1–L3 (Identity L3 обязателен обеим RoleViews). S08 дал бы только L4, недостижимый локальным flow, при почти гарантированном дублировании R2–R5. Completion-tail кандидаты (performance 14/14, HTTP runtime 11/11) требуют module-gate decisions и L4 adoption evidence, а не нового локального slice.
- **Boundedness:** центральное действие S05 — один mechanism (object-level authorization на одном read path); S14 по тексту `scenarios.md` объединяет operation cost, quota и SSRF target boundary — несколько механизмов, что план честно фиксирует как причину отклонения.
- Паритет role value (Identity/Abuse/Cache L3 все обязательны обеим RoleViews) означает, что выбор не «S05 важнее», а «S05 достижим и ограничим сейчас» — план аргументирует именно так и не завышает различие.

### 2. Минимальный A3 identity/trust/security readiness contract до authoring

Достаточный минимум (совпадает с составом Gate 0 в плане; детализация — для будущего authoring package):

1. один token/claims substrate с зафиксированными правилами проверки (подпись/dоверенный issuer, audience, expiry) — на концептуальном уровне, без обучения криптографии и без реализации issuance/rotation;
2. явная trust boundary: какой компонент аутентифицирует и где identity становится доверенной server-side;
3. правило отображения claims → subject/tenant context (единственный доверенный источник);
4. одна object-authorization rule, связывающая tenant ownership объекта с контекстом, при client-supplied ID как недоверенном входе;
5. одна выбранная denial/existence-leakage semantics (единый not-found против различения forbidden) с продуктово-security обоснованием;
6. минимальный audit context (см. B-3).

Все пункты проверяются по первичным источникам A3 (clusters `identity-access`, `tls-pki`, `threat-modeling-appsec` по `curriculum/tracks/catalog/a3-networks-linux-security.md`), не создают placeholder capability IDs и не становятся internal hard edge.

### 3. Gate 0 внутри S05 package достаточен; отдельный prerequisite package не нужен

Аргументы: (а) прецедент M1.8.7 — B5/RabbitMQ readiness был Gate 0 внутри authoring package и принят без отдельного пакета (acceptance M1.8.7, intake M1.8.8); (б) содержимое gate — решения и verification records, а не учебный flow, поэтому отдельный package дал бы artifacts без outcome coverage; (в) внешних A3 capability IDs ещё не существует, а `prerequisites.md` запрещает placeholder IDs — отдельный package не смог бы оформить зависимость строже, чем baseline specification. Условие достаточности: Gate 0 выполняется **до** первого учебного artifact и обладает правом остановки («зависимый authoring не запускается») — оба требования в плане зафиксированы.

### 4. Границы, удерживающие S05 от поглощения S14 и общего IAM/security курса

План выставляет все необходимые границы, и их достаточно:

- один tenant-scoped Orders read path, один primary scenario, ноль supporting scenarios;
- primary capability только `integrate-identity-access-control`; Abuse capability не получает ни relationships, ни места в project spec;
- S14-механизмы (quota, operation cost, SSRF) — в non-goals и в отвергнутых альтернативах как отдельный будущий package после выбора одного abuse mechanism;
- authentication — substrate assumption Gate 0, а не учебная тема; IdP, IAM infrastructure, cryptography, token lifecycle — non-goals;
- A3 используется как внешний readiness record по первичным источникам, а не как преподаваемый курс внутри slice;
- Identity L4 и любой cross-service/cross-team scope не заявляются;
- C1/A1 переиспользуются ссылками без новых coverage relationships.

Дополнительных границ reviewer не требует; B-3 усиливает проверяемость audit context внутри уже заявленного Gate 0.
