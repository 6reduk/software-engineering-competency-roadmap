## Findings

### F-1 (minor) — `claim/lease` publisher не объяснён нигде в slice

- artifact: `learn/transaction-boundary-failure-windows.md:93`; затрагивает `project-spec/resilient-order-confirmation.md:129`
- criterion: structure
- finding: learn сопровождает Mermaid оговоркой «Схема упрощает claim/lease publisher и HTTP error mapping», а project требует в decision record «способ claim/retry publisher и поведение при нескольких publisher instances». Термин claim/lease (захват pending-записи одним инстансом publisher с ограниченной арендой) нигде не расшифровывается и отсутствует в словаре learn.
- evidence: grep по пяти файлам — `claim` встречается только в этих двух местах без пояснения; локальный словарь learn покрывает publisher/sink, tombstone, fingerprint, reconciliation, но не claim/lease. Редакционный стандарт (09, раздел 4) требует расшифровки неоднозначных терминов при первом употреблении и запрещает контекстно-зависимые слова без уточнения объекта.
- impact: читатель learn не может понять, что именно упрощает схема, а участник проекта может неверно истолковать обязательный пункт decision record — например, принять claim за обязательный распределённый lock либо проигнорировать проблему нескольких инстансов. На техническую корректность модели это не влияет.
- recommendation: одна фраза при первом упоминании в learn (например, «захват записи одним инстансом publisher на ограниченное время (`claim/lease`)») и/или строка в словаре; достаточно правки одного файла.

### F-2 (note) — необъяснённые вторичные англицизмы вопреки обратной презумпции

- artifact: все пять файлов; первично `learn/transaction-boundary-failure-windows.md:51,62`, `interview/commit-succeeded-event-unknown.md:127,136`, `kata/recover-order-confirmation.md:50`
- criterion: structure
- finding: `replay` используется как самостоятельный термин во всех жанрах (replay result, same-key replay, replay-ит), но не объяснён при первом употреблении и отсутствует в словаре; `crash window` (kata:50) и вставки вида «already confirmed order» в русской фразе (learn:51, interview:136) также не раскрыты. Соседние принятые материалы для аналогичных понятий дают русское объяснение с английским термином в скобках.
- evidence: 09-editorial-standard.md, раздел 4: для вторичных англицизмов действует обратная презумпция в пользу русского слова; повторяющиеся смыслообразующие термины полагается включать в локальный словарь.
- impact: низкий — смысл восстанавливается из контекста, но это систематическое отклонение от принятого терминологического правила, заметное читателю, открывшему файл напрямую.
- recommendation: при ближайшей правке добавить `replay` в словарь learn и заменить «already confirmed order» / «crash window» русскими формулировками с термином в скобках.

### F-3 (note) — нумерация контрольных точек не отображена на идентификаторы F0–F3

- artifact: `README.md:39-44`, `learn/transaction-boundary-failure-windows.md:107-116`, `kata/recover-order-confirmation.md:66`, `project-spec/resilient-order-confirmation.md:62-69`
- criterion: structure
- finding: README и learn описывают «четыре контрольные точки» порядковым списком 1–4, project вводит идентификаторы F0–F3, kata задаёт fault hook именем `after_commit_before_publish`. Соответствие «точка 2 = F1, точка 3 = F2 = crash window kata» нигде не зафиксировано явно.
- evidence: сопоставление восстанавливается только по смыслу формулировок; единый fault-ID словарь в slice отсутствует.
- impact: низкий — содержание точек согласовано, но участнику, идущему по маршруту learn → kata → project, приходится самостоятельно устанавливать эквивалентность обозначений; риск неверного вывода минимален.
- recommendation: в project-таблице F0–F3 или в README указать маппинг одной строкой (например, «точки 1–4 соответствуют F0–F3; kata работает с F2»).

## Вывод по двум L3 evidence

Transaction L3 и Idempotency L3 — разные доказательства по faults, observations и acceptance criteria:

- **Transaction L3 (Evidence A, project:71-84):** faults — F0–F3 (частичный abort, unknown commit, crash до publish, потерянный ack); observations — состояние authoritative PostgreSQL и sink, обнаружимость pending event после restart, повтор того же `event_id`; acceptance — совместная durability order/result/event, 100% обнаружения F2, различение commit/unknown commit/publish/unknown publish в state transitions и logs. Interview зеркалит это отдельным вопросом 3 (failure-window map и recovery, interview:86-118).
- **Idempotency L3 (Evidence B, project:86-107):** faults — concurrent same-key race и retry после F1; observations — число committed results, business transitions и event identities, replay/conflict/retention responses; acceptance — не более одного `draft → confirmed`, детерминированные `409`, tombstone без повторной мутации. Interview зеркалит отдельным вопросом 5 (interview:140-158).

Оба раздела явно запрещают перекрёстный зачёт (project:84,107), kata не претендует на L3 (kata:97), а rubric interview фиксирует, что `probe` не заменяет выполненный experiment (interview:191). Требование раздельности выполнено.

## Вывод по единому контракту и различию kata/project

**Единый контракт подтверждён.** Программная и ручная сверка пяти файлов: `POST /orders/{order_id}/confirm` с пустым телом; UUID `Idempotency-Key`; fingerprint = method + `order_id`; `200` с `operation_id`, `order_id`, `status="confirmed"`; событие с `event_id`, `event_type="OrderConfirmed"`, `operation_id`, `order_id`, `confirmed_at`; 24-часовой retention с tombstone `409 idempotency_key_expired`; `409 idempotency_conflict` и `409 order_not_draft`; три сущности `orders`/`operation_results`/`order_events`; `READ COMMITTED`, `fsync=on`, `synchronous_commit=on`, autocommit + один внешний `with conn.transaction():` — идентичны во всех пяти файлах и в B3 readiness record. Противоречий не найдено.

**Kata и project дают разные наблюдаемые результаты.** Kata: один crash window F2, minimal scaffold участника, 10 прогонов (5 контрольных + 5 fault), evidence — recovery pending event и replay/conflict/expiry responses на уровне L1/L2. Project: четыре fault points F0–F3 включая unknown commit, реальный PostgreSQL, restart/recovery, 20 concurrent duplicate trials, retention, расширенный measurement envelope, decision record и два раздельных L3 experiment. Различие — не число терминов, а ширина failure windows и класс evidence; граница заявлена с обеих сторон (kata:50,97; project:84,107) и не размыта.
