# M1.8.10 — решение оркестратора по review B2 delivery plan

Консолидированный verdict `accepted_with_changes` принят: `0 blocker / 1 major / 1 minor / 3 note`. Механический аудит подтверждён без расхождений: 37 accepted artifacts, 203 relationships (`17 reference + 186 outcome-level`), 52/69 covered, 17 uncovered, 7 probe-only, Identity-aware Boundaries `not-started → partial`, состояния `0 complete / 8 partial / 2 not-started / 0 blocked`.

M1.8.10 пока не считается принятым: сначала автор планов закрывает C-1–C-4 по пакету [`M1.8.10a-delivery-plan-findings-correction.md`](../work-packages/M1.8.10a-delivery-plan-findings-correction.md), затем оркестратор выполняет verification- и acceptance-pass.

## Решение по Abuse L2

Перечень evidence criteria Abuse L2 — `request/cost bounds`, `field exposure`, `quota/rate`, `untrusted target rules` — трактуется как обязательная **проверка применимости категорий** для выбранного endpoint, а не как универсальное требование внедрить все четыре механизма в каждом сервисе.

Чтобы будущий S14 slice мог правдиво заявить Abuse L2, Gate 0 и учебные artifacts должны для каждой категории зафиксировать одно из двух:

1. категория применима — указаны threat case, control и наблюдаемое evidence;
2. категория неприменима в закреплённом contract — названы причина, граница решения и остаточный риск.

Для текущего bounded замысла ожидается следующая исходная диспозиция, которую Gate 0 обязан подтвердить либо изменить по фактическому substrate:

- `request/cost bounds` — центральное evidence: server-owned cost unit, admission до дорогой работы и request-shape bypass tests;
- `field exposure` — фиксированная server-owned export schema либо явный allowlist; произвольный выбор чувствительных полей не остаётся неразобранным;
- `quota/rate` — distributed/time-based quota не реализуется; явно фиксируется, что per-operation ceiling не защищает от множества отдельных допустимых запросов;
- `untrusted target rules` — callback/target отсутствует в contract или отвергается как неизвестный вход; SSRF target validation этим не проверяется и остаётся отдельным долгом.

Если Gate 0 не сможет честно заполнить эту матрицу, Abuse L2 запрещено добавлять в coverage будущего slice. Abuse L1 и L3 оцениваются по собственным evidence criteria и не возникают автоматически из названия сценария.

## Минимальный readiness contract будущего S14

Gate 0 внутри authoring package достаточен; отдельный prerequisite package не требуется. До первого учебного artifact он обязан закрепить:

- один воспроизводимый export endpoint и request-shape family;
- trusted tenant context, переиспользуемый из S05;
- server-owned cost unit, вычислимый до дорогой работы;
- threat model operation-cost amplification и tenant consequence;
- applicability matrix четырёх категорий Abuse L2;
- legitimate, at-limit, over-limit и bypass populations;
- workload, duration, dependency behavior и точку измерения;
- admission/rejection contract и измеримый threshold;
- audit/disclosure limits;
- recovery observation после снятия нагрузки;
- stop-condition: невычислимый cost, shared counter, distributed quota или coordination protocol возвращают вопрос оркестратору и требуют нового readiness decision.

Gate 0 перечисляет конкретные классы источников: официальный OWASP API Security материал по unrestricted resource consumption; официальную документацию выбранного framework по parsing, validation и binding; официальную документацию выбранного storage/runtime по стоимости и ограничениям операции; применимые HTTP/RFC источники для error contract; локальные воспроизводимые измерения отдельно маркируются как экспериментальное evidence, а не внешний нормативный источник.

## Условия acceptance-pass

- C-1–C-4 имеют отдельные видимые исправления и mapping в handoff автора.
- Числа, registry, 69 outcome rows, memberships, states и hard DAG не меняются.
- S14 остаётся одним operation-cost central action; SSRF, distributed quota и platform rate limiting не добавляются.
- Abuse L2 остаётся условным кандидатом до заполнения applicability matrix в Gate 0; запрет на relationship при неполном evidence записан явно.
- План остаётся в `review` до оркестраторского acceptance-pass.
- После verification оркестратор переводит план и связанные governance-артефакты в `accepted`, фиксирует решение программы и создаёт отдельный S14 authoring package. Module gate автоматически не присваивается.
