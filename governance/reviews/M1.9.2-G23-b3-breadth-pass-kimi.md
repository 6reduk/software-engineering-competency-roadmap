# M1.9.2 — G23 общий review полного B3 breadth-pass, профиль B (kimi)

## Профиль, scope и способ проверки

Профиль B — learning navigation, roles and human readability по `governance/work-packages/M1.9.2-G23-b3-breadth-pass-review.md`. Предметная корректность engine internals (профиль A) здесь не дублируется; технические утверждения проверялись только на отсутствие runtime claims и согласованность соседних ownership.

Способ независимой проверки:

1. Полностью прочитаны REVIEW-PROTOCOL, оба work package M1.9.2, orchestrator intake, acceptance G22 как контракт reference, все семь файлов `curriculum/tracks/b3/`, track skeleton B3 и границы B2/B5/B7, четыре файла метамодели, модель уровней, role-summary, обе routes и принятый editorial standard `docs/09`.
2. Механически пересчитаны сущности и связи (см. раздел пересчёта): modules, capabilities, outcomes по уровням, scenarios, role links по категориям, рёбра `Requires`/`Related`. Все счётчики совпали с заявленными в README и intake.
3. Механически разрешены все относительные ссылки и HTML/GitHub-anchors (включая кириллические заголовочные anchors) между семью файлами и на внешние workspace-цели: 0 неразрешённых. Каждый role-link outcome ID, scenario/prerequisite capability ID и Develops-список сверены с каталогами: рассинхронизации нет; Develops покрывают ровно 23 capabilities.
4. Ацикличность hard DAG проверена независимо: 23 узла, 8 рёбер `Requires`, все цели рёбер не имеют собственных `Requires`, следовательно цикл невозможен; `Related` (12 связей) в DAG не входит.
5. Каждая из 79 ролевых связей прочитана и сопоставлена с формулировкой соответствующего outcome; причины связей проверены на предметность (finding B-1).
6. Отчёт профиля A на момент этого анализа в `governance/reviews/` отсутствовал и не читался. Авторский handoff и intake использованы как карты проверки, а не доказательства.

Эксперименты не запускались; отчёт не подтверждает Gate 0, среду, версии engines и readiness.

## Verdict

`accepted_with_changes` — `0 blocker / 1 major / 3 minor / 2 note`.

Со стороны профиля B blueprint пригоден как первая полная карта B3: навигационный путь cluster → module → capability → outcome → scenario прослеживается без битых ссылок, роли различены содержательно, compactness выдержана. Единственный major (B-1) — шаблонные, непредметные причины ролевых связей: intake I-3 подтверждается фактом, и это следует закрыть до acceptance либо оформить явным решением. Blocker нет.

## Пересчёт сущностей и связей

Выполнен независимо по текущим файлам; совпадает с заявленным в README и intake:

- modules: 11 определений, 11 уникальных ID;
- capabilities: 23 строки, 23 уникальных ID; все primary clusters и primary modules разрешаются; Develops-списки modules покрывают ровно 23 capabilities без пропусков и лишних;
- LevelOutcomes: 70 строк, 70 уникальных ID; уровни: L1 = 23, L2 = 23, L3 = 23, L4 = 1 (`protect-store-invariants-l4-adopt-cross-team-policy`), L5 = 0;
- scenarios: 13 (TC01–TC03 + десять batch);
- role links: 79 строк = 42 required + 19 deepening + 18 conditional (reference: 6/3/2; batch: 36/16/16); каждая связь ссылается на существующий outcome ID;
- hard DAG: 23 узла, 8 рёбер `Requires` (1 reference + 7 batch); направление зависимая → prerequisite выдержано; все цели рёбер не имеют собственных `Requires`, циклов нет; пример порядка подан как «один из допустимых», не как единственный;
- `Related`: 12 связей (2 reference + 10 batch), явно исключены из DAG, скрытого hard order в формулировках «Почему не hard» не обнаружено;
- гигиена: YAML front matter всех семи файлов разбирается; `status: review`, `updated: 2026-09-09` везде; UTF-8 без BOM; один перевод строки в EOF; trailing whitespace и conflict markers отсутствуют; все относительные ссылки и anchors (включая кириллические) разрешаются; полей `coverage`, `versions`, `verified_baseline` нет.

## Ответы на обязательные вопросы

1. **Можно ли принять состав `11 modules / 23 capabilities / 70 outcomes / 13 scenarios` как первый полный B3 capability blueprint?** Да, после закрытия или явного disposition major B-1. Состав полон по skeleton, счётчики сходятся при независимом пересчёте, каждый кластер представлен навигационным домом и рабочим входом. Со стороны профиля B дефектов полноты нет; есть дефект содержательности ролевых причин (B-1) и три minor навигационно-редакционного свойства.
2. **Где симметрия batch помогает навигации, а где скрывает пробел или искусственное разделение?** Помогает: предсказуемая лестница L1–L3 и единый паттерн «модуль = законченный результат» делают десять новых кластеров сканируемыми; таблица README читается как карта. Скрывает: (а) полное покрытие capabilities ролевыми связями с шаблонными причинами маскирует отсутствие предметного обоснования (B-1); (б) одинаковые outcome-суффиксы маскируют различие действий в таблицах (B-3); (в) жёсткое «один module на кластер» оставляет maintenance-темы без cross-reference из storage-модуля (B-6). Искусственного разделения capabilities не обнаружено: в `security-operations` и `operational-nonrelational-stores` (отмечены intake I-1) действия различимы по наблюдаемому результату.
3. **Правдивы ли L1–L4, hard DAG, внешние prerequisites и ownership соседних вертикалей?** Да. Все 60 новых outcomes выдерживают уровневый контракт: L1 — объяснение наблюдаемого поведения с поддержкой, L2 — самостоятельное bounded действие, L3 — выбор/диагноз при неопределённости с защитой trade-offs; ни один новый L3 не сводится к «более длинному L1» — у каждого есть конкурирующие причины или выбор. Единственный L4 — сохранённый reference с названным межкомандным результатом; отсутствие новых L4/L5 обосновано отсутствием самостоятельного результата такого масштаба. DAG ацикличен (независимый обход), восемь `Requires` содержательно обоснованы, ложного утверждения о единственном topological order нет. Внешние prerequisites заданы словами и ссылками на существующие tracks без выдуманных capability IDs. Ownership согласован с track-файлами: B2 владеет application persistence/ORM, B5 — общими replication/sharding algorithms, B7 — cross-system RTO/RPO и incident process; store-specific replication/failover и restore/PITR остаются у B3, как записано в non-goals B5 и B7. Пересечений не выявлено.
4. **Полезны ли две RoleViews как hiring/learning baseline, или отдельные связи нужно удалить, понизить либо повысить?** Каркас полезен: проекции предметно различаются — Backend required сосредоточен на самостоятельном расследовании и локальном выборе (anomalies L3, conflicts L3, query-plans L3, compose-queries L3), Architecture — на защите договоров и границ (constraints L3, durability L3, replica L3, partitioning L3, store-model L3) при исполнительских операциях, вынесенных в conditional с явным «координация специалистов не требует исполнения». Backend не превращён в DBA: crash-recovery/failover/backup/restore/maintenance required только на L1 (распознать и передать), исполнение — conditional с названной ответственностью. Но 25 шаблонных причин (B-1) делают часть baseline непроверяемой по смыслу; до acceptance пересмотреть как минимум: повысить `design-store-partitioning-l2` у Backend из deepening в required либо обосновать, переформулировать conditional `validate-nonrelational-store-contract-l2` как ответственность, удалить связи, для которых предметная причина не находится.
5. **Какие findings обязательно закрыть до acceptance, а какие следует перенести в будущий content/Gate 0 без задержки breadth-pass?** До acceptance: B-1 (ролевые причины) и явное решение по B-3 (суффиксы — последняя возможность дешёвого переименования ID). Все engine/version readiness questions уже корректно отделены в `prerequisites.md` как future readiness questions и принадлежат будущему Gate 0, а не этому gate.
6. **Какие 1–2 кластера лучше углубить первыми?** Рекомендую оркестратору **SQ01 (sql-querying)** первым: ежедневная применимость для целевой роли максимальна, наблюдаемый результат компактен и проверяем данных-в/данных-out, технический риск версий и среды минимален — Gate 0 почти вырожден. Вторым — **SE01 (schema-evolution)**: высокая практическая ценность (каждая миграция с сосуществующими writers), хорошо проверяет границу B2/B3, но требует будущей проверки конкретных DDL/locking semantics — осмысленный первый кандидат на полный цикл с Gate 0. BR01 ценен для различения «копия есть / данные восстановлены», но требует выделенной среды и пригодной цепочки restore — выше стоимость подготовки при сопоставимой учебной отдаче; оставить третьим.
