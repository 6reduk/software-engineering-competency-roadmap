# M1.9.0 — G21 профиль A: B3 technical correctness and experimental causality

## Профиль, scope и способ проверки

Профиль A — техническая корректность и экспериментальная причинность. Проверяемый artifact — `governance/planning/intakes/b3-transaction-isolation-boundary.md` (далее intake) на границе B2 application transaction и B3 store isolation. Проверка выполнена независимо: прочитан весь context manifest work package, включая track skeletons B2/B3/B5/B6/B7, prerequisites, S07/S15 (README, learn, project-spec), обе RoleViews, модель уровней, learning flow, content/editorial standards и метамодель. Отчёт профиля B не существовал и не читался на момент завершения анализа; orchestrator intake использован только как карта проверки, а не как доказательство.

Первичные источники проверены повторно 2026-09-09:

- PostgreSQL 18 [Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html) — таблица 13.1, поведение REPEATABLE READ и SERIALIZABLE, пример rw-dependencies, SQLSTATE `40001`, predicate locking;
- PostgreSQL 18 [Explicit Locking](https://www.postgresql.org/docs/18/explicit-locking.html) — раздел Deadlocks (основание отклонённого кандидата 2);
- [Psycopg Transactions management](https://www.psycopg.org/psycopg3/docs/basic/transactions.html) — implicit transaction, savepoint-ловушка `transaction()`, transaction characteristics, предупреждение о serialization failures.

Эксперимент не выполнялся; ни одно Gate 0-условие не считалось подтверждённым. Все выводы ниже — оценка проекта будущей проверки, а не её результаты.

## Verdict

`accepted_with_changes`: **0 blocker / 0 major / 2 minor / 3 note**.

Предметная модель, заявленный schedule и одиночная смена механизма технически корректны и поддерживают причинный будущий эксперимент. Два minor — дешёвые уточнения текста и верификационной дисциплины, не требующие пересмотра выбора или дизайна.

## Findings

### A-1 — неточная версия dev-документации Psycopg

```yaml
severity: minor
artifact: governance/planning/intakes/b3-transaction-isolation-boundary.md
criterion: freshness
finding: Intake утверждает, что страница Psycopg Transactions management «отображает документацию 3.3.6.dev1». При независимой проверке 2026-09-09 страница отображает «psycopg 3.3.4.dev1 documentation».
evidence: Конкретный dev-номер в intake фактически неверен на дату проверки и в любом случае нестабилен между сборками документации. Сама оговорка (dev-версия не подтверждает применимость к ещё не выбранному stable driver) остаётся верной и ценной.
recommendation: Заменить конкретный номер на формулировку вида «страница отображает текущую dev-версию документации Psycopg» либо исправить номер и повторно сверить после закрепления stable driver в Gate 0. Инженерный вывод и границы intake не меняются.
```

### A-2 — явно не зафиксировано, что чтение и запись участника выполняются в одной транзакции

```yaml
severity: minor
artifact: governance/planning/intakes/b3-transaction-isolation-boundary.md
criterion: correctness
finding: Ключевое условие внутренней валидности опыта — предметное чтение каждого actor выполняется внутри той же транзакции, что и его запись, — лишь подразумевается («обе сессии сначала подтверждают чтение... только затем разрешаются изменения», модель «операции», поведение Psycopg по умолчанию), но не сформулировано явно.
evidence: Если будущая оснастка прочитает состав дежурства в autocommit-режиме вне транзакции, а запись выполнит отдельной write-only транзакцией, defect всё равно проявится (обе записи в разные строки фиксируются), но fixed ложно провалится: у write-only транзакций нет rw-зависимостей, обе фиксируются и при SERIALIZABLE, инвариант нарушен. Это дало бы ложный вывод «SERIALIZABLE не помогает», вызванный дефектом оснастки, а не поведением store.
recommendation: Добавить в раздел evidence одно предложение: чтение-решение-запись каждого участника выполняются в одной транзакции, и Gate 0 обязан подтвердить привязку наблюдаемого чтения к transaction ID транзакции, выполнившей запись (это частично уже покрыто категориями Transaction settings и Store observations — достаточна явная формулировка).
```

### A-3 — дисциплина фиксации snapshot в control

```yaml
severity: note
artifact: governance/planning/intakes/b3-transaction-isolation-boundary.md
criterion: correctness
finding: В PostgreSQL REPEATABLE READ snapshot фиксируется первым non-transaction-control statement транзакции. Intake гарантирует для control только «операция А завершается до первого предметного чтения Б»; случайный более ранний statement в транзакции Б (например, настройка или диагностика через SELECT) закрепил бы snapshot до commit А.
evidence: В defect/fixed барьер делает проект робастным: любой snapshot, взятый до разрешения записей, корректен. В control такой случай проявился бы видимым отказом (Б снял бы себя, инвариант нарушен, проверка «решений обоих участников» это ловит), то есть дизайн самокорректен, но источник сбоя был бы неочевиден.
recommendation: На уровне Gate 0 (категория «Координация») потребовать, чтобы предметное чтение было первым statement транзакции либо чтобы фиксирующий snapshot statement протоколировался. Изменение текста intake не обязательно.
```

### A-4 — атрибуция термина «write skew»

```yaml
severity: note
artifact: governance/planning/intakes/b3-transaction-isolation-boundary.md
criterion: practice
finding: Официальная документация PostgreSQL не использует термин «write skew» — только «serialization anomaly». Intake корректно приписывает PostgreSQL лишь допустимость serialization anomalies при REPEATABLE READ, а «write skew» определяет в собственном словаре как имя класса дефекта.
evidence: При authoring learn-материалов есть риск приписать термин официальной странице.
recommendation: Сохранить текущую дисциплину атрибуции в будущих материалах: заявленное для PostgreSQL — «serialization anomaly»; «write skew» — литературное имя класса, вводимое локально.
```

### A-5 — различение SQLSTATE как дешёвая проверка валидности fixed

```yaml
severity: note
artifact: governance/planning/intakes/b3-transaction-isolation-boundary.md
criterion: practice
finding: Intake требует сохранять SQLSTATE/error и стадию, не называя ожидаемый код. Для fixed ожидаем сигнал serialization failure (SQLSTATE 40001); deadlock (40P01) в заявленном расписании невозможен — записи идут в разные строки, явные блокировки запрещены.
evidence: Появление 40P01 вместо 40001 означало бы нештатное lock-взаимодействие, то есть скрытый второй механизм, разрушающий причинность сравнения.
recommendation: При будущем исполнении трактовать код ошибки как различающий сигнал; вносить перечисление кодов в intake не требуется.
```

## Ownership и отличие от S07/S15

Карта ответственности согласована с принятыми track skeletons. B2 сохраняет application operation, commit/rollback boundary, идемпотентность и внешние эффекты; B3 владеет MVCC/visibility/locks/anomalies/store signals — выбрасывающее действие лежит в `b3.cluster.transactions-concurrency`. B5 не проектирует межсистемную coordination для одного store; B7 не превращает локальную ошибку транзакции в incident/DR; B6 присутствует только как условная зависимость среды. Placeholder capability IDs не создаются; intake уровней и outcomes не назначает.

Отличие от S07 существенно, а не формально: S07 исследует повтор и конкурентный дубликат одной application command (same-key/different-key race, условный `UPDATE` одной строки, recovery публикации); выбранное действие исследует взаимозависимые решения двух разных операций над разными строками и общий инвариант, защищаемый store. От S15 отличие также сохраняется: прикладной cache и freshness не переносят готовность к изоляции в одном хранилище. Прикладная операция снятия с дежурства задана и не перепроектируется.

## Причинность control/defect/fixed

Дизайн образует чистую причинную цепочку. Control (последовательное исполнение, RR): инвариант сохранён операционным правилом — показывает, что правило работает без конкуренции. Defect (барьер после обоих чтений, RR): единственное отличие от control — расписание; обе транзакции фиксируются без exception, инвариант нарушен — аномалия вызвана concurrent snapshot, а не логикой операции. Fixed (то же расписание и барьер, только обе изоляции SERIALIZABLE): единственное отличие от defect — механизм; конфликт переносится в store signal (serialization failure, `40001`), инвариант сохранён. Четвёртая ячейка (последовательно + SERIALIZABLE) не требуется и не заявлена. Negative check и отдельная новая попытка закрывают ложные тривиальные объяснения («запрет всех записей», «retry как решение»). Барьер после обоих чтений гарантирует, что оба snapshot предшествуют обеим записям, поэтому результат не зависит от случайного порядка исполнения; случайный sleep отвергнут. Два условия нуждаются в явности при будущей реализации: чтение и запись участника в одной транзакции (A-2) и дисциплина первого statement в control (A-3) — оба закрываются категориями Gate 0.

## Ответы на обязательные вопросы профиля A

1. **Воспроизводим ли write-skew defect при заявленном schedule?** Да. При RR с обоими чтениями до разрешённых записей и записями в разные строки ни одна транзакция не встречает документированный same-row abort, обе фиксируются без exception, committed state нарушает инвариант. Барьер по сигналу чтений делает расписание детерминированным; условие воспроизводимости — чтение внутри транзакции каждого участника (A-2) и отключённые автоматические повторы (intake это требует).

2. **Может ли fixed дать требуемый store conflict без второго механизма?** Да. Чтение А строки Б против записи Б этой строки (и симметрично) образует цикл rw-зависимостей, который отслеживает SSI; документированная гарантия не позволяет такой паре обе зафиксироваться — одна получает serialization failure `40001`. Смена обеих транзакций на SERIALIZABLE необходима и достаточна; жертва и точка обнаружения не предписываются, что соответствует документации. Ложные срабатывания SSI возможны, но ложных пропусков аномалии гарантия не допускает.

3. **Минимальные observations для причинного вывода?** (а) прочитанные каждым участником значения (включая строку другого) с привязкой к его транзакции; (б) порядок барьерных сигналов, доказывающий «оба чтения до любых записей»; (в) эффективные настройки обоих actors — уровень изоляции внутри транзакции, autocommit, отсутствие внешней savepoint-обёртки и скрытого retry; (г) терминальный исход каждой транзакции с SQLSTATE и стадией; (д) итоговый committed state от независимого наблюдателя; (е) для новой попытки — свежее чтение и бизнес-отказ, различённые с store-конфликтом. Intake перечисляет все шесть; A-2 рекомендует сделать (а)+(в) явно одним условием.

4. **Разведены ли store conflict, rollback и прикладной отказ?** Да. Исходный конфликт — store signal с сохранённым кодом и стадией, завершающийся rollback одной транзакции; отдельная новая попытка объявлена явно, читает свежие данные и ожидаемо заканчивается бизнес-отказом (последний дежурный остаётся); журнал различает классы отказов. Универсальная retry-подсистема не проектируется — это соответствует документированному требованию повторить отвергнутую транзакцию целиком и не полагаться на данные, прочитанные в откаченной транзакции.

5. **Достаточны ли readiness-категории и что уточнить до authoring?** Восемь категорий достаточны как чек-лист Gate 0: store/версия/driver, topology и transaction ownership, transaction settings, durability-неприменимость, координация, store observations, reset/cleanup, источники. До authoring требуют конкретизации: способ проверки эффективного уровня изоляции внутри транзакции (при `isolation_level=None` Psycopg наследует server default); механизм read-сигналов и их отказы; доступность snapshot/txid-следа и привязка чтения к транзакции записи (A-2); повторная сверка страницы Psycopg с закреплённым stable driver (A-1). Это рабочие пункты Gate 0, не пробелы выбора.

6. **Можно ли принять intake после disposition findings, не подтверждая Gate 0 и не выполняя эксперимент?** Да. Intake — planning artifact; маркировка NOT_RUN и неподтверждённость всех readiness-категорий — его честное состояние, а не дефект. Оба minor исправляются текстом и не затрагивают выбранное действие, модель или причинную архитектуру сравнения.

## Ответы на open questions work package

1. **Достаточно ли описано получение snapshot?** Для defect/fixed — да: барьер после обоих чтений гарантирует, что оба snapshot предшествуют обеим записям, независимо от incidental statements. Для control — достаточно на уровне плана, но future harness должен закрепить дисциплину первого statement (A-3). Планировочная высота текста адекватна.

2. **Достаточны ли store observations без полного dependency graph?** Да. Значения чтений + барьерный порядок + оба терминальных исхода + SQLSTATE + committed state причинно объясняют конфликт. SIRead-блокировки видны в `pg_locks`, но внутренний граф SSI не экспонирован; intake правильно не требует его целиком и прямо фиксирует это в readiness.

3. **Следующий результат — blueprint или bounded content-planning package?** С технической стороны дополнительное решение сверх Gate 0 не требуется: минимальное предшествующее authoring решение — закрепление точного PostgreSQL build, stable Psycopg, координационной оснастки и способа верификации эффективных настроек, то есть сам Gate 0, плюс disposition findings A-1/A-2. Bounded content-planning package с Gate 0 может идти напрямую; полный B3 capability blueprint технически не обязателен для одного выбранного действия, хотя оркестратор вправе создать его для размещения будущих capabilities. Создание следующего пакета — отдельное решение оркестратора, не reviewer.

## Решение по принятию M1.9.0

M1.9.0 можно принимать после disposition двух minor (A-1, A-2) без подтверждения Gate 0 и без исполнения эксперимента. Блокирующих условий acceptance gate G21 по технической причинности нет: различие B2 application transaction и B3 store isolation правдиво, выбранное действие конкретно, bounded и отличимо от S07/S15, control/defect/fixed проектируют причинный будущий эксперимент и не выдаются за выполненный evidence, readiness-категории достаточны и ни одна не объявлена подтверждённой. Minor/note передаются оркестратору для decisions.
