## Консолидированные findings и диспозиции

Источник: 🔵 — GLM (профиль A); 🟡 — Kimi (профиль B). Полные evidence и рекомендации — в исходных review; здесь сжатая запись с предлагаемой диспозицией. Окончательное решение за оркестратором.

### Major

**C-1 (🔵 GLM-A-1 + 🟡 Kimi F-B-1, объединены). GET/SET failure points по разные стороны source read и их `source_read` counters сформулированы противоречиво.**
Gate 0 («Ошибка/timeout `GET` или `SET` даёт fail-closed `503 cache_unavailable`; request не идёт в PostgreSQL»), learn («ошибка `GET` или `SET` …», «не обращается к PostgreSQL после cache error») и interview (ответ на вопрос 6: «`503` сохраняет source reads равными нулю») объединяют две точки отказа с разными исходами: ошибка `GET` (включая повторный `GET` в критической секции) происходит до source read и даёт `source_read=0`; ошибка `SET` происходит после — runtime-подтверждено `source_read=1` на одиночный request и `32` на burst (каждый waiter последовательно становится владельцем; amplification ограничена числом requests, не 0 и не ≤1). Project-spec называет сценарий «Redis `SET` не выполнен», но не задаёт ожидаемый счётчик. Это open question 1 intake и anti-pattern G12 «не объединять Redis GET и SET failures».
Диспозиция: **fix до acceptance** — минимальная правка Gate 0 (строка outage), learn (раздел fail-closed), interview (ответ 6) и одной строки project-spec (сценарий 4): (a) `GET`-ошибка до source read → `503 cache_unavailable`, `source_read=0`; (b) `SET`-ошибка после source read → `503 cache_unavailable`, `source_read` уже ≥1, fill не выполнен, в burst amplification деградирует до ≤N без зависаний; популяция «outage 32/32, `source_read=0`» относится только к недоступности cache с начала запроса. Модель и populations не меняются.

**C-2 (🔵 GLM-A-2; смежно 🟡 C-12). Freshness bound 2.25 с не является герметичным: точка отсчёта 250-мс deadline не зафиксирована, зазор между deadline-проверкой и завершением `SET` не закрыт.**
«Deadline от получения source snapshot до завершения fill» допускает чтение «от возврата строк»: медленный SELECT, начатый до commit и вернувшийся после, проходит проверку и записывает v1 с полным `EX 2` — runtime-воспроизведено commit→истечение v1 = 2616.8 мс > 2250. Даже при правильном anchor проверка перед `SET` не атомарна с завершением `SET`: пауза в зазоре дала 2519.3 мс > 2250. PostgreSQL READ COMMITTED устанавливает snapshot на начало statement — корректный anchor именно этот. Контрвариант (anchor = начало statement + `SET` с остаточным TTL, `PX = 2000 − elapsed`) удержал 1959.9 мс ≤ 2250 при той же паузе, а медленный SELECT корректно отвергается (`503 summary_source_unavailable`, без fill). Авторский forced race (~2.0 с) дефект не вскрывает.
Диспозиция: **fix до acceptance** — одна формулировка в Gate 0 (строка freshness) и абзац в learn: anchor = момент установления read snapshot (statement start); зазор закрывается остаточным TTL либо явной оговоркой «2.25 с + задержка между проверкой и завершением `SET`». Та же правка естественно закрывает C-12 (показать worst-case арифметику). Новая архитектура не нужна.

**C-3 (🔵 GLM-A-3). «Без автоматического retry» не соответствует поведению pinned клиента по умолчанию; механизм исполнения бюджета 250 мс не зафиксирован.**
redis-py 8.0.1 по умолчанию применяет `Retry(ExponentialWithJitterBackoff, 10 повторов)` на `ConnectionError`/`TimeoutError` для connect и команд (проверено по установленному пакету). Одиночный `GET` к недоступному Redis ≈ 6.4–7.8 с, burst 32 ≈ 7.9 с — не ≤250/350 мс. Цитируемая страница redis-py async docs дефолтный retry не документирует. Авторские 290.44 мс воспроизводимы только при adapter-level инжекции (runtime: 60.8 мс) либо явно отключённом retry; механизм инжекции отказа в Gate 0 не зафиксирован. Correctness-гейты при этом выполняются (32×`503`, `source_read=0`).
Диспозиция: **fix до acceptance** — зафиксировать механизм: клиент с отключённым retry (`retry=Retry(NoBackoff(), 0)` или эквивалент) либо обёртка каждой команды в `asyncio.timeout(0.25)` (клиентские retry тогда происходят внутри бюджета), плюс указать механизм инжекции отказа для outage-популяции; при необходимости пересчитать порог 350 мс.

### Freshness/failure/coalescing boundary (A — механика, B — ясность)

Граница изложена связно и честно (B): invariant наблюдаем, late fill разобран на схеме с управляемой паузой, fail-closed обоснован через fan-out риск, one-process граница повторена во всех файлах без distributed overclaim. Механически (A): coalescing lifecycle доказан runtime (без stuck followers, re-read ≤N после ошибки владельца), DEL-failure семантика корректна, а вот freshness bound требует уточнения (C-2) и GET/SET counters — разведения (C-1). ### Cache L2/L3 и coverage (B — правдивость, A — механика)

Coverage правдив: L2 — самостоятельное применение pattern (kata + project normal path), L3 — непересекающееся по смыслу design-evidence (race timeline, commit ordering, измеренный amplification с сохранённым дефектным baseline, outage trade-off, recovery, ADR); L3-only наблюдаемые не существуют на уровне L2. Cache L4 корректно отложен; supporting capabilities не начислены (оба профиля, независимо). Арифметика 11 = 1 + 10 relationships к трём targets с ролями `1 reference / 2 explain / 2 probe / 1 practice / 3 assess / 2 integrate` подтверждена машинно (A) и сверена с регистрациями (B). Достаточность L3-evidence для acceptance — да, при закрытии C-1..C-3 как формулировок.

### Learning design и human readability (B)

Маршрут автономен и связен; rubric оценивает рассуждение, а не термины; kata без scaffold с одним дефектом; project сохраняет инжененную неопределённость; Mermaid и `<details>` добротны. Пробелы — C-6 (англицизмы) и три note (C-10, C-11, C-12).

4. **Измеряют ли пять burst-прогонов одну загрузку на key, без случайной сериализации или тёплого key?** Да: `DEL` перед каждым burst, одновременный старт и показ дефекта до исправнения (~32 reads) требуются явно; независимо воспроизведено 5×(32/32 корректных, ровно 1 read).
5. **Достаточно ли bounded fail-closed outage/recovery evidence для Cache L3 без distributed availability/read-your-writes/L4?** Да (оба профиля); оговорка воспроизводимости порогов по времени — C-3/C-8, correctness-гейты выполняются.
6. **Не превращается ли project-spec в готовую архитектуру?** Нет (оба профиля): contract/substrate закреплены как предмет Gate 0, структура adapters, механизм coordination, harness и ADR-рассуждение оставлены участнику.
