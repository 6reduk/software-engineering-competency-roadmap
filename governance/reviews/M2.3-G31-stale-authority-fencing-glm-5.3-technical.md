## Ответы на обязательные вопросы

1. **Подтверждён ли технический тезис?** Да, в трёх независимых плоскостях: (а) конструктивно — coordinator не участвует в пути эффекта, проверка поколения находится в едином условном UPDATE у ресурса, defect отличается от fixed именно наличием/отсутствием этой проверки; (б) документально — READ COMMITTED повторно проверяет WHERE на обновлённой строке, UPDATE меняет только удовлетворяющие условию строки, RETURNING возвращает фактически изменённые; (в) эмпирически — 10/10 defect-цепочек принимают `A-late/1` после `B-first/2`, 10/10 fixed-цепочек отвергают. Новый authority сам по себе старую команду не останавливает — она физически доходит до ресурса во всех 20 defect/fixed историях.

2. **Точная граница доказанной гарантии.** Один заказ, одна передача, явный отзыв без TTL/renewal/heartbeat, доверенные workers, отсутствие partition/crash/concurrent issuance/recovery поколений/обхода SQL-пути; гарантия действует от **первого принятого эффекта B** (порог `last_token` ресурса), а не от момента выдачи `t2`. До предъявления `t2` ресурс может принять и `t1`. Материалы называют это окно в каждом жанре (index:64, learn:73, interview:103, kata:123); риск расширения остаётся только при телеграфном чтении формулировки инварианта «после передачи полномочий…» без дочитывания — все пять файлов сужают корректно.

3. **Достаточность rerun и отражение нарушения порядка.** Технически достаточен: чистые контейнеры, полная серия 30 trials, исправленное наблюдение `prepared_value` с assert-ом тождества payload, обновлённые хеши. Процессное нарушение отражено finding-ом A-G31-1: две категорические фразы (WP:55, README:135) синхронизировать с уже существующим раскрытием в WP:124; повторный Gate 0 и задняя датировка не нужны; verdict профиля — `accepted_with_changes` с обязательной правкой до acceptance.

4. **Правдивость L1/L2/L3 evidence и supporting-роли.** Да: recount 35/11/roles сходится с YAML и coverage map; learn честно *объясняет* L3-компромисс (не начисляя execution evidence), interview probes, kata practice/assess на L1/L2 с заданным договором, project integrate/assess на L2/L3 через выбор и несколько историй; supporting leadership ограничена reference/explain/probe L1/L2 и явно не закрывает required Architecture leadership L3.

5. **Различие учебных действий.** Да: learn — объяснить модель и границы; interview — восстановить порядок и защитить вывод по следу с rubric самостоятельности; kata — самостоятельно воспроизвести заданный дефект и ввести проверку в точке эффекта (одна передача, один stale action, scaffold отсутствует); project — выбрать механизм и момент передачи, сравнить ≥2 альтернативы, собственная оснастка, ≥3 дополнительные failure histories, своя запись решения. Наблюдаемые результаты жанров не пересекаются; готового fixed нигде нет.

6. **Findings: обязательность и принадлежность.** До acceptance — A-G31-1 (major), A-G31-2 и A-G31-3 (односточные правки Gate 0/README в разрешённой зоне). Второму slice/Gate 0 — ничего. Learner implementation — дополнительные истории проекта (partition, unknown commit, обход, recovery поколений) остаются участнику по спецификации. Production backlog — HA coordinator, DR, эксплуатационный допуск (вне фазы B5, не назначаются). A-G31-4/A-G31-5 — no change.

7. **Можно ли принять M2.3 без второго slice и без proficiency.** Да: после исправления A-G31-1 (и односточных minor) пять материалов и coverage map самодостаточны; proficiency, module completion, ImplementationReference, production readiness в них не заявлены; решение о втором slice и close-out остаётся отдельным шагом оркестратора по контракту фазы.
