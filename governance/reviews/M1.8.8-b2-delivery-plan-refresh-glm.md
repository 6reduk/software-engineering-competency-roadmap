## Метод пересчёта (воспроизводимый алгоритм)

1. Из `curriculum/tracks/b2/level-outcomes.md` извлечены все `b2.level-outcome.*` ID в порядке следования → канонические 69; из `capabilities.md` — 19 `b2.capability.*`; из `modules.md` — 10 модулей с их `Develops`.
2. Из каждого `.md` в `curriculum/tracks/b2/slices/**` (32 файла) распарсен YAML frontmatter; учтены только `coverage`-записи артефактов со `status: accepted`.
3. Каждая запись классифицирована по префиксу target: `b2.capability.*` → capability-level, `b2.level-outcome.*` → outcome-level; relationship считается парой `(target, role)`.
4. Unique covered = число различных outcome-targets; probe-only = outcomes, у которых все связи имеют role `probe`; membership модуля = outcomes всех capabilities из его `Develops` (первичное + supporting), покрытые — те из них, что имеют хотя бы одну связь.
5. Каждая ячейка таблицы «Базовый outcome-level audit» и каждая строка реестра сопоставлены с YAML попарно (код артефакта + role).
6. Pre-S09 baseline получен повторением шагов 3–4 без артефактов `recoverable-order-confirmed-consumer/` и сверен с acceptance M1.8.6.

## Вывод по числам

Подтверждаю без расхождений:

- **32** accepted artifacts (6 slices: C 6, R 6, A 5, V 5, T 5, W 5), все со `status: accepted`.
- **188** relationships = **16** capability-level `reference` + **172** outcome-level (`explain` 42 / `probe` 44 / `practice` 22 / `assess` 43 / `integrate` 21). Поразрядная сверка с реестром плана по каждому артефакту и role сошлась.
- **49/69** покрытых, **20** непокрытых; состав непокрытых совпадает со списком выше.
- Ровно **два** новых unique outcomes относительно M1.8.6: `b2.level-outcome.design-asynchronous-workflows-l2-implement-background-flow` и `b2.level-outcome.design-asynchronous-workflows-l3-design-recoverable-workflow`; оба имеют `explain` (W1) и non-probe execution evidence (W3 practice/assess — L2; W4 integrate/assess — L2/L3).
- **7** `probe-only` — те же exact IDs, что в плане и что до M1.8.3: `manage-service-resource-lifecycle-l4…`, `design-http-api-contracts-l4…`, `evolve-api-contracts-l4…`, `control-concurrency-cancellation-l4…`, `verify-contract-compatibility-l4…`, `diagnose-service-performance-l4…`, `control-service-load-resources-l4…`.
- **11** S09-связей к **трём** semantic targets; roles `reference 1 / explain 2 / probe 2 / practice 1 / assess 3 / integrate 2` — совпадает с acceptance M1.8.7.
- Membership по модулям: см. критерий 8; «покрыто» в строках не складывается (двойной учёт shared capabilities — намеренный, оговорён в плане).
- Pre-S09 контрольная точка: 177 (15+162) и 47 covered — точно совпадает с acceptance M1.8.6, т.е. исторические 27 artifacts не изменены и прирост строго равен S09.

## Вывод по state transitions и DAG

- Единственный переход состояния: `b2.module.background-message-workflows` `not-started → partial` за счёт собственного S09 flow. Ни один другой модуль не менял состояние: identity-aware, external-integration и safe-evolution остались `not-started` (их coverage — только shared capabilities в чужих slices), семь остальных — `partial`.
- Automatic completion нет: `complete 0` корректен, поскольку ни один module gate явно не пройден (план это фиксирует как отдельный вид решения), Workflow L4, Idempotency L4, Architecture L4, Verification L4 не покрыты, а полный набор жанров шести модулей по принятому определению не эквивалентен `complete`.
- Новых downstream hard-DAG effects нет: Workflow capability — root, ни одна B2 capability её не требует (`Requires` из `prerequisites.md` не содержит `design-asynchronous-workflows`; она фигурирует только в «related, но не hard»). S09 не изменил readiness ни одного downstream-модуля.
- B5 readiness M1.8.7 корректно учтён как substrate gate S09 (RabbitMQ/`aio-pika`), а не как B5 proficiency и не как новая hard edge; B3 readiness аналогично ограничен S07. A3 для S05/S14 остаётся внешним условием authoring. Internal hard DAG и external conditional baseline в плане не смешаны.

## Вывод по S05, A3 readiness и границам authorization slice (механическая часть)

Профиль A подтверждает структурные предпосылки выбора S05; security framing, достаточность Gate 0 и различимость kata/project — предмет профиля B.
