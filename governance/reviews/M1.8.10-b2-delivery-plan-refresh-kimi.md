# M1.8.10 — независимое review B2 delivery plan, профиль B (kimi)

## Scope и профиль

Профиль B — sequencing, правдивость Abuse coverage и boundedness S14. Проверяемый артефакт: `curriculum/tracks/b2/module-delivery-plan.md` (`status: review`, snapshot 2026-08-27 после acceptance M1.8.9). В scope: выбор S14 operation-cost admission как следующего bounded package, правдивость кандидатов Abuse L1–L3, трактовка evidence criteria L2, граница с принятым Load Control evidence R2–R5, достаточность встроенного Gate 0 вместо отдельного readiness package, допустимость исключения SSRF-половины S14. Вне scope: механический пересчёт coverage/DAG (профиль A) и disposition — решение принимает оркестратор.

Прочитан полный context manifest work package; тела учебных материалов открыты точечно: I0/I1 (`tenant-scoped-orders-authorization` index и learn), YAML coverage I2/I3/I4, R2 (`bounded-concurrency-pool-saturation`), Gate 0 в `governance/work-packages/M1.8.9-identity-aware-boundaries-s05-slice.md`. Чужие review-отчёты текущего пакета не читались до завершения этого анализа.

## Verdict

`accepted_with_changes` — **0 blocker / 1 major / 1 minor / 1 note**.

Выбор S14, трактовка границы с Load Control, достаточность Gate 0 и исключение SSRF подтверждены. Единственный major касается правдивости заявки Abuse L2: план не показывает, как cost-only slice отвечает на полное каноническое evidence criteria L2.

```yaml

finding: План заявляет Abuse L2 (`...-l2-protect-typical-endpoint`) как primary outcome candidate, но нигде не разбирает применимость четырёх категорий его канонического evidence criteria — «Request/cost bounds, field exposure, quota/rate и untrusted target rules связаны с threat cases и тестами». evidence: Канонический текст L2 в `curriculum/tracks/b2/level-outcomes.md` перечисляет четыре категории одним списком, и capability description в `capabilities.md` повторяет тот же набор. Оркестратор передал именно этот вопрос как риск №1 в intake (`governance/reviews/M1.8.10-b2-delivery-plan-refresh-intake.md`). Если список — обязательная совокупность, cost-only slice не может правдиво заявить L2; если это набор применимых категорий, L2 достижим, но только при явном решении применимости каждой категории для bulk-export endpoint — такого решения в плане нет. Anti-pattern work package прямо запрещает начислять Abuse L2/L3 за частичное evidence.
impact: Без разбора применимости заявка L2 либо молчаливо переоценивает coverage (одна категория из четырёх), либо останется уязвимой при следующем coverage-аудите после authoring. Это влияет на exact outcome candidates — обязательный элемент decision brief.
recommendation: Минимальное исправление — добавить в decision brief (или обязать Gate 0 будущего authoring package) явную запись применимости четырёх категорий L2 для выбранного endpoint: request/cost bounds — центральное evidence; untrusted target rules — сознательно неприменимы, потому что callback URL удалён из package (со ссылкой на SSRF-долг); quota/rate — покрываются локальным per-operation cost ceiling, time-based rate и distributed quota исключены и названы; field exposure — определить tenant-scoped набор экспортируемых полей через переиспользованный trusted context либо явно обосновать неприменимость. Альтернатива — сузить кандидатов до L1 и L3, но это слабее: действие L2 («самостоятельно определяет abuse controls типового endpoint») как раз и есть процесс такого определения, и при записанной применимости заявка L2 правдива.
```

## Вывод по числам и state transitions

Механический пересчёт — зона профиля A; в рамках профиля B подтверждаю согласованность, релевантную sequencing-выводам:

- S05 даёт ровно 15 relationships: I0 — 1 capability `reference`, I1 — 3 `explain`, I2 — 3 `probe`, I3 — 2 `practice` + 2 `assess`, I4 — 2 `integrate` + 2 `assess`. Проверено непосредственно по YAML всех пяти artifacts; совпадает с планом и независимым пересчётом intake.
- Все 15 связей ведут только к Identity L1–L3; Abuse, Identity L4, A3, HTTP, Architecture, Verification targets в YAML I0–I4 отсутствуют — заявка плана «ровно три новых unique outcomes» подтверждается.
- Переход `not-started → partial` для Identity-aware Boundaries соответствует принятым определениям: собственный полный flow есть, Identity L4, Abuse L1–L4 и module-gate decision отсутствуют. Automatic completion нет; сводка `complete 0 / partial 8 / not-started 2 / blocked 0` внутренне согласована с таблицей модулей.
- Новых downstream hard-DAG эффектов нет: Identity не является prerequisite ни одной B2 capability (`prerequisites.md`), related-связь Abuse→Identity не участвует в topological order. План это отражает корректно и не смешивает external A3/B3/B5/B7 readiness с internal hard DAG.

## Вывод по S14, Abuse L1–L3, readiness и границе с Load Control

**Ответ 1 — выбор следующего package.** S14 operation-cost admission — следующий лучший bounded package; порядок менять не нужно. Он даёт максимум нового unique coverage (три полностью пустых outcomes, включая role-required Abuse L3 для обеих RoleViews), опирается на root-capability без internal hard prerequisites, переиспользует принятый S05 substrate и требует ровно одного нового external readiness record против двух у S15. S01 и S08 обоснованно проигрывают по новому coverage и риску дублирования; completion-tail HTTP runtime рассмотрен и отвергнут по тем же основаниям. Выбор не является предпочтением порядка тем: он влияет на dependencies, learning leverage и boundedness.

**Ответ 2 — правдивые Abuse outcomes.** L1 — правдиво: применение заданного operation-cost bound с negative tests соответствует «применяет заданные field/body/operation limits» (kata). L3 — правдиво: каноническое действие L3 дословно описывает «multi-tenant/adversarial workload и неоднозначную стоимость операции», а запланированный project spec с пятью populations, threat matrix и decision record воспроизводит abuse paths, сохраняет legitimate use, tenant isolation и bounded resource envelope. L2 — правдиво только условно: при явной записи применимости четырёх категорий evidence criteria (finding B-1). Без неё честный ответ — «L1 и L3; L2 под вопросом трактовки». L4 корректно не заявляется.

**Ответ 3 — минимальный readiness contract и достаточность Gate 0.** Минимальный контракт до authoring: один воспроизводимый export substrate и server-owned cost unit, вычислимый до дорогой работы; threat model operation-cost amplification; legitimate/adversarial populations; workload/duration; точка измерения; admission/rejection semantics; измеримый threshold; audit limits; recovery observation; явный stop-condition при потребности в distributed quota/shared counter или невычислимости cost. Плановый Gate 0 покрывает все пункты. Отдельный prerequisite package не нужен: A3/B7 не имеют capability IDs для ссылки, а прецедент M1.8.9 подтвердил Gate 0 внутри authoring package как принятый паттерн, не создающий hard-DAG edge. Встроенного Gate 0 достаточно (с note B-3 про классы источников).

**Ответ 4 — граница Abuse Controls / Load Control.** Проверяемая граница проходит по природе угрозы и точке решения. Load Control (принятое R2–R5): admission и backpressure при агрегированном насыщении под легитимным трафиком; fan-out amplification; bounded pools/deadlines; recovery после снятия нагрузки. Abuse Controls (новый пакет): per-request server-owned оценка стоимости до начала работы против adversarial request shape от аутентифицированного tenant; fail-closed при неизвестной стоимости; tenant-isolation consequence; сохранение legitimate use. Проверяемый критерий: если evidence воспроизводит перегрузку под конкурентной легитимной нагрузкой — это Load Control; если один сформированный запрос обходит cost bound или создаёт cross-tenant последствие — это Abuse. План границу держит: R2 используется только ссылкой, новых Load Control relationships не начисляется, «generic backpressure» и pool saturation повторно не преподаются. Переименования R2–R5 evidence в Abuse coverage нет.

**Ответ 5 — S14 без SSRF.** Честно использовать сценарий S14 можно: план выбирает один механизм из двух, объявляет SSRF первым пунктом Non-goals, запрещает подмешивать callback как negative case и нигде не заявляет закрытие сценария или capability целиком. Это соответствует правилу intake: scenario ID не используется как доказательство полного S14. Непокрытый долг сохранён, но размазан по разделам; finding B-2 просит консолидировать его в «Open questions и известный долг», чтобы SSRF-половина гарантированно дожила до отдельного будущего package с собственным Gate 0.

## Можно ли переходить к S14 authoring после disposition

Да, с одной оговоркой. Выбор S14 operation-cost package подтверждён, blocker отсутствуют, readiness модель достаточна. Переход к созданию authoring package допустим после того, как оркестратор примет решение по major B-1: либо correction-pass плана с записью применимости категорий L2, либо явное решение перенести эту запись в Gate 0 authoring package как обязательный элемент до первого учебного artifact. Minor B-2 и note B-3 могут быть закрыты тем же disposition. Сам authoring в любом случае остаётся заблокированным до исполнения Gate 0 — это заложено в план и не требует усиления.
