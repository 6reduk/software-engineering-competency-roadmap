## Консолидированные findings и диспозиции

Источник: 🔵 — GLM (профиль A); 🟡 — Kimi (профиль B). Полные evidence и рекомендации — в исходных review; здесь сжатая запись с предлагаемой диспо­зицией. Окончательное решение за оркестратором.

### Minor

**C-1 (🟡 Kimi B-1). Аббревиатура DLX не расшифрована ни в одном из пяти файлов; «DLX» и «delivery limit» отсутствуют в словаре learn.**

Первое употребление — README «Зафиксированный substrate» («переносится через `at-least-once` DLX…») — до всякого объяснения; далее DLX используется в learn («DLX, связанный с…», «маршрутизируется ли DLX»), interview («`at-least-once` DLX переносит message», «зависшего DLX transfer») и project-spec («Если DLX target недоступен»). Словарь learn содержит 9 терминов, но не DLX и не delivery limit. Нарушение редакционного стандарта §4 (порядок «русское объяснение → английский термин → короткое обозначение») и §13 п.2. Проверено консолидацией по всем пяти файлам — подтверждаюсь полностью.

Диспозиция: **fix-проход** — в README при первом употреблении дать строку вида «обменник, куда broker переносит сообщения, исчерпавшие попытки доставки (`dead-letter exchange`, далее DLX)»; в словарь learn добавить записи «DLX» и «Delivery limit» с определениями в контексте среза. Правка не касается YAML, coverage и технических claims.

### Note

**C-2 (🟡 Kimi B-2). Англицизм «seeded» (seeded crash/окно/hook) без пояснения при первом появлении.**

Встречается в Mermaid-заметке learn, в «Закреплённом substrate» kata и в ответе interview; смысл восстанавливается из соседних фраз («Одноразовый hook для заданного `event_id`»), поэтому понимание не блокируется.

Диспозиция: **fix-проход** (в том же проходе, что C-1) — при первом употреблении в learn дать «заранее внедрённый одноразовый (seeded)»; либо явное решение оркестратора оставить как есть.

**C-3 (🔵 GLM A-1). Роль `overflow=reject-publish` в закреплённой policy объяснена только неявно.**

Значение присутствует в learn, project-spec и readiness record, но ни один artifact не сообщает, что это документированное предусловие `dead-letter-strategy=at-least-once`, а не самостоятельный выбор поведения очереди. Конфигурация верна и воспроизведена; пробел — проверяемость читателем. Технически подтверждено официальной документацией quorum queues и runtime-воспроизведением.

Диспозиция: **fix-проход** — одна фраза в разделе «Одна delivery model» learn brief о том, что `overflow=reject-publish` — предусловие at-least-once стратегии. Смежна с C-1 по месту правки, закрывается тем же проходом.

**C-4 (🔵 GLM A-2). Readiness record не упоминает документированное предусловие at-least-once — включённый `stream_queue` feature flag.**

В RabbitMQ 4.0+ флаг required и не может быть выключен, поэтому на любом узле 4.3.5 условие выполняется автоматически; риск для будущей реализации нулевой.

Диспозиция: **fix-проход опционально** — одно упоминание в B5/broker readiness record work package (правка этой таблицы разрешена governance M1.8.7); либо зафиксировать как не требующее правки. Обязательства не создаёт.

## Согласованный вывод по технической базе (Gate 0)

Оба профиля подтверждают: B5/broker readiness record заполнен, итог `confirmed`, версии и semantics сверены с первичными источниками. Профиль A дополнительно выполнил минимальное runtime-воспроизведение на точном закреплённом субстрате (Docker `rabbitmq:4.3.5`, `aio-pika` 10.0.1, quorum-топология и policy один-в-один из Gate 0), в котором подтверждены:

- crash после durable result до ack (`os._exit(70)`) → автоматический requeue → redelivery с `redelivered=True` и сброшенным `delivery_tag` → duplicate → прежний result → `ack(multiple=False)` → source `0/0`, ровно один result;
- `reject(requeue=True)` при `delivery-limit=3`: ровно 4 доставки и 3 requeue, dead-letter на 4-м возврате с reason `delivery_limit` в `x-death`/`x-first-death-reason`;
- `nack(requeue=True)` не продвигает delivery-limit counter: 2893 доставки за 10 c без dead-lettering — эмпирическое обоснование отказа материалов от `nack`;
- недоступный poison target при at-least-once: source удерживает сообщения (не отбрасывает), перенос завершается после восстановления target (~35 c) — ровно как требует poison profile.

Граница runtime verification зафиксирована в review A честно: PostgreSQL/Psycopg-часть принята из верифицированного S07 baseline, producer-side/shutdown/failover не проверялись и материалами не обещаются; `x-acquired-count`-нюанс не затрагивает ни одного claims материалов. Единая RabbitMQ/`aio-pika` delivery model подтверждена документально и поведенчески — обязательное условие gate G8 выполнено.
