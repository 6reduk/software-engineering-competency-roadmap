# M1.9.1 — решение оркестратора по G22

## Решение

Консолидированный результат принят как `accepted_with_changes`: **0 blocker / 0 major / 1 minor / 4 note**. Оба независимых профиля подтверждают предметные границы B3, различимость одного модуля и трёх capabilities, честность десяти LevelOutcomes, ролевые проекции и пригодность кластера как reference blueprint.

До acceptance требуется один локальный correction-pass по [`M1.9.1a-G22-topological-order-correction.md`](../work-packages/M1.9.1a-G22-topological-order-correction.md). Повторный полный G22 и новые независимые профили не нужны: оркестратор проверит одну исправленную формулировку и неизменность семантических инвариантов.

## Disposition findings

| Finding | Решение | Обоснование |
|---|---|---|
| C-1, minor | Исправить до acceptance | Текущая фраза может представить один допустимый топологический порядок как единственный. Нужно явно сказать, что обязателен только порядок `explain` перед `protect`, а `diagnose` перестановочен. |
| C-2, note | Принять как правило следующей фазы, без правки каталогов | Семь файлов и развёрнутые обоснования — форма reference-примера, а не обязательный шаблон каждого следующего кластера. |
| C-3, note | Принять без правки | Детализация TC01 наследует принятый контракт G21. Она не задаёт обязательную глубину остальных сценариев. |
| C-4, note | Отложить до технически зависимого Gate 0 или content package | Ожидание «один успех и один `40001`» допустимо только при двух участниках и отсутствии фоновых writers; это условие будущего опыта, а не основание расширять blueprint сейчас. |
| C-5, note | Не включать в correction-pass | Перенос локальных пояснений ближе к первому употреблению полезен, но не влияет на принятие модели. Его можно выполнить при будущем содержательном редактировании сценария. |

## Решение об ускоренном breadth-pass

После acceptance M1.9.1 этот кластер используется как **reference**, а не как обязательная процессная форма. Следующая фаза должна:

- описать оставшиеся десять B3-кластеров одним bounded batch package;
- пройти один общий review всего batch, а не отдельный gate каждого кластера;
- сохранить обязательными уникальные semantic IDs, разрешимые связи, ациклический hard DAG, действие-центричные capabilities, честные уровни и правдивые ролевые проекции;
- не требовать для каждого кластера семи файлов, подробного сценария уровня TC01 или развёрнутого разбора всех отвергнутых альтернатив;
- выбрать после breadth-pass только один-два представительных кластера для глубокого пятижанрового authoring;
- запускать Gate 0 только перед материалом, чьи утверждения зависят от версии, среды или спорного runtime-поведения.

Эти правила фиксируют согласованное ускорение процесса. Они не создают coverage, runtime evidence, учебные материалы или решение о proficiency.

## Условия acceptance

M1.9.1 можно принять без повторного G22, когда оркестратор подтвердит:

- C-1 исправлен в одном Ownership-файле;
- один module, три capabilities, десять outcomes, три сценария и 11 ролевых связей не изменились;
- новых `coverage`, Gate 0, runtime claims и учебных материалов не появилось;
- семь каталогов остались в `status: review` до отдельного acceptance-pass;
- ссылки, YAML и Markdown hygiene не повреждены.
