# M1.8.13 — orchestrator intake

## Verdict

`accepted_for_review`: пакет допускается к двум независимым профилям G12. Intake не принимает технические claims, Cache L2/L3 coverage или Gate 0 как окончательно доказанные и не объявляет G12 пройденным.

Предварительных blocker, требующих остановить review, не найдено. Один возможный дефект failure semantics передан профилю A как обязательный вопрос: нулевой `source_read` доказан для Redis failure на начальном `GET`, но не может автоматически относиться к failure `SET`, выполняемого после PostgreSQL read.

## Gate 0 и единая модель

Материалы закрепляют одну лабораторную модель:

- `GET /orders/summary` одного tenant-scoped Orders service;
- PostgreSQL как source of truth и Redis как удаляемый производный cache;
- один Uvicorn worker/process и process-local per-key coalescing;
- tenant-safe key и проверку tenant/schema в cached value;
- cache-aside с TTL 2 секунды и заявленным freshness bound 2.25 секунды;
- PostgreSQL commit перед Redis `DEL`, включая допустимый late-fill race;
- fail-closed cache path с `503`, без database fallback при недоступном Redis;
- hit, cold miss, burst, tenant isolation, race, outage и recovery populations;
- явный отказ переносить one-process evidence на несколько workers или distributed coordination.

B5 признан неприменимым к заявленной process-local гарантии; это решение не создаёт hard-DAG edge и не начисляет внешнее coverage.

## Обязательные вопросы G12

1. Истинен ли freshness bound `TTL 2 с + source snapshot-to-fill deadline 250 мс = не более 2.25 с stale после commit` для всех разрешённых interleavings, и проверяется ли deadline перед поздним `SET`?
2. Разведены ли ошибки Redis `GET` до PostgreSQL read и `SET` после PostgreSQL read? Может ли общий claim `cache error → source_read=0` быть правдивым для обеих веток?
3. Освобождается ли process-local coordination state при exception/cancellation владельца, и получают ли followers определённый outcome без зависания либо скрытого повторного fan-out?
4. Действительно ли пять burst-прогонов измеряют одну загрузку на key, а не случайно сериализуют запросы либо переиспользуют тёплый key?
5. Достаточно ли bounded fail-closed outage/recovery evidence для Cache L3 без обещания distributed availability, read-your-writes или Cache L4?
6. Не превращается ли project-spec в готовую архитектуру и достаточно ли он оставляет участнику инженерных решений?
