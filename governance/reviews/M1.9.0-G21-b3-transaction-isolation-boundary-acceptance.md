# M1.9.0 — принятие B3 transaction/isolation boundary intake

## Итог

M1.9.0 и gate G21 приняты с verdict `accepted` после двух независимых профилей и точечного correction-pass:

- исходный итог G21 — `0 blocker / 0 major / 1 minor / 5 note`;
- C-1–C-6 закрыты в одном planning artifact без изменения выбранного action;
- отозванный A-1 не требовал правки: ссылка Psycopg корректно отображала `3.3.6.dev1`, а stable driver всё равно должен быть выбран и повторно проверен будущим Gate 0;
- выбран один store-level сценарий: общий инвариант дежурства при двух транзакциях, меняющих разные строки, и сравнение `REPEATABLE READ → SERIALIZABLE`;
- B2/B3/B5/B6/B7 ownership сохранён, S07/S15 readiness и coverage не перенесены;
- capability/outcome/module/scenario IDs, coverage, учебные жанры, код и ImplementationReference не создавались;
- эксперимент не выполнялся, все условия будущего Gate 0 остаются неподтверждёнными.

## Verification-pass M1.9.0a

- Предметное чтение, решение и запись каждого actor теперь явно выполняются в одной внешней транзакции; журнал должен связать их и terminal outcome с transaction/session identity.
- Autocommit-чтение с отдельной write-only transaction явно запрещено как разрушение исследуемой rw-зависимости.
- Control требует snapshot actor Б только после commit actor А; любой более ранний snapshot-forming statement должен быть протоколирован и подчинён тому же порядку.
- Fixed ожидает serialization failure `40001`; `40P01` или иной lock-related исход означает незапланированный второй механизм либо ошибку оснастки и не подтверждает fixed.
- Официальное понятие `serialization anomaly` отделено от локального инженерного названия `write skew`.
- Процессные оговорки собраны в одну справку, а необъяснённый `NOT_RUN` заменён обычной русской формулировкой.

Точечная проверка подтвердила metadata, отсутствие `coverage` и новых semantic IDs, три сравнённых кандидата, одно выбранное действие и 19 разрешающихся локальных ссылок. Runtime experiment не повторялся и не требовался.

## Граница принятия

Acceptance подтверждает пригодность intake как решения о направлении следующего zoom. Он не подтверждает поведение конкретной сборки PostgreSQL/Psycopg, B3 proficiency, Gate 0, capability blueprint, учебный материал или production adoption.

Future evidence должно отдельно различать control, write-skew defect и serialization conflict fixed; store conflict и rollback не подменяются прикладным отказом отдельной новой попытки. Конкретные victim и стадия обнаружения не предписываются.

## Следующий шаг

Создать ограниченный capability blueprint только для `b3.cluster.transactions-concurrency`: определить стабильный module boundary, action-oriented capabilities, применимые LevelOutcomes, prerequisites и требования двух RoleViews. Это документальный zoom без coverage и без Gate 0. Учебный authoring начнётся только после принятия blueprint и отдельного подтверждения технической среды.
