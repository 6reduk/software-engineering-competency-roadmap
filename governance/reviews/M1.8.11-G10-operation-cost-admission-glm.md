# M1.8.11 G10 — профиль A: security, technical correctness, measurement

Профиль A (glm). Scope: пять материалов `curriculum/tracks/b2/slices/cost-bounded-orders-export/`, Gate 0 и applicability matrix в `governance/work-packages/M1.8.11-operation-cost-admission-s14-slice.md`, регистрации M1.8.11 в `curriculum/tracks/b2/README.md` и `curriculum/tracks/b2/coverage-map.md`. Проверка выполнена по первичным источникам (PyPI, python.org, RFC 9110/9457, OWASP API4:2023) и минимальному runtime-воспроизведению вне репозитория. Отчёт профиля B не читался до завершения собственного анализа.

## Verdict

`accepted`: `0 blocker / 0 major / 2 minor / 2 note`.

Заявленный contract технически верен, воспроизводим на exact pinned stack и не содержит найденных обходов или overclaim. Оба minor касаются одного класса: материалы требуют свойств (strict binding, sanitized problem+json), которые framework даёт только при явной нестандартной конфигурации, но не предупреждают об этом. По правилам протокола minor могут быть перенесены в backlog; решение фиксирует оркестратор.

## Environment и метод воспроизведения

- Windows 11 Pro 10.0.26200; venv на системном CPython 3.14.0 (`python -m venv`), вне репозитория (`%TEMP%\m1811-g10-review`, удалён после прогона).
- `pip install fastapi==0.137.1 starlette==1.3.1 pydantic==2.12.5` разрешил все три пина вместе без конфликтов; `httpx==0.28.1` добавлен только для TestClient и не входит в проверяемый baseline. Импорты подтверждены: `python=3.14.0 fastapi=0.137.1 starlette=1.3.1 pydantic=2.12.5`.
- Substitutions: `IdentityContext` смоделирован immutable trusted-константой tenant (как предписывает kata: «Identity validation можно представить готовым immutable IdentityContext»); JWT-проверка S05 не воспроизводилась — она принята как trusted context. Fixture: 3000 Orders tenant-a + 5 Orders tenant-b, 5 публичных и 2 чувствительных поля.
- Выполненные cases: lax-проба коэрции Pydantic (4 варианта); 16 негативных shape-cases (string/float/bool `max_rows`, `fields` строкой, duplicate, unknown `debug`, sensitive `customer_email`/`payment_token`, extra `tenant_id`, extra `cost`, alias `maxRows`, пустой и шестизначный `fields`, `max_rows` 0/3001, отсутствие ключа); forged-tenant запрос с `X-Tenant-ID`, `?tenant_id` и `Authorization`; четыре population × 20 последовательных requests; покомпонентная проверка unit/header; 100 bypass + recovery; малый tenant для консервативности оценки; проба дефолтного FastAPI-обработчика ошибок; инспекция audit; захват warnings.
- Границы воспроизведения: один процесс, in-memory substrate, TestClient без сети, sync-endpoint, без concurrency; это независимая реализация заявленного contract (в source tree кода нет), поэтому она доказывает воспроизводимость и корректность contract, а не поведение несуществующей реализации. Мои median timings 0.908–1.719 ms на другой машине — диагностические и не сравниваются с Gate 0 числами.

## Findings

### F-1 — minor

```yaml
severity: minor
artifact: curriculum/tracks/b2/slices/cost-bounded-orders-export/learn/server-owned-cost-admission-boundary.md (раздел «Сначала связать форму»); kata/block-bulk-export-cost-bypass.md (Контракты); project-spec (threat/cost matrix)
criterion: correctness
finding: материалы требуют strict types («strict integer max_rows», «strict types … не становятся альтернативными путями»), но не предупреждают, что дефолт Pydantic/FastAPI валидирует в lax-режиме и молча коэрцирует вход.
evidence: на exact pinned stack lax-модель приняла {"max_rows": "400"}, {"max_rows": 400.0} и {"max_rows": true} (bool → int 1); отклонён только 400.7. Строгий contract достигнут только явной ConfigDict(strict=True). Реализатор на дефолтной конфигурации не пройдёт собственные type-variant cases из threat/cost matrix project-spec, а acceptance kata type-варианты явно не включает — lax binding может остаться незамеченным.
impact: скрытое расхождение закреплённого contract и фактического поведения; type-bypass семейство (bool/float/string) частично возвращается.
recommendation: одно-два предложения в learn brief (и пункт в контракты kata/project-spec): строгий режим включается конфигурацией модели; дефолт Pydantic в lax-режиме принимает str/float/bool для int.
```

### F-2 — minor

```yaml
severity: minor
artifact: learn (разделы «Сначала связать форму, затем считать», «Audit и диагностика»); kata (Контракты)
criterion: practice
finding: материалы требуют problem+json без эха значений, но не предупреждают, что дефолтный обработчик RequestValidationError в FastAPI возвращает application/json и включает loc+input — имя поля и само значение входа (включая forbidden/sensitive).
evidence: проба на bare-приложении без кастомного handler: status 422, content-type application/json (не problem+json), тело содержит "customer_email" и значение входа. Таким образом дефолт нарушает сразу оба требования — media type и disclosure boundary; санитизация является обязательной и нестандартной.
impact: реализация «из коробки» нарушает tenant/disclosure invariant и единый error contract, при этом базовые тесты статусов остаются зелёными.
recommendation: добавить предупреждение в learn/kata contracts: для безопасного input-invalid problem требуется собственный exception handler; сериализация errors() по умолчанию эхом возвращает input.
```

### F-3 — note

```yaml
severity: note
artifact: project-spec/cost-bounded-orders-export-api.md (словарь: «Recovery»); learn (measurement envelope)
criterion: scope
finding: термин recovery и формулировка «после прекращения adversarial workload» заимствуют лексику нагрузочного восстановления, хотя в этом substrate отказы бестранны (нулевые delta, нет consumed resources).
evidence: interview Q6 и learn сами дефусируют («не доказывает ограничение частоты», «восстанавливается в локальном процессе»), а таблица project-spec точна («200, 1600 cells; rejected requests суммарно дали zero work delta»). Риск остаётся только в названии.
impact: минимальный: читатель может приписать population смысл доказательства восстановления ресурсов.
recommendation: при случае уточнить в словаре project-spec: recovery здесь — отсутствие накопленного эффекта отказов и сохранность legitimate use, а не восстановление израсходованных ресурсов.
```

### F-4 — note

```yaml
severity: note
artifact: все пять материалов (блок versions)
criterion: freshness
finding: versions baseline не фиксирует версию httpx/httpx2, хотя задокументированное ограничение harness — именно deprecation warning httpx-пути TestClient.
evidence: при прогоне получен StarletteDeprecationWarning «Using httpx with starlette.testclient is deprecated; install httpx2 instead» — тот же класс предупреждения, что зафиксирован в Gate 0. Воспроизводимость TestClient-измерений зависит от этой зависимости, не упомянутой в versions.

recommendation: при следующем обновлении baseline включить фактическую версию httpx (или httpx2) в versions slice.
```

## Вывод по Gate 0, exact substrate и measurement

**Gate 0 можно считать `confirmed` на exact pinned stack.** Все четыре версии существуют, взаимно совместимы (pip разрешил пины вместе) и фактически запускаются; freshness note точна по каждому из четырёх компонентов. Measurement envelope воспроизводим: populations точны по статусам, строкам и ячейкам; reject-before-work доказан нулевыми delta обоих counters, а не только status code; `cells_serialized` корректно исключает header; консервативность оценки подтверждена малым tenant (оценка 2000 при фактических 20 ячейках — заявленный false-positive trade-off реален). TestClient warning воспроизведён и честно задокументирован как ограничение harness. Timings в материалах корректно маркированы diagnostic-only: мои medians на другом железе отличаются в ~2×, и никакое acceptance-условие от них не зависит.

Обязательные ответы профиля A:

1. **Gate 0 confirmed?** Да — по существованию, совместимости, запуску и честной freshness note (см. выше).
2. **Отклоняет ли control over-limit и shape-bypass до execution boundary?** Да — в независимом воспроизведении оба класса запросов дают cost-limit `422` с нулевыми delta `export_execution_started` и `cells_serialized`; ни один из 16 испытанных вариантов изменения формы не достиг executor. Оговорка: это доказательство воспроизводимости заявленного contract, поскольку реализация в source tree намеренно отсутствует.
3. **Что доказано counters/experiment, а что остаётся design requirement?** Доказано (воспроизводимо на substrate): reject-before-work, точность cell-unit, различимость двух 422 semantics, tenant non-trust, allowlist/header construction, консервативность оценки, бестронность отказов и сохранность legitimate use, отсутствие disclosure в error/audit при явной санитизации. Осталось design requirement будущей реализации: production weights/калибровка, quota/rate, SSRF, response-bytes/peak-memory bounds, CSV injection у потребителя, storage cost, multi-worker/concurrency поведение (envelope явно исключает concurrency), стоимость реального SQL scan. Материалы распределяют эти свойства именно так — как residual risks и stop conditions, а не как доказанное.

## Вывод по applicability matrix и границам cost-only S14

Все четыре категории имеют диспозицию. Request/cost bounds и field exposure — применимые, с threat case, control и наблюдаемым evidence, которое я воспроизвёл (populations, negative cases, counters, отсутствие эха). Quota/rate и untrusted target — честные `not applicable`: названы причина (per-operation ceiling не ограничивает сумму запросов; в contract нет адреса назначения), граница решения и residual risk; 100 bypass явно не выдаются за quota test, отсутствие callback — не за SSRF evidence. Это соответствует adjudication M1.8.10 (applicability check, а не внедрение всех четырёх механизмов) и evidence criteria Abuse L2 из каталога. **Матрица и residual risks достаточны для bounded Abuse L2 claim.** Cost-only половина S14 не подменяет весь сценарий: долг SSRF/untrusted-target назван явно в README, Gate 0, project-spec и coverage-map; обещания distributed quota, aggregate fairness, platform coordination, production storage cost, total memory/response bound и универсального threshold в материалах отсутствуют. Свойства, которые slice явно не доказывает: aggregate/multi-request consumption, rate/distributed abuse, SSRF, response-byte и peak-memory bounds, CSV injection downstream, production storage, variance размера строк, калибровка весов, поведение при concurrency — все они перечислены в самих материалах как границы или residual risks, пропусков в собственном списке материалов не найдено.

## Вывод по различию kata/project

Kata и project дают разные наблюдаемые результаты. Kata: один воспроизводимый дефект (row-only limit пропускает `500×5`), красный bypass-test до исправления, минимальная server-owned оценка, нулевые work delta и negative shape checks — один L1-наблюдаемый исход. Project: пять populations с exact-cell/counter корреляцией, полная applicability matrix со ссылками на собственные test names, threat/cost matrix, audit/error negative assertions, decision record с альтернативами и stop conditions — самостоятельный L2/L3 evidence-набор, недостижимый выводами kata. Различие наблюдаемых исходов реальное, а не косметическое разделение жанров.

## Ответы на open questions work package

1. **Содержательность recovery после 100 отклонённых запросов.** Population доказывает ровно две вещи: rejection-path не накапливает учитываемой работы (суммарные delta 0/0) и legitimate use сохранён (normal `200`/1600 сразу после серии). Он не доказывает восстановление ресурсов — в этом substrate отказы их не расходовали. Материалы сами проводят эту границу (interview Q6, learn), поэтому претензии к evidence нет; зафиксирован только лексический note F-3.
2. **Достаточность synthetic cell model и двух counters для L3 bounded resource envelope.** Достаточно внутри объявленного envelope: unit связан с наблюдаемой работой сериализации, оба индикатора причинно сидят за execution boundary, а всё, что модель не покрывает (SQL scan, response bytes, peak memory, размер строк, concurrency), явно вынесено в residual risks, stop conditions и triggers перекалибровки. L3 claim опирается на воспроизведённые abuse paths + сохранность legitimate use + design defense границ, что соответствует формулировке outcome; расширение модели было бы выходом за границы bounded package.

Да. Никакое evidence, на котором держится verdict, от этих правок не зависит: contract, measurement и disclosure boundary уже воспроизведены независимо.

## Независимость и границы

Review выполнен независимо: отчёт профиля B (если существует) не читался; проверки опирались на первичные источники и собственное runtime-воспроизведение, а не на intake-выводы (intake использован только как cross-check механических чисел). Исходные материалы не изменялись: единственный созданный файл — настоящий review-артефакт; harness выполнялся во временном каталоге вне репозитория и удалён. Ограничения: проверена воспроизводимость и корректность заявленного contract, а не конкретная реализация (её в source tree нет по design); timings не сравнивались (diagnostic-only по самому contract); concurrency, реальная DB и сеть находятся вне заявленного envelope и не проверялись.
