# M1.8.13 — принятие Application Caching/S15 slice

## Итог

M1.8.13 и gate G12 приняты с verdict `accepted`:

- два независимых профиля подтвердили однопроцессную cache-aside/coalescing модель, Cache L2/L3 evidence, coverage и human readability;
- `3 major / 4 minor / 5 note` закрыты correction-pass C-1–C-12;
- приняты пять artifacts и 11 relationships к трём semantic targets;
- Cache L2 проверяет применение cache-aside и process-local coalescing на одном concurrent-miss defect;
- Cache L3 проверяет tenant-safe key/value, bounded freshness, commit/invalidation race, отказ cache, recovery, измеримое amplification и честную границу topology;
- Cache L4, distributed coordination, Redis HA, multiple workers, zero-stale и read-your-writes не заявлены;
- kata остаётся одним Cache L2 defect, project отдельно интегрирует Cache L2/L3 и не содержит готового решения.

## Verification-pass M1.8.13a

C-1–C-12 проверены по исходному work package и пяти материалам:

- initial/repeated Redis `GET` failure до PostgreSQL read даёт `503 cache_unavailable` и `source_read=0`;
- post-read `SET` failure даёт тот же внешний ответ без fill, но `source_read≥1`; burst может дать до `N` последовательных source reads без зависания;
- freshness anchor — начало SQL statement в PostgreSQL `READ COMMITTED`;
- поздний fill использует `remaining_ttl = max(0, 2 секунды − elapsed_since_statement_start)`, пропускается при исчерпанном остатке, а `SET` завершается внутри 250-мс command budget;
- worst-case явно выведен как `statement_start + 2 секунды + 250 мс ≤ commit + 2,25 секунды`;
- redis-py 8.0.1 имеет явно отключённые автоматические retry, а внешний timeout ограничивает каждую команду;
- controlled adapter fault injection используется для воспроизводимого correctness threshold; реальный Docker/network outage оставлен host-dependent диагностикой;
- baseline объяснён как воспроизводимый и не выдан за latest; RFC 9457 связан с Problem Details;
- смыслообразующие англицизмы раскрыты, project-only burst threshold объяснён, lifecycle lock описан через `async with` / `try-finally`, а ссылки и diagram labels получили человеческий контекст.

Сохранены пять semantic IDs, 11 relationships, 3 targets и роли `1 reference / 2 explain / 2 probe / 1 practice / 3 assess / 2 integrate`. Версии, endpoint, tenant fixtures, TTL, budgets, one-process topology и регистрации не изменялись. Все относительные ссылки разрешаются; front matter, fences, Mermaid и `<details>` структурно корректны; conflict markers и trailing whitespace отсутствуют.

## Граница принятия

Acceptance относится только к Application Caching/S15 в одном Uvicorn worker/process. Граница 2,25 секунды является bounded-staleness contract указанного late-fill механизма, а не общей гарантией Redis или PostgreSQL. Fail-closed модель не доказывает доступность при реальном сетевом отказе, а adapter-level fault injection не заменяет production failure testing.

Принятие slice не завершает автоматически модуль, не начисляет B3/B5 или supporting coverage и не подтверждает Cache L4. Cross-worker coordination, migration/adoption и read-your-writes требуют отдельных решений и evidence.

## Следующий шаг

Выполнить M1.8.14: обновить B2 module delivery plan по принятому Cache L2/L3 coverage, пересчитать artifacts, relationships, covered/uncovered outcomes, probe-only и состояния десяти модулей, затем выбрать один следующий bounded package.
