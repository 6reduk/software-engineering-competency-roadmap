# M1.9.0 — orchestrator intake B3 transaction/isolation boundary

## Verdict

`accepted_for_review`: `0 blocker / 0 major / 0 minor / 2 note`.

Planning artifact допускается к независимому G21. Это решение подтверждает комплектность и ограниченность intake, но не принимает техническую причинность будущего эксперимента, не подтверждает Gate 0 и не разрешает создавать B3 blueprint либо учебные материалы.

## Проверенный результат

- Создан один заявленный файл `governance/planning/intakes/b3-transaction-isolation-boundary.md`; его metadata соответствуют пакету: `kind: plan`, `owner_track: b3`, `status: review`, дата и язык заданы, `coverage` отсутствует.
- Intake не создаёт capability, outcome, module или scenario ID, relationships, учебные жанры, код, SQL-решение, scaffold либо ImplementationReference.
- Сравнены три ограниченных действия, выбрано одно. Два остальных явно отклонены для текущего шага, а не объявлены ненужными для B3.
- Центральное действие конкретно: на одной модели дежурства сравнить `REPEATABLE READ` и `SERIALIZABLE`, меняя только уровень изоляции двух транзакций и наблюдая сохранение общего инварианта.
- Будущие `control / defect / fixed` разведены; runtime-результаты не заявлены. Эксперимент помечен `NOT_RUN`, все Gate 0 readiness-категории остаются неподтверждёнными.
- Названы store/version/driver, topology, transaction ownership/settings, координация actors, store observations, reset/cleanup и source freshness, которые должен проверить отдельный Gate 0.
- Exit trigger конечен: один выбор, карта ответственности, отклонённые альтернативы, наблюдаемое evidence и readiness. Следующий пакет остаётся отдельным решением оркестратора.

## Граница треков

Карта согласуется со skeleton matrix:

- B2 сохраняет прикладную операцию, commit/rollback boundary, идемпотентность и внешние эффекты;
- B3 владеет MVCC, visibility, isolation, locks, anomalies и store-level signals;
- B5 не присваивается работа внутри одного store и не проектируется межсистемная consistency;
- B7 не подменяется локальным опытом и сохраняет production reliability, continuity и cross-system recovery;
- B6 указан только как условная зависимость будущей среды, без самостоятельного platform action.

Сценарий не повторяет S07: конкурентные actors изменяют разные строки, а исследуемый результат — общий store-level write-skew invariant, не идемпотентный повтор одной application command. S15 используется только как контраст с application caching и не передаёт B3 собственный readiness либо coverage.

## Notes intake

### I-1 — точное расписание должно доказать причинность, а не только желаемый итог

G21 должен проверить, достаточно ли будущая синхронизация фиксирует момент получения snapshot обеими транзакциями. В control важно исключить ранее полученный snapshot у второго actor; в defect/fixed — доказать, что оба решения действительно основаны на требуемом чтении до разрешения записей. Случайный `sleep` справедливо запрещён.

### I-2 — fixed должен различать store conflict и прикладной отказ после новой попытки

Первичный fixed evidence — сохранённый инвариант и отказ одной транзакции со store signal. Отдельная новая попытка после rollback может дать прикладной отказ по свежим данным, но не должна скрывать исходный serialization conflict или превращаться в проект универсального retry. G21 должен проверить эту границу и отсутствие обещания, что жертва либо точка обнаружения заранее известны.

## Контрольные вопросы G21

1. Правдиво ли описан write-skew сценарий PostgreSQL и достаточно ли перехода `REPEATABLE READ → SERIALIZABLE` как единственного изменяемого механизма?
2. Детерминируют ли control/defect/fixed именно требуемую видимость данных и терминальные исходы обеих транзакций?
3. Достаточны ли proposed observations для причинного вывода без требования недоступного внутреннего serialization graph?
4. Не смешаны ли B2/B3/B5/B6/B7 и не переносятся ли S07/S15 readiness либо coverage?
5. Получают ли Backend и Architecture role depth на одном сценарии без искусственного назначения уровней или L4/L5 evidence?
6. Понятен ли intake работающему инженеру как документ выбора, а не середина внутреннего разговора или уже готовая лаборатория?
7. Достаточно ли конкретны будущий Gate 0, non-goals и exit trigger для следующего bounded решения?
