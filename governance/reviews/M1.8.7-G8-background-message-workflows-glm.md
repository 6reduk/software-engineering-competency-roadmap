## Runtime verification (минимальное воспроизведение)

Выполнено в изолированной среде: Docker 29.6.2, официальный образ `rabbitmq:4.3.5`, Python 3.14.0, `aio-pika` 10.0.1 (venv). Топология и policy воссозданы в точности как закреплено: durable quorum `orders.fulfillment`, direct DLX `orders.fulfillment.dlx`, durable quorum `orders.fulfillment.poison`, policy `delivery-limit=3` + `dead-letter-routing-key` + `dead-letter-strategy=at-least-once` + `overflow=reject-publish`; consumer `set_qos(prefetch_count=1)` + `consume(no_ack=False)`.

**Подстановка, заявленная явно:** durable business result воспроизводился атомарной записью файла с `fsync` + `os.replace` вместо строки PostgreSQL. Проверялись broker/adapter-semantics (requeue, redelivery, ack, счётчики, DLX-transfer), а не PostgreSQL-механика — она принята из верифицированного S07 baseline и стандартной семантики unique constraint.

| Тест | Проверяемое утверждение | Наблюдение |
|---|---|---|
| A | Crash после durable result до ack (`os._exit(70)`) → unacked delivery возвращается | Exit code 70; marker и result на диске; `finally`/graceful close не выполнялись; delivery вернулся в `messages_ready` в пределах нескольких секунд |
| A | Restart → redelivery того же event, `redelivered=True`, `delivery_tag` channel-scoped | Подтверждено: новый channel — tag снова 1; флаг `redelivered=True` |
| A | Duplicate → прежний result, `ack(multiple=False)` → terminal state | Подтверждено: найден тот же result, ack отправлен; source достиг `0/0` (счётчики сошлись асинхронно, ~4 c — укладывается в 30-секундный budget материалов); ровно один result |
| B | `reject(requeue=True)` при `delivery-limit=3` → dead-letter в poison с reason `delivery_limit` | Подтверждено: consumer получил 4 доставки (1 начальная + 3 redelivery), 4-й возврат → DLX; в `x-death`/`x-first-death-reason` — `delivery_limit`; source `0/0`, poison 1 |
| C | `nack(requeue=True)` не увеличивает delivery-limit counter | Подтверждено: 2893 доставки за 10 с без какого-либо dead-lettering — nack-loop фактически неограничен, что эмпирически обосновывает отказ материалов от `nack` |
| D | Недоступный poison target при at-least-once → source удерживает, transfer откладывается, потери нет | Подтверждено: при удалённой poison queue source сохранил dead-lettered сообщения (состояние `messages=2, ready=0, unacked=0` — pending transfer); после восстановления target перенос завершился в пределах ~35 c; причина `delivery_limit` |
| E | Точная семантика счётчиков | 5 nack + далее reject: dead-letter наступил ровно на 4-м reject; `x-delivery-count=4` — учитывались только reject-возвраты |

Границы runtime verification, зафиксированные честно:

- PostgreSQL/Psycopg часть (unique violation, read-after-conflict в `READ COMMITTED`) не воспроизводилась runtime; принято из принятого S07 baseline (18.6/3.3.4, verified 2026-08-21) и стандартной семантики PostgreSQL.
- Producer-side публикация, graceful shutdown, cluster failover не проверялись — они вне границ slice, и материалы их не обещают.
- Заголовок `x-acquired-count` в воспроизведении показал 4 после 5 nack + 4 reject, что расходится с буквальным прочтением таблицы acquired-count в документации (nack якобы инкрементирует acquired-count). Материалы не делают никаких утверждений об `acquired-count`, поэтому ни один проверяемый claim не затронут; зафиксировано как граница верификации, не как дефект материалов.

## Вывод по Workflow L2/L3 evidence и отсутствию overclaim

- Заявлены только `design-asynchronous-workflows` L2/L3. Роли соответствуют жанрам из work package: learn `explain`×2, interview `probe`×2, kata `practice`+`assess` (L2, с явными проверяемыми criteria и без готового решения — допустимая форма), project-spec `integrate`+`assess`×2 (L2/L3 раздельно).
- **L2 правдив:** kata даёт execution evidence одного заданного flow с duplicate path и явным ownership; poison path, отсутствующий в kata намеренно, покрыт project-spec Evidence A (bounded transition, наблюдение с обеих сторон) и объяснён в learn. Ни один artifact не приписывает proficiency за чтение.
- **L3 правдив:** project-spec требует states/transitions и invariants до реализации, три causal окна F0–F2 (не один exception с ярлыками), recovery новым process без ручного repair, decision record и residual risks. Соответствует формулировке LevelOutcome.
- **L4, B5 и supporting claims отсутствуют:** Workflow L4 нигде не заявлен, interview rubric прямо удерживает «Не доказанный L4»; B5 outcome IDs и placeholder IDs отсутствуют; Idempotency/Cancellation/Verification relationships не добавлены — coverage YAML содержит ровно 11 связей к 3 targets, и project-spec отдельным ответом объясняет, почему Verification не получает coverage.
