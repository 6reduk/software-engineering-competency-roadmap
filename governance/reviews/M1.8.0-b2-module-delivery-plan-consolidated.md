## Консолидированные findings

Источник: 🔵 — только GLM (профиль A); 🟡 — только Kimi (профиль B). Пересекающихся findings нет, согласование severity не потребовалось. Полные evidence и рекомендации — в исходных review; здесь сжатая запись с диспозицией.

### Minor

**C-1 (🔵 GLM-A1). Сценарий S13 в строке external service integration нарушает семантику колонки «Сценарии».**
По `scenarios.md` S13 принадлежит `b2.module.performance-resource-control`; остальные 9 строк сводной таблицы следуют ownership, а строка performance помечает чужой S08 квалификатором «slice использует». Без квалификатора колонка двусмысленна именно для модуля, которому план сам запрещает «ещё один pool-saturation slice».
Диспозиция: **fix-проход** — «S08; S13 затрагивает capability модуля» либо только S08.

**C-2 (🔵 GLM-A2). Фантомная инструкция «разрешить расхождение статуса runtime slice в README и artifact metadata».**
Расхождение невоспроизводимо: `b2/README.md` — «gate G4b — accepted», все 6 артефактов runtime slice — `status: accepted`, `governance/state/STATUS.md` — «G4b принят»; governance/state/OPEN-QUESTIONS.md и registry молчат. Пункт отправляет будущего читателя искать несуществующее противоречие.
Диспозиция: **fix-проход** — удалить пункт либо сослаться на конкретные расходящиеся файлы; если имелась в виду module-атрибуция R1 (module: `b2.module.http-service-runtime` при slice-README у performance-resource-control) — сформулировать вопрос именно так.

**C-3 (🟡 Kimi F-1). Внутреннее противоречие об обязательности project-spec в S06 package.**
П. 5 минимального artifact set допускает «одну компактную project specification **или** milestone», а раздел рисков требует «Project specification оставить **обязательной** частью end-to-end flow». Контрактная неоднозначность для автора и reviewer будущего пакета; оба принятых slices содержат полный жанр project-spec.
Диспозиция: **fix-проход до создания authoring package** — зафиксировать одну формулировку (project-spec обязателен, может быть сокращён до одного компактного milestone с отдельным наблюдаемым integration result сверх kata), слово «или» убрать.

### Note

**C-4 (🔵 GLM-A3). R1 назван «supporting brief», хотя является собственным learn-артефактом http-service-runtime.**
Реестр того же плана корректно указывает primary module R1 = HTTP service runtime, и именно R1 — основание состояния `partial`. Слово «supporting» описывает положение brief внутри performance-центрированного slice и противоречит собственной терминологии плана.
Диспозиция: **fix-проход** — «единственный собственный learn-brief (R1), но нет самостоятельного artifact flow».

**C-5 (🟡 Kimi F-2). Supporting candidate external-L2 уже имеет принятое покрытие.**
`b2.level-outcome.integrate-external-services-l2-design-typical-client-boundary` покрыт `explain` (R2) и `practice`/`assess` (R4); консолидатор подтвердил по YAML. Без явной ссылки автор нового пакета может повторно объяснить client boundary вопреки non-goal о дублировании.
Диспозиция: **контракт authoring package** — сослаться на R2/R4 как существующее покрытие и ограничить новый материал ролью downstream client как заменяемого adapter в S06.

**C-6 (🟡 Kimi F-3). «Adapters остаются заменяемыми» — слабейшая по наблюдаемости часть central action.**
Одна policy change сама по себе не доказывает заменяемость; наблюдаемой она становится при фактической подмене adapter (fake/in-memory) в проверке, что соответствует evidence criteria L2.
Диспозиция: **контракт authoring package** — зафиксировать наблюдаемый критерий: business behavior tests проходят на подменённом adapter без изменения application/domain кода.
