## Явные ответы на вопросы профиля B

**1. Не слишком ли широк набор `freshness + isolation + fallback + stampede` для одного slice и какая единая инварианта его связывает?**

Не слишком широк при условии, которое план выполняет: все четыре аспекта — подусловия одного наблюдаемого контракта одного read path. Объединяющая инварианта: для одного tenant-scoped key ответ либо удовлетворяет зафиксированному freshness invariant и tenant scope, либо является явным контролируемым failure/fallback исходом, а число store reads на key остаётся bounded при любом сочетании hit, miss burst, invalidation race и cache failure. Это не четыре проекта: stampede — amplification того же miss path, isolation — свойство того же key schema, fallback — поведение того же read при cache failure, freshness — тот же TTL/stale contract. Решающий аргумент: каноническое действие Cache L3 (`level-outcomes.md:102`) требует именно совокупности «concurrent miss, invalidation races, commit ordering и cache failure» — более узкий slice не закрыл бы заявленный outcome и обесценил бы выбор. Риск ширины сдержан структурой: kata изолирует один burst-miss defect, проект несёт полный envelope, а stop-condition при нескольких несовместимых stale policies (plan:339) отсекает расползание до authoring.

**2. Достижимо ли честное Cache L3 evidence в локальном учебном проекте без заявления Cache L4?**

Да. Evidence criteria L3 — «freshness invariant и failure windows объяснены; stampede/stale/recovery проверены в измеримом workload envelope» — воспроизводимы локальным нагрузочным harness с concurrent clients, управляемым cache failure и счётчиками store reads; прямой прецедент — принятый R2, доказавший Load Control L3 лабораторным failure envelope без production. План корректно не заявляет L4: его каноническое действие — изменение shared cache/key/invalidation convention между несколькими сервисами с mixed-version behavior и production feedback (`level-outcomes.md:103`), что локальным flow недостижимо; L4 исключён явно (plan:312) и помещён в non-goals (plan:330). Условие честности — named topology граница (finding B-1): one-process coalescing доказывает L3 только внутри названного envelope.

**3. Какие решения обязательно должны быть приняты в Gate 0 до написания первого материала?**

Один cache-store и pinned client/runtime с версиями; process/worker topology и граница гарантии coalescing; source of truth и один freshness invariant; tenant-safe key schema; TTL/stale policy; atomicity/coordination semantics выбранного механизма по B3 record и применимость B5 record; invalidation ordering относительно commit с допустимыми исходами race; failure/fallback behavior при недоступном cache; populations (hit, cold miss, burst, race, failure, recovery); counters и measurement points; workload, concurrency, duration; thresholds из reproducible workload; stop conditions. План покрывает все, кроме явных topology и invalidation ordering — finding B-1.

**4. Есть ли кандидат, объективно сильнее S15 сейчас?**

Нет. Проверены все три соперника. Callback/SSRF — сильнейший completion-tail по security-ценности, но даёт ноль новых unique outcomes: Abuse L1–L3 уже имеют non-probe evidence, а L4 требует multi-service adoption (plan:352). HTTP Runtime — 11/11 membership outcomes уже связаны, новых outcomes нет, риск повторить C1/R1 максимален (plan:356). External Integration — L1–L3 уже имеют non-probe evidence из R2/R4/R5, единственный пустой L4 локально недостижим (plan:360). S15 — единственный кандидат с новым unique coverage (два полностью пустых outcomes, включая role-required L3 для обеих RoleViews) при root-capability без internal hard prerequisites (`prerequisites.md:37`). Порядок очереди подтверждаю независимо.
