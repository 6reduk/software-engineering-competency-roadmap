Выполненные проверки: пять populations (allowed/unauthenticated/cross-tenant/forged-context/missing-object) на собранном ASGI-пути через TestClient; десять вариантов invalid token (malformed, wrong key, `alg=none`, `alg=HS256` с секретом атакующего, wrong issuer, wrong audience, expired, future `nbf`, пустой `sub`, нестроковый `tenant_id`); счётчик вызовов application operation для доказательства «validation failure до application flow»; component-граница прямым вызовом operation; deny-by-default для `None`/empty-string context; byte-равенство cross-tenant/missing 404 (status, media type, `Cache-Control`, body bytes); точная форма `WWW-Authenticate` для missing vs invalid; сканирование audit sink на подстроки token/ключей/Authorization header/чужих полей Order.

Границы воспроизведения: реальный network/TLS не поднимался (TestClient — in-process ASGI, что и заявлено материалами как «собранный ASGI/HTTP path»); timing-поведение не измерялось; реализации участников не проверялись (материалы — specification, не реализация).

## Вывод по Gate 0 и техническому substrate

**1. Можно ли считать Gate 0 `confirmed` на закреплённом наборе версий? Да.**

Все семь строк readiness record сверены с первичными источниками и воспроизведены runtime: token/claims substrate (RFC 7519 §4.1, RFC 8725 §§3.1/3.8–3.9 — заголовки разделов соответствуют цитированиям: «Perform Algorithm Verification», «Validate Issuer and Subject», «Use and Validate Audience»), validation model (PyJWT 2.13.0 API: `require` — existence-only, предупреждение о `algorithms` соответствует), trust boundary, object rule, denial/audit semantics (RFC 6750 §3, RFC 9110 §§15.5.2/15.5.5, RFC 9457 §3). Заявление Gate 0 о совместимости FastAPI↔Starlette подтверждено metadata (`starlette>=0.46.0`, без верхней границы) и установкой.

**2. Оставить Starlette 1.3.1 или обновиться до 1.6.0? Оставить 1.3.1.**

Основания (не «latest всегда лучше» и не «существование версии»):

1. **Diff 1.3.1→1.6.0 не затрагивает поверхность slice.** По GitHub release notes: 1.4.0/1.4.1/1.5.0 — GZipMiddleware (производительность, `exclude_content_types`); 1.5.1 — FileResponse/Range hardening; 1.6.0 — `max_body_size` и `http.response.debug` extensions. Ни одно не касается bearer security dependency, JSON/Problem responses, challenge headers, TestClient. Slice не использует GZip, FileResponse, Range, multipart; `max_body_size` — это S14 abuse-controls territory, явно вне scope.
2. **Прямой контрольный прогон:** тот же harness на 1.6.0 — 32/32 PASS, поведение собранного ASGI-пути идентично. Upgrade технически возможен, но не даёт slice ни одного наблюдаемого улучшения.
3. **Editorial standard §12** прямо санкционирует pinned воспроизводимый baseline вместо automatically-latest.
4. **Консистентность программы:** принятый V1 slice (`truthful-test-boundaries`, verified 2026-08-20) уже закрепляет `starlette: 1.3.1`; точечный bump одного slice рассинхронизирует baseline принятых материалов без security-драйвера.
5. Материалы честно раскрывают разрыв в каждом разделе актуальности и требуют повторить ASGI evidence при upgrade — это правильная модель владения debt.

Условие на будущее: любой B2 slice с file/Range-serving — baseline ≥1.5.1 (note 2).

## Вывод по единому contract

**3. Правдивы ли 401/404 и audit contracts относительно первичных источников и runtime? Да.**

Двухрежимная семантика 401 — точная реализация RFC 6750 §3: отсутствие credential → `WWW-Authenticate: Bearer` без `error` (RFC: `error` включается SHOULD только когда token был предъявлён и отвергнут), предъявленный невалидный token → `Bearer error="invalid_token"`; оба — `application/problem+json` с идентичным телом, без раскрытия причины криптографического отказа. Требование 401 MUST содержать challenge подтверждено RFC 9110 §15.5.2. Локальный 404-concealment опирается непосредственно на определение 404 в RFC 9110 §15.5.5 («or is not willing to disclose that one exists») и заявлен в материалах как локальное продуктово-security решение, а не универсальная норма — без overclaim. Byte-равенство двух denial-ответов (status, media type, cache header, body bytes) доказано runtime. Audit contract: три вида записей с контрактными полями, coarse internal reasons, полный запрет credentials/claims/чужих полей — воспроизведён и просканирован. Contract единообразен во всех пяти файлах и Gate 0; media types, тела Problem Details и `no-store` совпадают дословно. Цитирования RFC 8725 §§3.1/3.8–3.9 и RFC 9457 проверены — соответствуют сделанным утверждениям.

## Что не доказано данным bounded evidence envelope

Честные границы доказательств (ни одно из перечисленного материалами не заявляется, поэтому это не findings, а ответ на обязательный вопрос 4):

- **Timing side channels:** равенство response bytes не доказывает равенство времени ответа cross-tenant hit vs missing-object lookup; материалы этого и не обещают.
- **Storage/traffic-каналы:** application-visible rule не доказывает изоляцию на уровне хранилища (RLS/physical separation вне scope), а анализ трафика/длины ответов не проводился.
- **Transport security:** TLS/сеть не воспроизводились (TestClient — in-process ASGI); bearer-over-TLS — внешний A3 baseline.
- **Token lifecycle:** revocation, rotation, JWKS, short-lived enforcement — вне scope; токен валиден до `exp` независимо от отзыва.
- **Enforcement у участников:** project-spec требует evidence второго adapter path, но ревью проверяет specification, а не реализации; реальная дивергенция путей у участников остаётся их проверяемым риском.
- **Операционная безопасность логов:** доказана дисциплина собственного audit sink slice; реальные лог-пайплайны/агрегаторы вне конверта.
- **S14 abuse controls и перечисление корректных ID:** перебор `order_id` внутри своего tenant, rate/quota — вне scope по non-goals.
