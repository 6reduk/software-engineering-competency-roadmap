## Findings

### F1 — некорректная формулировка термина в словаре index

```yaml
severity: minor
artifact: curriculum/tracks/b2/slices/runtime-concurrency-lifecycle/README.md, раздел «Словарь», строка «Backpressure»
criterion: correctness
finding: «Backpressure | Наблюдаемое ограничение приёма новой работы, когда нижняя граница уже насыщена»
evidence: «нижняя граница» читается как математический lower bound, а не «нижележащая зависимость» (downstream); «граница насыщена» — бессмысленная связка. Словарь index — первая точка встречи читателя с термином, и он даёт ложную опору. В brief 2 тот же термин определён иначе и корректнее («Передача сигнала насыщения к источнику новой работы через ограниченный исход») — два словаря одного slice расходятся в формулировке ключевого понятия перегрузки.
recommendation: заменить «нижняя граница уже насыщена» на «нижележащая зависимость уже насыщена» и выровнять формулировку со словарём brief 2.
```

### F2 — acceptance-порог «normal p95 ≤ 450 мс» не определяет популяцию измерения

```yaml
severity: minor
artifact: curriculum/tracks/b2/slices/runtime-concurrency-lifecycle/learn/bounded-concurrency-pool-saturation.md, раздел «Измеримый failure envelope»; то же число в README.md, kata/stop-orphan-work-and-pool-exhaustion.md и project-spec/resilient-fanout-service.md
criterion: correctness
finding: порог «normal p95 ≤ 450 мс» повторён в четырёх файлах, но ни один не указывает, по какой популяции он измеряется: все запросы деградированного прогона, только успешные исходы или отдельный прогон без задержки
evidence: при fan-out 4 и 25% медленных вызовов вероятность хотя бы одной медленной ветви в запросе ≈ 68% (1 − 0.75⁴); такие запросы по модели завершаются по deadline на ~600–650 мс, поэтому p95 по всем запросам деградированного прогона не может быть ≤ 450 мс — критерий при этом прочтении невыполним в принципе. Выполнимы прочтения «p95 обычного профиля (без 700 мс ветви)» или «p95 по запросам, не задетым медленной ветвью», но их нужно угадать: README лишь намекает контрастом «обычный p95 … каждый деградировавший запрос», а kata определяет «обычный профиль» только в части 1. Два исполнителя kata/project могут измерить разные популяции и получить противоположные вердикты при одинаковом поведении сервиса — это нарушает проверяемость acceptance threshold, которую пакет сам объявляет обязательной.
recommendation: в таблице brief 2 указать популяцию явно (например, «normal p95 ≤ 450 мс — p95 обычного профиля, прогона без 700 мс ветви» либо «…по успешным исходам деградированного прогона») и повторить то же уточнение в README, kata и project-spec.
```

### F4 — перегрузка термина «baseline» внутри brief 2

```yaml
severity: note
artifact: curriculum/tracks/b2/slices/runtime-concurrency-lifecycle/learn/bounded-concurrency-pool-saturation.md
criterion: structure
finding: «baseline» используется в трёх ролях: (1) «Лабораторный baseline намеренно фиксирует…» — имя всего failure envelope; (2) «Снимите baseline … без задержки dependency» — контрольный замер эксперимента; (3) «возврат к baseline» / recovery — нулевые state counters
evidence: kata и project-spec для той же таблицы используют имя «Failure envelope», то есть устоявшееся обозначение внутри slice уже есть; тройная перегрузка мешает точному чтению acceptance-пункта о recovery и границы «проверка против измерение».
recommendation: назвать таблицу brief 2 «Failure envelope» (как в kata/project) и в шаге 1 эксперимента писать «контрольный замер (baseline) без задержки».
```

### F5 — не указана точка измерения перцентилей в истории S08

```yaml
severity: note
artifact: curriculum/tracks/b2/slices/runtime-concurrency-lifecycle/interview/runtime-resource-failure.md, раздел «Рабочая история S08»
criterion: correctness
finding: наблюдение «p50 около 180 мс, p99 выше 4 секунд» не указывает, на какой границе измерены перцентили
evidence: gateway по условию обрывает ожидание на 600 мс, поэтому p99 > 4 с возможен только как service-side latency самого handler (правдоподобно: в неисправной версии действует pool timeout HTTPX по умолчанию ~5 с). Кандидат, восстанавливающий failure path, вынужден угадывать, чьи это перцентили, — а история, которая учит отделять факты от гипотез, сама оставляет факт недоопределённым.
recommendation: дописать уточнение вида «(по метрикам сервиса; gateway обрывает ожидание на 600 мс)».
```

## Переносимость editorial standard (взгляд профиля A)

Структурный каркас перенёсся на контрастную тему без новых сущностей:

- runtime-тема собрана целиком из существующих capabilities и LevelOutcome; ни одного нового Capability/LevelOutcome или специального coverage-role не потребовалось — это подтверждает ownership-модель B2 и границы B1/B5/B6/B7 на второй, принципиально иной теме;
- формат «failure envelope» (workload / duration / dependency behavior / acceptance) показал себя как воспроизводимый паттерн: он стихийно унифицирован в четырёх файлах и является главным кандидатом на фиксацию в стандарте — именно он отличает «случайный tuning» от диагностики;
- version-pinning + `last_verified` + требование перепроверить failure-тест перед переносом в проект сработали: все закреплённые версии реальны, ни один claim не устарел;
- паттерн «сквозная история с одинаковыми числами во всех шести файлах» выдержан (проверено на 80/700 мс, 25%, 12/60 с, пул 8, 600/650/450 мс, 1 с, 2 с);
- Mermaid с вводной и практическим выводом, локальные словари при ≥5 терминах, скрываемые ответы — применены без превращения текста ни в спецификацию для LLM, ни в мини-учебник по `asyncio` (языковая семантика B1 дана ровно в объёме service-level решения).

Правила, которые следует учесть при стабилизации `authoring/standards/editorial-standard.md` (по результатам профиля A):

1. **Популяция численного порога.** Любой acceptance threshold обязан называть, по какой популяции и на какой границе он измеряется (из F2; рождено этим slice, для API-эволюции не проявлялось).
2. **Согласованность словарей.** Определение термина в словаре index не должно расходиться со словарями дочерних briefs (из F1).
3. **Перегрузка load-bearing термина.** Один термин не должен использоваться в нескольких ролях внутри материала (baseline: envelope / контрольный замер / state-zero — из F4).
4. **Соответствие источников claims.** Список первичных источников содержит только источники фактически сделанных утверждений (из F3).
5. **Точка измерения факта.** Наблюдаемое число в рабочей истории интервью называет, где оно измерено (из F5) — частный случай общего правила про факты в interview-материалах.

Итоговое заключение о human-readability и переносимости в целом должно опираться на оба профиля; консолидация — за оркестратором.
