## Findings

### F-01 — OpenAPI freshness baseline указан неоднозначно и не является текущим — CLOSED

```yaml
severity: minor
artifact: curriculum/tracks/b2/slices/evolvable-api-contracts/README.md:58-60; learn/http-contract-execution-boundary.md:117; learn/compatible-api-change.md:122
criterion: freshness
finding: Пакет заявляет проверку по текущей документации на 2026-08-15, но называет нормативной базой OpenAPI 3.1.1 и ссылается именно на неё без объяснения выбранного compatibility target.
evidence: OpenAPI 3.2.0 является последней опубликованной minor-версией с 2025-09-19, а 3.1.2 — последней patch-версией линии 3.1. При этом текущий FastAPI по официальной документации по-прежнему генерирует поле `openapi: 3.1.0`. Значит, здесь нужно различить latest specification и фактический FastAPI output target; формулировка «текущая нормативная база 3.1.1» этого не делает.
impact: Читатель не понимает, почему выбран устаревший patch и какие именно возможности/ограничения проверены на FastAPI. Поле `last_verified` становится слабо воспроизводимым без baseline версии.
recommendation: Зафиксировать в README и version-sensitive briefs: FastAPI-generated target — OpenAPI 3.1.0 (проверить по выбранной версии FastAPI), нормативная ссылка для линии 3.1 — 3.1.2; отдельно отметить, что latest OAS — 3.2.0 и материал не предполагает автоматическую поддержку её новых возможностей FastAPI/toolchain. Добавить компактный `versions` baseline для FastAPI/Pydantic/OpenAPI либо эквивалентную явную оговорку.
```

Подтверждающие источники:

- [OpenAPI versions and latest specification](https://spec.openapis.org/oas/)
- [OpenAPI 3.2.0](https://spec.openapis.org/oas/v3.2.0.html)
- [OpenAPI 3.1.2](https://spec.openapis.org/oas/v3.1.2.html)
- [FastAPI: generated OpenAPI is currently 3.1.0](https://fastapi.tiangolo.com/tutorial/first-steps/#openapi-and-json-schema)

Resolution: закрыто. Оба version-sensitive brief получили `versions` с OAS 3.1.2, latest OAS 3.2.0 и документированным FastAPI output 3.1.0. README теперь явно разделяет нормативный baseline семейства 3.1, latest OAS и фактическую поддержку закреплённого FastAPI/toolchain.

### F-02 — Negotiated coexistence не фиксирует cache variance — CLOSED

```yaml
severity: minor
artifact: curriculum/tracks/b2/slices/evolvable-api-contracts/kata/compatible-delivery-contract-change.md:44-48,80; interview/api-contract-evolution.md:57; learn/compatible-api-change.md:64-70
criterion: correctness
finding: Content negotiation или version/header signal предложены как допустимые стратегии сосуществования error representations, но package не требует согласовать cache key с request negotiation signal (`Vary`, либо запрет/иная корректная cache policy).
evidence: Если один URL/status возвращает legacy JSON и `application/problem+json` в зависимости от `Accept` или custom request header, shared/intermediary cache без соответствующей variance может отдать representation не тому consumer. Это нарушает центральный инвариант пакета даже при корректных producer tests.
impact: Участник может реализовать формально рабочую dual-format стратегию, которая становится несовместимой при появлении proxy/cache; interview rubric не отличит такой ответ от корректного.
recommendation: Добавить одну строку в brief/kata self-review: при negotiation назвать request signal, response media type и cache behavior; для `Accept` — проверить `Vary: Accept`, для custom header — соответствующий `Vary` или обоснованно исключить shared caching. Не разворачивать отдельный курс по HTTP caching.
```

Resolution: закрыто. Требование согласовать negotiation signal, response media type и cache variance добавлено в brief, interview follow-up, kata self-review и project checklist. Формулировка корректно допускает соответствующий `Vary` либо обоснованный запрет shared caching.

### F-03 — RFC 9457 contract не доводит определение нового problem type до нормативного минимума — CLOSED

```yaml
severity: minor
artifact: curriculum/tracks/b2/slices/evolvable-api-contracts/learn/http-contract-execution-boundary.md:69-89; kata/compatible-delivery-contract-change.md:44-46,69-71; project-spec/evolvable-orders-api.md:56,67
criterion: correctness
finding: Материал правильно делает `type` машинным идентификатором и запрещает parsing `detail`, но не требует определить для нового problem type его type URI, title и применимый HTTP status; также не фиксирует, что присутствующий `status` в body должен соответствовать фактическому HTTP status, а HTTP(S) type URI желательно документировать.
evidence: RFC 9457 требует документировать для нового problem type type URI, title и HTTP status. Если advisory `status` включён в body, generator обязан использовать тот же status в HTTP response. RFC также рекомендует разрешимую абсолютную type URI с human-readable документацией. Текущий JSON example корректен, но rubric допускает формально «RFC-compatible» набор без этих проверок.
impact: Участник может получить нестабильную taxonomy problem types или расхождение body/HTTP status — именно тот класс wire/schema drift, который slice должен предотвращать.
recommendation: Добавить компактный checklist: для каждого public problem type заданы стабильный absolute type URI, title и intended HTTP status; если body содержит `status`, runtime status совпадает; решение о dereferenceable documentation зафиксировано. Сохранить `detail` только human-readable, extensions — machine-readable.
```

Подтверждающий источник: [RFC 9457, sections 3.1 and 4](https://www.rfc-editor.org/rfc/rfc9457.html#section-3.1).

Resolution: закрыто. Brief, kata и project checklist теперь требуют stable absolute type URI, title, intended HTTP status, совпадение присутствующего body `status` с wire status и явное решение о human-readable документации HTTP(S) type URI.

### N-02 — Версии клиентов и направления совместимости стоит сохранять явными — CLOSED

```yaml
severity: note
artifact: весь package
criterion: practice
finding: Материал уже различает old/new producer/consumer combinations в project checklist, но в коротких объяснениях слово producer иногда означает API service целиком, а не producer конкретного request/response message.
evidence: Для request client является producer сообщения и server — consumer; для response роли меняются. Направление важно при sequencing и rollback.
impact: Не создаёт текущей технической ошибки, но явная compatibility matrix снизит риск путаницы в ответах учеников.
recommendation: В будущей редактуре добавить одну компактную матрицу `old/new client × old/new server` или явно говорить `API provider/caller` и отдельно `request/response producer`. Не расширять текущий scope.
```

Resolution: закрыто. В brief добавлена компактная caller/provider compatibility matrix для legacy/new сочетаний, включая условие, когда `new caller × old provider` требуется из-за rollback, а когда комбинация запрещается stop condition. Матрица не навязывает поддержку всех сочетаний.

## Narrow re-pass

Повторно проверены изменённые формулировки:

- OAS/FastAPI branching различает OAS 3.1.2 как нормативный baseline семейства 3.1, OAS 3.2.0 как latest и документированный FastAPI output `3.1.0`; ложного обещания поддержки OAS 3.2 нет;
- execution path показан ветвящимся, а не линейным: normal, exception/unwind и cleanup paths разделены; отдельно отмечены response-start boundary и scope-dependent cleanup;
- `Vary` сформулирован не только для `Accept`: custom request signal требует соответствующей variance либо запрета shared caching;
- problem-type checklist соответствует RFC 9457 и не превращает `detail` в machine field;
- compatibility matrix технически корректно разделяет caller/provider и делает rollback combination условной;
- новых blocker, major, minor или ownership overlap не обнаружено.

## Correctness checks passed

- Pydantic v2: annotation `T | None` без default действительно допускает `null`, но не делает поле omittable.
- FastAPI response model действительно участвует в документации, response validation/serialization и output filtering; прямой `Response` переносит ответственность за wire body и документацию на автора.
- `responses={...}` описывает дополнительные responses, но само по себе не проверяет соответствие прямого `JSONResponse` заявленной schema.
- Ограничение `response_model_include/exclude`: runtime output фильтруется, однако generated OpenAPI продолжает показывать полную model schema; рекомендация использовать отдельную output model корректна.
- RFC 9457: `type` — primary machine identifier, `detail` не предназначен для machine parsing, extension `errors` допустим.
- Structural/semantic/operational compatibility разделены корректно; schema diff не объявлен достаточным доказательством.
- Expand → migrate → contract, inventory, coexistence, stop/exit criteria и ограниченная обратимость сформулированы без копирования ownership B6/B7/C1.
- Interview корректно отделяет L4 reasoning probe от реального L4 execution evidence.
- Kata ограничена L2 и не подменяет project evidence; project spec соответствует scaffolding contract и не содержит готового решения.
- Scope остаётся B2: framework semantics используются для service/API boundary, язык принадлежит B1, HTTP baseline — A3, deployment mechanics — B6, production change discipline — B7.
