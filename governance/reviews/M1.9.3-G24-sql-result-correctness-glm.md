# M1.9.3 — G24 профиль A: SQL/PostgreSQL, Gate 0, measurement и coverage

## Профиль, модель и способ проверки

Профиль **A** (SQL/PostgreSQL, Gate 0, measurement, coverage). Модель — **glm** (суффикс имени файла). Проверяемый пакет — глубокий slice SQ01: пять учебных материалов `curriculum/tracks/b3/slices/sql-result-correctness/`, первый `curriculum/tracks/b3/coverage-map.md`, регистрация в `curriculum/tracks/b3/README.md` и заполненный `Gate 0 record` work package M1.9.3. Полностью прочитан context manifest G24 (протокол, оба work package, orchestrator intake, G23 acceptance, семь каталогов B3 в связанных записях, стандарты 05/09/10, метамодель). Handoff и intake использованы как карты проверки, а не доказательства.

Проверка выполнена тремя независимыми способами:

1. **Аналитический пересчёт** всех числовых утверждений из исходных tuples (fan-out, counts, суммы, balance, ранги, порядок) без SQL.
2. **Ограниченный runtime-повтор** на PostgreSQL 18.6 во временной среде вне проекта с cleanup (разрешён work package; детали ниже). Повтор выполнен только по сохранённому record — схема, fixtures и три служебных запроса взяты дословно из Markdown, без какого-либо сохранённого harness.
3. **Сверка первичных источников** PostgreSQL 18 по каждому engine-dependent утверждению (versioning, table expressions, aggregates, comparison, window, ORDER BY, psql).

## Сверка первичных источников

Все engine-dependent утверждения подтверждены документацией PostgreSQL 18 (внешние источники — в списке ниже; даты проверки 2026-09-10):

- **Versioning**: текущие поддерживаемые версии — 18.6, 17.11, 16.15, 15.19, 14.24; 19 — Beta 3. Заявление материалов «18.6 — текущая minor поддерживаемой ветви 18; 19 — beta» **верно на дату review**; поле `versions` — воспроизводимый baseline, не production-рекомендация, и так и подписано.
- **Table expressions**: `LEFT OUTER JOIN` дополняет несопоставленную левую строку NULL-правыми полями; условие в `ON` обрабатывается до соединения, в `WHERE` — после, и для outer join это меняет результат; `GROUP BY` сворачивает группу в одну строку. Подтверждает изложение механизма fan-out и разделение ON/WHERE.
- **Aggregates**: `count(*)` — число входных строк, `count(expr)` — число ненулевых значений; `sum` пустого входа возвращает NULL (не ноль), `count` — исключение; `DISTINCT` внутри агрегата сворачивает равные значения. Подтверждает 400/200, 0-counts, SUM=NULL, «100 вместо 200».
- **Comparison**: обычные операторы сравнения с NULL дают NULL («unknown»). Подтверждает UNKNOWN у `amount > 50` и «WHERE оставляет только истинные».
- **Window**: peers — строки, неразличимые по выражениям оконного ORDER BY; `rank` с пропусками, `dense_rank` без пропусков, `row_number` уникален. Подтверждает 1,1,2,3 и «rank дал бы 1,1,3,4».
- **ORDER BY**: без явной сортировки порядок неопределён и полагаться на него нельзя; дополнительные ключи упорядочивают равные. Подтверждает требование отдельного `ORDER BY line_total DESC, order_id ASC` и тезис «три совпавших наблюдения не заменяют договор».
- **psql**: `-X` отключает startup-файлы; `ON_ERROR_STOP` даёт код выхода 3 при ошибке в script. Заявление kata о `-X -v ON_ERROR_STOP=1` и коде 3 верно.

## Verdict

`accepted`: **0 blocker / 0 major / 1 minor / 3 note**.

Техническая основа пакета выдержала независимую проверку целиком: каждый численный результат, каждая engine-семантика и каждое freshness-заявление подтвердились аналитически, на живом PostgreSQL 18.6 в изолированном стенде и по первичным источникам. Coverage-пересчёт сошёлся с авторским и intake без расхождений. Verdict — рекомендация профиля A; принятие G24 остаётся отдельным решением оркестратора после второго профиля и consolidation.

### A-M1 — нормативное утверждение о сохранении строк окном не подтверждено ни одним из перечисленных источников

```yaml
severity: minor

criterion: freshness
finding: Утверждение «оконная функция вычисляет значение для каждой строки своего входа, сохраняя их» (brief; его вариации — в ответах interview, разделе «Группа и окно решают разные задачи», index и матрице kata) — нормативная SQL-семантика, но ни один из шести перечисленных источников её не содержит: страница functions-window определяет peers и ранги, а контраст с GROUP BY («the rows retain their separate identities» и «logically execute after ... GROUP BY») находится в tutorial §3.5 (tutorial-window.html), которого в списках нет. По редакционному стандарту §12 нормативное утверждение должно подтверждаться первичным источником соответствующей силы.
evidence: Утверждение истинно (подтверждено моим runtime-повтором и текстом §3.5), поэтому дефект — только в полноте freshness-маппинга, а не в содержании. Источники в пяти файлах повторены дословно, поэтому разрыв тиражирован во все пять точек входа.
recommendation: В общий блок «Источники и актуальность» (одна правка, синхронно в пяти файлах) добавить ссылку tutorial-window.html с формулировкой «[Оконные функции в запросе](https://www.postgresql.org/docs/18/tutorial-window.html) объясняют, почему окно не сворачивает строки и выполняется после GROUP BY». Дата проверки уже стоит в этом же блоке; отдельное датирование не требуется.
disposition: до acceptance (однострочная правка в пяти файлах) либо backlog.
```

## Ответы на обязательные вопросы

1. **Можно ли принять пакет как первый глубокий B3 slice SQ01 без расширения до полного SQL-курса?** Да. Все пять материалов держат один наблюдаемый дефект и один договор; join/window-функции разобраны ровно в объёме, нужном для причинной цепочки «кратность → гранулярность промежуточных строк → неверный агрегат»; нет перечислений синтаксиса, нет optimizer-контента; границы IO01/RM01/B4/B2/TC/SE01/BR01/L4-L5 повторены в каждой точке входа и в coverage map. Slice остаётся bounded.

2. **Где проходит первое наблюдаемое искажение и какие данные действительно отличают исправление от маскировки?** Первое искажение — на этапе второго `LEFT JOIN`: у заказа 1 промежуточный набор получает гранулярность «строка × платёж» (4 строки), суммы уже завышены (400/200, counts 4/4) до всякого GROUP BY; GROUP BY лишь сворачивает неправильный набор, что материалы и показывают. Различают исправление и маскировку пять данных: (a) две реальные равные стоимости 101/102 по 100 — отвергает `SUM(DISTINCT)` (100 ≠ 200); (b) заказ 2 без платежей — отвергает WHERE/INNER-«фиксы» и деление на число платежей; (c) пустой заказ 3 — отвергает потерю полного набора orders и синтетический «нулевой заказ»; (d) равные итоги 1/4 — отвергает row_number и «стабильность без ORDER BY»; (e) полностью пустой orders — требует ноль строк. Полная построчная сверка с порядком противостоит checksum-совпадению.

3. **Достаточен ли Gate 0 для authoring claims и честно ли сформулирован предел доказательства?** Да. Record закрепляет версию/источники/схему/fixtures/control/defect/fixed/expected, двунаправленный EXCEPT ALL, полную сверку строк, три чистых прогона, отдельный doccheck всех семи SQL-блоков и cleanup; предел сформулирован явно («доказывает семантику закреплённых схемы, данных, запросов и версии… не произвольного SQL… производительность и production readiness не проверялись»). Мой повтор из одного record без harness подтверждает заявленную воспроизводимость. 4. **Правдивы ли L1/L2/L3 и все 30 roles; отдельно по grouped/window L3.** Да.
