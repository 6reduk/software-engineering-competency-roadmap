## Findings

### F-B-1 — major

```yaml
severity: major
artifact: curriculum/tracks/b2/slices/tenant-scoped-orders-cache/learn/cache-aside-freshness-coalescing.md
criterion: correctness
finding: Раздел fail-closed объединяет ошибки Redis `GET` и `SET` в один контракт («ошибка `GET` или `SET` возвращает `503 cache_unavailable`», «read operation не обращается к PostgreSQL после cache error»), а единственная failure population с нулём source reads — это outage, где каждый request падает на начальном `GET`. Исход ошибки `SET`, которая происходит уже после выполненного PostgreSQL read, и его counter outcome в учебных материалах не сформулированы нигде (project-spec называет сценарий «Redis `SET` не выполнен», но не задаёт ожидаемый счётчик).
evidence: Читатель learn естественно обобщает «cache error ⇒ source_read=0» на обе точки отказа, хотя для post-read `SET` failure source read уже состоялся. Это ровно open question 1 intake и anti-pattern «не объединять Redis GET и SET failures, если они происходят по разные стороны source read» — на уровне human-readable формулировки материал объединяет их. Gate G12 требует, чтобы `GET`/`SET` failure paths и их source-read counters были сформулированы непротиворечиво.
recommendation: Минимальная правка learn (и при необходимости одной строки project-spec failure scenario 4): разделить два failure point — ошибка `GET` до source read (source read не выполняется) и ошибка `SET` после source read (read уже учтён в `source_read`, request всё равно завершается `503`) — и явно указать, к какой точке/population относится наблюдаемый ноль source reads. Техническая adjudication counter semantics остаётся профилю A.
```

## Вывод по Cache L2/L3 и coverage

Coverage правдив. Cache L2 подтверждается самостоятельным применением pattern: kata требует от участника построить key, TTL, hit/miss, isolation и failure checks и исправить один concurrent-miss defect; project закрепляет это на normal path. Cache L3 подтверждается другим, непересекающимся по смыслу evidence: управляемый late-fill race с timeline, commit → `DEL` ordering и rollback-контроль, измеренный amplification с сохранённым дефектным baseline, осознанный fail-closed trade-off с outage/recovery populations и ADR с альтернативами. Это не «один сценарий с двумя ярлыками»: L3-only наблюдаемые результаты (race timeline ≤2250 мс, отрицательная демонстрация двух workers, decision record) не существуют на уровне L2. Cache L4 отсутствует и корректно отложен в долг; supporting capabilities не начисляются, что согласуется с решением M1.8.12 G11. Арифметика relationships (11 = 1 + 10) и роли по жанрам совпадают с контрактом work package и регистрациями.

## Вывод по freshness/failure/coalescing boundary (со стороны learning design)

Граница изложена связно и честно: 2.25-секундный invariant сформулирован наблюдаемо («после commit… затем следующий успешный response обязан содержать новую version»), late fill разобран на sequence diagram с управляемой паузой, fail-closed обоснован через fan-out риск, one-process граница coalescing повторена во всех пяти файлах без distributed overclaim, а double-check и lifecycle cleanup (включая cancellation владельца) объяснены причинно. Два места требуют внимания: failure contract learn объединяет pre-read `GET` и post-read `SET` failure под одну формулировку (F-B-1, major) и вывод 2.25 с дан без явной арифметики (F-B-6, note). Математическая доказанность bound для всех interleavings — вопрос профиля A; со стороны читателя модель понятна, но именно эти две точки опираются на догадку читателя.

## Вывод по различию kata и project

Различие достаточное и наблюдаемое. Kata: воспроизвести один дефект (burst → почти 32 source reads), внести минимальную per-key coordination правку, доказать `source_read≤1` на пяти bursts и добавить regression checks — результатом является defect test, минимальный diff и counters. Project: интеграционный milestone со всеми populations, управляемым race с timeline commit/delete/fill, rollback-демонстрацией, forged-tenant negative population, cancellation владельца, outage/recovery, ADR с альтернативами и защитой — результатом являются raw observations, decision record и defense. Kata прямо отсылает race и workers в project, project явно требует раздельных L2/L3 evidence в review criteria. Пересечение populations (bursts, isolation, failure, recovery встречаются в обоих) является осознанным: kata оценивает исправление дефекта, project — интеграцию и проектирование; различие зафиксировано в ожидаемых артефактах, а не только в формулировках.

Project-spec при этом не является предписанной архитектурой (open question 4 review WP): закреплён substrate и contract — это предмет slice по замыслу Gate 0, — но структура adapters и application operation, механизм coordination, способ управляемой паузы, способ симуляции outage, устройство harness и ADR-рассуждение оставлены участнику; готового кода и ImplementationReference нет. Milestones задают наблюдаемые результаты, а не план реализации, что соответствует §8 документа 10.

## Ответы на обязательные вопросы профиля B

1. **Дают ли Cache L2 и L3 разные наблюдаемые evidence?** Да. L2 — корректное применение pattern (key/TTL/hit/miss/isolation/failure checks, исправленный дефект coalescing); L3 — race timeline, commit ordering, измеренный amplification с baseline, outage trade-off, recovery и ADR. Пересечение populations снято различием ожидаемых артефактов.
2. **Объясняет ли brief причинную модель или перечисляет решения Gate 0?** Объясняет. Каждый раздел learn идёт от проблемы через механизм к компромиссу: почему query tenant небезопасен, почему lock без повторного `GET` лишь сериализует stampede, почему commit → `DEL` допускает late fill, почему fail-open без admission восстанавливает stampede. Это причинная модель, а не перечень Gate 0.
3. **Достаточно ли различаются kata и project?** Да — см. отдельный вывод; результаты различимы наблюдаемо.
4. **Понятны ли человеку 2.25-секундная boundary, late fill и fail-closed без чтения work package?** В целом да: все три объяснены через наблюдаемые следствия и контрпримеры внутри самих материалов. Оговорки: вывод 2.25 с не показан арифметически (F-B-6), а fail-closed формулировка смешивает GET/SET failure points (F-B-1).
5. **Оставляет ли project-spec пространство для самостоятельного инженерного решения?** Да. Закреплены contract и substrate (предмет пакета), но архитектура, coordination mechanism, harness и способ воспроизведения отказов принадлежат участнику; ADR требует сравнения альтернатив, включая не выбранные.
6. **Можно ли принимать slice после disposition findings?** Да. Blocker нет; после исправления F-B-1 (major) и adjudication F-B-2/F-B-3 (minor) и notes оркестратором slice может быть принят без повторного review полного объёма.

## Ответ на вопрос о принятии slice

Slice можно принимать после disposition: устранение одного major (F-B-1 — разделение GET/SET failure points и их counter outcomes в learn), решения оркестратора по двум minor (гlossing англицизмов; burst-duration threshold) и фиксация решений по трём notes. Ни один finding не требует переработки структуры slice, изменения coverage или Gate 0.
