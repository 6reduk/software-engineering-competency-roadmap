# M1.8.5 — G7 review, Профиль A: domain и technical correctness

## Профиль, модель и scope

- Профиль: **A** — domain и technical correctness по `governance/work-packages/M1.8.5-G7-transactional-persistence-review.md`.
- Фактическая модель: `glm` (glm-5.3).
- Scope: пять артефактов `curriculum/tracks/b2/slices/transactional-orders-operation/` (index, learn, interview, kata, project-spec), B3 readiness record в `governance/work-packages/M1.8.5-transactional-persistence-s07-slice.md`, регистрации M1.8.5 в `curriculum/tracks/b2/README.md` и `curriculum/tracks/b2/coverage-map.md` — в части технических утверждений и границ B2/B3/B5. Learning design и human readability проверяет Профиль B; здесь они затронуты только через техническую проверяемость.

## Verdict

`accepted_with_changes`.

Счётчик: **0 blocker / 0 major / 1 minor / 3 note**.

Техническая основа среза подтверждена по первичным источникам: версии актуальны на 2026-08-21, транзакционная модель (`autocommit=True` + один внешний `with conn.transaction():`), утверждения о `READ COMMITTED` и повторной проверке `WHERE`, локальная durability при `fsync=on`/`synchronous_commit=on`, модель unknown commit и раздельность unknown commit / unknown publish корректны и честно ограничены. Единственный minor касается полноты measurement envelope проекта относительно его же acceptance-критерия (конкурентные разные key на одном draft order); замечания уровня note — уточнения одной фразой.

## Findings

### A-1 — minor — envelope

```yaml
severity: minor
artifact: curriculum/tracks/b2/slices/transactional-orders-operation/project-spec/resilient-order-confirmation.md
criterion: practice
finding: В Evidence B нет популяции «два разных key конкурентно подтверждают один draft order». Конкурентные испытания (20 trials и case 1) задают только одинаковый key; case 4 (новой key для already confirmed order) — последовательный.
evidence: Критерий приёмки «race создаёт не более одного `draft → confirmed` transition и одного event record/event_id» фактически проверяется только на same-key race, где единственность перехода гарантирована уже дедупликацией identity (unique constraint на operation_id), а не условным UPDATE. Реализация с «сначала свободный SELECT статуса, потом безусловный UPDATE» пройдёт все объявленные случаи и обнаружит двойной переход только при гонке разных key. Механизм, который её защищает (ожидание + повторная проверка WHERE на новой версии строки), в learn преподаётся, но ни одна объявленная популяция его не исполняет.
recommendation: Добавить в Evidence B один case: два разных key/fingerprint на одном draft order, отпущенные одновременно; ожидания — ровно один переход, один event record, одному запросу `409 order_not_draft`. Альтернатива — одна фраза в envelope, что единственность перехода при разных key гарантируется условным UPDATE и проверяется инспекцией схемы/состояния, а не конкурентным прогоном.
```

### A-2 — note — mechanics

```yaml
severity: note
artifact: curriculum/tracks/b2/slices/transactional-orders-operation/learn/transaction-boundary-failure-windows.md
criterion: correctness
finding: Утверждение «проигравший запрос ждёт завершения владельца key, затем воспроизводит committed result» опускает механику: после ошибки unique violation транзакция PostgreSQL находится в aborted-состоянии и отказывается выполнять дальнейшие команды до ROLLBACK, поэтому чтение сохранённого result происходит уже в новой транзакции.
evidence: Официальная документация Psycopg: «If a database operation fails, the server will refuse further commands, until a `rollback()` is called». Контрактное утверждение материала верно, но участник kata/project впервые встретит это механическое следствие без подсказки.
recommendation: Одна фраза в learn (или hint kata): проигравший завершает свою транзакцию rollback по ошибке ограничения и читает сохранённый result повторным чтением.
```

### A-3 — note — contract edge

```yaml
severity: note
artifact: curriculum/tracks/b2/slices/transactional-orders-operation/project-spec/resilient-order-confirmation.md
criterion: correctness
finding: Контракт не указывает, какой исход считается правильным, если два конкурентных replay одного key оказываются по разные стороны границы 24-часового retention (один успевает прочитать сохранённое тело, другой видит tombstone и получает `409 idempotency_key_expired`).
evidence: Критерий «все same-fingerprint responses семантически совпадают» сформулирован без оговорки о границе expiry; в объявленном envelope (retention-кейсы отдельно от конкурентных trials) расхождение не проявится, но реализатор case 5 с управляемым clock спросит о границе.
recommendation: Одно уточняющее предложение: expiry вычисляется на момент чтения каждого запроса; запросы, пересекающие границу, могут получить разные определённые исходы, и это не нарушение инварианта.
```

### A-4 — note — envelope consistency

```yaml
severity: note
artifact: curriculum/tracks/b2/slices/transactional-orders-operation/kata/recover-order-confirmation.md
criterion: practice
finding: Acceptance criteria kata включают conflict-, expiry- и new-key-проверки, но envelope объявляет число прогонов только для 10 основных прогонов (5 контрольных + 5 fault); количество прогонов дополнительных кейсов не указано (в project для аналогичных кейсов задано «по 5»).
evidence: Формулировка «не менее 10 независимых прогонов» оставляет место, однако критерий «Все 10 прогонов удовлетворяют объявленному threshold» не покрывает явно дополнительные проверки, и участник вынужден сам решать, сколько их выполнять.
recommendation: Указать, что conflict/expiry/new-key выполняются как по одному детерминированному прогону вне 10 основных (или перенести их в отдельный короткий список с числом).
```

## Отдельный вывод: Transaction L3 evidence

Evidence A (project) задаёт состояние F0–F3, restart-recovery и критерии атомарности `orders`/`operation_results`/`order_events` и обнаружимости pending event. Наблюдаемые точки (primary PostgreSQL после quiescence, sink log, логи publisher) достаточны, чтобы отличить commit, unknown commit, publish и unknown publish как разные state transitions. Эти критерии действительно не покрываются idempotency-наблюдениями; рекомендация A-1 не умаляет Transaction L3, а дополняет Evidence B.

## Отдельный вывод: Idempotency L3 evidence

Evidence B проверяет identity/result/conflict/retention, F1-retry и concurrent duplicates раздельно от recovery, с требованием сверять authoritative rows и event identities, а не количество HTTP 200. Единственное замечание — популяция гонки разных key (A-1): без неё (или без явной оговорки) критерий «race создаёт не более одного transition» опирается только на same-key race, где единственность обеспечивается identity, а не граничным механизмом. После минимального дополнения evidence соответствует заявленному уровню.

## Отдельный вывод: единый контракт и различие kata/project

Контракт HTTP-command, result, события и схемы воспроизводится без расхождений во всех пяти файлах (включая версии и settings). Kata и project дают разные наблюдаемые результаты: kata — один crash window `after_commit_before_publish`, restart/recovery и replay/conflict на минимальной self-built системе с 10 прогонами; project — четыре fault points, реальный substrate, restart/recovery, concurrent duplicates, retention и два раздельных L3-эксперимента с собственными envelope и decision record. Проверяемые результаты не пересекаются настолько, что один не подменяет другой.

## Первичные источники и граница runtime verification

Проверено по живым страницам 2026-08-21:

- [PostgreSQL Versioning Policy](https://www.postgresql.org/support/versioning/) — 18.6 current minor (2026-08-13), PG18 до 2030-11-14.
- [PostgreSQL 18: Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html) — Read Committed: аномалии, ожидание и повторная проверка WHERE.
- [PostgreSQL 18: WAL settings](https://www.postgresql.org/docs/18/runtime-config-wal.html) — synchronous_commit/fsync, локальный flush.
- [PostgreSQL 18: libpq PQstatus/PQtransactionStatus](https://www.postgresql.org/docs/18/libpq-status.html) — CONNECTION_BAD, PQTRANS_UNKNOWN.
- [Psycopg: Transactions management](https://www.psycopg.org/psycopg3/docs/basic/transactions.html) — autocommit + transaction(), savepoint при открытой implicit transaction, отказ команд после ошибки до rollback.
- [Psycopg: ConnectionInfo.status/transaction_status](https://www.psycopg.org/psycopg3/docs/api/objects.html) — OK/BAD, UNKNOWN при плохом соединении.
- [Psycopg: Release notes](https://www.psycopg.org/psycopg3/docs/news.html) — «Current release: Psycopg 3.3.4», 3.3.5 unreleased; [PyPI psycopg](https://pypi.org/project/psycopg/) — 3.3.4 (2026-05-01), latest.

**Граница runtime verification:** runtime-воспроизведение не выполнялось — на рабочей машине отсутствуют PostgreSQL-сервер и пакет psycopg (доступен только Python 3.14 без драйвера). Всё выше — документальная проверка по первичным источникам; реализуемость F1-harness (оба server outcome через управляемое разрывание соединения в protocol window) оценена аналитически и не проверена эмпирически. Это ограничение настоящего review, а не дефект материалов: сами материалы runtime-утверждений не публикуют и честно требуют raw summary от участника.

## Можно ли принимать slice

Да — после disposition единственного minor (A-1: внести case конкурентных разных key в Evidence B либо явно оговорить, что единственность перехода при разных key проверяется инспекцией условного UPDATE). Открытых blocker/major нет; notes A-2–A-4 — необязательные уточнения одной фразой, могут быть приняты оркестратором или перенесены в backlog. Решение о disposition и перенос статусов — за оркестратором; данный review gate не закрывает.
