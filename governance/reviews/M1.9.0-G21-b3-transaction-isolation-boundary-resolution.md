# M1.9.0 — решение оркестратора по G21 B3 transaction/isolation boundary

## Решение

Консолидированный отчёт сопоставлен с двумя исходными независимыми профилями. Итог принят как `accepted_with_changes`: `0 blocker / 0 major / 1 minor / 5 note`; minor A-1 профиля A отозван после повторной сверки первичного источника и не входит в итоговый счётчик.

До acceptance выполняется один ограниченный correction package [`M1.9.0a-G21-findings-correction.md`](../work-packages/M1.9.0a-G21-findings-correction.md). Повторный полный G21 и новые независимые профили после этих локальных правок не требуются; оркестратор выполнит точечную проверку C-1–C-6 и отдельный acceptance-pass.

## Подтверждённая граница

- B2 сохраняет application operation, commit/rollback boundary, идемпотентность и внешние эффекты; B3 исследует store-level isolation, visibility, anomalies и error signals.
- B5/B6/B7 не присваиваются: один store не превращается в distributed consistency, платформенный пакет или production reliability exercise.
- Выбрано одно действие: проверить общий инвариант двух операций, изменяющих разные строки, при переходе PostgreSQL `REPEATABLE READ → SERIALIZABLE`.
- S07 и S15 используются как контраст и не передают B3 свои версии, readiness, coverage или proficiency.
- `control / defect / fixed` являются проектом будущего evidence. Эксперимент не выполнялся, Gate 0 не подтверждён.
- Роли получают разный полезный depth без назначения outcomes, L4/L5 или production adoption.

## Disposition

| Finding | Решение | Обоснование |
|---|---|---|
| A-1, minor, отозван | Не менять intake | Повторная проверка официальной страницы показала `3.3.6.dev1`, как и указано в intake. Нестабильность dev-маркера уже корректно ограничена требованием повторной сверки после выбора stable driver. |
| C-1, minor | Исправить до acceptance | Чтение, решение и запись каждого actor должны явно находиться в одной транзакции; иначе future fixed способен ложно опровергнуть `SERIALIZABLE`. Наблюдаемое чтение нужно связать с transaction identity записи. |
| C-2, note | Исправить тем же проходом | Для control следует явно закрепить первое snapshot-forming statement либо протоколировать более раннее. Это делает причину отклонения control различимой. |
| C-3, note | Исправить тем же проходом | Уточнить, что PostgreSQL documentation подтверждает `serialization anomaly`, а `write skew` — локально введённое имя класса дефекта. |
| C-4, note | Исправить тем же проходом | Назвать `40001` ожидаемым различающим сигналом fixed; `40P01` должен означать незапланированное lock-взаимодействие, а не успешный результат сценария. |
| C-5, note | Исправить тем же проходом | Сжать процессные оговорки и вынести их из основного объяснения, чтобы документ не выглядел серединой внутреннего разговора. Audit trail при этом сохранить ссылками. |
| C-6, note | Исправить тем же проходом | Заменить необъяснённый `NOT_RUN` на обычную русскую формулировку; новый статусный словарь не нужен. |

## Условия correction-pass

- Правки локальны и не меняют выбранный action, бизнес-инвариант, три профиля опыта, список readiness-категорий или non-goals.
- Текст различает исходный store conflict, его rollback и отдельную новую попытку всей операции с новым чтением.
- Не предписываются конкретная serialization victim и точка обнаружения ошибки.
- Не добавляются скрытые locks, constraint, общая строка, application mutex, retry subsystem или второй эксперимент.
- Не выбираются PostgreSQL build и Psycopg version, не запускается среда и не подтверждается ни одно условие Gate 0.
- Metadata, отсутствие coverage и semantic IDs, ссылки и статус `review` сохраняются.

## Следующий фазовый выбор

После acceptance intake оркестратор должен отдельно назначить ограниченный B3 capability blueprint для `b3.cluster.transactions-concurrency`, а не сразу писать пятижанровый материал. Причина: B3 пока имеет только track skeleton; прежде чем начислять будущие уровни и coverage, нужно определить action-oriented capabilities, наблюдаемые LevelOutcomes, границы ролей и prerequisites хотя бы для выбранного кластера. Gate 0 остаётся обязательным до authoring технически зависимого учебного содержания.

Это направление не создаёт следующий пакет автоматически и не закрывает B2 debt.

## Acceptance после corrections

M1.9.0 можно принять без повторного G21, когда точечная проверка подтвердит C-1–C-6, сохранность границ и `status: review` исходного intake. Затем отдельный acceptance-pass может перевести intake и связанные work packages в `accepted`, обновить program status/decision log и назначить следующий bounded planning package.
