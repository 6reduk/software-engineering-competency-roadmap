## Согласованные выводы

### 1. Числа и state transitions

Контрольные величины подтверждены обоими профилями без расхождений: **17 artifacts / 130 relationships (11 `reference` + 119 outcome-level) / 41 покрытых / 28 непокрытых из 69 / 4 новых (Architecture L1–L3, Verification L1) / 7 probe-only / complete 0, partial 4, not-started 6, blocked 0.** Переходы применены по существующим определениям без изменения их смысла:

- Service Architecture `not-started → partial` — собственный принятый flow A0–A4 без module-gate decision; автоматического completion нет (Architecture L4, External Services L4, Verification L4 не покрыты).
- Transactional Persistence `blocked → not-started` — hard edge `manage-application-transaction-boundaries → design-service-architecture` требовал evidence вокруг application operation, и оно принято (A1 `explain`, A3 `practice/assess`, A4 `integrate/assess`; dependency direction зафиксирована). Оставшаяся зависимость — B3 conditional baseline — по действующему `prerequisites.md` не является internal hard edge; план корректно переводит её в pre-authoring readiness check (open question 2), сохраняя B3 conditional, а не скрытым полным prerequisite.
- Hard prerequisite DAG соблюдён по всей очереди; полнота набора жанров нигде не принята за module completion; `probe` нигде не учтён как execution evidence.

### 2. Выбор Service Verification/S10

Оба профиля отвечают «да» на вопрос gate, с разных сторон:

- **Профиль A (механика/структура):** decision brief полон по всем требованиям work package (один module, один primary scenario S10, ровно два supporting S03/S06, одно центральное действие, минимальный flow пяти жанров, non-goals, три отвергнутые альтернативы); S08 корректно оставлен ссылочным контекстом; нет ложных claims о новой hard DAG edge или автоматическом завершении модулей; выбор не противоречит DAG и не повторяет центральные действия S03/S06/S08.
- **Профиль B (обязательный вопрос «S10 или уже разблокированный S07 именно сейчас»):** **да, S10 предпочтительнее сейчас** — по capability gaps, prerequisite readiness, learning leverage и boundedness, а не по порядку тем. S07 при снятом internal hard block всё ещё упирается в неподтверждённый B3 conditional baseline и обязан держать двойную границу от B3 (store-level semantics) и B5 (recovery/consistency); S10 не имеет неподтверждённых внешних входов (A2 — только reference context), замыкается на одну seeded serializer/error-mapping regression на переиспользованном S03 substrate и конвертирует Verification L3 evidence, сегодня существующее лишь как побочный продукт S06/S08 (R3 `probe`, R5 `integrate`), в собственную capability, которую немедленно потребуют S07 и S11.
- **Честная оговорка (Kimi, N-1/N-2 ниже):** по критерию «пустое primary coverage» S10 проигрывает S07 и S05 — новое уникальное покрытие пакета фактически только Compatibility L1, а «9/12 membership связано» включает один probe-only. Work package прямо запрещает сводить выбор к максимально пустой capability; план эту слабость не скрывает, поэтому выбор не является выбором «ради полного набора жанров».

### Note

**C-1 (🟡 Kimi N-1). Явно назвать ожидаемое новое coverage пакета S10.**
Decision brief не называет ожидаемое *новое* outcome coverage: Verification L1–L3 и Compatibility L2/L3 уже имеют accepted relationships, оба L4 вне scope, поэтому единственный непокрытый candidate — Compatibility L1; ценность пакета — консолидация и собственный flow.
Диспозиция: **в authoring work package S10** (или при следующей правке плана) одной строкой зафиксировать: «ожидаемое новое coverage — прежде всего Compatibility L1; остальные outcomes получают собственный flow поверх существующих cross-module relationships».

**C-2 (🟡 Kimi N-2). «9/12 membership связано» включает один probe-only.**
Для Service Verification 9/12 по конвенции плана («покрыто = есть accepted relationship») верно, но включает Compatibility L4 с единственной связью `probe` в C3; execution-покрытие — 8/12 + 1 probe-only.
Диспозиция: **косметическая правка при следующем обновлении** — уточнить формулировку до «8/12 execution + 1 probe-only» там, где число используется в аргументации выбора; на вывод не влияет.

**C-3 (🟡 Kimi N-3). Ограничить измерение portfolio milestone одним сервисом.**
Milestone «убрать измеримо дублирующиеся slow/flaky checks» легитимен (дословно совпадает с evidence criterion Verification L3), но при неаккуратном authoring может разрастись в общий курс performance/flaky-test optimization.
Диспозиция: **в authoring work package S10** — ограничить измерение одним сервисом и critical paths, без общих бенчмарков и оптимизации тестовой инфраструктуры.

**C-4 (🔵 GLM N-1). Критерий снятия `blocked` не формализован.**
`prerequisites.md` задаёт только рёбра `Requires` без правила их «выполнения»; текущий переход TP `blocked → not-started` корректен, но при будущих разблокировках (Background workflows, Safe service evolution) тот же вопрос встанет без эталона для сверки.
Диспозиция: **решение оркестратора** — зафиксировать одно предложение-правило (например: hard prerequisite считается выполненным, когда prerequisite capability имеет принятые execution-evidence relationships минимум до L2) в определениях состояний плана или отдельным решением; удобный момент — следующий refresh.

**C-5 (🔵 GLM N-2). Сокращённые имена модулей в таблице Shared module membership.**
«HTTP runtime», «Identity-aware boundaries», «Performance/resource control» отличаются от полных названий `modules.md` и сводной таблицы того же плана; семантической неоднозначности нет (все 19 строк сверены), но машинный пересчёт требует ручного маппинга имён.
Диспозиция: **косметическая правка либо backlog** — привести имена к полным названиям или добавить module IDs.
