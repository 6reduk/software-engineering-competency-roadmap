# M1.8.15 — G14 профиль A: delivery mechanics, техническая корректность, measurement

## Профиль, модель и scope

Профиль A из `governance/work-packages/M1.8.15-G14-safe-service-evolution-review.md`: delivery mechanics, техническая корректность и measurement. Learning design, human readability и editorial-качество пяти материалов — scope профиля B и здесь не оцениваются. Фактическая модель: GLM (`glm-5.3`), окружение Claude Code CLI, Windows 11, CPython `3.14.0` — тот же pinned baseline, что и в Gate 0.

Проверены: запись Gate 0 в work package M1.8.15 (текущий `confirmed` и исторический `blocked`), все пять материалов slice, регистрации в `curriculum/tracks/b2/README.md` и `curriculum/tracks/b2/coverage-map.md`, принятые S03/S10 контракты, каталоги B2 и решения G12/G13. Выполнено независимое минимальное локальное воспроизведение протокола Gate 0 одноразовым harness вне проекта (подробности и substitutions ниже), удалённым после проверки.

## Verdict

`accepted_with_changes`: blocker и major отсутствуют; два minor требуют минимальных уточнений формулировок либо явного adjudication оркестратора, три note — рекомендации без обязательства. После disposition findings slice можно принимать (см. «Ответ на принятие»).

Счётчик: `blocker 0 / major 0 / minor 2 / note 3`.

## Метод и независимое воспроизведение

Помимо чтения первичных материалов выполнены:

1. **Механические проверки** (read-only): пять уникальных semantic IDs; 13 YAML relationships с распределением `1 reference / 3 explain / 3 probe / 1 practice / 3 assess / 2 integrate`; четыре unique targets, все существуют в `capabilities.md`/`level-outcomes.md`; все относительные ссылки разрешаются, anchor `#gate-0-record` существует; fences и `<details>` сбалансированы; conflict markers, trailing whitespace и `ImplementationReference` отсутствуют.
2. **Freshness-проверка по первичным источникам** (2026-09-08): [python.org](https://www.python.org/downloads/release/python-3140/) подтверждает выпуск 3.14.0 (2025-10-07) и что он superseded; [docs.python.org/3.14](https://docs.python.org/3.14/library/time.html) действительно отображает **3.14.7** — в точности как заявлено в Gate 0 и README; `time.monotonic` описан как не идущая назад часы для интервалов; [RFC 9457 §3](https://www.rfc-editor.org/rfc/rfc9457.html) — «The Problem Details JSON Object», определяет `type`/`status`/`title`/`detail` и расширения в §3.2. Все version/source claims корректны.
3. **Локальное воспроизведение протокола Gate 0**: одноразовый минимальный harness в системном временном каталоге вне проекта (`%TEMP%\g14-glm-review-7f3a1c`), удалённый после проверки (повторная проверка — каталог отсутствует). Честные substitutions относительно удалённого `s11-probe-1`: собственный probe-код, восстановленный по опубликованному протоколу (fixtures, матрица стадий, расписание, fault profiles); version label реализован заголовком ответа `X-Served-By` на каждом ответе, включая ошибочные; server receipts — журнал в процессе по request ID; interleave 90/10 выбран «каждый десятый», 50/50 — чередованием (запись Gate 0 interleave не фиксирует — см. F-1). Результаты на CPython 3.14.0, exit 0:

   - **healthy**: B→S1→S2→S3, все окна go; violations/errors `0/0` у обеих применимых когорт; exposure без расхождений; **600 POST**; потоки завершены (`threads alive 0`).
   - **degraded**: B, S1 go; S2 **stop**: scheduled `20 violations / 0 errors` на 100, legacy `0/0` — ровно как в записи Gate 0; S3 не запускалась, 0 её запросов; R на fixed `100 legacy + 100 scheduled`, оба счётчика 0; readback **80/80** GET равны исходным fixtures, включая окна; **600 POST + 80 GET**.
   - **server-error**: B go; S1 **stop**: единственный injected 503 на первом legacy-запросе к new дал `1 violation / 1 error` на 100; S2 отсутствует; R-old 100 legacy, оба счётчика 0; **300 POST**.

   Итого **1500 POST + 80 recovery GET** — арифметика записи Gate 0 воспроизводится полностью.

## Вывод по Gate 0 и границам experiment evidence

Текущий итог Gate 0 `confirmed` в его явно ограниченной модели обоснован. Распределение evidence:

- **Наблюдалось** (автором и независимо мной): три профиля с точными populations; нулевые счётчики в здоровых окнах; контролируемые нарушения `20/100` scheduled (contract violation без 5xx) и `1/100 + 1/100` legacy (503); остановка продвижения с нулём запросов следующей стадии; оба recovery (R-old 100 legacy, R-fixed 100+100) с нулевыми счётчиками; readback 80 заказов с равенством окон; postconditions завершения.
- **Следует из конфигурации генератора** (конструкция, а не измерение): точность распределений 90/10–50/50–100/100 (последовательный генератор назначает адресат по расписанию); состав 80/20 («каждый пятый»); длительность прохода ≈5 c как свойство слотов; «равномерность» нагрузки. Exposure-сверка переводит эти построения в проверяемый факт, но их достижимость — свойство генератора, а не внешнего мира.
- **Остаётся требованием будущей реализации участника**: реакция на потерянный сигнал/неполное окно (правило сформулировано, инъекция потери не выполнялась), конкурентная нагрузка, реальные proxy/deployment, durable storage и crash recovery, latency-сигналы (последние корректно не заявлены).

Границы не затушёваны: одно-процессность, общий словарь, отсутствие прокси и production claims названы в Gate 0 и повторены в каждом материале; routing внутри одного процесса нигде не выдаётся за deployment. Freshness-заявления точны в обе стороны (pinned 3.14.0 ≠ latest, ветка 3.14.7 названа как не-версия эксперимента).

## Вывод по stop/recovery/limited-reversibility

Stop-семантика проверена и непротиворечива: решение принимает владелец на границе окна по трём раздельным наблюдениям; «stop» связан с отсутствием запросов следующей стадии, а не только со словом в журнале; явное честное уточнение, что лаборатория не обещает мгновенной остановки каждого запроса внутри окна. Деградированный дефект выбран так, что ноль 5xx не спасает от нарушения клиентского контракта — ключевой учебный механизм работает.

Граница обратимости проведена по моменту появления обязательства, а не по удобству: до включения scheduled возврат legacy на old допустим и отработан; после первого принятого scheduled-заказа общий rollback на old корректно запрещён (новая семантика и данные не выживают), compensation отвергнута с предметным обоснованием, выбран roll-forward с readback. Выбор правилен относительно принятых обязательств; единственный непрояснённый угол — данные, созданные new до scheduled при R-old (F-2, minor). Предел доказательства roll-forward в общем in-memory state заявлен достаточно явно и последовательно (см. N-2): проверка подтверждает сохранность записей при смене маршрута и не претендует на durable recovery — это слабее production recovery, и это не скрывается.

## Ответы на обязательные вопросы профиля A

1. **Можно ли считать Gate 0 `confirmed` в его явно ограниченной модели?** Да. Независимое воспроизведение опубликованного протокола на том же runtime полностью совпало с записью по populations, счётчикам, exposure, stop и recovery; ограничения модели заявлены явно и нигде не нарушены.
2. **Что наблюдалось, что следует из генератора, что остаётся участнику?** См. «Вывод по Gate 0»: наблюдаемые прогоны и recovery; точность распределений и длительность — конструкция генератора, подтверждаемая exposure-сверкой; потеря сигнала, конкурентность, durability и deployment — требования будущей реализации, честно не заявленные как проверенные.
3. **Делает ли общий state roll-forward тавтологичным и достаточно ли явно ограничение?** Частично да (readback не может провалиться, пока реализация цела), и да, ограничение сформулировано явно и единообразно во всех пяти материалах и Gate 0; прямой подмены durable recovery нет. Остаточное улучшение — побудить участника L3 выбирать и честно ограничивать собственное размещение состояния (N-2).
4. **Правильно ли выбраны rollback/roll-forward после S1 и S2?** Да. После плохого S1 обязательств новой семантики нет — rollback на old с контрольным окном корректен; после плохого S2 приняты 80 scheduled-заказов — общий rollback запрещён, compensation lacks предметного основания, roll-forward с readback обоснован. Непрояснённая деталь R-old — F-2.
5. **Достаточно ли measurement evidence для Delivery L3 без ложного L4/production?** Достаточно: staged exposure, раздельные сигналы, измеренная остановка, подготовленный incident path, recovery и readback наблюдаемы; L4, межкомандность, B6/B7 и production readiness систематически исключены и не зарегистрированы.

## Ответ на принятие

Slice можно принять после disposition findings: открытых blocker/major нет, оба minor закрываются однострочными уточнениями формулировок (или явными решениями оркестратора с обоснованием), notes передаются в backlog/registration hygiene. Техническая основа, арифметика, stop/recovery-механика и coverage-правдивость подтверждены независимой проверкой; Materialы не содержат готовой реализации и не предъявляют platform requirements.
