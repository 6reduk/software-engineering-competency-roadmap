# M1.8.20 G19 — профиль A: HTTP Runtime/S01 (glm)

## Профиль, модель и scope

- Профиль: A — runtime mechanics, technical correctness и traceability.
- Фактическая модель: `glm` (glm-5.3).
- Scope: четыре материала `curriculum/tracks/b2/slices/request-context-loss-diagnosis/` (index, interview, kata, project-spec), записи Gate 0 в `governance/work-packages/M1.8.20-http-runtime-s01-slice.md`, регистрации в `curriculum/tracks/b2/README.md` и `curriculum/tracks/b2/coverage-map.md`, первичные источники и минимальное независимое локальное воспроизведение вне проекта. Learning design, navigation и human readability — профиль B; здесь они проверялись только на стыке с техническими утверждениями.

## Verdict

`accepted_with_changes`: `0 blocker / 0 major / 1 minor / 2 note`.

Все ключевые runtime-утверждения независимо воспроизведены на точно совпавшей pinned-сборке; единственный minor — недокументированная предпосылка одного заявленного порядка checkpoints (instrumentation выхода зависимости через `finally`). Slice может быть принят после disposition этого minor и двух note либо их явного adjudication оркестратором.

## Независимое воспроизведение

### Среда

Локальная среда полностью совпала с pinned Gate 0 — substitutions по версиям не потребовались: CPython 3.14.0 (MSC v.1944, AMD64, Windows), FastAPI 0.137.1, Starlette 1.3.1, Pydantic 2.12.5, HTTPX 0.28.1, AnyIO 4.11.0 (версии из `sys.version`/`importlib.metadata`). Собственный минимальный probe создан вне проекта (`%TEMP%/g19a_runtime_probe.py`), выполнен и удалён после проверки; отсутствие подтверждено вместе с авторским `m1820-probe.py` (оба `Test-Path` → отсутствует).

Собственные отличия моей модели от авторской записи, честно перечисленные:

1. Для атрибуции записей в конкурентной волне добавлен диагностический echo-заголовок операции; изучаемый контракт `X-Request-ID`/status/media type/body он не затрагивает.
2. Выход зависимости инструментирован через `try/finally` вокруг `yield` (см. Finding A-1: при коде сразу после `yield` заявленные автором порядки на error-ветвях не воспроизводятся).
3. Для recovery создан новый экземпляр fixed-сборки в том же процессе/event loop (как в G0.3); между группами — свежий экземпляр приложения; watchdog 5 с реализован `asyncio.wait_for`.

### Механизм, подтверждённый чтением первичного кода pinned-сборки

- Starlette 1.3.1 `build_middleware_stack`: `ServerErrorMiddleware → user middleware → ExceptionMiddleware → router`; отдельного `AsyncExitStackMiddleware` в стеке нет.
- FastAPI 0.137.1 `routing.request_response`: request-scope exit stack (`fastapi_inner_astack`) и function-scope стек создаются вокруг вызова endpoint; `await response(...)` (то есть `http.response.start`) исполняется внутри request-scope стека; `wrap_app_handling_exceptions` обёрнут вокруг стеков.

Из этой механики следуют ровно заявленные порядки: на success `response-start` раньше `dependency-exit`; на domain error и invalid query исключение разворачивает стек до обработчика, поэтому `dependency-exit` (при `finally`-instrumentation) раньше `error-map`/`validation-map` и `response-start`. Это подтверждает и оговорку материалов о version-sensitivity порядков.

### Фактические результаты прогона (369 ASGI-операций, exit 0, 0 неудачных проверок)

## Обязательные вопросы профиля A

1. **Можно ли считать Gate 0 `confirmed` в его явно ограниченной in-process модели?** Да. Все существенные наблюдения G0.2/G0.3 — порядки трёх ветвей, граница первой потери, task/thread topology (1/2/2 tasks, 1 thread), 90/90 потерь, нули в control/fixed/concurrent/recovery, отвержение bypass 3/3, игнорирование клиентского заголовка, арифметика 366+3 — независимо повторены на идентичной pinned-сборке. Ограничения модели (in-process ASGITransport, без сети/worker reuse/distributed propagation) заявлены автором и не превышены. Не поддаётся независимой проверке только идентичность удалённых артефактов (UUID, миллисекунды, SHA-256) — они и не заявлены как переносимые.
2. **Что повторено независимо, а что осталось авторским record?** Повторено: всё перечисленное в п.1. Осталось record: конкретные UUID и длительности G0.5 (замеряемые, но не переносимые), хеши удалённых файлов (intake I-1), и форма instrumentation выхода зависимости автора (выведена косвенно: только `finally`-вариант даёт записанные порядки — Finding A-1).
3. **Является ли `created → dispatch-enter` первой доказанной потерей и достаточно ли данных для связи с explicit empty context?** Да. Тройка control/defect/fixed изолирует единственный фактор — контекст запуска дочерней task: значение есть в родителе после `joined` (создание и reset не сломаны), отсутствует во всей downstream цепочке (включая reader на `response.start`), а восстановление только параметра контекста возвращает значение без правки reader/handler. Дополнительно чтение исходника pinned-сборки подтверждает механизм (context копируется при создании task; `Context()` пуст).
4. **Пройдёт ли proposed regression при ручной подстановке правильного заголовка или обходе pipeline?** Нет. Regression по kata проверяет свой ID в существенных точках + прохождение dependency/error path + полный ответ: подстановка заголовка оставляет downstream checkpoints `None` → падение; bypass даёт корректный ответ без pipeline checkpoints → отвергнут 3/3 в моём прогоне. Для invalid query ручной fallback в endpoint бесполезен вдобавке потому, что endpoint не вызывается.
5. **Достаточно ли evidence для Trace L1/L2 без исполнительного L3 и production-readiness claim?** Да, в границах пакета: L1 — предсказание + trace трёх ветвей (kata practice/assess); L2 — самостоятельная локализация, причинная правка одного фактора, regression и изоляция (kata practice/assess, project integrate/assess); L3 присутствует только как interview `probe` про неизвестную production topology, без execution claim, и материалы прямо отдают production reconstruction отдельному будущему результату.

## Отдельный вывод по Gate 0 и runtime boundaries

Gate 0 технически добросовестен и воспроизводим: среда, механизм и все измеримые утверждения подтверждены независимым исполнением и чтением первичного кода pinned-версий; boundary-оговорки (version-sensitivity порядков, отсутствие сети/worker reuse/production-claims) точны и не нарушены нигде — ни в материалах, ни в registration. Рекомендация intake I-1 (независимое воспроизведение вместо удалённого probe) выполнена; I-2 (не переносить порядок на другие сборки) подтверждён механикой `fastapi_inner_astack`/`wrap_app_handling_exceptions`, которая реально меняется между версиями FastAPI.

## Отдельный вывод по first-loss / root-cause / regression

Причинная цепочка slice корректна и различима: симптом (`missing` при сохранном status/body) → три конкурирующие гипотезы (не создан / потерян до читателя / неверный reader) → checkpoints после создания, на входе dispatch и перед ответом различают их → первая наблюдаемая потеря `created → dispatch-enter` (не первопричина сама по себе) → уточняющий опыт с одним фактором (пустой контекст запуска task) → причинное исправление со сохранением task boundary → regression с отрицательным bypass-контролем, закрывающий маскировку ручной подстановкой. Материалы нигде не выдают пару checkpoints за доказанную операцию между ними и не назначают первопричиной место `missing`.

## Ответ на принятие slice

Slice может быть принят (`accepted_with_changes`) после обработки одного minor A-1 (одно предложение про `finally`-instrumentation в kata) и фиксации решений по note A-2/A-3 оркестратором. Открытых blocker/major по Gate 0, context propagation, first-loss diagnosis, cleanup/isolation нет; причинная правка и отрицательный bypass-контроль признаются различающими root fix и маскировку. Замечание A-1 не влияет на валидность Gate 0 и на учебную причинную модель — только на сопоставимость trace участника с заявленными порядками.

## Ответы на open questions work package

1. **Достаточно ли удалённого авторского probe при независимом воспроизведении техническим reviewer-ом?** Да. Требуемое условие выполнено: минимальная модель восстановлена независимо на идентичной pinned-сборке, все существенные наблюдения совпали, готовое решение не сохранено ни в проекте, ни в review (мой probe удалён; в отчёте — только агрегаты и механизм). Удалённый probe остаётся незаменимым только для хешевой идентичности, которая не является предметом принятия.
2. **Достаточны ли C1/R1 как learn-переходы без отдельного learn-файла?** С технической стороны — да: C1 даёт модель фактического HTTP-ответа и границ исполнения, R1 — владельца, request scope и cleanup в `finally` (что прямо нужно лаборатории); недостающие механики (ContextVar, наследование контекста task, ASGITransport) объяснены внутри самих материалов с первичными источниками, и ни один шаг kata/project не заблокирован отсутствием learn. Финальное суждение об учебной ценности маршрута — за профилем B.

## Независимость и границы

- Отчёт создан до чтения любых других профильных отчётов G19; других G19-файлов в `governance/reviews/` на момент завершения анализа не было.
- Исходные материалы (`pilot/`, `docs/`, work packages, registrations, reviews) не редактировались; создан только настоящий файл.
- Временная модель размещалась вне проекта и удалена; консолидированный review, resolution и acceptance не создавались.
- Ограничение evidence: моё воспроизведение покрывает in-process ASGI-модель на pinned-сборке Windows/CPython 3.14.0; оно не подтверждает поведение иных версий, реальную сеть, worker reuse или production topology — что совпадает с заявленными границами самого пакета.
