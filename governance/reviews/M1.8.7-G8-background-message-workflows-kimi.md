## Вывод по Workflow L2/L3 evidence и отсутствию overclaim

- **Workflow L2** (`implement-background-flow`): evidence правдиво — kata требует самостоятельно реализовать заданный flow с явными точками ack/reject и duplicate path, а project Evidence A проверяет ownership классификации ошибок, момента ack и bounded poison transition поведением, а не именами классов. Критерии L2 из `level-outcomes.md` («Ack/retry/error ownership определены; duplicate и poison path проверены») покрыты наблюдаемыми проверками.
- **Workflow L3** (`design-recoverable-workflow`): evidence правдиво и отделено от L2 — interview Q3–Q5 и project Evidence B требуют от инженера самому задать states/invariants до реализации, воспроизвести разные causal windows (F0–F2 — это разные точки, а не один exception с разными labels, что прямо проверяется review criteria) и доказать, что redelivery после restart не создаёт второй business result. Это соответствует критерию L3 «State transitions/invariants наблюдаемы; replay/recovery не нарушают бизнес-результат».
- **Overclaim отсутствует**: Workflow L4 не заявлен ни в YAML, ни в тексте (rubric прямо маркирует его «Не доказанный L4»); B5 используется как language/readiness context без capability IDs; Idempotency, Cancellation и Verification не получают новых relationships — подтверждено пересчётом targets (все 11 relationships указывают только на capability `design-asynchronous-workflows` и её L2/L3 outcomes). Project-spec дополнительно содержит вопрос защиты, объясняющий, почему fault injection не добавляет Verification coverage.

## Вывод по единому consumer contract и различию kata/project

Все пять artifacts используют один контракт без расхождений: событие `OrderConfirmed(event_id, event_type="OrderConfirmed", operation_id, order_id, confirmed_at)`, durable quorum queue `orders.fulfillment`, `prefetch_count=1`, manual ack (`ack(multiple=False)`), ошибки только через `reject(requeue=True)`, один side effect `fulfillment_requests(source_event_id UNIQUE)`, policy `delivery-limit=3` + `at-least-once` DLX → `orders.fulfillment.poison`, fault marker `after_commit_before_ack` и process exit code 70. Числа согласованы между файлами: 10 прогонов, 30 секунд, counters `0/0`, минимум две доставки, одна row (learn envelope = kata envelope = project recovery profile; 30 секунд везде названы лабораторным timeout, а не broker guarantee).

Различие kata/project реальное, а не номинальное: kata исследует ровно одно окно (после commit до ack) на минимальной системе, которую участник создаёт сам, и явно отсылает poison к brief; project требует реальные RabbitMQ/PostgreSQL в отдельном репозитории, четыре различимых fault points (F0 до commit, F1 после commit до ack, F2 после duplicate detection до ack, F3 permanently invalid), три раздельных evidence profiles (recovery/control/poison с разными terminal criteria, включая недоступный DLX target как незавершённый профиль) и decision record. Наблюдаемые результаты kata и project различны, что требуется gate G8.
