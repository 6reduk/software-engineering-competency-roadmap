# M1.8.20 — решение оркестратора по G19 HTTP Runtime/S01

## Процессуальное решение

По прямому решению владельца программы профиль B временно не выполняется из-за недоступности SaaS-подписки. G19 не считается двухпрофильным review, consolidated-артефакт не создаётся, а профиль A не выдаётся за консенсус двух независимых рецензентов.

Получен один независимый профиль A с verdict `accepted_with_changes`: `0 blocker / 0 major / 1 minor / 2 note`. Рецензент независимо воспроизвёл минимальную runtime-модель на закреплённой сборке, подтвердил границу первой потери контекста, исправление через нормальное наследование task context, отсутствие обхода pipeline, измерительные populations и ограничения coverage.

Область отсутствующего профиля B — learning design, навигация, human readability, автономность материалов и различие kata/project — оценена оркестратором только как ограниченная risk assessment, а не как второе независимое review.

Итоговое решение: `accepted_with_changes`. До acceptance выполняется один ограниченный пакет [`M1.8.20a-G19-findings-correction.md`](../work-packages/M1.8.20a-G19-findings-correction.md). Повторный профиль A и полный G19 не требуются. Однопрофильное исключение относится только к G19 и не переносится автоматически на следующие gates.

## Подтверждённая техническая модель

- Исполненная среда совпала с pinned baseline Gate 0: CPython 3.14.0, FastAPI 0.137.1, Starlette 1.3.1, Pydantic 2.12.5, HTTPX 0.28.1 и AnyIO 4.11.0.
- Внешний ASGI middleware создаёт и очищает server-owned request context; входящий `X-Request-ID` не становится доверенным значением.
- Дефект возникает при запуске downstream task с явно пустым `Context`; первая наблюдаемая потеря находится на границе `created → dispatch-enter`.
- Исправление сохраняет task boundary и pipeline, позволяя новой task наследовать текущий context; ручной fallback в конечном response отвергнут отрицательным контролем.
- Независимый probe подтвердил control/defect/fixed/concurrent/recovery и bypass populations: 369 операций, ноль неуспешных проверок.
- Конкретный порядок dependency/error/response относится только к закреплённой сборке и выбранной instrumentation; он не является универсальным порядком FastAPI/Starlette.
- Coverage остаётся ограниченным Trace L1/L2 и interview probe L3: 10 relationships к четырём targets, без L3 execution и supporting overclaim.

## Оркестраторская risk assessment отсутствующего профиля B

Четыре материала образуют понятный маршрут без нового learn: index объясняет reuse принятых C1 и R1, interview проверяет реконструкцию пути, kata задаёт один локализуемый refactor defect, а project-spec оставляет участнику выбор context concern и refactor boundary. Kata и project не содержат scaffold или готового исправления; вопросы и ориентиры ответов находятся в скрываемых секциях.

Главный выявленный риск читаемости совпадает с техническим finding профиля A: без пояснения `try/finally` участник может получить другой trace и принять корректный стенд за сломанный. Дополнительная редакционная неоднозначность — запись recovery как «20 после волны» при общем количестве 60 — локальна и исправляется тем же проходом.

Остаточный риск после correction-pass — отсутствие независимого editorial/usability прочтения новым читателем. Он приемлем для этого gate, поскольку маршрут короткий, новая теория не создаётся, материал переиспользует два уже принятых brief, а изменения обратимы. Эта оценка не подтверждает production L3, сетевое поведение, worker reuse, observability maturity или завершение HTTP Runtime module.

## Disposition

| Finding | Решение | Обоснование |
|---|---|---|
| A-1, minor | Исправить до acceptance | Checkpoint выхода yield-зависимости на error-ветвях наблюдаем только при размещении instrumentation в `finally`. Предпосылку нужно явно назвать в Gate 0, interview и kata, иначе заявленный trace невоспроизводим для части корректных реализаций. |
| A-2, note | Исправить тем же проходом | Формулировка recovery должна явно показывать `3 × 20 = 60`, чтобы количество populations читалось без восстановления арифметики из других файлов. |
| A-3, note | Принять как осознанную границу | Slice реализует узкий диагностический частный случай S01: status/body сохраняются, но теряется обязательный диагностический header. README уже называет это ограничение; сценарий и каталоги в этом пакете не меняются. |

## Условия acceptance-pass

- Gate 0 и учебные материалы явно говорят, что `dependency-exit` checkpoint размещён в `finally` вокруг `yield`; это условие instrumentation, а не универсальное поведение произвольного кода после `yield`.
- README и project-spec однозначно задают recovery как три повтора по 20 операций, всего 60.
- Request path, public contract, pinned/current версии, context owner, seeded defect, first-loss boundary и результаты Gate 0 не меняются.
- Сохраняются четыре материала без нового learn, 10 relationships, четыре targets и role totals `1 reference / 3 probe / 2 practice / 3 assess / 1 integrate`.
- Не добавляются Lifecycle, Cancellation, Verification, HTTP Contract, B1, A3 или B7 coverage; L3 остаётся только interview probe.
- Все четыре материала остаются `review` до отдельного acceptance-pass; G19, module gates и program status не принимаются автором.
- После точечной проверки A-1/A-2 G19 можно принять без повторного полного review.
