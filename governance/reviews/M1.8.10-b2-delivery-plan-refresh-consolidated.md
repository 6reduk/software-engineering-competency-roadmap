## Консолидированные findings и диспозиции

Источник: 🔵 — GLM (профиль A); 🟡 — Kimi (профиль B). Полные evidence и рекомендации — в исходных review; здесь сжатая запись с предлагаемой диспо­зицией. Окончательное решение за оркестратором. Фактические утверждения обоих профилей перепроверены консолидацией по артефактам (см. «Подтверждения»).

### Major

**C-1 (🟡 Kimi B-1). План заявляет Abuse L2 как primary outcome candidate, не разрешая явно трактовку перечня его evidence criteria.**

Канонический L2 (`b2.level-outcome.enforce-api-security-abuse-controls-l2-protect-typical-endpoint`) требует: «Request/cost bounds, field exposure, quota/rate и untrusted target rules связаны с threat cases и тестами» — четыре категории одним списком; тот же набор повторяет описание capability. План покрывает центральным действием только request/cost bounds; untrusted target rules исключены вместе с callback/SSRF (Non-goals), distributed quota исключены (локальный per-operation cost ceiling), field exposure экспортируемых полей не упомянута вообще — перепроверено консолидацией grep-ом: явной записи применимости категорий L2 в плане нет ни в decision brief, ни в Gate 0. Если список — обязательная совокупность, cost-only slice не может правдиво заявить L2; если набор применимых категорий — L2 достижим, но только при явном решении по каждой категории для выбранного endpoint. Intake выдал именно этот вопрос как риск №1; anti-pattern WP запрещает начислять Abuse L2/L3 за частичное evidence.

Диспозиция: **fix-проход либо явное решение** — минимальное исправление: добавить в decision brief (Scope) явную запись применимости четырёх категорий L2: request/cost bounds — центральное evidence; untrusted target rules — сознательно неприменимы, callback URL удалён из package (ссылка на SSRF-долг, C-2); quota/rate — локальный per-operation cost ceiling, time-based rate и distributed quota исключены и названы; field exposure — tenant-scoped набор экспортируемых полей определяется через переиспользованный trusted context либо явное обоснование неприменимости. Равноценная альтернатива по протоколу — явное решение оркестратора сделать эту запись обязательным элементом Gate 0 будущего authoring package до первого учебного artifact. Сужение кандидатов до L1/L3 — более слабый вариант: действие L2 («самостоятельно определяет abuse controls типового endpoint») и есть процесс такого определения.

### Minor

**C-2 (🟡 Kimi B-2). Непокрытый SSRF-долг канонического S14 не зафиксирован в разделе «Open questions и известный долг».**

Канонический S14 содержит два механизма (operation cost/quota и SSRF target boundary); после выбранного пакета вторая половина останется непокрытой. Долг рассеян по Non-goals, строке 1 очереди, «Изменению решения относительно M1.8.8» и рискам, но раздел Open questions перечисляет четыре других долга без SSRF. Перепроверено консолидацией: формулировки плана подтверждаются, нигде план не заявляет закрытие S14 целиком — риск только в «забывании» при следующем refresh. Intake риск №3 требует именно явной фиксации долга.

Диспозиция: **fix-проход** — одним пунктом в «Open questions и известный долг»: SSRF/untrusted-target половина S14 остаётся непокрытой после этого пакета, требует отдельного будущего bounded package с собственным Gate 0, метка S14 не считается закрытой.

**1. S14 operation-cost admission — следующий лучший bounded package; порядок менять не нужно.** Подтверждено обоими профилями: максимум нового unique coverage (три полностью пустых outcomes, включая role-required Abuse L3 обеих RoleViews), root-capability без internal hard prerequisites, переиспользование принятого S05 substrate, один новый внешний readiness record против двух у S15 (B3 cache-store + B5 coordination). Выбор влияет на dependencies, learning leverage и boundedness, а не является предпочтением порядка тем.

**2. Правдивые Abuse outcomes.** L1 — правдиво без условий: применение заданного operation-cost bound с negative tests соответствует каноническому действию. L3 — правдиво: каноническое действие дословно описывает «multi-tenant/adversarial workload и неоднозначную стоимость операции», а запланированный project spec с пятью populations, threat matrix и decision record воспроизводит abuse paths, сохраняет legitimate use, tenant isolation и bounded envelope. L2 — правдиво **условно**: только при явной записи применимости четырёх категорий evidence criteria (C-1); без неё честный ответ — «L1 и L3; L2 под вопросом трактовки». L4 корректно не заявляется без multi-service adoption. Профиль A механически подтвердил: все три кандидата сегодня не имеют ни одной принятой связи, то есть заявка не повторяет существующее coverage.

**3. Минимальный A3/B7 readiness contract до authoring и достаточность Gate 0.** Состав (согласован с планом): один воспроизводимый export substrate и server-owned cost unit, вычислимый до дорогой работы; threat model operation-cost amplification; legitimate/adversarial populations; workload и duration; точка измерения; admission/rejection semantics; измеримый acceptance threshold; audit limits; recovery observation; явный stop-condition при потребности в distributed quota/shared counter или невычислимости cost. Плановый Gate 0 покрывает все пункты; отдельный prerequisite package не нужен — A3/B7 не имеют capability IDs для ссылки, а прецеденты M1.8.7/M1.8.8/M1.8.9 приняли Gate 0 внутри authoring package как не-hard-edge. Встроенного Gate 0 достаточно при условии C-3 (классы первичных источников фиксируются до старта) и C-1 (запись применимости категорий L2 — в плане или как обязательный элемент Gate 0).

**4. Граница Abuse Controls / Load Control.** Проверяемая граница проходит по природе угрозы и точке решения. Load Control (принятое R2–R5): admission и backpressure при агрегированном насыщении под легитимным трафиком, fan-out amplification, bounded pools/deadlines, recovery. Abuse Controls (новый пакет): per-request server-owned оценка стоимости до начала работы против adversarial request shape аутентифицированного tenant, fail-closed при неизвестной стоимости, tenant-isolation consequence, сохранение legitimate use. Проверяемый критерий: перегрузка под конкурентной легитимной нагрузкой — Load Control; один сформированный запрос, обходящий cost bound или создающий cross-tenant последствие, — Abuse. План границу держит: R2/I1 используются ссылками, новые Load Control/Identity relationships не начисляются, generic backpressure повторно не преподаётся; переименования R2–R5 в Abuse coverage нет.

**5. S14 без SSRF.** Использовать сценарий честно можно: план выбирает один механизм из двух, объявляет SSRF первым пунктом Non-goals, запрещает подмешивать callback как negative case и нигде не заявляет закрытие сценария или capability целиком — scenario ID не используется как доказательство полного S14. Долг сохранён, но требует консолидации (C-2), чтобы SSRF-половина гарантированно дожила до отдельного будущего package с собственным Gate 0.
