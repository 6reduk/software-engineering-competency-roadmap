# M1.9.4 — G25 консолидированный review intake SE01

## Назначение и способ консолидации

Настоящий отчёт объединяет два завершённых независимых профиля gate G25 по `authoring/workflow/review-protocol.md` и work package `M1.9.4-G25-schema-evolution-intake-review.md`: профиль A (glm) — PostgreSQL, data correctness и будущий Gate 0; профиль B (grok) — learning/editorial, levels и boundedness. Дубликаты объединены, расхождения разрешаются через цели программы и первичные источники, а не голосованием. Исходные отчёты остаются независимыми записями и не изменялись. Консолидация выполнена в сессии автора профиля A по явному поручению пользователя (прецедент цикла G24); компенсация — фактический базис каждого finding профиля B перепроверен по строкам intake (см. «Независимость и ограничения»).

Документ не принимает M1.9.4 и SE01, не назначает corrections выполненными, не создаёт acceptance, Gate 0, correction package, runtime implementation, учебные материалы, coverage или ImplementationReference и не запускает BR01. Решение о создании Gate 0 + пятижанрового authoring package остаётся отдельным решением оркестратора.

## Схождения и расхождения

**Предметных противоречий нет.** Оба профиля независимо подтвердили общую фактическую основу:

- арифметика oracle: шесть ID с копейками `0, 12000, 1300, 999999999999, 789, 2501` пересчитана профилем A аналитически (совпадение дословное, границы домена покрыты fixtures 0,00 и 9999999999,99) и принята профилем B как ожидаемый набор, строящийся из входных команд и подтверждений, а не чтением backfill;
- пять состояний и четыре контракта R-old/W-old/R-new/W-new достаточны для выбранного действия; третья версия и drop старого представления намеренно не вводятся;
- конечная граница честна в теле: «проверенное новое представление при сохранённой совместимости, а не демонтаж»; удаление `amount_rub` — непересекаемая граница rollback; лабораторная проверка не выдаётся за production migration/cutover/adoption (профиль A — по существу границы, профиль B — по подписи пятого состояния, см. C-6);
- 2/60 секунд — предложенные предохранители, не измерения и не SLO; все восемь категорий readiness «не подтверждены»; ветка документации 18 не закрепляет baseline SE01;
- разделение B2/B3/B6/B7 правдиво и совпадает с ownership-таблицами B3 README и track-файлами; соседние B2-срезы не импортируются как evidence; SQ01-принятие не переносится;
- самостоятельность участника сохранена: нет готовой миграции, scaffold, единственного предписанного trigger/adapter или framework; store-side — рекомендация направления, не решение;
- механика: metadata соответствуют work package M1.9.4 (`id`, `kind: plan`, `owner_track: b3`, `status: review`, поле `coverage` отсутствует), якоря и относительные ссылки разрешаются (оркестратор считал 17 локальных, профиль B — 19 с внешними; расхождение только в базе подсчёта), conflict markers и trailing whitespace отсутствуют.

**Расхождение verdict-меток отсутствует** (оба `accepted_with_changes`). Единственная содержательная развилка двух профилей — не конфликт, а комплементарность: профиль A признал различение «Сверка» и «validation» концептуально корректным на уровне дизайна; профиль B нашёл, что в прозе документа термин `validation` употреблён без глосса и в двух смыслах. Приняты оба вывода: дизайн верен, редакция термина — C-5.

## Adjudication единственного major (C-1)

Базис перепроверен консолидацией независимо и по первичному источнику. [Transaction Isolation PostgreSQL 18](https://www.postgresql.org/docs/18/transaction-iso.html): при READ COMMITTED каждая команда видит снимок на своё начало, а при ожидании конкурентного обновления «the search condition … is re-evaluated … using the updated version of the row». Следовательно, одношаговый UPDATE, вычисляющий новое значение из текущей версии строки (включая случай ожидания W-old), применит 12000, а не захваченные ранее 10000 — устаревшая запись не возникнет, защита не сработает, и Defect молча совпадёт с Fixed по наблюдаемому исходу. На REPEATABLE READ та же попытка завершится `could not serialize access due to concurrent update` — иная наблюдаемая сигнатура.

Intake описывает Defect как «захватывает старое значение… останавливается на барьере… затем наивный перенос пытается применить прежние 10000» и оставляет «воспроизводимость гонки» в неподтверждённой readiness, но не требует от Gate 0 зафиксировать форму наивного переноса и изоляционную зависимость сигнатуры. Major обоснован тремя независимыми следами: заметка оркестратора I-1 (требование различающего исполняемого механизма), сверка профиля A с первоисточником, подтверждение профиля B («исполняемый Defect — зона профиля A и будущего Gate 0»). Это не дефект содержания выбранной границы, а недостающее условие определённости различающего эксперимента — ядро ценности SE01.

Закрытие — одна-две фразы в intake (без SQL): наивный перенос обязан применять значение, захваченное до барьера, отдельной последующей записью; Gate 0 заранее фиксирует изоляцию соединений переноса и W-old, объявляет ожидаемую сигнатуру Defect (применённое расхождение либо отвержение с SQLSTATE) и доказывает воспроизведение пробы до полного прогона. Альтернатива по протоколу — явное решение оркестратора с перенесением условия в постановку Gate 0.

## Verdict

`accepted_with_changes`: **0 blocker / 1 major / 4 minor / 3 note**.

Техническая основа выбранной миграционной границы подтверждена с обеих сторон без единого расхождения: домен и точность пересчитаны, пять состояний и матрица полны, концептуальное разделение enforcement/сканирования/обязательности соответствует документации PostgreSQL 18, evidence различает три класса отказов, resume/rollback/cleanup определены, границы B2/B3/B6/B7 и конечная граница опыта честны, readiness неподтверждена. Документ читается как связный planning artifact с одной рабочей проблемой и одним предметным правилом. Единственный major локализован в формулировке требования к будущему Gate 0 и закрывается точечной правкой без структурных изменений. Это рекомендация консолидации; принятие G25, назначение correction package и решение о Gate 0 + authoring — отдельные решения оркестратора.

## Консолидированные ответы на шесть обязательных вопросов

1. **Достаточно ли определён intake, чтобы после corrections создать один Gate 0 + authoring package SE01?** Да — при закрытии C-1 (обязательно) и C-2–C-5 (рекомендуется одним correction-pass). Оба профиля сходятся: предмет, инвариант, четыре контракта, пять состояний, различающий опыт, сверка шести ID, неподтверждённая readiness и границы B2/B3/B6/B7 заданы достаточно для одного лабораторного пакета и последующего пятижанрового SE01 без расширения до курса migrations; открытые вопросы 1–5 не меняют ownership. Создание Gate 0 этим ответом не разрешается — это отдельное решение оркестратора.

2. **Какой точный наблюдаемый результат отличает Defect от Fixed?** Defect: перенос захватывает 100,00 по ID 2 до барьера, W-old подтверждает 120,00, наивный перенос применяет прежние 10000 — исход либо диагностируемое расхождение с эталоном 12000 (несогласованная пара при сверке), либо отвержение защиты/изоляции с наблюдаемым SQLSTATE; в обоих случаях след показывает отсутствие перехода к завершению, stop зафиксирован, ожидаемый отказ ограничения не выдаётся за потерю данных, подтверждённые записи W-old/W-new (ID 3 = 1300, ID 5, ID 6) сохранены. Fixed: на том же чередовании (плюс INSERT ID 5 и W-new INSERT/UPDATE в проходе) финальная популяция в точности равна oracle {1:0, 2:12000, 3:1300, 4:999999999999, 5:789, 6:2501}, нули по пропускам/NULL/расхождениям/потерям, ограничение проверено и действует, повтор после прерывания даёт тот же набор. Различие наблюдаемо извне стенда. Форма двухшагового захвата — обязательное условие Gate 0 (C-1), не готовый SQL в intake.

3. **Какие условия обязан доказать будущий Gate 0 до первого учебного материала?** Закреплённые версии PostgreSQL server/client и параметры запуска; topology, права и transaction/autocommit/isolation каждого из шести соединений, включая lock-пробу; конкретная семантика выбранных DDL/ограничений по первичным источникам закреплённой версии с фактическими пробами (NOT VALID действует на новые строки, VALIDATE — SHARE UPDATE EXCLUSIVE, SET NOT NULL со сканом или без); lock-режимы, конфликтующая пара, bounded wait и SQLSTATE; двухшаговый механизм Defect с заявленной сигнатурой и доказанным воспроизведением (C-1); форма атомарности W-new и доказательство отсутствия обходящих writers для adapter-варианта; достижимость 2/60-секундных предохранителей либо обоснованные иные числа; права наблюдателя для `pg_locks`/`pg_stat_activity`; независимый oracle, полная сверка шести ID и отрицательные пробы, включая решение о границах домена (C-7); идемпотентный resume без порчи сумм; воспроизводимые reset/cleanup; не менее двух повторов каждого профиля; сохранение текста probe, fixtures, команд, настроек, журналов и контрольных сумм вместе (урок C-8 цикла SQ01: хэш без исходного файла недостаточен); порядок включения согласованности после механизма совместимости (C-8).
