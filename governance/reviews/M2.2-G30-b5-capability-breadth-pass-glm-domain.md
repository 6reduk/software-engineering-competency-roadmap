## Техническая корректность моделей

Все 12 модельных областей профиля проверены по формулировкам capabilities, outcomes и сценариев. Ошибок и устаревших утверждений не найдено; спорных утверждений, требующих внешнего первичного источника, не возникло — проверяемые различения стабильны. Выборочно проверенные различения:

- partial failure: timeout ≠ доказанный rollback; отказ связи ≠ остановка исполнителя;
- read consistency: read-your-writes / монотонность / eventual / линеаризуемость разведены; обещание сессии не выдано за глобальное; CAP/PACELC применён только там, где уместен (L3);
- causal order: happens-before (send/receive) отделён от wall-clock; конкурентная пара не называется причинной;
- stale authority: истечение lease / мнение исполнителя / принятие ресурсом разделены; election сам по себе не исключает старый эффект (fencing в точке эффекта);
- leadership: safety отделена от progress; остановка прогресса ≠ нарушение safety; потеря большинства учтена;
- placement: число копий ≠ число независимых failure domains; подтверждение записи ≠ видимость каждой копии;
- delivery/replay: подтверждение брокера ≠ получение потребителем ≠ бизнес-эффект; область порядка локальна; гарантия доставки ≠ exactly-once бизнес-эффект;
- idempotency/retry: уникальный message ID ≠ бизнес-идентичность; бюджет повторов и изоляция poison work — отдельные решения;
- cache/load: TTL ≠ гарантия свежести без временных допущений; отказ в приёме ≠ молчаливая потеря принятой работы; гонка заполнения и массовое истечение учтены;
- cross-system atomicity: локальный rollback ≠ отмена намерения ≠ компенсирующий эффект; outbox/CDC не приписана дедупликация эффекта получателя; координация vs saga сравниваются по атомарности, промежуточной видимости, блокированию и цене восстановления;
- multi-region: номинальная ≠ оставшаяся мощность; второй регион ≠ готовность failover;
- mixed-version: синтаксическая совместимость ≠ сохранение смысла; отсутствие ошибки ≠ подтверждение инварианта; лабораторный результат ≠ production evidence.

## Ответы на обязательные вопросы

1. **Можно ли принять состав 6/17/51/11/34 как первый полный B5 capability blueprint?** Да. Все 11 кластеров трассируются cluster → module → capability → outcomes → scenario; totals пересчитаны и сходятся; карта остаётся картой ожидаемых действий без coverage, proficiency и runtime claims. Замечания — только note.
2. **Где объединение кластеров помогает, а где скрывает?** Помогает: `compose-delivery-and-business-effects` держит единый результат «доказать межсистемный бизнес-эффект через границы доставки» при пяти различимых действиях (договор доставки, повтор эффекта, распространение повторов, фиксация+публикация, атомарность/компенсация); `preserve-authority-across-failures` связывает порядок, полномочия и leadership с правом на эффект; `place-state-with-bounded-failure-cost` объединяет размещение, перенос владения и ёмкость по общему договору данных при изменении состава участников. Скрытых разнородностей и пробелов не найдено; ближайший шов (retry-propagation ↔ load-control) явно оформлен Related-ребром с обоснованием.
3. **Правдивы ли L1–L3, hard DAG, external prerequisites и ownership?** Да. Все 17 L2 требуют самостоятельного ограниченного действия (строит/задаёт/определяет при явных границах), все 17 L3 — выбора и защиты при неопределённости и конкуренции ограничений, а не более длинного объяснения; одинаковые классы суффиксов ID не маскируют содержательную разницу — тела исходов предметно различны. DAG аци­кличен, направления верны, runtime readiness вынесена из зависимостей. A1/A3 — hard baseline словами со ссылками; B2/B3 — conditional с точным указанием сценариев; присвоений из B2/B3/B6/B7/C1 не найдено (см. guardrails ниже).
4. **Полезны ли обе RoleViews как baseline?** Да. Категории распределены предметно, зеркальности нет (например, `model-partial-failures`: Backend L3 vs Architecture L2; `bound-repeat-effects`: Backend L3 vs Architecture L2 — обосновано различием «разбирает реальный инцидент» vs «разделяет ответственность участников»). Прецедент B2 (условность только на L4-специализациях) делает 0 conditional у Architecture структурно согласованным с программой.
5. **Выполнены ли guardrails G29?** (1) Bounded depth — да: consensus/leadership, distributed transactions и multi-region раскрыты моделями, применимостью, историями и trade-offs; non-goals модулей 2–4 явно исключают доказательства, реализацию протокола, production topology и runbook. (2) Decision taxonomy — да: пять типов соответствуют обязательному минимуму work package, применены к трём кандидатам без выбора; note A-G30-2 — о правиле для верификационно-центричного кандидата. (4) C1 carrier — да: контекст, варианты, выбранная гарантия, предположения об отказах, цена и сигнал пересмотра присутствуют; шесть полей заполнены с honest-статусами; C1 coverage/proficiency/L4-L5 evidence не заявлены.
6. **Что закрывать до acceptance?** Обязательного ничего: 0 blocker / 0 major. A-G30-1 и A-G30-3 — backlog/консолидация; A-G30-2 — к будущему выбору slice; A-G30-4 — no change.
