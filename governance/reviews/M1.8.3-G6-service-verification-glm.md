# M1.8.3 — G6 review Service Verification/S10, профиль A

## Профиль, модель и scope

Профиль A — domain, learning design и human readability. Модель — `glm`. Scope — пять новых артефактов slice `risk-based-service-verification` и связность маршрута между ними; регистрационные разделы `curriculum/tracks/b2/README.md` и `curriculum/tracks/b2/coverage-map.md` прочитаны как контекст. Полностью прочитан весь context manifest work package: протокол review, оба work package M1.8.3, стандарты 05/09/10, каталоги B2 (modules, capabilities, level-outcomes, prerequisites, scenarios S03/S06/S08/S10), module-delivery plan с decision brief S10, acceptance M1.8.2, принятый contract context (C1/C2/C4) и boundary/evidence context (A1/A4/R5).

Version-sensitive утверждения (FastAPI/Starlette/Pydantic, RFC 9457, «422 Unprocessable Content») в этом профиле по первичным источникам не перепроверялись и runtime не воспроизводились — это зона профиля B. Ниже всё относится к учебному дизайну, человеческой читаемости и правдивости заявленных уровней.

## Findings

### F1 — minor

```yaml
severity: minor
artifact: curriculum/tracks/b2/slices/risk-based-service-verification/learn/truthful-test-boundaries.md
criterion: structure
finding: В разделе «Один контракт, один дефект» подпись «Обещанный ответ:» стоит непосредственно перед JSON-блоком запроса, и только дальше идут статус-строка и тело ответа.
evidence: Редакционный стандарт §6 требует, чтобы перед кодом/JSON читатель понимал, какую гипотезу иллюстрирует пример. В README, interview, kata и project-spec вводные предложения однозначны («В следующем запросе отсутствует конец окна:» → запрос; «Публичный контракт требует … и согласованное тело:» → ответ). Learn-brief — единственный файл, где метка ответа прикреплена к блоку запроса; в точке, где задаётся канонический substrate, читатель вынужден перечитывать, чтобы разделить запрос и ответ.
recommendation: Заменить вводное предложение перед JSON запроса на «Точный invalid request:» (или переместить блок запроса до фразы об обещанном ответе) — однострочная правка без изменения содержания.
```

### F2 — note

```yaml
severity: note
artifact: curriculum/tracks/b2/slices/risk-based-service-verification/learn/truthful-test-boundaries.md
criterion: practice
finding: «Composition root» впервые используется в модели без русского глосса; определение есть только в принятом S06-материале по ссылке, а внутри slice глосс появляется позже и в kata («application factory или эквивалентная точка сборки»).
evidence: Термин входит в цепочку механизма, на которой держится seeded defect. Читатель, не читавший S06, понимает смысл из контекста («регистрация обработчика», «собранное приложение»), но первое употребление в brief не самодостаточно.
recommendation: При первом употреблении добавить короткий глосс в скобках, например «точка сборки приложения (`composition root`)».
```

### F3 — note

```yaml
severity: note
artifact: все пять артефактов slice
criterion: practice
finding: Терминологическая консистентность: «проверка» и «check» используются как синонимы для одной сущности; в таблице четырёх границ встречается «стоимость зависит от способа запуска consumer/provider» без уточнения объектов; в project-spec «fault cards» употребляется до словаря и не имеет словарной статьи.
evidence: Стандарт §4/§6: один термин для одной сущности, контекстно-зависимые слова (`consumer`, `provider`) требуют уточнения. Понимание не ломается: словари learn/interview/kata/project покрывают ключевые понятия, а «client/consumer» в повествовании не конфликтуют.
recommendation: Выбрать одно обозначение для «проверка/check» в связном тексте (допустимо оставить «check» только в составе введённых терминов «contract check», «component check»); уточнить ячейку про consumer/provider («запускается ли проверка против реального сервиса или согласованного представителя»); добавить «fault card» в словарь project-spec.
```

## Вывод по Verification/Compatibility L1–L3 и отсутствию L4

- **Verification L1** — правда: kata требует добавления точной regression check по заданному подходу с наблюдаемыми acceptance criteria; learn и interview поддерживают объяснением и probe.
- **Verification L2** — правда: kata-участник самостоятельно выбирает минимальные boundaries и локализацию; interview probe различает рассуждение по механизмам от перечисления типов.
- **Verification L3** — заявлен только project-spec (`integrate`/`assess`) и обоснован: service-wide portfolio, измеримое до/после, удаление дублирования, повторная fault injection. Kata L3 не заявляет.
- **Compatibility L1** — ожидаемое новое покрытие пакета; заявлено в learn (`explain`), interview (`probe`) и kata (`practice`/`assess`) с действиями, наблюдаемыми в acceptance criteria kata («поддержите заданную client contract check вместе с исправлением»). Соответствие формулировки outcome «вместе с additive change» точнее проверить профилю B (механика coverage-целей); по учебному дизайну завышения нет.
- **Compatibility L2** — kata обнаруживает несовместимый фактический ответ до «rollout» (до исправления) и объясняет пределы evidence; interview probe и learn explain согласованы.
- **Compatibility L3** — только project-spec: два представительных consumer expectations, inventory/версии, semantic checks, связь с release/migration decision. Ни один другой артефакт L3 совместимости не присваивает.
- **L4** — не заявлен нигде; interview-фоллоуап о межкомандных expectations явно маркирован как граница, а не evidence.

## Вывод по единому wire contract и различию kata/project

Единый substrate выдержан во всех пяти файлах: `POST /orders`, `Accept: application/problem+json`, один и тот же invalid body (`c-42`/`p-7`/`quantity 1`/`scheduled`/`start 2026-08-21T10:00:00Z`), `422`, `application/problem+json`, идентичные `type`/`title`/`status`/`detail` и расширение `errors` с `#/delivery/window/end` + `required`. История дефекта согласована: handler для `RequestValidationError` не зарегистрирован либо зарегистрирован не для того типа; исходные три класса проверок остаются зелёными. Version baseline (`fastapi 0.136.3`, `starlette 1.3.1`, `pydantic 2.13.4`) и даты совпадают в пяти YAML. Единственная локальная несостыковка подачи примера — F1 (подпись, не содержание).

Kata и project дают разные наблюдаемые результаты: kata — контрольный/дефектный/исправленный прогоны на одном дефекте с диагностической матрицей и decision note; project — inventory рисков всего сервиса, два consumer expectations, минимум три механизма отказа, заранее объявленный measurement envelope и доказательное удаление одной дублирующей проверки с повторной fault injection. Граница сформулирована в самих материалах и подтверждается их структурой.

## Ограничения профиля

Нормативные и version-sensitive утверждения (поведение FastAPI 0.136.3 default/custom handler path, `422 Unprocessable Content` относительно RFC, claims RFC 9457 об `errors`/JSON Pointer, актуальность latest FastAPI) не проверялись по первичным источникам и не воспроизводились runtime — это обязательная зона профиля B. Выводы выше не зависят от этих утверждений: они относятся к учебному дизайну и читаемости при принятии технической основы work package как заданной.

## Можно ли принимать slice после исправления findings

После внесения исправлений и отдельного acceptance-прохода slice может переводиться в `accepted` при условии подтверждения второго профиля (B) по технической корректности, coverage и contract consistency.
