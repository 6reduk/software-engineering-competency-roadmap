## Консолидированные findings и диспозиции

Источник: 🔵 — GLM (профиль A); 🟡 — Kimi (профиль B). Полные evidence и рекомендации — в исходных review; здесь сжатая запись с предлагаемой диспозицией. Окончательное решение за оркестратором. Фактические утверждения обоих профилей перепроверены консолидацией по артефактам (см. «Подтверждения»).

### Minor

**C-1 (🔵 A F-1). Материалы требуют strict types, но не предупреждают, что дефолт Pydantic/FastAPI валидирует в lax-режиме.**
На exact pinned stack lax-модель приняла `{"max_rows": "400"}`, `400.0` и `true` (bool → int); strict contract достигается только явной конфигурацией модели. Реализатор на дефолтах не пройдёт собственные type-variant cases из threat/cost matrix project-spec, а acceptance kata type-варианты явно не включает — lax binding может остаться незамеченным.
Диспозиция: **fix-проход** — одно-два предложения в learn («Сначала связать форму, затем считать») и пункт в контракты kata/project-spec: строгий режим включается конфигурацией модели; дефолт Pydantic в lax-режиме принимает str/float/bool для int.

**C-2 (🔵 A F-2). Дефолтный обработчик RequestValidationError в FastAPI возвращает `application/json` с эхом `loc`+`input` — имени поля и значения входа, включая forbidden/sensitive.**
Проба на bare-приложении без кастомного handler: status 422, content-type `application/json` (не problem+json), тело содержит имя sensitive-поля и значение. Дефолт нарушает сразу оба требования — media type и disclosure boundary; санитизация обязательна и нестандартна, при этом базовые тесты статусов остаются зелёными.
Диспозиция: **fix-проход** — предупреждение в learn (разделы binding/error) и kata contracts: безопасный input-invalid problem требует собственного exception handler; сериализация `errors()` по умолчанию эхом возвращает input. Правка выполняется тем же проходом, что C-1.

**C-3 (🟡 Kimi B-1). Термины `allowlist`, `harness` и `seam` используются без объяснения при первом употреблении и отсутствуют в локальных словарях всех пяти файлов.**
`allowlist` — нормативный элемент contract в README, learn, kata и project-spec, но нет в словаре README; `harness` (learn, timings) и `seam` (kata, подсказка 3 — смыслообразующий для выполнения) не расшифрованы и не в словарях. Редакционный стандарт §4 требует порядок «русское объяснение → английский термин в скобках».
Диспозиция: **fix-проход** — однострочные глоссы при первом употреблении (`разрешённый список полей (allowlist)`, `измерительный стенд (harness)`, `наблюдаемая точка перехвата (seam)`) либо записи в словари README/learn/kata.

**C-4 (🟡 Kimi B-2). Внутренняя метка `S05` употреблена в читательском тексте project-spec без человеческого названия и разрешающейся ссылки.**
«Trusted identity и object scope уже решены в S05» — единственные упоминания без ссылки на принятый S05 brief, который README slice содержит. Project-spec обязан быть автономной точкой входа (редакционный стандарт §4).
Диспозиция: **fix-проход** — при первом упоминании дать название и ссылку `../../tenant-scoped-orders-authorization/learn/trusted-context-object-authorization-boundary.md` (как в README slice).

### Note

**C-5 (🔵 A F-3). Лексика recovery заимствует нагрузочную терминологию при бестронных в этом substrate отказах.**
Материалы сами дефусируют смысл (interview Q6, learn), риск только в названии/формулировке «после прекращения adversarial workload».
Диспозиция: **опционально тем же проходом** — уточнение в словаре project-spec: recovery здесь — отсутствие накопленного эффекта отказов и сохранность legitimate use, а не восстановление израсходованных ресурсов.

**C-6 (🟡 Kimi B-3). Обе Mermaid-схемы имеют вопрос до схемы и вывод после, но намеренные упрощения явно не названы.**
README flowchart и learn sequence diagram не показывают input-invalid отказ на этапе binding и audit path; читатель схемы изолированно может решить, что любой отказ проходит через cost-оценку.
Диспозиция: **опционально** — по одной фразе после схем о неназванных ветках.

**C-7 (🟡 Kimi B-4). Формулировки substrate в project-spec слегка отличаются от общего envelope без объяснения («минимум 3000 Orders», «для двух tenant»).**
Противоречия по существу нет: второй tenant нужен для isolation evidence L3, «минимум» — требование к реализации участника; редакционный стандарт §11 требует объяснять намеренные различия чисел.
Диспозиция: **опционально** — одно предложение в spec о назначении второго tenant и минимуме fixture.

**C-8 (🔵 A F-4). Versions baseline не фиксирует версию httpx/httpx2, хотя задокументированное ограничение harness — deprecation warning именно httpx-пути TestClient.**
Диспозиция: **отложено** — включить фактическую версию httpx (или httpx2) в versions slice при следующем обновлении baseline.

**C-9 (🟡 Kimi B-5). Диспозиции applicability matrix в spec уже заполнены; участник дополняет только evidence-ссылки.**
Соответствует adjudication M1.8.10 (пакетное закрепление диспозиций) и authoring contract; риск — копирование pre-filled матрицы как нормы будущими slices без package-level adjudication.
Диспозиция: **запись в resolution G10, без правки материалов** — pre-filled диспозиции допустимы только при adjudicated package design; самостоятельность L2 подтверждается собственной реализацией, evidence-ссылками и decision record.

## Согласованный вывод по Gate 0, substrate и measurement

Оба профиля подтверждают: Gate 0 можно считать `confirmed` на exact pinned stack. Профиль A воспроизвёл стек (существование версий по первичным источникам, совместимость пинов, фактический запуск) и весь measurement envelope: точные граничные populations, нулевые delta обоих counters для rejected cost cases (доказательство reject-before-work, а не только status code), корректность cell-unit без header, консервативность оценки (малый tenant: оценка 2000 при фактических 20 ячейках — заявленный false-positive trade-off реален), бестронность 100 отклонённых запросов и сохранность legitimate use после них. TestClient deprecation warning воспроизведён и честно зафиксирован в Gate 0 как ограничение harness; timings корректно диагностические — acceptance от них не зависит, и medians на другом железе закономерно отличаются. Профиль B подтвердил, что envelope и числа идентичны во всех пяти материалах и синхронизированы с регистрациями. Разделение доказанного и design requirement зафиксировано профилем A: counters/experiment доказывают reject-before-work, tenant non-trust, allowlist/header construction, консервативность и disclosure-границу при явной санитизации; production weights, quota/rate, SSRF, response-bytes/peak-memory, CSV injection, storage cost и concurrency остаются design requirements/residual risks — материалы распределяют их именно так.

## Ответы на открытые вопросы work package

1. **Recovery после 100 запросов.** Согласованный ответ: population доказывает, что отказы не оставляют учитываемой работы (суммарные delta 0/0 — независимо воспроизведено профилем A) и что legitimate use сохранён (`200`/1600 cells сразу после серии); он не доказывает восстановление ресурсов — в этом substrate отказы их не расходовали. Материалы проводят эту границу сами (interview Q6, learn); лексическая неаккуратность зафиксирована как C-5.
2. **Достаточность cell model и двух counters для L3.** Согласованный ответ: достаточно внутри объявленного synthetic envelope при честных residual risks, stop conditions и triggers перекалибровки; всё, что модель не покрывает (SQL scan, response bytes, peak memory, размер строк, concurrency, storage), явно вынесено за границу доказательства. L3 claim опирается на воспроизведённые abuse paths + сохранность legitimate use + design defense, что соответствует формулировке outcome.

## Рекомендация оркестратору

1. **Принять M1.8.11 с verdict `accepted_with_changes`** и выполнить один точечный correction-pass по пяти материалам slice: обязательны C-1–C-4 (предупреждения о lax-дефолте и эхе дефолтного обработчика в learn/kata/project-spec; глоссы `allowlist`/`harness`/`seam`; ссылка на S05 brief в project-spec); опционально тем же проходом C-5–C-7. Правки не затрагивают versions, contract, формулу, threshold, populations, counters, coverage YAML и регистрации — повторный полный review не требуется, достаточно verification-прохода по чек-листу правок.
2. **Зафиксировать в resolution:** C-9 — толкование pre-filled applicability matrix (допустима только при adjudicated package design; самостоятельность L2 — в реализации и evidence участника); C-8 — обязательство включить httpx/httpx2 в versions при следующем обновлении baseline; согласованные ответы на два открытых вопроса пакета (recovery, достаточность L3 envelope).
