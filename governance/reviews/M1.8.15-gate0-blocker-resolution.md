# M1.8.15 — решение по блокировке Gate 0

## Установленная причина

Блокировка признана обоснованной. Принятые S03/S10 материалы задают контракт и проверки, но намеренно не содержат исполняемую Orders API implementation. Исходная редакция M1.8.15 одновременно требовала фактические healthy/degraded rehearsals и запрещала создание runtime implementation, поэтому автор не мог честно подтвердить Gate 0.

Это дефект orchestration contract, а не недостаток работы автора.

## Решение

Разрешить для Gate 0 одноразовый экспериментальный стенд в системном временном каталоге вне проекта. Он может содержать минимальные contract-faithful old/new probe services, локальное управление traffic, генератор legacy/scheduled cohorts и сбор сигналов, необходимых для проверки staged exposure, stop и recovery.

Стенд проверяет только readiness rollout-механики S11. Он не доказывает полноценную реализацию S03, не входит в учебные материалы, не передаётся учащемуся, не становится scaffold, project repository или ImplementationReference и удаляется после эксперимента.

## Возобновление

Предыдущий `blocked` Gate 0 record остаётся в work package как аудиторский след. Автор выполняет новый readiness-pass и заменяет текущий итог на:

- `confirmed` — если временный стенд дал воспроизводимые healthy/degraded, exposure, stop, recovery и cleanup evidence;
- новый `blocked` — если даже минимальная модель требует строительства deployment/observability platform либо не позволяет честно наблюдать требуемые сигналы.

После `confirmed` автор продолжает исходный M1.8.15 в прежнем Ownership. Gate G14 и program status этим решением не изменяются.
