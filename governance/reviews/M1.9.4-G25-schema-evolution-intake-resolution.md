# M1.9.4 — решение оркестратора по G25

## Решение

Консолидированный результат принят как `accepted_with_changes`: **0 blocker / 1 major / 4 minor / 3 note**.

Два независимых профиля подтверждают выбранную границу SE01: одна таблица и одно денежное правило, пять промежуточных состояний, две версии доступа, различимые control/defect/fixed, независимая сверка и честное разделение ответственности B2/B3/B6/B7. Intake пока не принят: C-1 не гарантирует, что будущий опыт действительно воспроизведёт устаревший backfill, а не получит свежую строку из-за повторной проверки условия `UPDATE` в PostgreSQL либо иную сигнатуру при другой изоляции.

До acceptance выполняется один ограниченный correction-pass по [`M1.9.4a-G25-findings-correction.md`](../work-packages/M1.9.4a-G25-findings-correction.md). Он закрывает C-1–C-6 и явно переносит C-7/C-8 в обязательные входы будущего Gate 0. Повторный полный G25 и новые независимые профили не нужны: оркестратор проверит mapping и сохранность предметной границы.

## Disposition findings

| Finding | Решение | Обоснование |
|---|---|---|
| C-1, major | Исправить до acceptance | Различающий дефект — центральное основание выбора SE01. Intake должен требовать двухшаговое «захватить значение → применить после барьера», фиксировать изоляцию и ожидаемую сигнатуру, но не выдавать готовый SQL. |
| C-2, minor | Исправить до acceptance | Авторитетным является подтверждённое изменение суммы приложением, а не последующая техническая копия backfill. Без этого oracle допускает неверное буквальное прочтение. |
| C-3, minor | Исправить до acceptance | В topology фактически шесть соединений. Readiness должна охватывать и отдельный сеанс lock-пробы. |
| C-4, minor | Исправить до acceptance | Машинный `NOT_RUN` и необъяснённый Gate 0 противоречат принятому human-readable стандарту. |
| C-5, minor | Исправить до acceptance | Термины должны быть понятны при первом употреблении, а сверка данных не должна смешиваться с проверкой ограничения хранилища. |
| C-6, note | Исправить в том же проходе | Заголовок пятого состояния должен честно отражать конец лабораторного опыта: новое представление обязательно, старое ещё сохранено. |
| C-7, note | Зафиксировать как обязательное решение будущего Gate 0 | До authoring нужно решить, являются ли отрицательные и избыточно точные суммы частью домена, как они ограничиваются и какими пробами проверяются. Округление самим типом не считается отвержением. |
| C-8, note | Зафиксировать как обязательное решение будущего Gate 0 | Ограничение согласованности нельзя включать раньше механизма совместимости, если прежний W-old должен оставаться допустимым. Точный механизм выбирается только по исполняемой пробе. |

## Сохраняемые инварианты

- выбранное действие остаётся переходом `amount_rub numeric(12,2)` → `amount_minor bigint` через дополнительный столбец, сосуществование и backfill;
- предметный oracle сохраняет шесть ID и ожидаемые суммы в копейках; в Defect для изменённой приложением строки ожидается 12000, а не 10000;
- пять состояний и четыре пути R-old/W-old/R-new/W-new сохраняются; третья версия приложения и удаление старого столбца не добавляются;
- будущий опыт остаётся control/defect/fixed с конкурентными INSERT/UPDATE, независимой сверкой, lock-профилем, resume и cleanup;
- числа 2/60 секунд остаются предложенными лабораторными предохранителями, а не измерениями или SLO;
- все восемь readiness-категорий остаются неподтверждёнными до Gate 0;
- не создаются SQL, migration, scaffold, runtime harness, учебные материалы, coverage, ImplementationReference или BR01;
- не меняются B3 catalogs, role projections, prerequisites, STATUS, DECISIONS и program/module status.

## Acceptance boundary

После авторского handoff оркестратор выполняет точечный verification-pass C-1–C-8. Только отдельный acceptance-pass может перевести intake и связанные G25 artifacts в `accepted` и разрешить подготовку отдельного Gate 0 + пятижанрового authoring package SE01. Acceptance intake не подтверждает readiness, runtime evidence, coverage, proficiency или завершение B3.
