# M1.9.3 — решение оркестратора по G24

## Решение

Консолидированный результат принят как `accepted_with_changes`: **0 blocker / 1 major / 2 minor / 5 note**.

Два независимых профиля подтверждают техническую состоятельность SQ01: каноническая SQL-семантика и Gate 0 воспроизводимы, пять жанров образуют ограниченный маршрут, 30 coverage relationships механически точны, а grouped/window L3 имеет собственное содержание. Пакет пока не принят: C-1 делает центральное L3-задание project-spec условным evidence, потому что его неоднозначность уже разобрана в скрытом ответе interview того же автономного slice.

До acceptance выполняется один ограниченный correction-pass по [`M1.9.3a-G24-findings-correction.md`](../work-packages/M1.9.3a-G24-findings-correction.md). Он закрывает C-1–C-3, C-6 и C-7 и уточняет C-5. Повторный полный G24 и новые независимые профили не нужны: оркестратор проверит mapping, отсутствие раскрытого проектного решения и сохранность coverage/SQL-инвариантов.

## Disposition findings

| Finding | Решение | Обоснование |
|---|---|---|
| C-1, major | Исправить до acceptance | Автономный interview раскрывает оба прочтения того же требования, различающие данные и под-решение. Project-spec должен измерять самостоятельное разрешение другой неоднозначности, а не память о скрытом ответе. Предписывать порядок чтения нельзя: это ломает контракт автономных точек входа. |
| C-2, minor | Исправить до acceptance | Термины должны быть понятны в каждом автономном файле. Правка локальна и не требует расширения содержания. |
| C-3, minor | Исправить до acceptance | Нормативное утверждение о том, что окно не сворачивает строки, должно иметь прямой первичный источник. Добавляется PostgreSQL tutorial по окнам во все пять синхронных source-блоков. |
| C-4, note | `no-change` | Повтор канонического договора — сознательная цена автономности пяти точек входа. Сейчас сокращение создаст дополнительный редакционный churn и риск неравноценных входов. При будущем изменении договора все пять копий проверяются синхронно. |
| C-5, note | Уточнить в correction-pass | `assess` L2 проекта остаётся правдивым как интеграция SQL с собственной оснасткой и расширенными данными, но не считается независимым вторым подтверждением после kata. Новое проектное требование должно включать хотя бы один расширенный различающий набор, а не только канонический пример. Coverage не меняется. |

| C-8, note | Правило для будущих Gate 0, без изменения текущего record | Хэш без сохранённого хэшируемого артефакта не используется как воспроизводимое доказательство. Текущий record уже честно называет его идентификатором запуска и содержит отдельное воспроизводимое evidence; переписывать историю Gate 0 не нужно. |

## Обязательное решение по C-1

В project-spec нужно заменить дополнительное требование про «платежи больше 50» на другую предметную неоднозначность. Новое задание обязано:

1. не иметь готовой пары трактовок или различающей таблицы ни в одном `<details>` текущего slice;
2. требовать минимум два осмысленных прочтения, разные ожидаемые результаты и decision record;
3. использовать как минимум один новый расширенный набор данных, определяемый участником, а не только канонические заказы 1–4;
4. проверять и composition, и grouped/window decision, чтобы оба L3 outcomes оставались правдивыми;
5. не предписывать конкретный SQL, CTE, JOIN, окно или единственную внутреннюю структуру.

Допустимые направления: смысл ранжирования переплаты, состав и порядок отдельной сводки возвратного риска, либо другой показатель, который требует одновременно определить состав строк и оконный порядок. Формулировку нельзя сводить к уже разобранным вариантам «сохранить все строки или отфильтровать», «только оплаченные» либо `amount > 50`.

## Сохраняемые инварианты

- пять учебных artifacts и coverage map остаются `status: review` до отдельного acceptance-pass;
- PostgreSQL/psql 18.6, каноническая схема, fixtures, expected rows, defect 400/200, `balance`, ранги `1,1,2,3` и порядок `1,4,2,3` не меняются;
- исходный Gate 0 record и его результаты не переписываются; runtime experiment не повторяется;
- 30 relationships, 8 targets и роли `reference 2 / explain 6 / probe 6 / practice 4 / assess 8 / integrate 4` не меняются;
- kata остаётся L1/L2, project-spec — L2/L3; L4/L5 и соседнее coverage не добавляются;
- готовый fixed SQL, scaffold, learner implementation и ImplementationReference не добавляются;
- B3 README, coverage map, catalogs, STATUS, DECISIONS и следующий SE01 package не изменяются.

## Acceptance boundary

После авторского handoff оркестратор выполняет точечный verification-pass C-1–C-3/C-5–C-7. Только отдельный acceptance-pass может перевести пять материалов, coverage map, исходный authoring work package и G24 work package в `accepted`. Принятие SQ01 не означает выполнение проекта участником, proficiency, module gate или начало SE01.
