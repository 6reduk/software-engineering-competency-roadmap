# M2.2 — принятие B5 capability breadth-pass

## Итог

M2.2 и G30 приняты после двух независимых профилей, консолидации и correction-pass M2.2a:

- приняты 6 modules, 17 capabilities, 51 LevelOutcomes L1–L3 и 11 scenarios для всех 11 кластеров B5;
- приняты 34 role links: Backend `11 required / 1 deepening / 5 conditional`, Architecture `13 required / 4 deepening / 0 conditional`;
- сохранены 5 ацикличных `Requires` и 8 навигационных `Related`;
- README начинается с предметной проблемы и содержит 11 полностью кликабельных цепочек с русскими названиями;
- пояснена выборочность hard edge для leadership assessment без изменения DAG;
- Architecture requirements явно относятся к выбранной B5 `depth`-специализации и model-level выбору, а не реализации каждого механизма;
- bounded depth, таксономия пяти типов решений, шов replication B3/B5 и C1 decision-record carrier сохранены;
- три кандидата остаются различимыми, а blueprint не начисляет coverage и не подтверждает proficiency, выполнение сценариев, Gate 0, runtime evidence или module completion.

Семь каталогов `pilot/b5` переведены в `accepted`. Повторный G30 не требуется.

## Disposition notes

- Тип будущего slice определяется объектом гарантии, а не жанром verification. Расширение таксономии требует отдельного решения.
- Одинаковые outcome suffixes сохранены как компактная конвенция; второй outcome того же уровня внутри capability должен получить предметно различимый slug.
- Историческая неизменность до авторского SHA-256 snapshot остаётся `NOT_VERIFIED`.

## Выбор первого deep slice

Первым выбран кандидат **«старый исполнитель после передачи полномочий»** вокруг TO01/CL01.

Причины выбора:

1. Это наиболее B5-специфичный из трёх кандидатов: он проверяет различие между знанием участника о лидерстве и правом создать эффект у общего ресурса.
2. Он меньше повторяет принятые B2 messaging/idempotency и B3 transaction/schema материалы, чем композиция доставки и эффекта.
3. Он даёт связный результат обеим ролям: Backend размещает проверку полномочия на границе эффекта, Architecture выбирает authority и цену сохранения safety/progress.
4. Дефект и исправление различимы наблюдаемо: устаревшее действие либо принято ресурсом после передачи владения, либо отвергнуто по более старому fencing token.

Кандидат чтения после записи остаётся возможным вторым slice другого типа — visibility/consistency. Решение о нём принимается только после acceptance первого slice с повторной проверкой контраста и стоимости среды. Композиция доставки/эффекта остаётся долгом карты, но не запускается параллельно.

Следующим разрешён M2.3 с обязательным Gate 0 до создания учебных материалов. Выбор конкретного coordinator/resource substrate выполняется внутри Gate 0 и не создаёт platform/B3 coverage.
