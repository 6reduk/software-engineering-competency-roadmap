## Ответы на шесть обязательных вопросов

1. **Достаточно ли определён intake, чтобы после corrections создать один Gate 0 + authoring package SE01?** По профилю B — да, после закрытия B-1 (и желательно B-2). Предмет, инвариант, четыре контракта, пять состояний, control/defect/fixed, сверка шести ID, rollback/roll-forward без drop, readiness «не подтверждены» и границы B2/B3/B6/B7 заданы так, что можно спроектировать один лабораторный пакет и затем пятижанровый SE01, не расширяя его до курса migrations. Открытые вопросы 1–5 не меняют ownership. Исполняемая форма Defect и точные DDL/lock — зона профиля A и будущего Gate 0, не пробел учебной границы intake. Этот ответ не разрешает создать Gate 0: это решает оркестратор после консолидации.

2. **Какой точный наблюдаемый результат отличает Defect от Fixed?** Defect: перенос захватывает 100,00 по ID 2, W-old подтверждает 120,00, наивный перенос пытается записать 10000 копеек; исход — либо диагностируемое расхождение с последней подтверждённой суммой, либо отвержение защитой; сверка/ошибка запрещает объявить успех; в следе нет перехода к завершению. Нельзя выдать ожидаемый отказ ограничения за потерю данных. Fixed: на том же чередовании (плюс W-old INSERT ID 5 и W-new INSERT/UPDATE) последняя подтверждённая сумма сохранена; независимый ожидаемый набор ID 1–6 в копейках `0, 12000, 1300, 999999999999, 789, 2501` сверен; после прерывания и продолжения получается тот же набор. Oracle строится из входных команд и подтверждений, не из чтения backfill. Конкретный двухшаговый механизм захвата устаревшего значения — условие будущего Gate 0, не готовый SQL в intake.

3. **Какие условия обязан доказать будущий Gate 0 до первого учебного материала?** Закрепить версии PostgreSQL и клиента; topology и владение пятью соединениями; фактическую семантику выбранных DDL/ограничений по первичным источникам этой версии; режимы блокировок и достижимость предложенных 2/60 секунд либо обоснованно другие лабораторные числа; детерминированные барьеры writer/backfill/validation без `sleep`; независимый oracle и полную сверку шести ID плюс отрицательные пробы; resume без порчи суммы; cleanup/reset; что лабораторный результат — expand/backfill/validate при сохранённом старом представлении, а не production cutover и не adoption. Сохранить текст probe вместе с хэшами (урок границы SQ01). Учебные жанры не писать, пока эти пункты не подтверждены. Редакционно: в будущих материалах термины из B-2 объяснять при первом употреблении.

4. **Правдивы ли границы двух capabilities и L1–L3, особенно самостоятельность L2/L3?** Да для intake. Адресация только `plan-compatible-schema-transitions` и `validate-online-data-change`; шесть формулировок согласованы с `level-outcomes.md`. Hard edge «планирование совместимости → проверка изменения» сохранён; Related к моделированию и диагностике не повышены. Coverage не начисляется. L2-самостоятельность участника после intake сохраняется в выборе механизма и SQL, не в повторном изобретении таблицы и инварианта — для planning artifact это правильно. L3 каталога («неизвестный потребитель», «конфликт срока и доступности») назван и сознательно не реализован третьей версией. Заданный сценарий с двумя известными путями нельзя выдавать за самостоятельное L3-решение в будущем authoring: это субстрат объяснения (L1) и ограниченного выполнения (L2). RoleViews (Backend: plan L2 + deepening L3, online change условно; Architecture: plan L3, online change L1 + условный L3) intake не переопределяет.

5. **Где заканчивается B3 и начинается ответственность B2/B6/B7?** B3 заканчивается на состояниях одной таблицы, store-ограничениях, DDL/backfill, локальных блокировках, сверке полноты/корректности и лабораторной границе продолжения. B2 начинается на контрактах приложения и полном составе writers: лаборатория задаёт две версии как вход; неизвестный потребитель и удаление старого поля — вопрос B2, не третья реализация в B3. B6 — выделенная среда, права и, если стенд от этого зависит, оркестрация job; платформенный rollout не проектируется. B7 — эксплуатационный stop/go, SLO, incident; лабораторные сигналы B3 не становятся production gate. Соседние B2-срезы (eligibility отмены; HTTP-rollout окон доставки) не импортируются как evidence миграции.

6. **Какие findings обязательны до acceptance, а какие относятся к будущему Gate 0, learner implementation или backlog?** До acceptance: B-1. B-2 — до acceptance либо backlog по решению оркестратора (minor). Backlog / no change: B-3. Future Gate 0: версии, семантика DDL, lock-пара, достижимость 2/60, исполняемый Defect, выбор store-side vs adapter, независимый oracle на стенде — это не findings профиля B, а неподтверждённая readiness intake. Learner implementation: не поставлять готовый SQL/migration/scaffold; не выдавать этот сценарий за L3; сохранить самостоятельность механизма. No change: сравнение кандидатов, split ownership, маркировка 2/60, честность конечной границы в теле, metadata/hygiene. Никакой finding этого отчёта не запускает BR01 и не принимает SE01.
