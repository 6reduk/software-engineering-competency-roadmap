# G20: независимый review post-S01 consolidation — Codex

## Профиль, verdict и граница решения

**Профиль A — traceability, governance и mechanical consistency.** Reviewer — Codex, агент на базе GPT-6; фактический суффикс отчёта — `codex`.

**Verdict: `accepted`. Счётчик: `0 blocker / 0 major / 0 minor / 1 note`.**

Snapshot, точные связи, memberships и hard DAG воспроизводятся. Досье сохраняет границу между принятым заданием и выполненной работой. Десять gate cards дают различимые условия рассмотрения, но ни одна не принимает gate. Рекомендация одного B3 boundary intake допустима в обозначенных границах.

Это verdict одного независимого профиля, а не acceptance M1.8.21 или G20 от имени оркестратора. Статус отчёта — `review`; обязательный второй профиль либо отдельное исключение именно для G20 этим отчётом не заменяются.

## Фактический scope и метод

Проверены delivery plan и пять файлов consolidation в текущем состоянии 2026-09-09. Прочитаны общий governance/context manifest, каталоги B2, обе RoleViews, H0–H3, R1 и C1. Front matter accepted artifacts разобран программно. README и project-spec остальных slices использованы для проверки конкретных route, gate и readiness claims; это не повторное полное предметное ревью двенадцати учебных пакетов. Проверены также исходные границы B3 в принятом track skeleton.

Пересчёт выполнен собственным Python/PyYAML проходом из Study, без запуска кода self-check из плана и без использования авторского `validation.json`:

1. Из `curriculum/tracks/b2/**/*.md` выбраны parsed metadata с `status: accepted` и `coverage`; фактически все 61 находятся в `slices/`. Проверены уникальность artifact IDs, допустимость targets и отсутствие повторов `(target, role)` внутри artifact.
2. Построен multiset `(artifact path, exact target, role)`. Capability references отделены от outcome relationships до вычисления covered и probe-only.
3. Из registry плана извлечены все коды, пути, genres и численные role totals; набор путей и каждое распределение ролей сопоставлены с YAML.
4. Все 69 строк outcome audit разобраны по точному ID, ссылке на artifact и каждой роли. Сравнение multisets показало ноль missing и extra relationships; проверено равенство набора строк каталогу outcomes.
5. Membership получен из `Develops` каталога modules и outcomes соответствующих capabilities. DAG построен исключительно из таблицы hard `Requires`; related и внешние specifications исключены.
6. Проверены local links/anchors и Markdown шести файлов. Fenced code исключался из анализа ссылок/HTML, inline code — из подсчёта `<details>`; таблицы проверялись с учётом escaped pipes. Ошибки и ограничения проверяющего кода не выдавались за findings материалов.

Первая черновая проверка DAG захватила related-таблицу и дала 21 ребро. После ограничения канонической hard-таблицей повторный успешный проход дал **13 рёбер / 8 корней / 19 узлов в topological order**. В выводах используется только исправленный проход. Ошибка кодировки первого вывода файла также устранена повторным UTF-8 чтением.

Runtime-проекты участника не выполнялись (`NOT_RUN`). G19 используется как принятое историческое основание с его ограничениями; текущие версии библиотек, production behavior и proficiency не переподтверждаются этим review. Свежесть внешних release records не является предметом consolidation refresh.

- **Severity:** `note`.

- **Evidence:** `git status --short` из Study вернул `fatal: not a git repository`. Независимого pre-M1.8.21 snapshot у reviewer нет. Авторский temp snapshot не использовался как независимое основание. Текущий YAML и registry согласованы, однако такое равенство не восстанавливает прежние байты.
- **Impact:** это ограничивает исторический scope verdict, а не опровергает текущий snapshot, coverage или границы досье. Изменение вне Ownership не обнаружено и не утверждается. Ограничение уже предусмотрено G20 и явно названо в плане; требовать невозможное восстановление прошлого как correction не нужно.
- **Минимальная recommendation:** при disposition сохранить эту оговорку; не переименовывать текущую сверку в независимый historical diff. Для следующего bounded authoring при необходимости строгого доказательства заранее сохранить независимый path/hash snapshot либо VCS baseline.

H3 оставляет выбор диагностического concern и границы участнику; H2 задаёт посев. S10 с известной handler-registration ошибкой и R5 с fan-out/resource действием не переименованы в S01. H3 требует **396 = 366 + 27 + 3** операций; G19 probe **369 = 366 + 3**. Readiness сохраняет это различие, recovery 60 и отдельную concurrent population 36. Ни одна из этих арифметик не начисляет production Trace L3.

В [debt register](../../curriculum/tracks/b2/consolidation/debt-register.md#d19):

- D19 хранит историю принятого navigation/genre action и disposition `closed-content`.
- D20 хранит закрытый content/exercise action и открытый самостоятельный refactor, raw traces, regression, isolation/recovery и review. Disposition — `after-readiness`.
- D26 учитывает выполнение, review и регистрацию всех двенадцати проектов; одна реализация не закрывает остальные одиннадцать.
- D27 учитывает отдельные решения по scope модулей.

Последний раздел реестра прямо объясняет D20/D26 как две проекции одного отсутствующего результата, а не два проекта. D19/D20 не удалены и не назначены повторным content package. Ссылки на них в README, routes, gates и readiness описывают новый статус согласованно.

Найдены ровно D01–D27 без повторов. Категории: 11 uncovered, 7 probe-only, 1 execution, 1 navigation, 4 scope, 1 external readiness, 1 implementation reference, 1 module decision. Dispositions: **1 candidate-now / 1 closed-content / 6 after-readiness / 5 requires-real-adoption / 12 conditional-specialization / 2 accepted-limitation**. Это 27 сохранённых записей, не 27 открытых задач и не рейтинг severity. D21 `candidate-now` означает кандидат на рассмотрение с собственной readiness, а не второе назначение рядом с B3.

## B3 intake и конечность следующего шага

[Сравнение плана](../../curriculum/tracks/b2/module-delivery-plan.md#сравнение-следующей-фазы) рассматривает именно три требуемых варианта. D21 предлагает отдельный S12 experiment, но distinct mechanism и применимая B7 readiness ещё не установлены. HTTP gate preparation не близок к принятию: H3/R5 остаются заданиями, а S02/production tracing и применимые L4 нельзя получить новым обзорным документом.

Выбор B3 допустим как **одно следующее управленческое действие программы**. Обе внешние RoleViews относят B3 к depth. [B3 scope](../../curriculum/tracks/catalog/b3-transactional-data.md) действительно владеет isolation/MVCC/locks/anomalies, а application persistence оставляет B2. S07 проверяет application transaction/side effects, S15 — application cache; их применение PostgreSQL/Redis не является самостоятельным B3 результатом. Поэтому intake устраняет реальный риск смешать этих владельцев, а не просто повышает coverage.

Конкретное store-level действие намеренно выбирается будущим intake. Уже сейчас ограничены его область, один документальный deliverable и критерии: одна граница B2/B3, один owner concern, один будущий наблюдаемый результат, readiness и разрешённый Ownership без неразрешённого конфликта. Для такого документального шага не требуется выдавать неисполненный runtime Gate 0 за подтверждённый. Runtime readiness будет условием зависимого execution/authoring package.

Exit конечен: один документ в review передаётся на независимый review и решение оркестратора; ни content package, ни полный B3 blueprint не принимаются автоматически. Возврат к B2 имеет конкретные triggers D21/D26, а не бесконечное требование снова описать десять partial. Это не запрещает участнику начать уже принятый B2 проект и не утверждает, что переход к B3 лучше такого проекта для любого отдельного инженера.
