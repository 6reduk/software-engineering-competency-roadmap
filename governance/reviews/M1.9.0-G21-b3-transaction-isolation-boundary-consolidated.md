# M1.9.0 — G21 консолидированный review B3 transaction/isolation boundary

## Назначение и способ консолидации

Настоящий отчёт объединяет два завершённых независимых профиля G21 по `authoring/workflow/review-protocol.md`: дубликаты объединены, противоречия разрешены через первичные источники и цели программы, а не голосованием. Исходные отчёты остаются независимыми записями и не изменялись; консолидация создана по решению оркестратора после получения обоих профилей. Ни одна readiness-категория Gate 0 этим документом не подтверждается; эксперимент не выполнялся.

Единственное фактическое противоречие между профилями — номер dev-версии, отображаемый страницей [Psycopg Transactions management](https://www.psycopg.org/psycopg3/docs/basic/transactions.html).

- Профиль A (glm) зафиксировал minor A-1: страница отображает `3.3.4.dev1`, intake заявляет `3.3.6.dev1`.
- Профиль B (kimi) независимо подтвердил `3.3.6.dev1` по официальной странице.
- Разрешение повторным обращением к первоисточнику без кэша 2026-09-09: страница отображает **`3.3.6.dev1`** — заявление intake верно.

**Finding A-1 отозван** как основанный на устаревшей кэш-копии. Попутное наблюдение сохраняется как редакционная опция (без номера finding): маркер dev-версии на этой странице чувствителен к зеркалам/кэшу, что лишь подтверждает оговорку самого intake — dev-документация не подтверждает применимость к стабильному driver, и повторная сверка при закреплении версии в Gate 0 обязательна.

## Консолидированные ответы на обязательные вопросы

### Профиль A — техническая причинность

1. Write-skew defect воспроизводим при заявленном schedule: при RR с обоими чтениями до разрешённых записей и записями в разные строки same-row abort невозможен, обе транзакции фиксируются без exception, инвариант нарушен; условие воспроизводимости — единая транзакция чтение-запись (C-1) и отключённые автоповторы.
2. Fixed даёт требуемый store conflict без второго механизма: цикл rw-зависимостей отслеживается SSI, одна транзакция откатывается с `40001`; смена изоляции обеих транзакций необходима и достаточна; жертва и точка обнаружения не предписываются.
3. Минимальные observations: значения чтений обоих участников с привязкой к транзакциям, барьерный порядок, эффективные настройки (изоляция в транзакции, autocommit, отсутствие savepoint-обёртки и скрытого retry), терминальные исходы с SQLSTATE и стадией, committed state независимого наблюдателя, различённая новая попытка.
4. Store conflict, rollback и прикладной отказ разведены корректно: исходный конфликт — store signal с rollback; новая попытка — отдельная, с новым чтением, ожидаемо заканчивается бизнес-отказом; retry-подсистема не проектируется.
5. Readiness-категории достаточны; до authoring требуют конкретизации способ верификации эффективной изоляции, механизм read-сигналов, доступность snapshot/txid-следа с привязкой чтения к транзакции записи (C-1) и повторная сверка Psycopg с закреплённым stable driver.
6. Intake принимаем после disposition findings без подтверждения Gate 0 и без эксперимента: NOT_RUN и неподтверждённые категории — честное состояние planning artifact.

### Профиль B — boundary и читаемость

1. Работающий backend/tech lead понимает проблему и выбранное действие без чтения всех B2-документов; процессные оговорки (C-5) не на пути понимания.
2. Сравнение кандидатов содержательно: единые измерения, причины выбора и отклонений предметны, решение из сравнения следует.
3. Последовательно ясно, что принято только направление будущей проверки, а не среда, evidence, capability или учебный материал.
4. Сценарий полезен обеим RoleViews при разной глубине: Backend — воспроизведение и объяснение store signals; Architecture — защита гарантии, её стоимость и граница ответственности вызывающей стороны; равный уровень не приписан.
5. Критичных фрагментов внутренней нотации нет; зафиксированы только C-5 и C-6.
6. Intake принимаем после disposition findings; следующий шаг — отдельное решение оркестратора.

### Open questions work package

1. **Snapshot в control/defect/fixed:** описано достаточно — для defect/fixed барьер гарантирует предшествование обоих snapshot обеим записям, control самопроверяем; дисциплина первого statement закрепляется в Gate 0 (C-2).
2. **Store observations без полного dependency graph:** достаточно — значения чтений, барьерный порядок, исходы, SQLSTATE и committed state причинно объясняют конфликт; intake правильно не требует внутренний граф SSI.
3. **Следующий результат и минимальное решение перед authoring:** по обеим консолидированным позициям минимальное обязательное решение перед authoring учебных материалов — подтверждение среды Gate 0 (закрепление build, stable Psycopg, координационной оснастки, верификации эффективных настроек) плюс disposition C-1. Порядок документальных шагов — capability blueprint или bounded content-planning package с Gate 0 — выбор оркестратора: оба профиля согласны, что blueprint документален и не требует runtime, а любой учебный контент требует подтверждённой среды; reviewer следующий пакет не создаёт и не предписывает.

## Решение о принятии M1.9.0

M1.9.0 можно принимать: оба независимых профиля получены, открытых blocker/major нет, единственный minor C-1 закрывается одним предложением в корректирующем проходе. Принятие выполняется отдельным acceptance-pass оркестратора после disposition всех findings; настоящий отчёт Gate 0 не подтверждает, эксперимент не выполнял и следующий пакет не назначает.

- Оба профиля выполнены независимо: каждый reviewer подтвердил, что отчёт другого не существовал и не читался до завершения анализа; проверяемые материалы не редактировались ни одним из них; каждый создал ровно один собственный отчёт, консолидация создана отдельно по решению оркестратора.
