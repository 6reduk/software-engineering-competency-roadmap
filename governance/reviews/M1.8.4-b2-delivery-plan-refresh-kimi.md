# M1.8.4 — review обновлённого B2 delivery plan, профиль B

- Профиль: **B — domain, learning sequencing и выбор S07**.
- Модель: `kimi`.

- Scope: доменная достаточность prerequisite evidence, корректность очереди и decision brief, выбор S07, границы B2/B3/B5, роль-ценность. Механический пересчёт чисел (155/42/27/7 probe-only, memberships) — зона профиля A; здесь числа проверены точечно как основание для доменных выводов, без претензии на полный recount.
- Review выполнено независимо: отчёт профиля A не читался, исходные файлы не редактировались.

## Verdict

**`accepted`** — `blocker 0 / major 0 / minor 1 / note 3`.

Все критерии профиля B пройдены. Единственный minor имеет минимальный путь закрытия при создании S07 authoring work package и не требует переработки плана до disposition; решение по нему и по notes остаётся за оркестратором.

## Findings

### F-1 (minor)

- artifact: `curriculum/tracks/b2/module-delivery-plan.md` (decision brief, scope)
- criterion: practice
- finding: Один S07 slice заявляет одновременно Transaction L3 (`manage-application-transaction-boundaries-l3-resolve-side-effect-consistency`) и Idempotency L3 (`design-idempotent-service-operations-l3-design-failure-safe-operation`). Evidence criteria обоих outcomes в `level-outcomes.md` формулируются через failure windows, recovery и duplicates/races — есть риск, что одно и то же наблюдение (crash window одной Orders operation) будет зачтено дважды.
- evidence: `role-requirements.md` (interpretive guardrails) прямо требует: «Один проект может дать evidence нескольким outcomes, но решение о proficiency требует разных наблюдений и объяснения trade-offs». План запрещает начислять coverage за простое упоминание idempotency, но не фиксирует различение наблюдений для двух L3.
- recommendation: При создании S07 authoring work package зафиксировать, что Transaction L3 подтверждается наблюдением выбора transaction boundary и перечисления failure windows commit/side effect, а Idempotency L3 — отдельным наблюдением semantics повторной обработки (identity, result, duplicates). Сам план править не обязательно; достаточно disposition оркестратора.

### F-2 (note)

- artifact: `curriculum/tracks/b2/module-delivery-plan.md` (decision brief, non-goals/risks)
- criterion: scope
- finding: Центральное действие S07 (commit в базе, неизвестный исход публикации события после crash) неизбежно называет partial failure и duplicate/at-least-once delivery — термины владения B5 (`b5.cluster.failure-models`, `b5.cluster.idempotency-retries` в route). План корректно выносит delivery guarantees и distributed transactions в non-goals, но не фиксирует, какие именно B5-термины разрешены как ссылочный контекст.
- evidence: Anti-pattern work package — «не превращать B2 material в пересказ B5»; без явного allowlist граница держится только на дисциплине автора.
- recommendation: В S07 authoring work package перечислить допустимые ссылочные B5-термины (partial failure, unknown outcome, duplicate/at-least-once delivery) с явной пометкой «называются, но не преподаются».

### F-3 (note)

- artifact: `curriculum/tracks/b2/module-delivery-plan.md` (очередь, отвергнутые альтернативы)
- criterion: structure
- finding: Обоснование выбора S07 против S05 опирается только на «A3 identity/trust baseline не подтверждён в snapshot». Не использован более сильный структурный аргумент: по `prerequisites.md` A3 для identity integration и API abuse controls — **hard baseline**, тогда как B3 для transaction boundaries — **conditional**.
- evidence: `prerequisites.md`, таблица external specifications: A3 — hard baseline для identity/abuse; B3 — conditional для transaction boundaries/storage-backed idempotency/caching.
- recommendation: При disposition или следующем refresh добавить одну фразу, что S05/S14 несут hard external baseline, а S07 — только conditional; это делает выбор принципиальным, а не circumstantial.

### F-4 (note)

- artifact: `curriculum/tracks/b2/module-delivery-plan.md` (таблица «Сравнение ближайших bounded actions», строка S07)
- criterion: structure
- finding: Фраза «Лучший leverage; выбрать при явном prerequisite подтвердить B3 до authoring» грамматически сломана и при чтении без контекста open question 2 может быть понята двояко.
- evidence: Критерий профиля B — понятность decision brief человеку без истории внутренних обсуждений.
- recommendation: Переформулировать, например: «Лучший leverage; выбрать с явным условием подтвердить B3 baseline до authoring».

- **Module state transition**: Service Verification `not-started → partial` корректен по определениям плана — появился собственный полный flow (V0–V4) с содержательным покрытием Verification L1–L3 и Compatibility L1–L3, но нет L4 и module-gate decision. Остальные состояния не меняются от supporting relationships S10 — согласуется с правилом «собственные содержательные artifacts».

## Вывод по S07 и внешнему B3 prerequisite

S07 — корректный следующий bounded package, и план правильно трактует B3 как условие запуска authoring, а не как hard DAG edge и не как уже принятое proficiency evidence. Ключевой структурный аргумент (см. F-3): для S05/S14 внешний A3 baseline по `prerequisites.md` является hard, для S07 внешний B3 — conditional; поэтому «подтвердить baseline до authoring» для S07 — лёгкая проверка применимых допущений, а не прохождение трека.

**Ответ 1.** S07 — действительно следующий лучший bounded package; менять выбор не нужно. Основания: внутренний hard prerequisite выполнен принятым execution evidence (Architecture L2/L3 через A1/A3/A4, D-044); пять целевых outcomes пусты и при этом Transaction L3 и Idempotency L3 — required для обеих RoleViews; центральное действие едино и bounded; риск дублирования принятых slices нейтрализован явными ссылками S04/S06/S10 и non-goals.

**Ответ 2.** Минимально достаточный проверяемый артефакт — короткий **B3 readiness contract**, зафиксированный оркестратором как обязательный первый шаг внутри S07 authoring work package (отдельная секция context manifest или компактная note, на которую ссылается work package). Не полный B3 slice и не отдельный prerequisite package. Содержание contract — четыре пункта из критерия профиля B:

1. выбранный store/driver и его transaction demarcation API (begin/commit/rollback, unit-of-work граница);
2. применимые isolation assumptions: предполагаемый уровень изоляции и допустимые аномалии, на которые опирается сценарий;
3. commit/rollback semantics: когда изменение данных считается durable, что происходит при ошибке до/после commit;
4. поведение driver/store при ошибках и неизвестном исходе (например, потеря соединения во время commit → неизвестное состояние commit) и как это отображается в failure windows S07.

Каждый пункт формулируется как допущение с ссылкой на owner-track context (`b3.cluster.transactions-concurrency`, `b3.cluster.storage-wal-recovery`), а не как преподаваемый материал. Этот contract проверяем: S07 authoring не стартует, пока все четыре пункта не зафиксированы.

**Ответ 3.** Да, после disposition findings можно создавать S07 authoring work package; отдельный prerequisite package не требуется. Условие: authoring work package включает B3 readiness contract из ответа 2 как gating-шаг до написания учебных материалов (план это допускает: «пакет остаётся выбранным, но authoring не запускается» без подтверждения baseline) и различение наблюдений для Transaction L3 / Idempotency L3 (F-1).
