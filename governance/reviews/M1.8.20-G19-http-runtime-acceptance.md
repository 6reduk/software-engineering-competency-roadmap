# M1.8.20 — принятие HTTP Runtime/S01 slice

## Итог

M1.8.20 и gate G19 приняты с verdict `accepted` как явное однопрофильное исключение:

- профиль A независимо воспроизвёл техническую модель на закреплённой сборке и подтвердил Gate 0, первую потерю контекста, исправление и отсутствие обхода pipeline;
- профиль B временно не выполнялся по решению владельца программы из-за недоступности SaaS-подписки; consolidated review не создавался;
- learning/editorial область прошла ограниченную оркестраторскую risk assessment без заявления второй независимой проверки;
- `1 minor / 2 note` получили disposition, A-1 и A-2 закрыты correction-pass M1.8.20a, A-3 принят как осознанная узкая граница S01;
- приняты четыре artifacts и 10 relationships к четырём semantic targets;
- Trace L1 проверяется восстановлением заданного пути, Trace L2 — локализацией первой потери и самостоятельным refactor с регрессией;
- Trace L3 остаётся только interview probe; production reconstruction, supporting coverage и завершение HTTP Runtime module не заявлены.

Однопрофильное исключение относится только к G19 и не заменяет отсутствующее независимое usability-review для следующих gates.

## Verification-pass M1.8.20a

- Gate 0, interview и kata теперь явно связывают наблюдаемый `dependency-exit` на error paths с размещением записи в `finally` вокруг `yield`.
- Уточнено, что произвольный код после `yield` без `finally` может не выполниться при вбросе исключения в генератор зависимости.
- Отсутствующий checkpoint сначала требует проверки instrumentation и сам по себе не доказывает ошибку assembly.
- Это уточнение не переопределяет исполненный порядок dependency/error/response закреплённой сборки.
- README и project-spec однозначно задают recovery: три повтора, в каждом 20 последовательных операций — пять последовательностей по четыре; всего `3 × 20 = 60`.
- Узкий вариант S01 сохранён: status/body остаются корректными, а дефект проявляется потерей обязательного диагностического `X-Request-ID`.

Сохранены request path, public contract, context owner, seeded defect, граница `created → dispatch-enter`, pinned/current версии и исходные результаты Gate 0. Coverage неизменно: `1 reference / 3 probe / 2 practice / 3 assess / 1 integrate`; L3 не получил execution evidence.

## Граница принятия

Acceptance относится к локальной in-process ASGI-модели одного request-context refactor. Независимый probe подтвердил 369 операций без failed checks, но результат не доказывает production network behavior, worker reuse, process-crash recovery, observability maturity или production Trace L3.

Четыре материала дают HTTP Runtime собственные index/interview/kata/project-spec и вместе с переиспользуемыми C1/R1 образуют пятижанровый учебный маршрут. Регистрация задания не означает, что участник выполнил project-spec, и не создаёт ImplementationReference либо module-gate decision.

## Следующий шаг

Обновить B2 consolidation snapshot после принятого S01: включить четыре artifacts и 10 relationships в accepted totals, снять закрытый content-долг D19/D20, повторно оценить HTTP Runtime gate и выбрать одно bounded продолжение либо переход к следующей вертикали. Полный G19 повторять не требуется.
