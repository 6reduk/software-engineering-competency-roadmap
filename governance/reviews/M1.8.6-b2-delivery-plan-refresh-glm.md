## Метод пересчёта (воспроизводимо)

1. Из `modules.md` посчитаны модули (10); из `capabilities.md` — capabilities (19); из `level-outcomes.md` — outcomes по каждой capability (3–4 на capability), сумма проверена.
2. Для каждого из 27 artifacts прочитан YAML `coverage`; посчитаны все entries по ролям, отдельно capability-level `reference` и outcome-level.
3. Построено объединение outcome-целей по 19 capabilities; уникально покрытые сравнены с каталогом 69; непокрытые выписаны явно.
4. `probe-only` определён как outcome, у которого все принятые связи имеют роль `probe`.
5. Membership/покрыто модуля посчитаны как union outcomes всех capabilities из его `Develops` (primary + supporting) в `modules.md`.
6. Состояния модулей пересчитаны по определениям плана; «собственный artifact» — по полю `module:` в YAML.
7. Hard DAG взят из `prerequisites.md` (колонка `Requires`); проверено, какие capabilities зависят от вновь покрытых transaction/idempotency.
8. Сравнение с M1.8.4: 42 покрытых + 5 новых S07 = 47; 27 − 5 = 22.

- **Новых downstream hard-DAG effects нет.** В `prerequisites.md` ни одна capability не `Requires` `manage-application-transaction-boundaries` или `design-idempotent-service-operations` — они leaves в колонке `Requires`. S07 не делает ни один downstream hard prerequisite вновь выполненным.
- Hard prerequisites самого S07 корректны: `transaction ← architecture` (Architecture L1–L3 приняты с execution evidence), `idempotency ← http-contracts` (принято ранее). Ни то, ни другое не изменилось S07.
