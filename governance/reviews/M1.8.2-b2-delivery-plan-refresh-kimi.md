## Findings

### N-1 (note)

- artifact: `curriculum/tracks/b2/module-delivery-plan.md`, decision brief и очередь, позиция 1
- criterion: scope
- finding: decision brief нигде не называет ожидаемое *новое* outcome coverage пакета S10. По факту Verification L1–L3 и Compatibility L2/L3 уже имеют accepted relationships, оба L4 явно вне scope, поэтому единственным непокрытым candidate остаётся Compatibility L1. Ценность пакета — консолидация и собственный flow, а не новое покрытие.
- evidence: базовый outcome audit показывает accepted relationships для всех primary outcome candidates (Verification L1–L3); критерий «пустое primary coverage» из M1.8.2 §4 для S10 формально не выполнен, и будущий reviewer может переоткрыть этот вопрос.
- recommendation: при следующей правке плана (или в authoring work package S10) одной строкой зафиксировать: «ожидаемое новое coverage — прежде всего Compatibility L1; остальные outcomes получают собственный flow поверх существующих cross-module relationships». Правки сейчас не требуется — честность «9/12 membership уже связано» в плане уже есть.

### N-2 (note)

- artifact: `curriculum/tracks/b2/module-delivery-plan.md`, сводка модулей и очередь, позиция 1
- criterion: correctness
- finding: «9/12 membership уже связано» для Service Verification включает Compatibility L4, у которого единственная связь — `probe` в C3. По принятой в плане конвенции («покрыто = есть accepted relationship») это корректно, но execution-покрытие membership составляет 8/12 плюс один probe-only.
- evidence: базовый audit показывает для Compatibility L4 только `[C3] probe only`; семь probe-only outcomes план сам отделяет от execution evidence.
- recommendation: при следующем обновлении плана уточнить формулировку до «8/12 execution + 1 probe-only» там, где число используется в аргументации выбора. На вывод это не влияет.

### N-3 (note)

- artifact: `curriculum/tracks/b2/module-delivery-plan.md`, минимальный artifact set, пункт 5
- criterion: scope
- finding: project milestone требует «убрать измеримо дублирующиеся slow/flaky checks». Это ближайшая к границе scope формулировка пакета: при неаккуратном authoring она может разрастись в общий курс performance/flaky-test optimization.
- evidence: формулировка дословно совпадает с evidence criterion Verification L3 («flaky/slow duplication сокращено измеримо»), поэтому она легитимна; риск только в исполнении.
- recommendation: в authoring work package S10 ограничить измерение одним сервисом и critical paths, не вводя общие бенчмарки и оптимизацию тестовой инфраструктуры.

## Отдельный вывод по числам и state transitions

Числа — зона профиля A; здесь они проверены выборочно, насколько они несут доменный смысл:

- 41/28 и четыре новых unique outcomes (Architecture L1–L3, Verification L1) воспроизводятся из YAML 17 artifacts; мой пересчёт строк базового аудита даёт 41 покрытый и 7 probe-only (Lifecycle L4, HTTP L4, Evolution L4, Cancellation L4, Compatibility L4, Diagnosis L4, Load L4), 69 канонических строк без пропусков.
- Переход Service Architecture `not-started → partial` обоснован: собственный полный flow A0–A4 принят, но Architecture L4, External Services L4 и Verification L4 не покрыты, module-gate decision отсутствует. Автоматического completion нет.
- Переход Transactional Persistence `blocked → not-started` доменно корректен: hard edge требовал именно architecture evidence вокруг application operation, и оно принято (см. критерий 1). Оставшаяся зависимость — B3 conditional baseline — по действующему `prerequisites.md` не является internal hard edge, поэтому сохранение `blocked` было бы молчаливым изменением смысла DAG. План правильно переводит её в pre-authoring readiness check.
- Классификация `complete 0 / partial 4 / not-started 6 / blocked 0` противоречий не вызывает; HTTP runtime `partial` по одному собственному learn R1 соответствует определению «есть собственное принятое содержательное покрытие».

## Отдельный вывод: действительно ли S10 предпочтительнее уже разблокированного S07 именно сейчас

**Да, согласен с выбором плана** — по аргументам capability gaps, prerequisite readiness, learning leverage и boundedness, а не по вкусовому порядку тем:

- **Prerequisite readiness.** S10 не имеет ни одного неподтверждённого внешнего входа: A2 нужен только как reference context. S07 при снятом internal hard block всё ещё упирается в B3 conditional baseline (transaction/isolation, driver/store behavior), readiness которого никем не подтверждена; запуск authoring S07 сейчас перенёс бы непроверенное внешнее допущение внутрь пакета.
- **Boundedness.** S10 замыкается на одну seeded regression и переиспользует три принятых substrate (C1, C2, A1/A4, R5). S07 обязан одновременно отсечь B3 снизу (store-level semantics) и B5 сверху (recovery/consistency theory) — две границы вместо одной, при пустом собственном покрытии всех девяти transaction/cache/idempotency outcomes.
- **Learning leverage.** Verification L3 требуется обеим RoleViews, но сегодня его evidence — побочный продукт S06/S08. Собственный flow конвертирует scattered evidence в управляемую capability, которую немедленно потребляют следующие пакеты: S07 (распределение failure-window evidence по честным границам) и S11 (stop conditions, verification перед rollout).
- **Честная оговорка.** По критерию «пустое primary coverage» S10 проигрывает S07 и S05: новое уникальное покрытие пакета — фактически Compatibility L1 (N-1). Если бы программа максимизировала только счётчик покрытых outcomes, правильным выбором был бы S07 или S05. Но work package прямо запрещает сводить выбор к максимально пустой capability, а по совокупности readiness + leverage + boundedness S10 выигрывает. План эту слабость не скрывает («9/12 membership уже связано»), что снимает подозрение в выборе «ради полного набора жанров».

## Можно ли создавать S10 authoring package после disposition findings

**Да.** Blocker и major отсутствуют; все три note носят характер уточнений формулировок и границ исполнения, а не дефектов плана. При подготовке authoring work package S10 рекомендую учесть: явно назвать ожидаемое новое coverage (прежде всего Compatibility L1, N-1); зафиксировать один конкретный Orders serializer/error-mapping regression и внешний client contract до authoring (это уже стоит в плане); ограничить измерение portfolio milestone одним сервисом (N-3). Возврат плана в `accepted` — отдельным acceptance-проходом оркестратора после disposition обоих профилей.
