# M1.8.17 — G16 профиль A (модель: GLM)

## Профиль, модель и scope

Профиль A: integration mechanics, technical correctness и measurement по work package `M1.8.17-G16-external-integration-review.md`. Фактическая модель — GLM, суффикс файла `glm`. Scope: Gate 0 и пять материалов `curriculum/tracks/b2/slices/truthful-pricing-client-boundary/` — реальность outbound HTTP-границы, контракт и матрица, one-attempt evidence, measurement envelope, versions/freshness, отсутствие технического overclaim. Learning design, human readability и различие kata/project как учебная задача принадлежат профилю B и здесь не оцениваются. Отчёт другого профиля не читался до завершения настоящего анализа.

## Метод: независимое локальное воспроизведение

Авторский stdin probe не сохранён, поэтому технический профиль выполнил собственный минимальный эквивалент той же процедуры во временном каталоге **вне проекта** (`%TEMP%\g16-probe-glm`); probe удалён после проверки. Исходные материалы не изменялись.

**Substitutions (раскрыты полностью):**

1. Воспроизводился не авторский скрипт (недоступен), а независимо написанный минимальный probe той же процедуры: ThreadingHTTPServer на OS-выделенном loopback порту, FastAPI Quote с общим HTTPX AsyncClient в lifespan, ASGITransport на входе Quote с явно запущенным lifespan, populations control 6 / defect 33 / fixed 33 / recovery 6 + 4 URL-negative checks.
2. Defect-мутация реализована в общей ветви известных integration failure моего адаптера — эквивалент заданной автором мутации.
3. В ветвях timeout/transport поздняя запись ответа в уже брошенный клиентом сокет подавлена (`BrokenPipeError`); это та же поправка, которую автор описал как `close_connection`, смысл инъекций не менялся.
4. Версионных замен не потребовалось: локальное окружение точно совпало с закреплённым baseline (Python 3.14.0, FastAPI 0.137.1, Starlette 1.3.1, HTTPX 0.28.1, httpcore 1.0.9, Pydantic 2.12.5, AnyIO 4.11.0).

**Наблюдения полного прогона (exit 0, 0 ошибок верификации):**

- арифметика: `82` входящих проверки, `79` попыток клиента, `79` приёмов сервера; на каждом request ID `attempts=receipts=1`, включая все 27 failure operations в обоих профилях;
- все 11 строк fixed-профиля совпали с матрицей в точности: `200 offers`, `200 no_offers`, `502 decoding/media/schema/http/transport`, `504 timeout`;
- дефект: `27/27` ложных `no_offers`; строки full/empty на дефекте остались корректными; после исправления `0/27`; recovery `6/6` на том же клиенте;
- URL-негативы: `http://evil.test:9999/x`, `//evil.test`, `p-7?host=evil` → `422` без попыток и приёмов; допустимый `p-7` с `base_url=http://evil.test` → одна попытка, сервер видел `Host: 127.0.0.1:<port>`, authority не изменился;
- исключения: timeout-строка → `httpx.ReadTimeout` (подкласс `TimeoutException`), transport-строка → `httpx.RemoteProtocolError` (подкласс `TransportError`); порядок catch существенен — `TimeoutException` нужно перехватывать раньше `TransportError`;
- drain ненулевой только в timeout-строках (~250 мс: 350-мс обработчик минус ~100 мс операции) — удалённая работа продолжается после локального timeout; прочие строки 0 мс;
- тайминги: max операция 110.72 мс (< 500 мс), max drain 250.06 мс (≤ 1 с), закрытие клиента 0.26 мс, cleanup сервера с проверкой порта 683.20 мс (≤ 1 с), порт закрыт, server thread не жив;
- дополнения вне знаменателей матрицы: дополнительные поля отклоняются (`extra="forbid"`); lax-режим Pydantic молча превращает `"12500"` в `int 12500` — именно strict mode отклоняет coercion-строку, как заявляет материал.

**Версии и freshness (проверено по первичным источникам 2026-09-08):** current stable подтверждены полностью — Python 3.14.7 (python.org), FastAPI 0.141.1 (PyPI), Starlette 1.6.0 (PyPI), HTTPX 0.28.1 stable и `1.0.dev6` как pre-release (PyPI, загрузка 2026-08-31), Pydantic 2.13.5 (PyPI). Source-to-claim mapping корректен: каждый из семи источников подтверждает конкретное утверждение (см. критерий 16).

**Механика пяти материалов:** уникальные semantic IDs (5), `status: review`, идентичные `versions`/`last_verified`; YAML содержит ровно 9 relationships к трём targets с ролями `1 reference / 2 explain / 2 probe / 1 practice / 2 assess / 1 integrate` — совпадает с registration в `coverage-map.md`; относительные ссылки разрешаются; fences/`<details>`/`<summary>` сбалансированы; trailing whitespace и conflict markers отсутствуют; поля `ImplementationReference` нет (термин встречается только в disclaimers об отсутствии). Числа (82/79, 27/27, 0/27, 6/33/33/6, 100 мс/500 мс/1 с/350 мс) едины во всех пяти файлах и в work package.

## Вывод по Gate 0 и границам runtime evidence

Gate 0 `confirmed` от 2026-09-08 **можно считать независимо подтверждённым в его явно ограниченной модели**. На идентичном baseline воспроизведены: полная матрица 11 строк с точными категориями и статусами, арифметика 82/79, дефект 27/27 и исправление 0/27, one-attempt per-ID 1/1 на всех строках включая failures, recovery 6/6 на том же клиенте, trusted authority, drain/cleanup в границах, классы исключений `ReadTimeout`/`RemoteProtocolError`. Границы заявлены честно: phase timeouts ≠ общий deadline; timeout ≠ remote cancellation (подтверждено drain ~250 мс); пороги — учебный envelope конечного loopback-профиля, не production SLO; TLS/proxy/DNS/SSRF/disconnect/pool не проверялись и не заявляются; версии pinned ≠ current, перенос требует повтора матрицы. Авторские timing-числа не повторяются точно (и не должны для одноразового прогона), но все внутри порогов и одного порядка; материалы корректно требуют от участника собственных измерений.

Непроверенными остались только буквальные значения авторского прогона и сам его скрипт; процедурный эквивалент воспроизводим третьей стороной, что закрывает вопрос open question 1 work package: несохранённый stdin probe достаточен при условии независимого воспроизведения, которое выполнено.

## Вывод по failure→empty boundary

Различение business absence и integration failure **технически состоятельно и различимо во всех применимых строках**. Единственная мутация общей ветви отказов даёт 27/27 ложных отсутствий и не разрушает корректные full/empty (симметричная ошибка «всегда 502» отклоняется отдельной проверкой empty). После исправления ни один из девяти failure-путей не приводит к `no_offers` (0/27); проверка статуса до тела закрывает ловушку 503-с-пустым-массивом; strict schema закрывает null/missing/identity/coercion; раздельные границы decoding (bytes→значения) и schema (структура/типы) сохранены. Contract checks обладают различающей силой: они падают на дефекте и проходят на исправленном коде, что и требуется от seeded-defect evidence.

## Ответы на обязательные вопросы профиля A

1. **Gate 0 `confirmed` в его явно ограниченной модели?** Да. Независимое воспроизведение на идентичном baseline не нашло ни одного расхождения по существу; ограничения модели заявлены в материалах точно и не шире наблюдаемого.
2. **Что повторено, что осталось непроверенным?** Повторены: матрица, арифметика, one-attempt, дефект/исправление, recovery, authority-негативы, классы исключений, drain-паттерн, strict/coercion, extra-fields, current versions. Непроверены: буквальные timing-значения авторского прогона (порядок и границы совпали) и построчный release каждого response (косвенно — чистое закрытие ресурсов).
3. **Доказывают ли 79/79 отсутствие hidden retry для всех применимых строк, включая failures?** Да — в рамках этого эксперимента: per-ID attempts=receipts=1 на всех 82-проверочном контуре, включая 27 failure operations в обоих профилях; счётчик попыток на границе клиента и приёмы сервера раздельны; retries=0 на transport, без loop/redirects/auth resend. Утверждение корректно ограничено: для connect-refused строки server receipt мог бы отсутствовать — материалы выделяют это явно, и такая строка в матрицу не входит.
4. **Есть ли путь, где технический отказ становится предметным отсутствием после исправления?** Нет. После исправления 0/27; empty-строка остаётся `200 no_offers`, поэтому «всегда ошибка» также не проходит. Путь отсутствует по построению и подтверждён исполнением.
5. **Достаточно ли Gate 0 для bounded External L1/L2 без L3/production?** Да. L1 использует заданный клиентский договор (kata: apply + assess), L2 — самостоятельный выбор внутреннего представления и владельца (project-spec: integrate + assess); обе опираются на один воспроизведённый substrate. L3/L4, production readiness и supporting coverage не заявлены.
