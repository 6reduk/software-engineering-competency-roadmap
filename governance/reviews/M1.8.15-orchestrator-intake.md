# M1.8.15 — orchestrator intake

## Verdict

`accepted_for_review`: пакет допускается к двум независимым профилям G14. Intake подтверждает комплектность и непротиворечивость передачи, но не принимает Gate 0, технические утверждения, Delivery L1–L3 coverage или учебные материалы и не объявляет G14 пройденным.

Предварительных blocker, требующих остановить review, не найдено. Главный предмет независимой проверки — достаточность ограниченного одно-процессного эксперимента для проверки механики rollout/stop/recovery без превращения его в доказательство production readiness, полноценной реализации S03 либо Delivery L4.

- созданы ровно пять разрешённых artifacts в `curriculum/tracks/b2/slices/safe-orders-service-rollout/`;
- изменены только Gate 0 record work package и разрешённые регистрации в `curriculum/tracks/b2/README.md` и `curriculum/tracks/b2/coverage-map.md`;

## Gate 0 и единая модель

Материалы используют один bounded эксперимент:

- CPython 3.14.0 и стандартная библиотека, один процесс с локальными old/new/fixed HTTP probes;
- legacy и scheduled cohorts с неизменными ожиданиями S03/S10;
- стадии B, S1, S2, S3 и два разных recovery path до и после появления scheduled-обязательств;
- отдельные нулевые пороги contract violations и unexpected errors по каждой применимой когорте;
- точное распределение exposure по request ID и server receipts как обязательное условие `go`;
- healthy-путь B–S3, остановка degraded-пути после S2 и остановка server-error-пути после S1;
- roll-forward после принятых scheduled-заказов и readback 80 сохранённых заказов;
- явные ограничения: нет конкурентной нагрузки, durable storage, process crash, proxy/deployment platform, production SLO или production-readiness claim.

Арифметика handoff согласуется с Gate 0: healthy 600 POST, degraded 600 POST, server-error 300 POST, итого 1500 POST; readback после degraded — 80 GET. Код одноразового стенда удалён согласно принятому исключению, поэтому G14 должен проверять достаточность сохранённого протокола и честность границ, а не требовать включить harness или готовую S03-реализацию в проект.

## Coverage intake

YAML пяти материалов содержит:

- index: `reference` на capability безопасной поставки изменений;
- learn: `explain` для Delivery L1–L3;
- interview: `probe` для Delivery L1–L3;
- kata: `practice` и `assess` только для Delivery L1;
- project-spec: `integrate` и `assess` для Delivery L2/L3.

L1, L2 и L3 описаны разными действиями: выполнить заданный checklist и остановиться; самостоятельно спланировать типовой rollout и безопасный возврат; подготовить и провести ограниченно обратимое изменение после появления новых обязательств. Правдивость этого различия должен подтвердить G14. Supporting links на S03/S10 контекстом coverage не считаются.

- распределение ролей: `1 reference / 3 explain / 3 probe / 1 practice / 3 assess / 2 integrate`;
- все targets существуют в каталогах capability и LevelOutcome;

- известный временный каталог стенда отсутствует.

## Обязательные вопросы G14

1. Достаточно ли Gate 0 разделяет измеренное поведение, вычисленную арифметику и ограничения disposable-модели, не выдавая routing внутри одного процесса за реальный deployment или production readiness?
2. Действительно ли exposure проверяется независимо от ответа сервиса и охватывает каждый request ID, включая ожидаемые 422 и внедрённый 503?
3. Правдивы ли stop/go transitions: S3 отсутствует после плохого S2, S2 отсутствует после плохого S1, а recovery выбирается по моменту появления необратимого обязательства?
4. Подтверждает ли общий in-memory state только ограниченный roll-forward/readback сценарий, без скрытого обещания durability либо восстановления после process crash?
5. Дают ли kata и project различимые наблюдаемые результаты для Delivery L1 и Delivery L2/L3, не превращаясь в одно упражнение с разными ярлыками?
6. Достаточно ли project evidence для Delivery L3 в локальной лаборатории, если Delivery L4, межкомандная координация и production rollout явно исключены?
7. Понятны ли читателю cohort, exposure, stop/go, rollback, roll-forward, compensation и incident path без чтения work package?
8. Оставляют ли kata/project участнику инженерную работу и не подменяют ли её готовой реализацией или предписанной платформой?
