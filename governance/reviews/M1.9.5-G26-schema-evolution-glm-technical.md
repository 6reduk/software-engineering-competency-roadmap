# M1.9.5 — G26 профиль A: PostgreSQL, schema evolution, Gate 0 и coverage

Профиль **A** (PostgreSQL/schema evolution, Gate 0, встроенные probe и журналы, измерения, coverage). Модель — **glm** (суффикс имени файла). Предмет — bounded slice SE01: пять материалов `curriculum/tracks/b3/slices/compatible-orders-amount-migration/`, регистрация в B3 README и coverage map, а также Gate 0 record с встроенным evidence внутри work package M1.9.5. Авторский handoff, orchestrator intake и авторские самопроверки использованы как карта поиска, а не как доказательства.

**Verdict: `accepted_with_changes` — 0 blocker / 1 major / 1 minor / 2 note.**

Техническое содержание Gate 0 и пяти материалов проверено независимыми методами и подтверждено. Verdict — рекомендация профиля; принятие SE01 остаётся за оркестратором после консолидации двух профилей.

## Независимый runtime-повтор (2026-09-13)

Выполнен ограниченный повтор во временной среде вне blueprint: контейнер `se01-g26-20260913` из того же образа по digest `postgres@sha256:4ef4dbc9…3c2280` (совпадает с локальным тегом `postgres:18.6` и с манифестом Docker Hub), `--network none`, tmpfs, trust только внутри контейнера. Сборка идентична заявленной: `PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2)`, psql 18.6. Подтверждено живьём:

- начальное состояние: SELECT и INSERT нового пути — `42703`;
- `numeric(12,2)`: ввод 1.001 → сохранено **1.00** (округление, не отвержение); переполнение `10000000000.00` → `22003`; `-0.01` → `23514` по CHECK;
- stale-применение **без** ограничения: после подтверждённых 120.00 запись 10000 проходит и оставляет расхождение `120.00|10000` — вторая опасная ветка реальна;
- `pair_ok … NOT VALID` при живых исторических NULL: новое несогласованное изменение отвергнуто `23514` (Failing row `120.00, 10000`); строка с NULL нового поля проходит CHECK равенства — CHECK сам по себе не доказывает заполненность;
- W-old UPDATE только рублей при действующем pair_ok без механизма совместимости падает `23514` — подтверждение порядка «совместимость раньше enforcement»;
- VALIDATE в явной транзакции наблюдался держащим `ShareUpdateExclusiveLock` (не конфликтует с RowExclusiveLock writer);
- шаг обязательности: `minor_present … NOT VALID` → VALIDATE → `SET NOT NULL`; NULL-запись → `23502`; все ограничения `convalidated=t`;
- lock-профиль: владелец с удерживаемым UPDATE — `RowExclusiveLock|t`; ждущий `SET NOT NULL` пойман в заблокированном состоянии `Lock/relation|AccessExclusiveLock|f|{392}` с `pg_blocking_pids`; после lock_timeout — `55P03` «canceling statement due to lock timeout»; после ROLLBACK владельца отдельный повтор DDL прошёл; незакреплённых locks — 0.

Cleanup подтверждён: таблица/ограничения удалены (`to_regclass → t`), 0 сеансов и 0 locks с префиксом `g26-`, контейнер остановлен и удалён (`docker ps -a` пуст). Временные файлы reviewer удалены; авторский каталог с оригиналами evidence не тронут. Техника маркеров `psql` (`\echo :SQLSTATE`) проверена собственным употреблением: после успеха — 00000, после отказа — код отказа.

Полный повторный прогон `probe.py` (шесть профилей, resume, cleanup-цепочка) не выполнялся: независимый повтор покрывал engine-зависимые семантики, а не воспроизведение таймингов; заявленные длительности проверены сверкой с журналом, но не повторным измерением.

## Сверка первичных источников (2026-09-13)

- [Versioning](https://www.postgresql.org/support/versioning/): 18.6 — текущий minor ветки 18 на дату review; baseline актуален.
- [Release 18.6](https://www.postgresql.org/docs/18/release-18-6.html): выпущен 2026-08-13, включая изменения psql, — совпадает с записью Gate 0.
- [ALTER TABLE 18](https://www.postgresql.org/docs/18/sql-altertable.html): ADD COLUMN и SET NOT NULL — ACCESS EXCLUSIVE; ADD CONSTRAINT … NOT VALID откладывает проверку старых строк, но применяется к новым изменениям; VALIDATE CONSTRAINT — SHARE UPDATE EXCLUSIVE; при валидном CHECK, доказывающем отсутствие NULL, SET NOT NULL пропускает полное сканирование — использованный порядок (minor_present → VALIDATE → SET NOT NULL) соответствует документации.
- [Numeric types 18](https://www.postgresql.org/docs/18/datatype-numeric.html): избыточный scale округляется — «округление не есть отвержение» подтверждено дословно.
- [Transaction isolation 18](https://www.postgresql.org/docs/18/transaction-iso.html): Read Committed переоценивает WHERE на актуальной версии строки (EvalPlanQual) — поэтому одношаговый UPDATE молча даёт Fixed и запрещён как «воспроизведение» дефекта; двухшаговая форма в kata/probe корректна.
- [Explicit locking 18](https://www.postgresql.org/docs/18/explicit-locking.html): AccessExclusive конфликтует со всеми режимами, включая RowExclusive; locks держатся до конца транзакции.
- [Trigger definition 18](https://www.postgresql.org/docs/18/trigger-definition.html): BEFORE ROW может изменять записываемую строку; `UPDATE OF amount_rub` ограничивает срабатывание — конструкция автора (backfill не будит trigger) технически безупречна.
- [Error codes 18](https://www.postgresql.org/docs/18/errcodes-appendix.html): 42703/23514/23502/22003/55P03 — точно те условия, что заявлены.
- [Docker Hub](https://hub.docker.com/v2/repositories/library/postgres/tags/18.6): digest тега = `sha256:4ef4dbc939d61acea57712655ddb4b4ab27419c913f94cca0cd57cb3ea3c2280` — совпадает с locator в Gate 0 и project-spec байт-в-байт.

pg_locks/pg_stat_activity/pg_blocking_pids и psql (`-X`, `-At`, ON_ERROR_STOP=0, SQLSTATE-переменная) проверены живым употреблением в runtime-повторе, а не только по документации.

## Ответы на обязательные вопросы

**1. Можно ли принять пакет как глубокий B3 slice SE01 без расширения до production migration platform?** Да. Одна таблица, два контракта доступа, пять состояний, один инвариант пары; production cutover, removal `amount_rub`, CDC/partitioning и платформа миграций явно вне границ, пределы доказательства названы в каждом файле. Ничто в материалах не подталкивает к расширению.

**2. Где первое наблюдаемое неверное решение и какие данные отличают Defect, безопасный stop и Fixed?** Первое неверное решение — считать значение, захваченное до барьера, пригодным к применению после подтверждённого W-old изменения (kata называет это прямо). Различающие данные: (a) Defect — SQLSTATE 23514 на отдельном stale-UPDATE, readback `2 = 120.00|12000`, следующая стадия не вызывается; (b) безопасный stop — тот же 23514 плюс сохранённая сумма и явное отсутствие auto-продвижения: отказ transporte ≠ завершение миграции и ≠ потеря бизнес-значения; (c) Fixed — freshness-предикат, RETURNING пуст (0 затронутых строк), полный oracle 1–6, безопасный повтор пачки. Дополнительно мой повтор показал: без ограничения то же действие применяет расхождение `120.00|10000` — обе ветки наблюдаемо различимы, и одношаговый UPDATE (EvalPlanQual) действительно молча даёт Fixed, что материалы честно запрещают как доказательство.

**3. Достаточен ли Gate 0 для authoring claims и честно ли ограничен его вывод?** Да. Все восемь readiness-категорий закрыты наблюдаемым evidence; digest-верификация по двум независимым путям исключает подмену; две неудачные попытки сохранены и не засчитаны. Ограничения названы явно и в записи, и в материалах: неизвестный writer, recovery после реального потерянного commit-ответа (проверена только управляющая ветка), малая популяция, отсутствие production выводов. Вывод Gate 0 честно локален.

**4. Правдивы ли L1/L2/L3 и все 30 roles; оба L3 outcomes?** Да, все 30 назначений соответствуют фактическому содержанию жанров. Отдельно по L3: **plan-L3** («при неизвестных потребителях и ограничении простоя выбирает переход; сравнены промежуточная совместимость, сложность и необратимые шаги») — project-spec требует сравнить минимум два механизма/порядка на различающих данных, исследовать неизвестного writer через права и формы записи, взвесить срок против доступности и оформить decision record с границей применимости; interview L3 проверяет то же рассуждение. **validate-L3** («при конфликтующих требованиях к сроку и доступности выбирает способ изменения; сопоставлены нагрузка, блокировки, корректность гонок; защищены сверка, граница отката и roll-forward») — этапы «Блокировки и срок» и «Полнота и восстановление» требуют ровно этих наблюдений, включая выбор собственной конфликтующей пары и собственного профиля нагрузки. Назначения integrate/assess не механические: проект обязан дать L3-evidence обеих способностей.

**5. Достаточно ли различаются kata и project-spec для `practice/assess` и `integrate/assess`?** Достаточно. Общий substrate (fixtures, четыре текущие команды, oracle, шесть соединений, ориентиры порогов) делает решения сравнимыми и не подменяет выбор: механизм совместимости, порядок ограничений, harness, guardrails, конфликтующая пара и способ сравнения альтернатив остаются за участником; авторский trigger не выдан (в learn описан класс решения с предпосылками и обходами, без SQL), kata содержит только ошибочные шаги, project-spec явно отказывается выбирать. Риск воспроизведения авторского Gate 0 снижен тем, что фиксируются данные и инвариант, а не решение. Учебная самостоятельность kata/project и человеческая читаемость детально проверяются профилем B.

**6. Нужно ли до acceptance менять форму хранения встроенного probe/журналов?** Да — см. Аудируемость сохраняется полностью: проверка сводится к повторному хешированию. Альтернатива — явное решение оркестратора оставить встроенную форму с обоснованием.

**7. Какие findings закрыть до acceptance, а какие относятся к другим категориям?** До acceptance: A-1 (перенос либо явное решение) и A-2 (одна строка metadata). A-3 и A-4 — no change.
