## Findings

### F-1 (minor) — роль заголовка `Accept` нигде явно не объяснена

- artifact: все пять файлов; первично `learn/truthful-test-boundaries.md:128`, `README.md:30`
- criterion: correctness
- finding: `Accept: application/problem+json` используется как элемент substrate, но ни один файл не объясняет, что это заданный контракт приложения, а не механизм content negotiation FastAPI. Ложного утверждения о negotiation в материалах нет, но и исключающего пояснения тоже.
- evidence: grep по пяти файлам — `Accept` встречается только в описании запроса клиента и в инструкциях проверки. Runtime-воспроизведение (сценарии D1/D2 ниже) показало, что FastAPI 0.136.3 / Starlette 1.3.1 игнорирует `Accept` при выборе media type: default path с `Accept: application/problem+json` возвращает `application/json`, custom handler с `Accept: application/json` возвращает `application/problem+json`. RFC 9457 §3 прямо отмечает, что сервер может вернуть `application/problem+json` независимо от `Accept`.
- impact: участник может составить ложную модель «сервер вернул Problem Details, потому что клиент попросил через Accept». Дефектный сценарий (тот же запрос с тем же `Accept` получает `application/json`) опровергает её лишь неявно.
- recommendation: одна фраза в `learn/truthful-test-boundaries.md` (раздел «Один контракт, один дефект» или «Четыре границы на одном substrate»): `Accept` здесь — декларация клиентского контракта; FastAPI/Starlette не выполняет content negotiation, media type ответа определяется зарегистрированным exception handler либо default error path.

### F-2 (note) — табличный шортхенд «неверно типизированный handler»

- artifact: `learn/truthful-test-boundaries.md:118`
- criterion: correctness
- finding: в таблице границ формулировка «Отсутствующий/неверно типизированный handler» менее точна, чем фактическая модель dispatch по exception type.
- evidence: точная модель присутствует в `kata/detect-orders-error-contract-regression.md:100` («зарегистрируйте mapping для другого exception type») и `interview/green-tests-broken-contract.md:71` («зарегистрирован не для того exception type»). Воспроизведение сценария C подтвердило: handler, зарегистрированный для `ValueError`, не перехватывает `RequestValidationError` — lookup идёт по классу исключения.
- impact: низкий — две из пяти материалов дают точную модель, табличная строка читается в её контексте и не порождает неверного вывода.
- recommendation: при следующей правке learn заменить на «отсутствующий или зарегистрированный для другого exception type handler».

### F-3 (note) — транспорт TestClient на закреплённом baseline уже deprecated

- artifact: metadata `versions` всех пяти файлов
- criterion: freshness
- finding: на Starlette 1.3.1 `starlette.testclient` через httpx печатает `StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated; install httpx2 instead`. Материалы закрепляют fastapi/starlette/pydantic, но не версию тестового транспорта.
- evidence: runtime-воспроизведение 2026-08-20 (Python 3.14.0, venv, точные пины); на заявленное поведение warning не влияет — все сценарии прошли.
- impact: при будущем обновлении baseline wire-level checks могут потребовать смены HTTP-транспорта тест-клиента; текущие выводы slice не затронуты.
- recommendation: при следующем обновлении `versions` baseline дополнительно зафиксировать версию тестового транспорта (httpx/httpx2).

## Первичные источники и runtime reproduction (профиль B)

Дата всех проверок: **2026-08-20 (UTC)**.

- [RFC 9457 — Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html) — §3, §3.1, §3.2: члены `type/status/title/detail/instance`, extension members MAY, собственный пример RFC использует расширение `errors` с `pointer` в fragment-форме JSON Pointer (RFC 6901). Claims материалов поддержаны.
- RFC 9110 (HTTP Semantics) — reason phrase `422 Unprocessable Content`; подтверждается также примером в тексте самого RFC 9457. Зависимости от reason phrase в материалах нет.
- PyPI JSON API (`pypi.org/pypi/fastapi/json`, `/starlette/json`, `/pydantic/json`): fastapi latest 0.141.1 (2026-07-29) — совпадает с заявленным в README:95; fastapi 0.136.3 (2026-05-23), starlette 1.3.1 (2026-06-12), pydantic 2.13.4 (2026-05-06, latest) существуют; Requires-Dist fastapi 0.136.3 допускает закреплённые starlette/pydantic.
- [FastAPI — Handling Errors](https://fastapi.tiangolo.com/tutorial/handling-errors/) — подтверждает default handler для `RequestValidationError`, механизм переопределения через `@app.exception_handler(...)` и регистрацию по классу исключения.
- **Runtime reproduction выполнено** (безопасная локальная среда): Python 3.14.0, venv, `pip install fastapi==0.136.3 starlette==1.3.1 pydantic==2.13.4 httpx` без конфликтов (`pip check` чист). Приложение: `POST /orders` (success 201 `{"order_id": ...}`), правило «scheduled требует window.end» через `model_validator`. Результаты:
  - A (handler зарегистрирован): `422`, `application/problem+json`, каноническое тело с `errors[].pointer="#/delivery/window/end"`, `code="required"` — **подтверждено**;
  - B (handler не зарегистрирован): `422`, `application/json`, `{"detail": [...]}` — **подтверждено**;
  - C (handler для `ValueError` вместо `RequestValidationError`): вывод байт-в-байт как B — lookup по классу исключения, **подтверждено**;
  - D (Accept-вариации): `Accept` не влияет на media type ни в default, ни в custom path — **подтверждено** (и является evidence для F-1).
- **Ограничения проверки**: git-репозиторий недоступен — scope изменений подтверждён только файлово (по work package это не finding); документация Starlette TestClient и Pydantic Validators не переоткрывалась, т.к. соответствующее поведение воспроизведено runtime на точном baseline (сильнее документальной сверки).
