# M1.8.13 — G12 review Application Caching/S15 — профиль A (glm)

Профиль A: caching, consistency, concurrency, freshness и measurement. Проверка выполнена независимо по первичным источникам и минимальному runtime-воспроизведению на exact pinned substrate. Learning design, редакционное качество и полнота coverage-правдивости по содержанию — зона профиля B и здесь не оценивались (механические проверки YAML/ссылок выполнены).

## Verdict

`accepted_with_changes`

Счётчик: **0 blocker / 3 major / 2 minor / 2 note**.

Модель slice технически состоятельна и воспроизводится на заявленном стеке целиком: coalescing, tenant isolation, corruption-проверки, commit→DEL ordering, допустимый late fill, fail-closed behavior и recovery подтверждены runtime-экспериментом. Все три major — это противоречия формулировок Gate 0/материалов фактическому поведению заявленного механизма (GET/SET counters, механика freshness bound, дефолтный retry redis-py). Каждое исправляется минимальной правкой формулировки или точным указанием механизма; переделка модели или расширение пакета не требуются.

| redis-py | 8.0.1 | PyPI + локальная установка |
| PostgreSQL | 18.6 (Docker) | образ `postgres:18.6`, `psql select version()` |

Harness: минимальное FastAPI-приложение, реализующее каноническую модель slice (cache-aside, per-key `asyncio.Lock` + повторный `GET`, `SET ... EX 2`, deadline-проверка перед `SET`, fail-closed `503` problem+json с `Retry-After: 1` и `Cache-Control: no-store`, counters `cache_hit/cache_miss/cache_error/source_read/fallback_503/cache_invalidation_error`, write path commit→`DEL`), плюс драйвер кейсов. Один Uvicorn worker, один process, один event loop.

### Substitutions (документируемые отклонения, не меняющие модель)

1. Trusted `IdentityContext` имитируется заголовком `X-Trusted-Tenant` (в модели — server-created context из проверенного credential); write path реализован как debug-endpoint `commit → DEL`.
2. Psycopg async на Windows требует `SelectorEventLoop`: launcher устанавливает `WindowsSelectorEventLoopPolicy` перед uvicorn (`loop="none"`). На семантику `asyncio.Lock`, таймаутов и Redis-команд не влияет.
3. Для управляемых interleavings добавлены test-only hooks: fault-injection флаги (GET/SET/DEL failure на adapter-уровне), барьеры до/после deadline-проверки, «медленный» SELECT через `pg_sleep`, отмена owner-task, трассировка событий. Это инструменты проверки, а не часть учебной модели.
4. Вариант `deadline anchor = statement start` и `SET` с остаточным TTL (`PX = 2000 − elapsed`) — контрвариант для проверки исправимости freshness bound (не входит в материалы).

### Cases и наблюдения (2026-09-02/03)

Baseline-режим: `SET ... EX 2`, deadline от receipt — буквально как написано в brief.

| Case | Наблюдение |
|---|---|
| C0 cold + 20 warm | cold `200 v1 (3, 12500)`, `source_read=1`; 20/20 hits, `+0` reads, ~43 мс |
| C1 пять bursts ×32 (DEL перед каждым, одновременный старт) | каждый burst: 32/32 корректных `200`, `source_read=1`; 63–69 мс (в первом прогоне 63–101) |
| C2 tenant-a/tenant-b параллельно | значения различны, leakage `0`, reads 1+1 |

| C3 forced late fill (пауза после SELECT до SET; commit+DEL; release) | ключа нет сразу после commit+DEL; late fill v1; v1 допустима сразу после commit; v2 обязательна ≈1.9–2.0 с от commit ≤ 2250 мс (согласуется с авторскими 2049.22 мс) |
| C4 реальный outage (docker stop) | 32/32 `503 cache_unavailable`, `Retry-After: 1`, `application/problem+json`, `source_read=0` — но 7911–7922 мс ≫ 350 мс |
| C4b закрытый порт | 32/32 `503`, `source_read=0`, 7919.9 мс |
| C5 recovery | 32/32 `200`, `source_read=1`, 71.3 мс ≤ 150 мс (автор: 106.01) |
| C6a injected GET-failure | 32/32 `503`, `source_read=0`, 60.8 мс |
| C6b injected SET-failure | одиночный: `503 cache_unavailable` при `source_read=1`; burst 32: 32×`503`, `source_read=32`, 619.6 мс |
| C7 отмена owner внутри секции | 31/31 followers `200`, зависаний нет, `+1` read, 83 мс |
| C8 `asyncio.Lock` cancellation (CPython 3.14.0) | отмена владельца → waiter получает lock за 0.0 мс; отмена стоящего в очереди → следующий за 0.1 мс |
| C10 timing `expired` event | событие на 78–139 мс позже номинального TTL — мгновенного expiration event нет |
| C9a медленный SELECT (700 мс, statement до commit, возврат после) | reader получил `200 v1`; commit→истечение v1 = **2616.8 мс > 2250** |
| C9b пауза 500 мс между deadline-проверкой и SET | commit→истечение v1 = **2519.3 мс > 2250** |

Дополнительно инспектирован установленный redis-py 8.0.1: `Connection.retry` по умолчанию — `Retry(ExponentialWithJitterBackoff, _retries=10)` на `ConnectionError`/`TimeoutError`; `_connect` оборачивает connect в `async_timeout(socket_connect_timeout)`. Одиночный `get()` к недоступному Redis: **6388–7802 мс** (11 попыток), burst 32 — 7959 мс.

Границы воспроизведения: один host (Windows/Docker Desktop, localhost), один process, лабораторные fixtures; временные числа не переносятся на другие host/механизмы отказа. Correctness-наблюдения (статусы, counters, отсутствие зависаний) устойчивы; временные пороги — нет (см. A-3/A-6).

## Findings

### A-1 — major

```yaml
severity: major
artifact: governance/work-packages/M1.8.13-application-caching-s15-slice.md (Gate 0, строка «Cache outage…»); learn/cache-aside-freshness-coalescing.md; interview/concurrent-miss-stale-order-summary.md (вопрос 6); project-spec (scenarios 3–4)
criterion: correctness
finding: Общий тезис «Ошибка/timeout GET или SET даёт fail-closed 503 cache_unavailable; request не идёт в PostgreSQL» фактически неверен для ошибки SET: SET выполняется после чтения PostgreSQL, и source read уже произошёл. Learn смягчает («не обращается к PostgreSQL ПОСЛЕ cache error»), но interview (ответ на вопрос 6: «503 сохраняет source reads равными нулю») обобщает на обе ветки, а project-spec (обязательный сценарий 4 «Redis SET не выполнен») не задаёт ожидаемый counter-исход.
evidence: Runtime C6a/C6b на pinned стеке: GET-failure → 32/32 503, source_read=0 (верно); SET-failure → одиночный request 503 при source_read=1, burst 32 → 32×503 при source_read=32 (каждый waiter последовательно становится владельцем и перечитывает source; amplification ограничена числом requests, но не 0 и не ≤1). Это подтверждает подозрение orchestrator intake.
recommendation: Минимальная правка формулировок Gate 0/learn/interview/project-spec: (a) ошибка/timeout GET (включая повторный GET в критической секции) — до source read: 503 cache_unavailable, source_read=0; (b) ошибка SET — после source read: 503 cache_unavailable, source_read уже ≥1, fill не выполняется, в burst amplification деградирует до ≤N (N — число запросов), зависаний нет. Популяция «outage 32/32, source_read=0» относится только к недоступности cache с начала запроса.
```

### A-2 — major

```yaml
severity: major
artifact: governance/work-packages/M1.8.13-application-caching-s15-slice.md (Gate 0, строка «Cache pattern, TTL и freshness invariant»); learn «Freshness — это договор о версии»; README; project-spec Invariant 2
criterion: correctness
finding: Bound 2.25 с (TTL 2 с + 250 мс) не является герметичным в заявленной формулировке. (1) Не зафиксирована точка отсчёта 250-мс deadline: «от получения source snapshot до завершения fill» допускает чтение «от возврата строк». Медленный SELECT, начатый до commit и вернувшийся после, проходит deadline и записывает v1 с полным EX 2 — v1 живёт дольше 2.25 с от commit. PostgreSQL READ COMMITTED устанавливает snapshot на начало statement («sees a snapshot of the database as of the instant the query begins to run») — правильный anchor именно этот. (2) Deadline проверяется перед SET, но между проверкой и фактическим завершением SET есть неатомарный зазор: пауза планировщика/загрузка в этом зазоре продлевает жизнь v1 сверх обещания при фиксированном EX 2.
evidence: Runtime C9a (anchor=receipt, EX 2, pg_sleep 700 мс): commit→истечение v1 = 2616.8 мс > 2250; C9b (пауза 500 мс между проверкой и SET): 2519.3 мс > 2250. Контрвариант (anchor=statement start + SET с остаточным TTL): C9a → deadline_exceeded, fill нет, 503 summary_source_unavailable, v2 почти немедленно; C9b → commit→истечение v1 = 1959.9 мс ≤ 2250. Нормальный forced race C3 укладывается (≈1.9–2.0 с; автор: 2049.22 мс), поэтому дефект не виден в авторском эксперименте.
recommendation: Зафиксировать anchor = момент установления read snapshot (начало statement) и закрыть зазор одним из способов: SET с остаточным бюджетом свежести (PX = 2000 − elapsed от snapshot) либо явная оговорка «2.25 с + задержка между deadline-проверкой и завершением SET». Одно предложение в Gate 0 и абзац в learn; новая архитектура не нужна.
```

### A-3 — major

```yaml
severity: major
artifact: governance/work-packages/M1.8.13-application-caching-s15-slice.md (Gate 0, строка «Cache outage…»); learn «Почему outage выбран fail-closed»; kata (контракты); project-spec (contract «budget 250 мс … без request-path retry»)
criterion: practice
finding: Утверждение «без автоматического retry в request path» не соответствует поведению pinned клиента по умолчанию: redis-py 8.0.1 для async-соединений применяет Retry(ExponentialWithJitterBackoff, 10 повторов) на ConnectionError/TimeoutError и для connect, и для команд. Цитируемая страница redis-py async docs описывает asyncio.timeout-обёртку и pooling, но дефолтный retry не документирует — источник не покрывает claim. Как следствие, «budget 250 мс» не материализуется сам: одиночный GET к недоступному Redis занимает ~6.4–7.8 с, burst 32 — ~7.9 с.
evidence: Инспекция установленного redis-py 8.0.1 (conn.retry._retries=10, backoff ExponentialWithJitterBackoff, supported errors ConnectionError/TimeoutError); runtime: single get() 6388/6638/7802 мс, burst 7911–7959 мс при полной корректности fail-closed (32×503, source_read=0). Авторские 290.44 мс воспроизводимы только при adapter-level инжекции отказа (мои C6a: 60.8 мс) либо при явном отключении retry; механизм в Gate 0 не зафиксирован.
recommendation: Зафиксировать механизм исполнения бюджета: либо конструкция клиента с отключённым retry (retry=Retry(NoBackoff(), 0) / эквивалент), либо обёртка каждой команды в asyncio.timeout(0.25) (тогда клиентские retry происходят внутри бюджета), и указать механизм инжекции отказа для outage-популяции. Correctness-гейты (503, source_read=0) выполняются в обоих случаях — исправление касается формулировки и воспроизводимости измерения.
```

### A-6 — note

```yaml
severity: note
artifact: Gate 0 строка 10; kata acceptance; project-spec envelope
criterion: practice
finding: Временные пороги честно помечены как лабораторные и отделены от correctness-гейтов (в kata прямо сказано: при невоспроизводимости порогов записать отличие, не ослабляя correctness). ### A-7 — note
```

```yaml
severity: note
artifact: learn «Coalescing…» (абзац о cleanup); kata подсказка 4; источники
criterion: freshness
finding: Заявленный lifecycle («cancellation владельца обязана освободить секцию; следующий waiter может стать владельцем, но не должен получить зависший Future») runtime-верен на CPython 3.14.0: async with освобождает lock при CancelledError, waiters FIFO-честны, зависаний нет (C7, C8). Однако цитируемая страница asyncio.Lock документирует task-level синхронизацию и честность, но не описывает освобождение при отмене владельца — это поведение «acquire + try/finally release», следующее из эквивалентной формы async with.
evidence: Runtime C7/C8; docs.python.org 3.14 asyncio-sync: fair FIFO, not thread-safe; про cancellation-release не сказано.
recommendation: В learn/kata одной фразой указать механизм: lock освобождается, потому что async with эквивалентен try/finally, а не потому, что это задокументированное свойство Lock.
```

## Вывод по freshness/failure/coalescing boundary

- **Freshness:** математика «commit → старая version ≤ 2.25 с» корректна только при anchor «момент установления snapshot (statement start)» и при закрытии зазора между deadline-проверкой и завершением SET (остаточный TTL либо оговорка +ε). При буквальном прочтении текущего текста (receipt) воспроизведены нарушения: 2616.8 мс и 2519.3 мс. Исправленный контрвариант удерживает 1959.9 мс даже при намеренной паузе.
- **Failure:** ветка GET (до source read) и SET (после) имеют разные counter-исходы; заявления материалов обязаны их различать. DEL-failure семантика корректна: commit не откатывается, `cache_invalidation_error_total` растёт, старое значение ограничено TTL (математика подтверждена: v1 не живёт дольше snapshot+2.25 с ≤ commit+2.25 с при корректном anchor).
- **Coalescing:** `asyncio.Lock` + повторный `GET` достаточны для заявленного lifecycle — stuck followers нет (отмена владельца освобождает секцию, waiters FIFO), повторное чтение после ошибки владельца ограничено числом waiters (≤N), после успешного fill — ноль. Single-flight/Future semantics не требуются для заявленных claims; скрытой потребности в них материалы не создают. One-process граница выдержана: нигде не заявлено cross-worker поведение, отказ от B5 обоснован.

## Ответы на обязательные вопросы профиля A

1. **Gate 0 confirmed на exact pinned stack?** Да, с оговорками A-1..A-3: стек существует, запущен целиком и воспроизводим третьей стороной; три major — противоречия формулировок, а не решений.
2. **Математически и операционно доказан ли bound 2.25 с для всех заявленных interleavings?** Нет в текущей формулировке: медленный pre-commit SELECT при anchor=receipt (2616.8 мс) и зазор check→SET (2519.3 мс) превышают обещание. 3. **Redis failure points до/после source read и правдивость counters?** GET (включая повторный в секции) — до: 503, source_read=0, верно. SET — после: 503, source_read≥1 (runtime: 1 и 32), в материалах не сформулировано — A-1. Формулировка «деградация до ≤N при SET-failure» отсутствует — включена в рекомендацию A-1.
5. **Что доказывает локальный эксперимент?** См. раздел выше: substrate, amplification, isolation, race, fail-closed, recovery; не доказано и не заявлено — multi-worker/distributed/read-your-writes/L4.
