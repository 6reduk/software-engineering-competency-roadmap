# M1.8.19 — решение оркестратора по G18 B2 consolidation dossier

## Процессуальное решение

По прямому решению владельца программы профиль B временно пропущен из-за недоступности SaaS-подписки. G18 не считается двухпрофильным review, consolidated-артефакт не создаётся, а профиль A не выдаётся за консенсус двух независимых рецензентов.

Получен один независимый профиль A с verdict `accepted_with_changes`: `0 blocker / 0 major / 1 minor / 2 note`. Профиль подтвердил snapshot G17, no-new-coverage boundary, полноту debt register, корректность module-gate semantics, соответствие implementation-readiness принятым project-spec и обоснованную новизну кандидата S01.

Область отсутствующего профиля B — usability, learning navigation, самостоятельность входов и практическая ценность следующего действия — оценена оркестратором только как risk assessment, а не как второе независимое review. Однопрофильное исключение действует лишь для G18 и не переносится автоматически на следующие gates.

Итоговое решение: `accepted_with_changes`. До acceptance выполняется один ограниченный пакет [`M1.8.19a-G18-findings-correction.md`](../work-packages/M1.8.19a-G18-findings-correction.md). Повторный профиль A и полный пересчёт G18 не требуются.

## Подтверждённые границы и инварианты

- Досье является производной картой, а не вторым source of truth для coverage.
- Snapshot остаётся `57 artifacts / 249 relationships / 58 covered / 11 uncovered / 7 probe-only`.
- Собственный содержательный вход существует у `10/10` модулей, полный пятижанровый маршрут — у `9/10`, принятых module-gate решений — `0/10`.
- В досье ровно 10 module routes, 10 gate cards, 27 уникальных debt records и 11 implementation-readiness sections.
- Все десять gate cards имеют статус `not-ready-for-gate`; coverage, project-spec и readiness не выданы за proficiency участника.
- L4 требует реального adoption/migration evidence только там, где это следует из outcome или RoleView.
- Новые semantic entities, coverage relationships, ImplementationReference и module-gate decisions не создавались.

## Оркестраторская risk assessment отсутствующего профиля B

Навигация выглядит пригодной для работающего инженера: README даёт короткий порядок выбора работы, routes разделяют два RoleView и собственные/supporting маршруты, gate cards отвечают «что ещё нужно доказать», а implementation-readiness переводит 11 project-spec в самостоятельную работу без scaffold и готового решения. Единственная обнаруженная навигационная асимметрия — стартовый checklist ведёт только в Backend RoleView; она закрывается тем же correction-pass.

Рекомендация S01 признаётся bounded и отличной от существующих C1, S10 и runtime R1–R5: новое действие — самостоятельно локализовать первую потерю request context после refactor и закрепить её регрессионной проверкой при неизменном публичном контракте. Это решение подтверждает только качество кандидата. Оно не подтверждает B1/A3 readiness, не запускает authoring и не обещает завершение HTTP Runtime; отдельный следующий work package возможен лишь после acceptance досье и собственного Gate 0.

Остаточный риск однопрофильного gate — отсутствие независимой проверки того, насколько быстро новый читатель действительно найдёт нужный маршрут и поймёт карточки gate. Риск приемлем для документального consolidation package: механическая и семантическая связность подтверждены, а две найденные проблемы локальны и обратимы. При дальнейшем накоплении навигации полезность следует проверять на реальном читателе либо вторым editorial/usability профилем.

## Disposition

| Finding | Решение | Обоснование |
|---|---|---|
| M-1, minor | Исправить до acceptance | Слово `identity` без объекта можно спутать с capability Identity. Нужно назвать supporting idempotency и пояснить identity/result повторяемой операции. |
| N-1, note | Исправить тем же проходом | Оба RoleView равноправны; стартовый checklist должен давать явный вход и для Backend, и для Architecture. |
| N-2, note | Принять как ограничение доказательства | Без Git/VCS и сохранённого независимого pre-snapshot нельзя повторно доказать прошлое состояние файлов вне Ownership. Это не дефект текущего досье; ограничение фиксируется в audit trail и не подменяется утверждением о независимом diff. |

## Условия acceptance-pass

- Формулировка Workflow gate однозначно говорит об idempotency и не читается как требование чужой Identity capability.
- Checklist старта содержит явные ссылки на оба RoleView.
- Пять файлов досье и регистрация остаются в `review` до отдельного acceptance-pass.
- Сохраняются snapshot, все количества структур, статусы gate и no-new-coverage boundary.
- Не меняются debt taxonomy, project requirements, S01 scope и его условная readiness boundary.
- Фиксируется ограничение Ownership-проверки; недоказанный независимый pre-snapshot не реконструируется задним числом.
- После точечной проверки M-1/N-1 можно принять G18 без повторного полного review.
