## Подтверждённые утверждения (сверено с первичными источниками)

1. **OpenAPI versions.** `oas_3_1_baseline: 3.1.2`, `latest_oas_at_verification: 3.2.0` — реестр [spec.openapis.org/oas/](https://spec.openapis.org/oas/) подтверждает: v3.2.0 — последняя опубликованная, v3.1.2 существует. Утверждение README «на дату проверки опубликована OAS 3.2.0, но её возможности не предполагаются автоматически доступными во FastAPI» — корректно и сформулировано с правильной осторожностью.
2. **FastAPI output.** `fastapi_documented_output: 3.1.0` — страница [FastAPI: First Steps](https://fastapi.tiangolo.com/tutorial/first-steps/) показывает генерируемый документ с `"openapi": "3.1.0"`. Ссылка learn-документа на якорь `#openapi-and-json-schema` валидна.
3. **FastAPI dependency scopes.** Утверждение learn/http-contract «ресурс с областью `function` освобождается до отправки ответа, а с областью `request` — после неё» и граница `response start` точно соответствуют [FastAPI: Dependencies with yield — Early exit and `scope`](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/), включая `request` как scope по умолчанию. Mermaid-схема с ветвями exception/cleanup согласуется с sequence-диаграммой в документации FastAPI.
4. **RFC 9457.** Сверено с [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html):
   - «Поле `status` в теле должно совпадать со статусом HTTP» — §3.1.2: "Generators MUST use the same status code in the actual HTTP response" ✓;
   - «клиент не должен строить логику на тексте `detail`» — §3.1.4: "Consumers SHOULD NOT parse the 'detail' member" ✓;
   - рекомендация абсолютного стабильного URI в `type` — §3.1.1 (RECOMMENDED absolute URIs) ✓;
   - чек-лист типа проблемы (type URI, title, status) — §4: "New problem type definitions MUST document…" ✓;
   - машинно-читаемые расширения и игнорирование неизвестных членов — §3.2 ✓.
5. **Pydantic v2.** «`Window | None` без default остаётся обязательным ключом» — соответствует семантике Pydantic v2 (поле без значения по умолчанию required; см. [Pydantic: Fields](https://docs.pydantic.dev/latest/concepts/fields/) — not-required достигается только default/default_factory) ✓.
6. **HTTP-кэш.** Требование `Vary: Accept` либо обоснованного запрета общего кэширования при выборе представления по заголовку соответствует RFC 9110 §12.5.5 (Vary) и модели proactive negotiation (RFC 9110 §12.1; в RFC 9457 §1/§3 использованы те же ссылки) ✓.
7. **Прочее.** `response_model` фильтрует/валидирует результат, прямой `JSONResponse` обходит выходную модель, `responses={...}` только документирует (FastAPI docs: Response Model / Additional Responses) ✓; различие 400/422 в interview соответствует RFC 9110 §15.5.1/§15.5.21 (RFC 9457 §3 использует пример "422 Unprocessable Content") ✓; формат ошибки валидации FastAPI `{"detail": [...]}` с `type: "missing"` для отсутствующего поля ✓.

## Findings

### Minor

**M1. Сокращённый пример ответа валидации FastAPI выдаётся за фактический.**
- Evidence: `learn/http-contract-execution-boundary.md:34-40` — «реальный клиент получает другой ответ» и пример `{"detail": [{"loc": ["body", "delivery", "window"], "type": "missing"}]}`.
- Impact: фактический ответ FastAPI/Pydantic v2 содержит также `msg` (и обычно `input`, `url`). Читатель, сверяющий пример с реальным ответом или строящий по нему строгий клиентский разбор, получит расхождение — в материале, который учит сверять документацию с реальностью, это особенно заметно.
- Recommendation: добавить `msg` (например `"msg": "Field required"`) или явно пометить пример как сокращённый.

**M2. Два семейства примеров сквозной ситуации.**
- Evidence: `learn/compatible-api-change.md:36-43` использует `{"product_id": "p-7", "quantity": 2}` и `customer_id: "c-42"`; `kata/…:40-43` и `project-spec/…:68-78` используют `{"sku": "book-1", "quantity": 1}` и `"c-17"`.
- Impact: README позиционирует ситуацию как сквозную; расхождение `sku` vs `product_id` заставляет читателя перепроверять, та ли это система. На обучение не ломает, но добавляет шум.
- Recommendation: унифицировать имена полей (например, везде `sku`) или одной фразой указать, что примеры документов независимы.

**M3. Расхождение терминологии consumer/producer.**
- Evidence: `learn/compatible-api-change.md:212` аргументирует отказ от producer/consumer в пользу `API caller`/`API provider`; при этом `interview/…:253-254` определяет «Клиент (`consumer`)», «Сервис-поставщик (`producer`/`provider`)», а `project-spec/…:334` — «Потребитель (`consumer`)».
- Impact: учащийся встречает термины, которые один из документов слайса объявляет запутывающими. Локальные словари смягчают проблему, но не снимают её.
- Recommendation: в interview и project-spec добавить кросс-ссылку на caller/provider-терминологию learn или синхронизировать словари.

### Note

**N1. Freshness-якорь есть только у learn-документов.**
- Evidence: `last_verified`/`versions` заданы только в двух learn; interview (вопрос 1 о Pydantic v2) и kata (шаг 3) содержат версионно-чувствительные утверждения; модульный `verified_baseline` в `curriculum/tracks/b2/modules.md` отсутствует.
- Impact: при смене мажорной версии Pydantic/FastAPI не к чему привязать пересмотр interview/kata.
- Recommendation: добавить module-level `verified_baseline` (метамодель это предусматривает) либо `last_verified` в артефакты с версионными утверждениями.

**N2. Расширение `errors[].pointer` отличается от примера RFC.**
- Evidence: `learn/http-contract-execution-boundary.md:150-152` использует `"pointer": "/delivery/window/end"`; пример RFC 9457 §3 использует fragment-форму JSON Pointer (`"pointer": "#/profile/color"`).
- Impact: юридически допустимо (RFC разрешает собственные расширения problem type), но при совпадении имени члена с примером RFC разница представления pointer может смутить.
- Recommendation: принять fragment-форму `#/…` либо одной фразой зафиксировать, что это собственное соглашение сервиса.

**N3. Описание interview в coverage-map шире фактического coverage.**
- Evidence: `curriculum/tracks/b2/coverage-map.md:41` — «L1–L4 follow-ups по design/evolution/compatibility»; фактические targets interview — только L2–L4.
- Impact: только навигационное расхождение описания, не контента.
- Recommendation: поправить формулировку в coverage-map на «L2–L4» (это вне проверяемого пакета).
