## Консолидированные findings

Источник: 🔵 — GLM (профиль A); 🟡 — Kimi (профиль B). Полные evidence и рекомендации — в исходных review; здесь сжатая запись с диспозицией.

### Minor

**C-1 (🔵 GLM). «Карта оставшихся пробелов»: устаревшее «три полных по жанрам slices».**
После M1.8.3 полных по жанрам flow четыре (evolvable contracts, service architecture, service verification, performance/resource control) — что сам Executive conclusion того же файла и утверждает; ячейка таблицы противоречит ему. Решений не искажает: вывод «module gate не выводится из набора жанров» сохраняется.
Диспозиция: **fix-проход** — заменить «три» на «четыре» в одной ячейке.

**C-2 (🔵 GLM). «Сводка 10 модулей», строка Background workflows: «roots для workflow/idempotency».**
Workflow — действительно root, но `design-idempotent-service-operations` имеет hard edge на `design-http-api-contracts` (`prerequisites.md`); соседние ячейки формулируют такие ребра корректно. На очередь и состояния не влияет: prerequisite удовлетворён, модуль остаётся `not-started`.
Диспозиция: **fix-проход** — переформулировать ячейку («workflow — root; idempotency требует HTTP contract (покрыт)»).

**C-3 (🟡 Kimi F-1). Один S07 slice заявляет Transaction L3 и Idempotency L3 — риск двойного зачёта одного наблюдения.**
Evidence criteria обоих outcomes строятся на failure windows/recovery/duplicates; guardrails `role-requirements.md` требуют разных наблюдений для proficiency по разным outcomes. План запрещает начислять coverage за упоминание, но не фиксирует различение наблюдений для двух L3.
Диспозиция: **disposition → обязательное требование к S07 authoring work package** — Transaction L3 подтверждается наблюдением выбора boundary и перечисления failure windows commit/side effect; Idempotency L3 — отдельным наблюдением semantics повторной обработки (identity, result, duplicates). План править не обязательно.

### Note

**C-4 (🟡 Kimi F-3). Аргумент S07 против S05/S14 не использует hard-vs-conditional различие внешних baseline.**
По `prerequisites.md` A3 для identity/abuse — hard baseline, B3 для transaction boundaries — conditional; это делает выбор S07 принципиальным, а не только circumstantial (у S05 «baseline не подтверждён» — тяжелее последствие, чем у S07).
Диспозиция: **fix-проход (опционально, в том же проходе)** — одна фраза в разделе отвергнутых альтернатив; допустим следующий refresh.

**C-5 (🟡 Kimi F-4). Грамматически сломанная фраза вывода в таблице «Сравнение ближайших bounded actions».**
«Лучший leverage; выбрать при явном prerequisite подтвердить B3 до authoring» читается двояко без контекста open question 2.
Диспозиция: **fix-проход** — переформулировать («Лучший leverage; выбрать с явным условием подтвердить B3 baseline до authoring»).

**C-6 (🟡 Kimi F-2). Не зафиксирован allowlist допустимых B5-терминов как ссылочного контекста.**
Центральное действие S07 неизбежно называет partial failure / unknown outcome / duplicate delivery — термины владения B5; без явного перечня граница «называются, но не преподаются» держится только на дисциплине автора.
Диспозиция: **disposition → требование к S07 authoring work package** — перечислить допустимые ссылочные B5-термины с явной пометкой.

## Согласованный вывод по S07 и внешнему B3 prerequisite

S07 — действительно следующий лучший bounded package; смены выбора не требуется. Оба профиля независимо сошлись на практически одном и том же минимальном артефакте B3 readiness; объединённая форма — **B3 readiness contract как обязательный gating-шаг внутри будущего S07 authoring work package** (не slice, не отдельный prerequisite package):

1. выбранный driver/store и закреплённые версии;
2. transaction demarcation API (begin/commit/rollback, граница unit-of-work);
3. применимые isolation assumptions для одной Orders operation (предполагаемый уровень изоляции и допустимые аномалии);
4. commit/rollback semantics: когда изменение считается durable, что происходит при ошибке до/после commit;
5. поведение driver/store при ошибке и неизвестном исходе (например, потеря соединения во время commit) и отображение этого в failure windows S07.

Каждый пункт — допущение со ссылкой на owner-track context (`b3.cluster.transactions-concurrency`, `b3.cluster.storage-wal-recovery`), а не преподаваемый материал. Проверяемость: authoring не стартует, пока все пункты не зафиксированы; условная спецификация не становится hard DAG edge. Тем самым главный open question work package (форма подтверждения B3 readiness) закрыт согласованно.
