# M1.8.20 — orchestrator intake HTTP Runtime/S01

## Verdict

`accepted_for_review`: `0 blocker / 0 major / 0 minor / 2 note`.

Пакет допускается к двум независимым профилям G19. Intake подтверждает комплектность, согласованность контракта и соблюдение границ authoring package, но не принимает технические утверждения Gate 0, качество учебного материала, Trace L1/L2 coverage, L3 probe или module gate.

## Проверенный scope

- Gate 0 имеет итог `confirmed` от 2026-09-08 и заполнен до authoring; G19, program status и module status не изменялись.
- Созданы ровно четыре материала: index, interview, kata и project-spec. Отдельный learn не создан; index использует принятые C1 и R1 как объясняющие переходы без новых relationships для этих файлов.
- Все четыре материала имеют уникальные semantic ID, `status: review`, один модуль `b2.module.http-service-runtime` и согласованный набор pinned versions.
- YAML содержит ровно 10 relationships к четырём targets: `1 reference / 3 probe / 2 practice / 3 assess / 1 integrate`.
- Coverage ограничено capability Trace Request Execution, Trace L1/L2 и одним interview probe L3. Исполнительное L3, Lifecycle, Cancellation, Verification, HTTP Contract, B1, A3 и B7 не заявлены.
- Во всех материалах сохранён один лабораторный путь `GET /quote`, три исхода `200/503/422`, `application/json`, полные JSON-тела и серверный `X-Request-ID`.
- Центральный дефект — запуск дочерней задачи с явно пустым `contextvars.Context()`. Наблюдаемая первая потеря находится между `created` родительской задачи и `dispatch-enter` дочерней; исправление сохраняет task boundary и штатно наследует контекст.
- Исходный симптом не раскрывает причину. Наблюдения различают как минимум создание, propagation и чтение ответа; поздний `missing` не выдаётся за место первопричины.
- Measurement envelope разделяет control, defect, fixed, concurrent и recovery: 366 основных ASGI-операций и три отрицательных bypass-контроля. Заявлены 90/90 потерь в defect и нулевые потери, смешивание ID, contract и cleanup violations в остальных группах.
- Kata задаёт один скрываемый посев и требует локализовать причину; project требует самостоятельно выбрать diagnostic concern и refactor boundary. Готового scaffold, решения и ImplementationReference нет.
- Материалы явно ограничивают результат in-process ASGI-моделью без сети, worker reuse, distributed propagation, production tracing и production L3.

## Notes intake

### I-1 — удалённый probe не является независимым runtime evidence

Work package сохраняет команды, версии, модель, хеши удалённых временных файлов, агрегаты и примеры traces, но исполняемый harness отсутствует. Это соответствует запрету на готовое решение и допустимо для intake. Профиль A должен независимо воспроизвести минимальную эквивалентную модель вне проекта, явно описать substitutions и удалить её после проверки либо снизить силу вывода по Gate 0.

### I-2 — точный порядок относится только к закреплённой сборке

Порядок `yield` dependency, error mapping, response start и cleanup заявлен как наблюдение FastAPI 0.137.1 / Starlette 1.3.1 в HTTPX ASGITransport, а не как универсальное правило. G19 должен проверить эту оговорку и не переносить локальный порядок на сеть, другие версии, middleware stacks или production workers.

## Контрольные гипотезы G19

1. Корректно ли `asyncio.create_task(..., context=Context())` моделирует намеренную потерю `ContextVar`, а штатное создание задачи — причинное исправление без ручного fallback?
2. Действительно ли checkpoints находят первую наблюдаемую потерю, не смешивая её с доказанной первопричиной или поздним response symptom?
3. Согласованы ли success, domain-error и invalid-query пути с закреплённой сборкой и честно ли ограничена переносимость их порядка?
4. Доказывают ли concurrent и recovery populations изоляцию и cleanup только в заявленной одно-процессной модели?
5. Отвергает ли отрицательный bypass-контроль ложное исправление, которое сохраняет внешний ответ, но минует pipeline?
6. Отличается ли задача от C1, S10 и R1–R5 центральным инженерным действием и наблюдаемым результатом?
7. Различимы ли L1 и L2 evidence, а L3 честно остаётся только interview probe без production execution claim?
8. Достаточно ли автономны index, interview, kata и project при переиспользовании двух learn-переходов?
9. Не раскрывает ли материал решение до самостоятельного построения гипотез и остаются ли kata/project разными по свободе выбора?
10. Можно ли принять пакет без объявления HTTP Runtime module completion и без закрытия production/L4 долга?

## Граница intake

Intake не подтверждает внешнюю актуальность всех версий, авторские runtime-числа, production behavior, proficiency участника, закрытие D19/D20 выполненной реализацией или готовность module gate. Эти решения принадлежат G19, adjudication findings и отдельному acceptance-pass.
