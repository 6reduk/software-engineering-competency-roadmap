## Консолидированные findings и диспозиции

Источник: 🔵 — GLM (профиль A); 🟡 — Kimi (профиль B). Полные evidence и рекомендации — в исходных review; здесь сжатая запись с предлагаемой диспо­зицией. Окончательное решение за оркестратором. Фактические утверждения обоих профилей перепроверены консолидацией по артефактам (см. «Подтверждения»).

### Minor

**C-1 (🟡 Kimi B-1). В сводной таблице 10 модулей внешний A3 baseline поставлен в одну фразу с internal hard prerequisite.**

Ячейка «Hard prerequisites, влияющие на очередь» модуля identity-aware-boundaries: «identity integration требует HTTP contract; A3 security baseline обязателен». Слова «обязателен» без маркера внешности читаются как internal hard edge — именно то смешение, которое `prerequisites.md` разводит по классам, а сам план выдерживает во всех остальных местах (очередь, decision brief, DAG-раздел). Парные ячейки transactional (B3) и background (B5) смягчены словами «readiness»/«substrate gate». Проверено консолидацией: формулировка и контраст с соседними строками подтверждаются дословно. На выводы плана (очередь, `not-started`, gate) не влияет; риск — неверное чтение `blocked` читателем, ограничившимся таблицей.

Диспозиция: **fix-проход** — переформулировать одну ячейку, например: «identity integration требует HTTP contract (hard, подтверждён); A3 security baseline — внешний readiness gate будущего authoring package». Изменение одной строки без правки структуры таблицы; альтернатива по протоколу — явное backlog-решение оркестратора.

### Note

**C-2 (🔵 GLM A-note). Число 188 считает relationships как пары (target, role).**

Kata и project-spec артефакты дают две связи на один target (`practice`+`assess` либо `integrate`+`assess`): уникальных пар (artifact, outcome-target) — 129, с capability — 145, а не 172/188. Конвенция сквозная (M1.8.6 считал 177 тем же способом) и совпадает с формулировками реестра; риск — только для будущего reviewer-а, пересчитывающего уникальные пары.

Диспозиция: **без обязательства** — при следующем refresh планов добавить одну фразу о конвенции подсчёта в преамбулу реестра; либо зафиксировать как не требующее правки.

**C-3 (🟡 Kimi B-2). Метка «Gate 0» используется без локального определения.**

Полное описание механизма дано в decision brief как «обязательный readiness gate внутри будущего authoring package», а имя «Gate 0» появляется позже без связки. Суть findings сохраняется: связка «readiness gate» = «Gate 0» для читателя без истории M1.8.6 не установлена явно.

Диспозиция: **fix-проход опционально** — при первом описании механизма в decision brief добавить «(далее Gate 0)»; либо заменить единственное «Gate 0» на «readiness gate». Форма — на усмотрение оркестратора.

**C-4 (🟡 Kimi B-3). Состав Gate 0 фиксирует «правила безопасного audit context» без минимальной проверяемой конкретики.**

Ни набор полей audit record (subject, tenant, decision, outcome, request correlation), ни запрет логирования token/secrets не названы даже как примеры, хотя Identity L2 evidence criteria в `level-outcomes.md` прямо требуют «audit context сохраняется» — то есть audit record станет проверяемым элементом slice. Риск невысок: Gate 0 ещё будет детализироваться authoring package.

Диспозиция: **без правки плана** — требование переносится в будущий S05 authoring package: Gate 0 обязан зафиксировать минимальный набор полей audit record и запрет логирования credentials. В плане достаточно существующей фразы-намерения.
