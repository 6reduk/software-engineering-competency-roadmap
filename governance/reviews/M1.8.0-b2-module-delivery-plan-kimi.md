# Ревью M1.8.0 — план поставки модулей B2 (профиль B: domain, learning design, scope)

## Профиль и scope

Профиль B: предметная корректность, learning design и ограниченность scope следующего пакета. Проверяемый объект — `curriculum/tracks/b2/module-delivery-plan.md` (snapshot 2026-08-18, `status: review`).

Проверялись: выбор Service architecture как следующего модуля; тезис о разблокировке transaction boundaries; сравнение с альтернативами; пригодность S06; наблюдаемость central action; primary/supporting capabilities и outcome candidates; утечки scope; минимальный artifact flow; различимость kata и project milestone; ясность плана; трактовка external prerequisites и ImplementationReference. Числа coverage проверены выборочным пересчётом (см. таблицу критериев).

Использованные источники фактов: blueprint-каталоги `curriculum/tracks/b2/` (README, modules, capabilities, level-outcomes, prerequisites, scenarios, coverage-map), оба role route, YAML metadata всех 12 принятых artifacts двух slices, точечное чтение тел `b2.learn.http-contract-execution-boundary` и `b2.project-spec.resilient-fanout-service`. Старые review-отчёты как источник фактов не использовались.

## Verdict

**accepted_with_changes** — blocker: 0, major: 0, minor: 1, note: 2.

План предметно корректен, выбор модуля обоснован DAG и состоянием покрытия, S06 scope ограничен и не дублирует принятые slices. Единственный minor касается внутренней неоднозначности формулировки минимального artifact set и должен быть снят до authoring package. Ни одно finding не требует изменения выбора модуля или очереди.

## Findings

### F-1 (minor)

- artifact: `curriculum/tracks/b2/module-delivery-plan.md` — «Минимальный artifact set», п. 5, против раздела «Риски и решения до authoring»
- criterion: scope
- finding: П. 5 допускает «одну компактную project specification **или** milestone», а раздел рисков требует «Project specification оставить **обязательной** частью end-to-end flow». Не определено, является ли жанр project-spec обязательным для S06 package и что означает «milestone» вне project-spec.
- evidence: Для будущего authoring package это контрактная неоднозначность: автор не сможет однозначно решить, достаточно ли одного milestone без project-spec, а reviewer пакета получит два конфликтующих критерия приёмки. Оба принятых slices содержат полный жанр project-spec, поэтому прецедент также требует обязательности.
- impact: Риск разночтения scope будущего пакета и спора на gate G5.
- recommendation: Зафиксировать одну формулировку: project-spec обязателен, но может быть сокращён до одного компактного milestone с отдельным наблюдаемым integration result сверх kata (это и есть смысл раздела рисков); слово «или» убрать.

### F-2 (note)

- artifact: `curriculum/tracks/b2/module-delivery-plan.md` — decision brief, supporting candidates
- criterion: scope
- finding: Supporting candidate `b2.level-outcome.integrate-external-services-l2-design-typical-client-boundary` уже имеет принятое покрытие `explain`/`practice`/`assess` в runtime slice (R2, R4).
- evidence: Ограничение «только в объёме adapter boundary» корректно сужает переиспользование, но без явной ссылки на существующее покрытие автор может повторно объяснить client boundary, что нарушит non-goal о дублировании принятых slices.
- recommendation: В authoring package сослаться на R2/R4 как на существующее покрытие client boundary и ограничить новый материал ролью downstream client как заменяемого adapter в S06.

### F-3 (note)

- artifact: `curriculum/tracks/b2/module-delivery-plan.md` — decision brief, центральное наблюдаемое действие
- criterion: practice
- finding: Формулировка «adapters остаются заменяемыми» наблюдаема слабее остальных частей central action: одна policy change сама по себе не доказывает заменяемость adapter.
- evidence: По evidence criteria L2 (`design-service-architecture-l2-structure-typical-feature`) проверяется тестируемость business behavior без ненужного I/O; заменяемость становится наблюдаемой только при фактической подмене adapter (fake/in-memory) в проверке. Kata «провести одну policy change» без такого критерия может быть выполнена при скрытом coupling.
- recommendation: В authoring package зафиксировать наблюдаемый критерий: business behavior tests проходят на подменённом adapter без изменения application/domain кода.
