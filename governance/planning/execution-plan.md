# План реализации программы

## 1. Принцип построения

Программа развивается от общего к частному, но не проектируется целиком до последней темы заранее. Сначала создаётся минимальная глобальная модель, затем один пилотный трек проходит полный цикл. Выводы пилота возвращаются в глобальные шаблоны, после чего начинается масштабирование.

```text
Program skeleton
    ↓
Role × Track view
    ↓
Pilot track blueprint
    ↓
One thin end-to-end slice
    ↓
Review and template correction
    ↓
Pilot track module by module
    ↓
Second track and scaling
```

## 2. Измерения матрицы

Измерения не перемножаются в отдельные копии материала.

| Измерение | Назначение | Источник истины |
|---|---|---|
| Вертикальные треки | Области инженерной ответственности | Track map |
| Уровни L1–L5 | Масштаб наблюдаемого поведения и решений | Level model + capability matrix |
| Роли | Проекция требований: `core/depth/awareness` и целевой уровень | Role views |
| Zoom-иерархия | `program → track → cluster → capability → topic → artifact` | Индексы соответствующего уровня |
| Тип артефакта | `learn → interview → kata → project spec → solution link` | Topic/module coverage map |

Каноническая единица знания — capability/topic. Роль только ссылается на неё. Уровень описывает прогрессию поведения и не создаёт пять копий одной заметки. Типы артефактов закрепляют одну компетенцию разными способами.

## 3. Ограничения против разрастания

1. Не строить полный список тем всех треков до проверки пилота.
2. На глобальном уровне фиксировать только mission, границы и 5–12 competency clusters трека.
3. Полную capability matrix строить только для активного трека.
4. Не создавать отдельный учебный текст для каждой роли.
5. Не создавать автоматически отдельный текст для каждого уровня: один brief может покрывать несколько уровней с явными depth markers. Не каждая capability обязана иметь L1–L5; неприменимые уровни не заполняются искусственно.
6. Не требовать все пять типов артефактов для каждой атомарной темы; coverage определяется ценностью.
7. Ограничивать work package одним модулем или тонким end-to-end slice.
8. Любая новая мета-сущность должна иметь реальный сценарий навигации, review или автоматической проверки структуры.

## 4. Этапы

### M0. Master blueprint — завершён

Приняты видение, карта треков, уровни, learning flow, content standard, repository-per-vertical и исходные role views.

### M1. Матрица и пилот

#### M1.1. Утвердить метамодель

Результат:

- определения `role`, `track`, `cluster`, `capability`, `topic`, `artifact`;
- правила идентификаторов и ссылок;
- минимальная схема метаданных;
- правила, что является каноническим источником истины.

Gate: структурное ревью не обнаруживает неоднозначного владения или необходимости дублировать материал.

#### M1.2. Создать skeleton matrix всей программы

Для A1–A3, B1–B11, C1 фиксируются:

- mission и границы;
- 5–12 competency clusters;
- основные prerequisites и связи;
- роль трека в первых двух role views;
- целевые уровни без детализации тем.

Gate: нет критических пробелов, перекрытий без явного owner и технологий без основной вертикали.

#### M1.3. Выбрать пилотный трек

Критерии:

- возможность компетентно проверить материал;
- применимость L1–L5;
- богатство interview и production scenarios;
- связи с несколькими соседними треками;
- умеренный размер;
- способность проверить все типы артефактов.

Предварительный выбор: **B2 Backend & API Engineering**. Он ближе всего к основной аудитории, хорошо проверяем текущей экспертизой и связывает Python, HTTP/security, PostgreSQL, distributed systems, infrastructure и reliability.

Gate: пилот достаточно репрезентативен, но его можно завершать модуль за модулем.

#### M1.4. Построить blueprint пилотного трека

Результат:

- модули и capabilities;
- наблюдаемые критерии применимых уровней L1–L5;
- prerequisites;
- типичные рабочие и interview scenarios;
- предварительная coverage map без написания полного контента.

Gate: каждая capability проверяема действием; применимые уровни отличаются масштабом решений, а не количеством терминов; отсутствие уровня допустимо и объяснимо.

#### M1.5. Реализовать тонкий end-to-end slice

Выбирается один компактный модуль пилотного трека и создаётся минимальный полный набор:

- 1–3 engineering briefs;
- interview questions/follow-ups;
- несколько mini-tasks разных типов;
- одна project specification или milestone проекта;
- связи с уровнями и соседними темами.

Выбранный slice: **совместимая эволюция API-контракта в FastAPI/ASGI-сервисе**. Request execution раскрывается только в объёме, необходимом для проверки фактической contract boundary; глубокий runtime материал остаётся контрастному slice.

Gate: читатель может повторить тему, проверить понимание, выполнить практику и увидеть её место в проекте без чтения всего репозитория.

#### M1.6. Провести первое provisional-калибрование

По итогам первого slice предварительно корректируются:

- шаблон engineering brief;
- шаблоны interview/kata/project spec;
- метаданные;
- размер work package;
- review checklists.

Gate: шаблоны помогают качеству и навигации, но не заставляют заполнять пустые разделы. После этого gate шаблоны ещё не считаются стабильными.

#### M1.7. Реализовать второй контрастный slice

Внутри B2 выбирается модуль с другим типом сложности. Предварительный вариант: **concurrency, cancellation и resource lifecycle backend-сервиса**. Он проверяет, подходят ли метамодель и шаблоны не только для API design, но и для runtime/debugging/performance материала.

После второго slice:

- сравниваются структура, гранулярность и coverage обоих пакетов;
- устраняется backend/API-specific переобучение шаблонов;
- проводится практическая проверка сценариями `повторение`, `интервью`, `поиск пробела`, `переход к задаче`;
- шаблоны получают статус `accepted-for-pilot-track`.

Gate **G4b — Contrast slice**: два разных модуля создаются по одной модели без искусственных разделов, дублирования и потери навигации. Обязательные reviewers и критерии G4b определены в `authoring/workflow/review-protocol.md`.

#### M1.8. Наполнить пилотный трек

Модули создаются последовательно. Каждый модуль проходит цикл `design → content → review → correction → accepted`. Следующий модуль начинается после закрытия существенных замечаний предыдущего.

Gate модуля: scope/non-goals, capability coverage, корректность, практическая полезность, interview relevance, отсутствие ненужного дублирования и рабочая zoom-навигация.

### M2. Проверка масштабирования

Вторым выбирается связанный, но отличающийся трек — предварительно B5 Distributed Systems & System Design. На нём проверяется, не были ли шаблоны чрезмерно заточены под FastAPI/backend.

После B5 детализируется C1 Engineering Leadership & Architecture на кейсах решений и миграций из B2/B5/B7.

### M3+. Последовательное расширение

Новые вертикали добавляются по одной. Приоритет определяется ролью, зависимостями и ценностью покрытия, а не исходным порядком списка технологий.

## 5. Work package

Минимальная управляемая единица работы:

```text
scope
→ authoring
→ independent review
→ adjudication
→ correction
→ acceptance
→ status/index update
```

Work package — не отдельный абзац или файл. Обычно это:

- изменение матрицы одного уровня;
- один thin slice;
- один модуль;
- одно существенное изменение стандарта.

Авторство пакета отделено от оркестрации и независимого review. Оркестратор создаёт work-package артефакт с `Objective`, `Ownership`, `Context manifest`, ожидаемыми результатами и acceptance checks. Автономный автор следует [контракту автора](../../authoring/workflow/content-author-workflow.md), не выходит за ownership и оставляет результат в `review`. Reviewer не редактирует проверяемые файлы. После каждого принятого пакета оркестратор выдаёт новый актуальный `/goal`, ссылающийся на контракт и следующий work package.

## 6. Definition of Done пилотного трека

- границы и prerequisites согласованы;
- все capabilities имеют owner, ID и наблюдаемые критерии применимых уровней;
- каждый модуль имеет индекс и coverage map;
- ключевые capabilities покрыты briefs, interview и практикой;
- проектные спецификации проверяют интеграцию, а не копирование инструкции;
- внешние утверждения опираются на актуальные первичные источники;
- ссылки и zoom-навигация позволяют загрузить только нужный контекст;
- нет существенного дублирования между уровнями, ролями и артефактами;
- замечания review закрыты или явно приняты как известный долг;
- материал проверен хотя бы в сценариях повторения, подготовки к интервью и поиска пробела;
- ретроспектива фиксирует изменения метамодели, шаблонов и процесса;
- статус и журнал решений обновлены.
