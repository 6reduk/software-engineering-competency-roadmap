# M1.3 — выбор пилотного трека

## Решение

Пилотным выбран **B2 Backend & API Engineering**.

Пилот проверяет не полноту B2, а пригодность метамодели, уровней и учебного flow на двух контрастных end-to-end slices. Полная capability matrix B2 создаётся следующим пакетом M1.4.

## Зачем нужен пилот

Пилот должен дать evidence для четырёх решений:

1. Можно ли описывать компетенцию через наблюдаемое инженерное действие, а уровни — через масштаб контекста, автономность и качество решений.
2. Работает ли единый flow `learn → interview → kata → project-spec → implementation-reference` без обязательного артефакта каждого типа для каждой темы.
3. Достаточно ли engineering brief для повторения, интервью и перехода к практике без превращения материала в учебник или справочник API.
4. Сохраняется ли навигация от роли и уровня до конкретного материала, упражнения и проектного milestone.

## Критерии выбора

Кандидат оценивается качественно. Числовой рейтинг не применяется: точность такого балла была бы фиктивной.

| Критерий | Что считается сильным сигналом |
|---|---|
| Проверяемость | В текущей команде можно независимо проверить техническую корректность и практическую ценность |
| Диапазон уровней | Есть естественно различимые действия от L1 до L5 без искусственного заполнения каждого уровня |
| Interview value | Тема даёт базовые вопросы, follow-ups, debugging и design discussion |
| Production value | Есть реальные failure modes, trade-offs и operational consequences |
| Связность | Материал требует явных, но ограниченных связей с несколькими соседними треками |
| Умеренный размер | Вертикаль можно выпускать модуль за модулем, не проектируя всю программу заранее |
| Artifact coverage | На ней естественно проверяются briefs, interview, katas и project specs |
| Контраст внутри трека | Можно выбрать два slices с разным характером инженерной работы |

### Evidence для B2

| Критерий | Evidence |
|---|---|
| Проверяемость | Backend/API входит в текущую профессиональную область авторов и допускает review по спецификации, тестам, traces и наблюдаемому поведению |
| Диапазон уровней | В B2 естественно меняются автономность и масштаб: локальный endpoint → владение сервисом → межкомандная миграция; L5 проверяется, но не создаётся искусственно |
| Interview value | HTTP semantics, compatibility, async/cancellation, debugging и system-design follow-ups дают разные форматы интервью |
| Production value | Breaking changes, исчерпание pools, утечки ресурсов, неверные deadlines и опасный rollout имеют наблюдаемые последствия |
| Связность | B2 интегрирует знания B1/A3/B3/B7, сохраняя собственное service-level решение и не копируя owner-content |
| Умеренный размер | 10 clusters можно выпускать независимыми modules; пилот ограничен двумя сценарными slices |
| Artifact coverage | Change/failure scenarios естественно превращаются в brief, interview rubric, kata и milestone project spec; регистрация реализации проверяется позднее |
| Контраст | Contract evolution проверяет semantics/migration, runtime slice — diagnosis/resource control |

## Сравнение кандидатов

| Кандидат | Сильные стороны | Ограничение для первого пилота | Итог |
|---|---|---|---|
| B1 Python Engineering | Высокая проверяемость, сильные interview-сценарии, широкий L1–L4 | Языковые темы хуже проверяют service/project flow и L5 организационный масштаб | Сильный последующий кандидат |
| **B2 Backend & API Engineering** | Соединяет код, контракт, runtime, delivery и эксплуатацию; естественные L1–L4, применимость L5 проверяется; все типы практики | Нужна дисциплина границ с B1/B3/B5/B7 | **Выбран** |
| B3 Transactional & Operational Data Systems | Богатые failure modes, диагностика и архитектурный выбор | Первый slice легко перерастает в глубокий учебник по СУБД | Последующий depth-трек |
| B5 Distributed Systems & System Design | Максимальная ценность для Architecture и L4–L5 | Слишком абстрактен для первичной проверки code-level kata и framework-sensitive brief | Контрастный трек M2 |
| B7 Reliability, Observability & Production Engineering | Сильные production scenarios и leadership context | Многие упражнения требуют готовой системы и наблюдаемой среды | После появления B2 project scaffold |
| C1 Engineering Leadership & Architecture | Прямо соответствует глобальной цели | Интегрирующий трек нуждается в уже созданных технических кейсах | Детализировать после B2/B5/B7 |

## Первый end-to-end slice

### Рабочее название

**Эволюционирующий HTTP API: от request lifecycle до совместимого контракта в FastAPI/ASGI.**

### Фокус

- concrete change scenario: в минимальном FastAPI-сервисе заказов требуется добавить условно обязательные параметры доставки и новый error contract, пока старый и новый клиенты должны работать одновременно;
- путь запроса через ASGI application и middleware только в объёме, необходимом для понимания границ контракта и resource scope;
- HTTP semantics, validation и error contract;
- backward-compatible и breaking changes;
- rollout, deprecation и проверка потребителей;
- последствия решений для наблюдаемости и эксплуатации.

### Primary clusters

- `b2.cluster.request-runtime`;
- `b2.cluster.api-contracts`;
- `b2.cluster.validation-serialization-errors`;
- `b2.cluster.evolution-delivery`.

### Почему это один slice

Request lifecycle не становится отдельным обзором ASGI. Он объясняет, где именно возникает и исполняется внешний контракт. Центральное проверяемое действие slice — **спроектировать и провести совместимое изменение API, объяснив поведение системы и последствия для клиента**.

Минимальный project substrate — один FastAPI-сервис, legacy-клиент и новый клиент. Всё, что не требуется для изменения контракта и доказательства совместимости, оформляется cross-link, а не дополнительным brief.

### Не входит

- полный справочник HTTP, FastAPI, Pydantic или ASGI;
- исчерпывающая реализация auth;
- глубокая теория distributed consistency;
- полная CI/CD и Kubernetes delivery pipeline;
- готовая эталонная реализация проекта.

## Контрастный end-to-end slice

### Рабочее название

**Concurrency, cancellation и resource lifecycle backend-сервиса.**

### Фокус

- concrete failure scenario: сервис выполняет fan-out к медленной зависимости; клиентские disconnect/deadline не останавливают работу, соединения не освобождаются вовремя и pool исчерпывается под нагрузкой;
- выбор sync/async boundary;
- cancellation propagation и deadlines;
- cleanup ресурсов и lifespan;
- connection pools, bounded concurrency и backpressure;
- диагностика зависаний, утечек и latency amplification.

### Primary clusters

- `b2.cluster.request-runtime`;
- `b2.cluster.async-background-integration`;
- `b2.cluster.performance-resource-control`.

### Центральное наблюдаемое действие

**Диагностировать и переработать сервис с неверной отменой и исчерпанием пула: ограничить concurrency, провести deadline/cancellation через границы вызовов, обеспечить bounded cleanup в контролируемых lifecycle boundaries и подтвердить результат тестами и telemetry.**

Минимальный project substrate — один endpoint, одна управляемая медленная dependency и ограниченный connection pool. Общая теория event loop, autoscaling и очередей остаётся cross-link или non-goal.

### Контраст с первым slice

Первый slice проверяет semantic contract, совместимость и управляемую эволюцию. Второй проверяет runtime reasoning, debugging, performance и failure handling. Общий request lifecycle обеспечивает сопоставимость, но центральные действия и evidence различаются.

### Не входит

- полный курс по `asyncio` — языковая семантика принадлежит B1;
- внутреннее устройство event loop во всех реализациях;
- общая теория очередей и распределённых систем;
- инфраструктурный autoscaling;
- готовая эталонная реализация проекта.

## Предварительный level probe

Это не LevelOutcomes M1.4, а проверка, что уровни могут отличаться наблюдаемым масштабом работы.

| Уровень | Первый slice: contract evolution | Второй slice: runtime failure |
|---|---|---|
| L1 | С поддержкой изменить локальный endpoint, соблюдая заданные HTTP/error conventions | С поддержкой воспроизвести отказ и исправить локальный cleanup по заданному подходу |
| L2 | Самостоятельно реализовать типовое совместимое изменение и тесты старого/нового клиента | Самостоятельно диагностировать известный класс ошибки cancellation/resource handling и добавить regression tests |
| L3 | Владеть миграцией сервиса при неоднозначных требованиях, выбрать стратегию совместимости и безопасный rollout | Диагностировать нетипичное исчерпание ресурсов под нагрузкой, выбрать limits/deadlines и доказать восстановление telemetry |
| L4 | Провести межкомандную миграцию нескольких потребителей и сформировать применимые contract conventions | Согласовать runtime/resource policy для нескольких сервисов и провести изменение без каскадной деградации |
| L5 | Не предполагается автоматически; outcome допустим только при обнаружении B2-owned организационного API/platform действия | Не предполагается автоматически; организационные reliability/governance outcomes остаются B7/C1, если B2-owned действия нет |

## Cross-track boundaries

| Track | Роль в slices | Граница ownership |
|---|---|---|
| B1 Python Engineering | Hard baseline для Python и async semantics | B1 объясняет язык/runtime; B2 владеет применением на service/request boundary |
| A3 Networks, Linux & Security | Hard baseline для HTTP/network behavior | A3 объясняет протоколы и сетевые отказы; B2 владеет внешним API и реакцией сервиса |
| B3 Transactional & Operational Data Systems | Conditional reference при появлении persistence | B3 владеет driver/transaction/store semantics; в пилот они не включаются без необходимости сценария |
| B7 Reliability, Observability & Production Engineering | Reference для telemetry, SLI и operational validation | B7 владеет общей методикой; B2 владеет service-specific instrumentation и remediation |
| A2 Software Engineering Practice | Reference для testing/change discipline | Не является предварительным требованием всего трека |
| B6 Platform, Cloud & Infrastructure Engineering | Delivery context | Pipeline, orchestration и autoscaling не входят в slices |
| C1 Engineering Leadership & Architecture | Coordination/governance context L4+ | C1 владеет организационным решением; B2 — техническим контрактом и service policy |

## Проверка artifact flow по этапам

| Тип | Когда проверяется |
|---|---|
| `learn`, `interview`, `kata`, `project-spec`, `index` | M1.5, первый end-to-end slice |
| Структура coverage и metadata всех типов | M1.5–M1.6 |
| `implementation-reference` | После самостоятельной реализации project spec; до этого проверяется только registration/review contract без ссылки на готовый код |

Отсутствие ImplementationReference в первом опубликованном slice не означает, что полный flow уже подтверждён.

## Границы пилота

Пилот не должен:

- детализировать все 10 clusters B2 до написания первого slice;
- создавать пять версий одного материала для L1–L5;
- доказывать освоение уровня одним тестом или одной задачей;
- копировать материалы B1, B3, B5 или B7;
- фиксировать шаблоны как стабильные до сравнения двух slices;
- создавать GitHub-репозиторий B2 до принятия blueprint пилота.

## Success criteria

M1.3 считается успешным, если:

1. выбранный трек удовлетворяет всем критериям без blocker-компромисса;
2. каждый slice имеет одно центральное наблюдаемое действие и явные non-goals;
3. slices различаются типом инженерного мышления, но используют одну метамодель;
4. для M1.4 понятны первичные clusters и cross-track boundaries;
5. независимое review не выявляет причины сменить пилот или объединить B2 с соседним треком.

## Failure / reconsideration triggers

Реакция зависит от типа обнаруженной проблемы:

| Trigger | Действие |
|---|---|
| Capability B2 невозможно сформулировать без копирования owner-capability из B1/B3/B5/B7 | Rework границ B2 blueprint; сменить пилот только если у B2 не остаётся собственного central action |
| Уровни отличаются объёмом терминологии, а не действием, автономностью или масштабом | Rework LevelOutcomes; неприменимый уровень не заполнять |
| Project spec требует сначала спроектировать значительную часть другого трека | Сузить scenario или заменить project substrate; сменить пилот при неустранимой зависимости |
| Два slices требуют несовместимых metadata или coverage | Recalibrate метамодель/templates после анализа реальных потребителей |
| Slice нельзя удержать в 1–3 briefs и одном project milestone | Уменьшить slice; смена B2 не требуется, пока доступен другой репрезентативный B2 scenario |
