# Публикация программы и воспроизводимое продолжение authoring

## Цель

Подготовить текущий учебный план к сохранной публикации на GitHub, честно
зафиксировать состояние его модулей и оставить самодостаточный комплект
архитектурных, процессных и авторских инструкций, позволяющий продолжить создание
материалов с того же места.

Порядок ниже обязателен из-за зависимостей между состоянием программы,
публичной структурой репозитория и публикуемым snapshot. Работа выполняется по
одному пункту; следующий пункт начинается только после проверки результата
предыдущего.

## Зафиксированные смысловые границы

- Самостоятельное изучение материалов, выполнение kata и проектов, выбор
  консультанта или LLM-провайдера находятся вне scope текущего authoring epic.
- Подтверждение навыков относится к конкретному пользователю программы. Оно
  опирается на его собственные результаты и выбранный им способ проверки.
- Закрытие модуля означает готовность самого учебного пакета к самостоятельному
  использованию, а не факт обучения или присвоение грейда человеку.
- Acceptance отдельного материала, slice или phase close-out не закрывает модуль
  автоматически. Для модуля требуется отдельное решение по явным критериям.
- Долг описывает состояние программы и материалов: отсутствующее покрытие,
  неполные жанры, неподтверждённые границы, технические ограничения и условия
  возврата к authoring.

## Последовательность

### P0. Создать локальную точку сохранения — выполнено

Цель — немедленно защитить уже выполненную работу до структурных перемещений.

- Проверить, почему существующий `.git` не является рабочим репозиторием.
- Инициализировать локальный Git-репозиторий без изменения содержания программы.
- Добавить минимальный `.gitignore` для локальных настроек, временных файлов,
  секретов и машинно-зависимых артефактов.
- Зафиксировать исходный pre-publication snapshot отдельным commit.
- Сохранить commit SHA и файловый manifest как исходную точку следующих шагов.

Выход: текущее состояние восстановимо локально; удалённый GitHub-репозиторий ещё
не создаётся.

Результат 2026-09-19:

- отдельный репозиторий создан на ветке `main` непосредственно в каталоге
  blueprint;
- исходный snapshot содержит 510 файлов;
- commit: `f10acb6a2713fdbd86f75273589b233bb671eaa3`;
- `git fsck --full --no-dangling` завершён без ошибок;
- remote и GitHub-репозиторий отсутствуют;
- сохранённый commit является полным файловым manifest исходной точки.

### P1. Выполнить module-state audit и принять решения о закрытии — выполнено

Цель — отделить готовность учебных пакетов от coverage, review материалов и
обучения пользователя.

Для каждого модуля зафиксировать:

- вертикаль, capabilities и обязательные LevelOutcomes;
- существующие и принятые brief/interview/kata/project-spec;
- открытый предметный и редакционный долг;
- внешние readiness-зависимости;
- итоговое состояние: `not-started`, `blueprint-only`, `partial`,
  `ready-for-gate` или `closed-for-authoring`;
- доказательства и причину решения.

Закрывать только модули, для которых отдельный gate подтверждает достаточный
самостоятельный маршрут и отсутствие блокирующего долга. Проведённые review
используются как evidence качества материалов, но не подменяют module gate.

Выход: канонический реестр состояний модулей и отдельные решения по тем модулям,
которые действительно можно закрыть.

Результат 2026-09-19:

- создан [канонический реестр](../state/MODULE-STATE.md), отделяющий готовность учебного
  пакета от learner progress и proficiency;
- пересчитаны 61/259 accepted artifacts/relationships B2, 10/60 B3 и 5/35 B5;
- из 27 определённых модулей: 10 `closed-for-authoring`, 3 `partial`,
  14 `blueprint-only`, 0 `not-started`;
- остальные 12 вертикалей зафиксированы как `track-skeleton-only`, поскольку их
  module boundaries ещё не проектировались;
- исторические B2 gate cards переведены в `superseded` как authoring gate и
  сохранены как rubric для добровольной проверки пользовательской работы;
- решение зарегистрировано как D-080;
- commit: `2bac19a6a79256a234926e2295ed5b4374b6a7dd`.

### P2. Спроектировать и применить публичную структуру репозитория — выполнено

Цель — разделить учебное содержание и средства управления программой без
дублирования source of truth.

Целевая структура должна различать как минимум:

```text
curriculum/       учебный план, вертикали, модули и материалы
governance/       архитектура программы, спецификации, решения, review,
                  work packages, состояние и трекеры
authoring/        воспроизводимые инструкции для агентов и skills
tools/            безопасные validators и state-loading helpers
```

До перемещения файлов подготовить карту старый путь → новый путь и способ
атомарного обновления всех относительных ссылок. Не создавать параллельные копии
канонических документов.

Выход: принятая migration map и критерии проверки ссылок, ID и lifecycle.

Текущее состояние: [migration map](repository-structure.md) принята владельцем
программы и применена 2026-09-19. Учебное содержание, governance, authoring и
tools разделены без compatibility-копий; ссылки и IDs проверены. Решение
зарегистрировано как D-081.

### P3. Создать воспроизводимый state/load-state контур — выполнено

Цель — продолжать работу идемпотентно с последней принятой точки.

Контур должен содержать:

- канонический current-state manifest;
- текущую фазу, последний принятый gate и ровно один следующий bounded шаг;
- реестр модулей и их состояний;
- открытый долг с owner, trigger и disposition;
- ссылки на решения, work packages, review и acceptance;
- версию схемы состояния и проверку внутренних ссылок;
- инструкцию `load state`, не зависящую от истории диалога или памяти одного LLM.

Повторный запуск проверки на неизменном snapshot должен давать тот же результат и
не менять репозиторий.

Выход: один канонический вход восстановления контекста и машинно проверяемое
состояние программы.

Результат 2026-09-19:

- создан канонический [current-state manifest](../state/current-state.yaml) со
  схемой версии 1;
- принятый G35, module-state audit, фазовые close-out B2/B3/B5, долг и
  публикационный контур связаны явными source paths;
- зафиксировано ровно одно следующее действие — P4;
- [load-state инструкция](../state/LOAD-STATE.md) не зависит от истории диалога
  или LLM-провайдера;
- read-only validator `tools/validate_state.py` проверяет lifecycle boundaries,
  состояния модулей, debt contract, source files и acceptance statuses;
- два запуска validator на неизменном snapshot дают одинаковый `STATE_OK` и не
  меняют рабочее дерево.

### P4. Упаковать authoring skills и agent instructions — выполнено

Цель — сохранить методику создания материалов независимо от конкретного
поставщика LLM.

- Выделить из принятых editorial standard, author workflow, review protocol,
  Gate 0 и work-package conventions стабильные инструкции.
- Создать repo-local инструкции ролей как минимум для автора, технического
  reviewer, learning/editorial reviewer и оркестратора.
- Создать переносимые skills для authoring, review, correction, module-state
  audit и load-state.
- Не копировать машинные настройки, память сессий, секреты, vendor-specific
  runtime-файлы или чужие системные skills без проверки лицензии.
- Для каждого skill/agent указать входы, Ownership, stop conditions, ожидаемый
  handoff и lifecycle boundary.

Выход: подкаталог `authoring/`, достаточный для продолжения работы новым агентом
из чистого контекста.

Результат 2026-09-19:

- создан [authoring toolkit](../../authoring/README.md) с канонической
  навигацией на standards, workflow, роли и skills;
- зафиксированы инструкции автора, технического reviewer,
  learning/editorial reviewer и оркестратора;
- добавлены skills для authoring, независимого review, correction-pass,
  module-state audit и load state;
- общий [lifecycle contract](../../authoring/workflow/lifecycle-boundaries.md)
  разделяет planning, Gate 0, authoring, review, correction, acceptance,
  module-state audit и publication;
- каждый skill задаёт входы, Ownership, stop conditions, handoff и запрет
  неявного перехода lifecycle;
- инструкции не содержат vendor-specific runtime, локальную память или секреты.

### P5. Подготовить публичный README и лицензию — выполнено

README должен объяснять:

- цель и текущую границу программы;
- структуру учебного плана:
  `Program → RoleView → Track → Cluster/Module → Capability → LevelOutcome → Artifact`;
- 15 вертикалей и текущее состояние B2/B3/B5 относительно остальных;
- ролевые представления Backend / Distributed Systems и Architecture / Technical
  Leadership;
- `core`, `depth`, `awareness`, `integrating depth`;
- уровни L1–L5 и необязательный L6 как наблюдаемое поведение, а не автоматический
  hiring-grade;
- как самостоятельно построить маршрут: выбрать роль и рабочую задачу, получить
  срез capabilities по вертикали и требуемой глубине, затем использовать brief,
  interview, kata и project-spec;
- что обучение пользователя и подтверждение его навыков находятся вне scope
  репозитория;
- как читать module state, долг и условия возврата к authoring;
- как выполнить load state и продолжить создание материалов.

До добавления лицензии владелец выбирает режим переиспользования. Требуется
отдельно решить, используется ли одна лицензия для всего репозитория либо
раздельные лицензии для текстовых материалов и исполняемых tools.

Выход: README, LICENSE, notice об авторстве/ограничениях и понятная стартовая
навигация.

Результат 2026-09-19:

- корневой README переписан как публичная стартовая страница и объясняет модель
  `Program → RoleView → Track → Cluster/Module → Capability → LevelOutcome → Artifact`;
- описаны 15 вертикалей, два RoleView, значения `core`, `depth`, `awareness` и
  `integrating depth`, уровни L1–L6 и самостоятельный маршрут по четырём жанрам;
- зафиксированы границы learner execution и proficiency, состояния модулей
  `10/3/14/0`, долг, return triggers и порядок Load state;
- владелец выбрал раздельное лицензирование: CC BY 4.0 для содержания и MIT для
  `tools/` и самостоятельного исполняемого кода;
- правообладатель указан как `Shestakov Dmitriy <6reduk@gmail.com>`;
- созданы `LICENSE` и `NOTICE`, включая правило для встроенных code snippets,
  per-file overrides и сторонних материалов;
- решение зарегистрировано как D-084.

### P6. Выполнить pre-publication validation — выполнено

Проверить:

- YAML/front matter и уникальность semantic IDs;
- все относительные ссылки и anchors после migration;
- отсутствие секретов, локальных абсолютных путей и временных файлов;
- согласованность module states, debt register, STATUS и current-state manifest;
- доступность README-навигации из чистого checkout;
- воспроизводимость load-state инструкции;
- соответствие license/notice фактическому содержимому;
- чистый `git status` после повторного запуска validators.

Выход: подписанный commit SHA кандидата на публикацию и validation report.

Результат 2026-09-20:

- три независимых read-only профиля проверили privacy/security, структуру и
  навигацию, state/governance и воспроизводимость;
- correction-pass закрыл два unique major и пять unique minor findings; три
  точечных повторных проверки вернули `PASS` без остаточных findings;
- создан воспроизводимый `tools/validate_publication.py` и закреплён
  `PyYAML==6.0.3`;
- принят [P6 validation report](../reviews/P6-pre-publication-validation.md);
- state переведён на P7; внешний GitHub-репозиторий, push и tag не создавались;
- SHA кандидат-коммита сообщается в handoff после фиксации этого результата и не
  записывается внутрь самого себя.

### P7. Создать GitHub-репозиторий и опубликовать snapshot

Перед внешней записью владелец подтверждает:

- GitHub owner/organization;
- имя репозитория;
- public/private visibility;
- выбранную лицензию;
- допустимость публикации всего прошедшего secret/privacy audit содержимого.

После подтверждения:

- проверить `gh auth status` без раскрытия токенов;
- создать удалённый репозиторий через `gh`;
- добавить remote, отправить основную ветку и тег первого публичного snapshot;
- проверить README, LICENSE, ссылки, default branch и точный remote commit SHA.

Выход: канонический GitHub URL и проверенный immutable tag.

### P8. Выполнить post-publication handoff

- Записать GitHub URL и tag в current-state manifest.
- Проверить load state из опубликованного checkout.
- Зафиксировать следующий режим: использование материалов либо отдельный bounded
  authoring package только по зарегистрированному долгу и return trigger.
- Не превращать публикацию в подтверждение proficiency, module completion или
  качества будущих пользовательских реализаций.

Выход: публикация воспроизводима, состояние не зависит от текущего рабочего
каталога, а продолжение начинается с явно зафиксированного шага.

## Открытые решения, которые нельзя угадывать

1. GitHub owner/organization, имя и visibility репозитория.
2. Лицензия для текстов и исполняемых файлов — решено в P5/D-084.
3. Окончательное имя публичного репозитория и default branch.
4. Политика review/work-package истории — решено в D-085: текущий очищенный
   snapshot публикует полный audit trail как исторический ненормативный слой;
   локальная pre-publication Git-история не отправляется без отдельного аудита.

Эти решения запрашиваются непосредственно перед пунктом, который от них зависит,
а не блокируют локальную фиксацию и module-state audit.

Выполнить **P7 — создать GitHub-репозиторий и опубликовать очищенный snapshot**.
Перед внешней записью владелец подтверждает owner, имя и visibility.
