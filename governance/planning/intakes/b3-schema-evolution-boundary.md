# SE01: сменить представление суммы заказа без потери текущих изменений

В таблице заказов сумма хранится десятичным числом рублей. Новая версия программы должна работать с целым числом копеек, но старые процессы ещё читают и записывают рубли. Существующие строки нужно заполнить в новом представлении — выполнить backfill. Если перенос прочитал 100,00 рублей, затем пользователь изменил сумму на 120,00, запись старого результата переноса может вернуть новому читателю 10000 копеек. Команда изменения схемы (DDL) при этом могла завершиться успешно.

Поэтому результат перехода определяется совместимостью путей доступа и сохранностью последнего подтверждённого приложением значения каждого заказа. Процент обработанных строк не доказывает полноту, отсутствие NULL не доказывает правильность суммы, а завершение проверки ограничения не заменяет проверку читателей и писателей приложения (readers/writers). Ожидание блокировки при DDL или проверке ограничения хранилища (validation) нужно отличать от ошибки данных. Сверка данных отдельно сравнивает все ID и суммы с независимым ожидаемым набором; validation проверяет выполнение ограничения хранилища. Преждевременное удаление старого столбца закрывает обычный возврат старого приложения, даже если сверка ещё не закончена.

Это один planning artifact по [M1.9.4](../../work-packages/M1.9.4-schema-evolution-se01-intake.md), подготовленный по [контракту автора](../../../authoring/workflow/content-author-workflow.md) и [редакционному стандарту](../../../authoring/standards/editorial-standard.md). Здесь выбран предмет будущего опыта, но нет готовой миграции или учебного задания. Лабораторный опыт и предварительная проверка среды до создания учебных материалов (Gate 0) не выполнялись. Все пункты readiness ниже — **не подтверждены**.

Каждый кандидат ограничен одной таблицей `orders`. Значения и контракты ниже — локальные проектные решения для сравнения, а не результаты измерений.

|---|---|---|---|

Выбор сделан по различимости ошибки и полноте SE01, а не по длине SQL. Shadow column означает дополнительный столбец с новым представлением того же значения; это не новая сущность и не отдельное хранилище.

## Одно действие и предметный договор

**Действие:** перевести одну таблицу заказов с десятичной суммы рублей на обязательное целое число копеек через период сосуществования двух версий доступа, перенос существующих строк и проверку ограничения.

**Единственное предметное правило:** смена представления сохраняет последнее подтверждённое изменение суммы заказа через W-old либо W-new; пока оба представления доступны, `amount_minor = 100 × amount_rub`. Backfill — неавторитетное техническое копирование: подтверждение его записи не делает её новым бизнес-изменением суммы и не даёт права перекрыть более свежее подтверждённое изменение приложения. Промежуточный незаполненный новый столбец допустим только до завершения переноса и не должен быть выдан читателю как готовая сумма.

Предлагаемая исходная схема: одна непартиционированная таблица `orders`, ключ `order_id`, обязательный `amount_rub` типа `numeric(12,2)`. Новое представление — обычный заполняемый столбец `amount_minor` типа `bigint`, сначала допускающий NULL. В предметной области опыта одна валюта, суммы от 0,00 до 9999999999,99, ровно два десятичных разряда; нет округления, курсов, возвратов, DELETE и связей с другими таблицами. Это ограничение входа, а не новая финансовая capability. Ключи назначаются в заранее заданных строках (fixtures); генератор ключей не исследуется.

Ровно две версии приложения с четырьмя контрактами:

- **R-old:** читает по ID только `order_id` и `amount_rub`, получает точное десятичное значение; не использует позиционный `SELECT *`.
- **W-old:** создаёт заказ или заменяет сумму существующего по ID, передавая только рубли; имена столбцов заданы явно. Успех операции означает подтверждённую запись, а не отправку команды.
- **R-new:** читает оба представления по ID. Пока новый столбец пуст, получает эквивалентную сумму из старого; если заполнен, использует копейки. Несогласованная заполненная пара — ошибка, а не основание молча выбрать удобное значение.
- **W-new:** принимает целые копейки в том же диапазоне и обеспечивает согласованную запись обоих представлений в одной логической операции. Частичный успех двух записей недопустим.

В период сосуществования нужен механизм совместимости: подтверждённые W-old/W-new не оставляют неверную заполненную пару, новый INSERT имеет оба представления, UPDATE старой строки согласует их. Это требование к результату; конкретные trigger/adapter, защита от устаревшего backfill и порядок блокировок остаются предметом будущего Gate 0 и самостоятельной реализации. Простое заполнение NULL в backfill само по себе этот договор не обеспечивает.

R-new с переходным чтением и W-new с записью обоих полей сохраняются до конца опыта. Третья версия, читающая только новый столбец после удаления старого, не вводится. Поэтому результат — проверенное новое представление при сохранённой совместимости, а не демонтаж всех временных механизмов.

## Состояния и матрица совместимости

Таблица задаёт **проектную допустимость**, которую будущий Gate 0 должен проверить для каждой клетки; сейчас это не наблюдённая совместимость. «Условно» запрещает считать состояние достигнутым до проверки названного условия.

| Состояние | R-old | W-old | R-new | W-new | Условие перехода и состояние данных |
|---|---|---|---|---|---|
| Исходное: только рубли | Допустим | Допустим | Запрещён: нет столбца | Запрещён: нет столбца | Зафиксированы fixtures и старый договор |
| Расширение: новый nullable-столбец | Допустим | Допустим | Не включён | Не включён | Старое поле авторитетно; до механизма совместимости новый столбец не используется как готовые данные |
| Сосуществование и backfill | Допустим | Условно: механизм совместимости действует | Условно: переходное чтение и проверка согласованности | Условно: целостная запись пары | Старые строки могут иметь NULL, заполненные пары должны совпадать; текущие INSERT/UPDATE не теряются |
| Сверка и validation | Допустим | Условно: защита новых записей продолжает действовать | Допустим при сохранении договора | Допустим при сохранении договора | Нулевые пропуски и расхождения по всем ID, включая изменённые во время прохода; проверка store-ограничения завершена |
| Завершение опыта: новое представление обязательно, старое сохранено | Допустим | Условно: механизм совместимости сохранён | Допустим | Допустим | Новые нарушения отвергаются, успешные записи сохраняют инвариант; повтор backfill ничего не портит |

«Допустим» не обещает отсутствие ожидания блокировки. В каждом состоянии отдельно проверяются чтение, INSERT и UPDATE применимых версий. В исходном состоянии отрицательные пробы нового пути должны дать наблюдаемый отказ, а не фиктивную зелёную клетку. На расширении новые пути намеренно выключены; это не runtime-успех.

Переход к обязательности допускается только при непрерывной защите текущих writes между сверкой и validation. Если защиту выключили, нулевой счётчик в прошлом снимке уже не основание перехода. Во время коротких DDL допустимо ограниченное ожидание, но не скрытая остановка всех writers на весь backfill.

## Будущий Gate 0: данные, различающий опыт и evidence

Все количества ниже — **предлагаемые входы и пороги**, измерений пока нет. Fixtures — заранее заданные строки; oracle — независимый ожидаемый результат, с которым сверяют миграцию.

Минимальный набор: четыре исходных заказа с ID 1–4 и суммами 0,00; 100,00; 12,34; 9999999999,99. До любого воздействия отдельно зафиксировать ожидаемые копейки 0; 10000; 1234; 999999999999. Во время переноса W-old меняет ID 2 на 120,00 и создаёт ID 5 с 7,89; W-new создаёт ID 6 с 2501 копейкой и меняет ID 3 на 1300 копеек. Конечный независимый ожидаемый набор: ID 1–6 с копейками 0, 12000, 1300, 999999999999, 789, 2501. Он строится из входных команд W-old/W-new и их подтверждений, не чтением результата backfill; подтверждение технической копии не меняет oracle.

| Профиль | Управляемая последовательность | Ожидаемое различие, которое ещё требуется наблюдать |
|---|---|---|
| Control | Чистый набор, исправный переход, те же четыре записи между пачками без конфликтующего чередования | Полный ожидаемый набор, разрешённые reader/writer работают, завершение не запрещается всегда |
| Defect | Шаг 1: наивный перенос читает и сохраняет старое значение ID 2 (100,00 рублей → 10000 копеек) до барьера; W-old подтверждает 120,00; шаг 2: после барьера перенос отдельной записью пытается применить именно сохранённые 10000 | Эталон ID 2 остаётся 12000. Заранее выбранная сигнатура — применённое расхождение либо отвержение записи защитой/изоляцией с конкретным SQLSTATE. Сверка/ошибка запрещает объявление успеха; в следе видно отсутствие перехода к завершению |
| Fixed | На чистом наборе повторяется то же чередование; защита переноса учитывает текущую запись; W-old INSERT и W-new INSERT/UPDATE также приходятся на проход | Последняя подтверждённая сумма сохранена; все шесть ID сверены; после прерывания и продолжения получается тот же набор |

До полного control/defect/fixed будущий Gate 0 обязан зафиксировать уровни изоляции (isolation level) соединений backfill и W-old и заранее объявить ожидаемую сигнатуру Defect: применённое расхождение либо отвержение записи с конкретным SQLSTATE. Короткая предварительная проба обязана воспроизвести выбранную сигнатуру и показать два различимых шага захвата и последующего применения сохранённого значения. Одношаговый `UPDATE`, который после ожидания повторно проверит условие на свежей версии строки и тем самым превратит Defect в Fixed, не считается подтверждением сценария; молчаливое совпадение с Fixed запрещает полный прогон. Конкретные SQL, библиотека и реализация барьера не предписаны.

В Defect нельзя выдавать ожидаемую ошибку ограничения за потерю данных: сохранить фактический исход и отдельно показать, почему перенос не завершён. В Fixed нельзя убрать конкурентный UPDATE или изменить oracle ради успеха. Дополнительная проба неполноты: W-old создаёт ID 5 после фиксации наивного списка строк; его отсутствие в списке переноса должно обнаруживаться полной сверкой, даже если конкретный механизм совместимости уже заполнил новое поле.

Для прерывания остановить backfill после подтверждённой пачки, сохранив таблицу и текущие записи; затем возобновить и повторить уже пройденную пачку. Позиция прохода — вспомогательное состояние оснастки вне таблицы, не вторая предметная таблица. Нужен результат повторного применения без порчи суммы, а не только счётчик «обработано».

### Контур измерения и условия остановки

- Предлагаемая topology: один выделенный PostgreSQL, без реплик; шесть отдельных ролей/соединений — W-old, W-new, backfill, DDL/validation, наблюдатель и writer-сеанс lock-пробы, удерживающий конфликтующую транзакцию. По умолчанию readiness проверяет все шесть; безопасное совмещение ролей в реализации будущего Gate 0 требует явного обоснования. Владельцы соединений и настройки ещё не подтверждены.
- Нагрузка: четыре исходные строки, четыре успешные текущие записи, backfill пачками не более двух строк. Чтения обеих версий выполняются на барьерах по матрице и после продолжения. Отрицательные пробы не смешиваются со счётчиком успешных writes.
- Предлагаемый предел всего прогона — 60 секунд; ожидания отдельной операции — 2 секунды. Это предохранители малого опыта, не SLO. Их достижимость, настройки timeout и точные режимы блокировок остаются неподтверждёнными до Gate 0.
- Отдельный lock-профиль: намеренно удержать конфликтующую транзакцию, запустить выбранную DDL/validation, наблюдать блокирующий и ожидающий сеансы; после ограниченного отказа освободить блокирующий сеанс и повторить допустимый шаг. Конкретную конфликтующую пару операций выбрать и проверить до опыта; ожидание нельзя выводить только из долгой длительности команды.
- На стороне клиентов сохранять порядок барьеров, ID операций и строк, начало/конец, подтверждение либо ошибку с SQLSTATE. На стороне store — состояние ограничений, `pg_locks`, `pg_stat_activity`, блокирующие сеансы и фактическую длительность ожидания; права наблюдателя ещё требуют проверки.
- Для каждого подтверждённого INSERT/UPDATE нужен readback: проверочное чтение суммы и сверка по ID. Финальная популяция — все шесть строк, а не только затронутые backfill; сравниваются множества ключей и значения, включая ID 2, 3 и поздние ID 5, 6. В кратком финальном окне записи завершены, соединения чтения видят их подтверждённое состояние; это граница сверки, не способ обойти concurrent backfill.
- Пороги завершения: пропущенных и лишних ID — 0, NULL в новом представлении — 0, расхождений суммы — 0, потерянных подтверждённых записей — 0; применимые операции по матрице проверены, ограничение действительно проверено и действует. Несогласованную пару и пустое новое значение отдельно пробуют записать в конечном состоянии с ожидаемым отказом, затем откатывают отрицательную пробу.
- Stop: любое расхождение, неизвестный writer, потерянный сигнал/подтверждение, превышенный лимит, неожиданный отказ или нарушение порядка барьеров. В Defect и lock-профиле ожидаемый отказ также останавливает продвижение, но отмечается как намеренное воздействие. После stop следующая стадия не запускается автоматически.

Перед каждым профилем требуется чистый воспроизводимый набор; после stop для resume сохраняется именно незавершённое состояние. Планируется не менее двух повторов каждого профиля с одинаковым порядком барьеров. Будущий пакет должен сохранить текст/сценарий технической пробы (probe), fixtures, команды, настройки, журналы и контрольные суммы вместе: один хэш без исходного файла недостаточен для воспроизведения, как отмечено в границах принятия SQ01.

Cleanup выполняется после сохранения свидетельств: откатить открытые транзакции, закрыть принадлежащие опыту соединения, удалить только выделенные объекты опыта и подтвердить отсутствие оставшихся блокировок. Reset для нового профиля и resume текущего — разные действия. Ни probe, ни стартовый каркас (scaffold), ни журнал runtime в этом intake не создаются.

## Возврат, продолжение и необратимость

До включения новых путей допустим отказ от перехода с сохранением старой таблицы; удаление неиспользуемого нового столбца требует отдельной проверки отсутствия потребителей. Во время сосуществования можно остановить backfill и вернуть работу только на старый путь, **если** все подтверждённые W-new суммы доступны в рублях и старый договор проверен. Одного переключения версии для этого недостаточно.

После сбоя предпочтительно сохранить оба представления, выяснить судьбу последней операции и продолжить с проверенной позиции; retry не означает слепой повтор команды с неизвестным результатом. Повторное заполнение не должно затирать более свежие изменения. После validation возврат приложения не равен снятию ограничения: при работающем механизме совместимости старый путь ещё допустим.

Удаление `amount_rub` или механизма, нужного W-old, — граница обычного rollback; она намеренно **не пересекается**. Если обнаружен неизвестный потребитель, остановиться и передать вопрос B2, сохранив оба поля. Исправление вперёд (roll-forward) означает восстановить согласованность и продолжить совместимое состояние, не уничтожая подтверждённые записи. Производственный выбор stop/go остаётся B7 совместно с владельцами приложения и платформы.

Для проектной границы прочитаны 2026-09-11 официальные [ALTER TABLE PostgreSQL 18](https://www.postgresql.org/docs/18/sql-altertable.html) и [Explicit Locking PostgreSQL 18](https://www.postgresql.org/docs/18/explicit-locking.html). Первый источник разделяет операции изменения схемы, проверки ограничений и их требования к блокировкам; второй описывает конфликты блокировок. Поэтому «DDL выполнился» и «операция не мешает другим» требуют разных свидетельств. Это проверка общей основы intake, не выбор конкретного SQL и не подтверждение readiness. Ветка документации 18 не закрепляет server/client baseline SE01; точные операции, minor version, параметры и применимость источников должны быть установлены заново в разрешённом Gate 0.

## Non-goals, открытые вопросы и exit trigger

Не входят: полный курс migrations/PostgreSQL DDL, ORM-specific framework, универсальная migration platform, partition migration, CDC, cross-store replication, API evolution, Kubernetes/platform rollout, production migration, SLO/incident, денежные вычисления и округление, BR01, L4/L5, готовые SQL/migration/scaffold и ImplementationReference. Лабораторная проверка не докажет production readiness, масштабирование или реальный adoption.

Открытые вопросы будущему пакету, не требующие расширения Ownership сейчас:

1. **Механизм совместимости:** store-side либо adapter на строго учтённых путях. Рекомендуется сначала исследовать store-side вариант: неизменённый W-old должен оставаться допустимым; adapter требует отдельного доказательства отсутствия обходящих его writers. Выбор SQL и механизма не предписан.
2. **Закрепление обязательности и согласованности (C-8):** какие конкретные ограничения и шаги validation сохраняют старые writes и укладываются в лимит? Обязательный вход будущего Gate 0 — выбрать и проверить порядок включения механизма совместимости и ограничения согласованности так, чтобы W-old оставался допустимым в каждой заявленной точке. Преждевременное применение ограничения (enforcement) до действующего механизма совместимости не считается корректным переходом. Рекомендуется разделить проверяемые переходы; окончательный выбор зависит от версии и опыта. Решение и его проверка **не подтверждены**.
3. **Детерминированный дефект:** защита может отвергнуть устаревшую запись до появления неверной пары. Рекомендуется принимать такой исход как диагностируемый незавершённый перенос, сохранив доказательство stop; нельзя объявлять его успешным backfill.
4. **Среда и лимиты:** точные версии, права и достижимость предложенных 2/60 секунд неизвестны. Будущий Gate 0 вправе обосновать другие лабораторные числа до запуска, сохранив одну таблицу, инвариант и конфликтующее чередование.
5. **Учёт потребителей:** для лаборатории достаточно двух версий. Для переноса решения в эксплуатацию потребуется подтверждение B2 об остальных writers; до него удаление старого поля запрещено, production adoption не заявляется.
6. **Границы входных сумм (C-7):** обязательный вход будущего Gate 0 — определить допустимость отрицательных и избыточно точных сумм, соответствующие ограничения и отрицательные пробы при сохранении заявленного предметного домена. Нужно решить, защищаются ли границы явными ограничениями или остаются ограничением входа/fixtures; округление входа самим типом не считается его отвержением. Решение и его проверка **не подтверждены**.

C-7/C-8 остаются обязательными неподтверждёнными входами будущего Gate 0; correction-pass не выбирает за него механизм и не требует выполнения лабораторного опыта.

Exit trigger intake: выбрано одно действие с одним правилом, определены старые/новые пути, состояния и матрица, различающий опыт, сверка, readiness и границы ответственности; две альтернативы отклонены по предметным причинам. Эти элементы представлены для независимого review. Только после него оркестратор решает, создавать ли Gate 0 + пятижанровый authoring package. Наличие этого файла не означает прохождение review или принятие SE01.
