# Проект: провести Orders rollout по наблюдаемым условиям

Команда готова выпустить поддержку доставки по временному окну в Orders API. Старый operations script отправляет заказ без `delivery`; новый checkout использует `delivery.mode="scheduled"` и обе границы `window.start/end`. Совместимое изменение уже определено в [S03](../../evolvable-api-contracts/project-spec/evolvable-orders-api.md), а проверка публичной ошибки взята из [S10](../../risk-based-service-verification/kata/detect-orders-error-contract-regression.md). Ваша ответственность — провести выпуск одного сервиса, остановить его при нарушении условия и сохранить уже принятые обязательства.

Проект выполняется самостоятельно в отдельном репозитории. Стартового scaffold и эталонной реализации нет. Можно использовать собственный результат S03 либо построить минимальную лабораторию; выбор организации процессов, состояния, управления маршрутами и журналов остаётся вашим. Авторский disposable-стенд удалён и не передаётся участнику.

В отличие от [kata](../kata/stop-unsafe-orders-rollout.md), здесь недостаточно исправить одно условие перехода в готовом checklist. Нужно самостоятельно связать подготовку среды, порядок действий, наблюдение и восстановление так, чтобы другой инженер мог исполнить план и проверить его результат.

## Неизменный вход и пространство решений

Сохраняются существующие правила: отсутствие `delivery` не ломает старый запрос; `pickup` не требует окна; scheduled требует обе границы и `start < end`. Проект не вводит новый способ версионирования, другую ошибку или вторую миграцию API.

Группа запросов с одинаковыми ожиданиями — когорта (cohort). Old принимает legacy; new и исправленная fixed принимают обе когорты. Scheduled → old запрещён во всех стадиях. После первого принятого scheduled-заказа нельзя считать возврат старого binary безопасным восстановлением: он не сохраняет новую возможность обслуживания по умолчанию.

Вы определяете, как доказать readiness перед разрешёнными стадиями, обеспечить совместимое состояние new/fixed, связать запрос с реальным обработчиком и организовать решение владельца. Выбор архитектуры не оценивается по числу компонентов. Убедительное простое решение ценнее недоказанной сложной схемы.

Явно выберите и опишите размещение состояния между old/new/fixed. Объясните, какой отказ способно обнаружить проверочное чтение ранее принятых записей (readback) в выбранной topology и чего оно не доказывает. Общее состояние допустимо при честно названном ограничении: например, чтение из общего словаря после смены маршрута не проверяет перенос данных между хранилищами или сохранность после аварии процесса. Конкретная БД, миграция, replication или иной механизм не предписаны.

Контрольные точки и числа ниже фиксированы для сопоставимости результатов slice. Они не дают готового плана подготовки, команд и реализации; эти части вы проектируете сами.

## Контрольные стадии и измерение

Фактический охват версии запросами (exposure) должен совпасть с таблицей. Каждая строка — отдельное окно, а не настройка, которую можно принять на веру.

| Стадия | Legacy old/new | Scheduled old/new | Смысл контрольной точки |
|---|---:|---:|---|
| B | 100/0 | 0/0 | Подтвердить исходное поведение |
| S1 | 90/10 | 0/0 | Проверить новую версию без новых обязательств |
| S2 | 50/50 | 0/100 | Ограничить переход и проверить новую семантику |
| S3 | 0/100 | 0/100 | Подтвердить полное обслуживание обеих когорт |

Scheduled в B/S1 выключен; его отсутствие не считается успешной проверкой. Ограниченная exposure здесь относится к направлению legacy-трафика на new, а scheduled с момента включения идёт только на совместимую версию.

Окно — 5 секунд, последовательная нагрузка без retry: 100 запросов со слотами 50 мс либо 200 со слотами 25 мс, сначала legacy, затем scheduled. У каждой применимой когорты 80 корректных и 20 ошибочных запросов, каждый пятый — ошибочный. Legacy-ошибка — пустые `items`; scheduled-ошибка — отсутствие `window.end`. Полное fixture-окно равно `2026-08-21T10:00:00Z`–`2026-08-21T12:00:00Z`, без зависимости от текущей даты.

Корректный POST возвращает 201 и `order_id`. Старый ошибочный запрос сохраняет 422 и `{"error":"invalid order"}`. Новый клиент отправляет `Accept: application/problem+json`; missing-end проверяет как 422 с `Content-Type: application/problem+json`, `status=422`, `type=https://api.example.test/problems/invalid-delivery-window` и `errors` с `pointer=#/delivery/window/end`, `code=required`. Это готовые ожидания S03/S10, не задание создать новый test portfolio.

Для каждого stop/go — решения запретить или разрешить следующую стадию — нужен полный набор наблюдений:

| Сигнал | Точка измерения и группа | Порог каждого окна |
|---|---|---|
| Contract violations | Клиентская проверка каждого ответа; legacy и scheduled отдельно | 0 |
| Unexpected errors | Клиентские 5xx/transport failures/timeout; отдельно по тем же когортам | 0 |
| Exposure и полнота | Фактическая версия ответа и независимая серверная запись по request ID | Точное совпадение с таблицей, все запросы учтены |

Назначьте исполняющего инженера владельцем всех решений, зафиксируйте его действия при нарушении и отсутствие права продолжать без данных. Ожидаемые 422 не входят в unexpected errors. HTTP timeout — 1 с, предохранитель полного controller pass — 5,25 с. Потерянный сигнал, неполное окно или превышение этого предохранителя означает stop. Это лабораторные пороги, не production defaults и не latency SLO. Не добавляйте порог задержки без отдельного измерения.

Когорту определяйте из управляемого набора запросов и проверяйте по наблюдению сервера. Недоверенный заголовок произвольного production-клиента не может сам обосновать безопасный маршрут.

Сохраните по каждой стадии матрицу наблюдений маршрута и формы запроса (route/form evidence matrix) либо эквивалентные счётчики для обязательных сочетаний `cohort × old/new × valid/invalid`, где сочетание применимо по таблице. В частности, в S1 нужны наблюдения обеих legacy-форм на old и на new; scheduled в B/S1 и scheduled → old неприменимы. План назначения запросов выберите сами, сохранив заданные доли, populations и правило каждого пятого ошибочного запроса. Сопоставьте план с фактическими наблюдениями: суммарное exposure не доказывает полноту сочетаний. Для R аналогично укажите фактический обработчик old либо fixed. Исходный Gate 0 не сохранил interleave форм на old/new; его агрегаты не заменяют эту матрицу вашей реализации.

## Результат планирования: Delivery L2

До первого прогона подготовьте короткий план, который объясняет, почему действия выполняются в выбранном порядке. Он должен отделять запуск new, изменение маршрутов и разрешение scheduled; указывать предварительные и итоговые условия, способ проверки каждой стадии, владельца и условия завершения.

В плане должны быть подготовлены два разных пути. До scheduled возврат на old допустим и завершается R-окном 100 legacy, scheduled 0. После S2/S3 в этой истории выбран roll-forward — исправление вперёд с сохранением новой семантики. Обоснуйте, почему обычный rollback не выполняет обязательства, а compensation — отдельное предметное уменьшение последствий — потребовала бы отсутствующего соглашения об отмене или изменении окна.

Сохраните первоначальную редакцию плана и изменения, вызванные экспериментом. Отчёт, написанный только задним числом по зелёным результатам, не доказывает, что stop conditions и восстановление были подготовлены до воздействия новой версии.

Проверка L2 опирается на исполненный healthy B–S3 и отдельный отказ до новых обязательств: в S1 первый legacy-запрос к new получает контролируемый 503. Процесс обязан остановиться до S2, вернуть 100 legacy-запросов на old и подтвердить нулевые нарушения/ошибки. Если такого безопасного пути нет, план типового rollout пока не подтверждён.

Назовите предел R-old: возврат legacy-трафика до первого scheduled-обязательства доказывает управление маршрутом, но не доступность заказов, ранее принятых new. В Gate 0 они остаются в общем состоянии new/fixed в памяти, а непрерывность данных между раздельными хранилищами и readback этих записей не проверялись. Если выбранная вами topology использует раздельное состояние, задайте проверку сохранности и доступности таких принятых записей и передайте её результат при защите безопасного возврата.

## Результат работы с ограниченной обратимостью: Delivery L3

В отдельном прогоне воспроизведите детерминированный отказ S2: все missing-end ответы new имеют 422, но обычный `application/json` с `detail` вместо ожидаемого Problem Details. Остальные операции сохраняют заданное поведение. Дефект выбран так, чтобы после 80 успешных scheduled-заказов 20 из 100 scheduled-запросов нарушили контракт при нулевом числе 5xx.

Владение риском должно быть видно до S2: чем вы подтвердили доступность fixed, сохранение состояния, измерение по когортам и возможность запретить S3; кто выполняет последовательность остановки и восстановления (incident path). Не подменяйте это обещанием «при проблемах откатимся».

После stop S3 не должна получить ни одного запроса. Для выбранного восстановления направьте обе когорты на fixed: R-окно 100 legacy + 100 scheduled, оба счётчика 0, точное exposure fixed. Затем прочитайте все 80 ранее принятых scheduled-заказов и сравните идентификаторы, данные и окна. Успех новых POST не заменяет эту проверку.

Если fixed не готова, состояние недоступно или чтение расходится, зафиксируйте незавершённый recovery. Не удаляйте доказательства и не возвращайте scheduled на old ради зелёного отчёта. Владелец должен назвать нарушенное предположение и условие, при котором восстановление можно продолжить.

Самостоятельная ценность этого результата — связь риска, заранее подготовленных средств наблюдения, измеренной остановки и сохранённых обязательств. [S03 project](../../evolvable-api-contracts/project-spec/evolvable-orders-api.md) уже имеет supporting Delivery L3; новый проект не заявляет первое execution evidence вообще и не начисляет уровень за повторение API-дизайна.

## Защита и завершение

Передайте reviewer собственные команды запуска и очистки, точные версии, матрицу допустимости, план до запуска, timeline трёх профилей, измерения по каждому окну и решения владельца. Отделите ожидаемые числа от фактически полученных. Если поток неполон или измерение недостоверно, это должно быть видно.

| Критерий review | Достаточное наблюдение |
|---|---|
| L2: порядок и проверки | План до запуска и healthy B–S3, совпадающие с реальным выполнением |
| L2: безопасный возврат | 503 в S1, отсутствие S2, R-old 100 legacy без нарушений |
| L3: preparedness | До S2 подтверждены fixed, состояние, сигналы и способ stop |
| L3: ограниченная обратимость | 20/100 scheduled violations, отсутствие S3, решение не возвращать scheduled на old |
| L3: восстановление обязательств | R-fixed 100+100 и равенство всех 80 прежних заказов |
| Завершение | Сохранён отчёт, дефектный маршрут не используется, ресурсы очищены |

После проверки результата завершите процессы, подтвердите закрытие портов и удалите временные данные среды. Репозиторий самостоятельного проекта и отчёт сохраняются для review; одноразовые ресурсы лаборатории удаляются. Cleanup не является компенсацией. При повторении профиля начинайте с чистого состояния, предварительно сохранив результаты предыдущего.

Не входят в проект: CI/CD и observability platform, Kubernetes/service mesh, новая API migration, multi-service coordination, production rollout и Delivery L4. Локальная модель с памятью не доказывает durable recovery после аварии. Укажите такие ограничения собственного решения, не маскируя их тестами другой границы. Ссылка на реализацию может регистрироваться только после самостоятельного выполнения и review; сейчас её нет.

## Словарь и актуальность

- **Когорта / exposure** — клиентские ожидания / фактические обращения к версии.
- **Stop/go** — запрет либо разрешение следующей стадии по измерению.
- **Incident path** — исполнимая последовательность остановки, восстановления и проверки с владельцем.
- **Roll-forward / compensation** — совместимое исправление / предметное действие над последствиями.
- **Postconditions** — наблюдаемые признаки завершения стадии или восстановления.

[Gate 0](../../../../../../governance/work-packages/M1.8.15-safe-service-evolution-s11-slice.md#gate-0-record) на CPython 3.14.0 подтвердил ограниченную локальную модель 2026-09-06. [Python HTTPServer](https://docs.python.org/3.14/library/http.server.html) — одна возможная примитива для локальных запросов, не предписанная архитектура проекта. Документация ветки отображает 3.14.7; другая версия или технология требует собственной readiness-проверки при том же измерительном протоколе. [RFC 9457 §3](https://www.rfc-editor.org/rfc/rfc9457.html#section-3) задаёт формат Problem Details; конкретные клиентские ожидания взяты из S10.
