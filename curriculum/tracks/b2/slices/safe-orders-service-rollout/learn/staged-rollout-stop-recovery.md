# Как остановить rollout и сохранить обязательства сервиса

У Orders API появилась доставка по временному окну. Старый operations script продолжает отправлять запрос без `delivery`; новый checkout использует `delivery.mode="scheduled"` и `window.start/end`. Совместимость входа уже определена в [S03](../../evolvable-api-contracts/project-spec/evolvable-orders-api.md), проверки ошибки — в [S10](../../risk-based-service-verification/kata/detect-orders-error-contract-regression.md). Инженеру остаётся выпустить изменение так, чтобы ошибку обнаружили до расширения её воздействия.

Простой возврат исполняемого кода кажется универсальной страховкой. Но после ответа 201 клиент уже получил подтверждение заказа с окном доставки. Возврат старого binary не отменяет это обязательство и не учит старую версию обслуживать новую семантику. Поэтому план восстановления зависит от того, что сервис успел принять.

## Три разных действия

Сначала новая версия появляется в среде. Затем к ней направляют часть запросов — это управление фактическим охватом версии (exposure). Наконец, клиентам разрешают использовать новую возможность. Эти действия можно разнести: new уже запущен, но scheduled ещё выключен, а к новой версии обращаются только старые клиенты.

Такое разделение уменьшает неопределённость. Если legacy ломается до включения scheduled, инженер исследует регрессию старого поведения. После включения scheduled появляется другая ответственность: сохранить уже принятые окна при восстановлении. Один переключатель «новая версия включена» скрывает эту границу.

Группа с одинаковыми клиентскими ожиданиями — когорта (cohort). В лаборатории cohort задаёт сам генератор fixtures и сверяет с серверной записью запроса. Клиентский заголовок без доверенного контекста не доказывает принадлежность production-клиента к группе.

## Стадия заканчивается решением

Перед стадией нужны исправная исходная версия, доступные проверки, владелец решения и допустимый путь восстановления. Это предварительные условия (preconditions). После окна инженер подтверждает достигнутое распределение запросов и сохранение клиентских ожиданий — итоговые условия (postconditions). Истечение пяти секунд само по себе не выполняет ни одного из них.

Общая лабораторная матрица показывает, когда меняется обратимость. Группа однотипных запросов или наблюдений конкретной когорты в одном измерительном окне и её численность называются population. Числа в таблице — запросы в одном окне.

| Стадия | Legacy old/new | Scheduled old/new | Допустимое восстановление |
|---|---:|---:|---|
| B | 100/0 | 0/0 | Исходная old |
| S1 | 90/10 | 0/0 | Вернуть 100 legacy на old |
| S2 | 50/50 | 0/100 | После первого scheduled 201 — fixed |
| S3 | 0/100 | 0/100 | Fixed с поддержкой обеих когорт |

New и fixed принимают обе когорты; scheduled → old запрещён всегда. Отсутствующая population B/S1 не считается проверенной. Даже успешные 100 scheduled-запросов S2 не доказывают работу новых клиентов на старой версии.

Окно измерения (measurement window) здесь равно 5 секундам. Выполняются последовательно 100 или 200 запросов со слотами 50 или 25 мс, сначала legacy, затем scheduled, без retry. В каждой применимой когорте 80 корректных запросов и 20 ошибочных, каждый пятый — ошибочный. Legacy передаёт пустые `items`, scheduled пропускает `window.end`; полное fixture-окно — `2026-08-21T10:00:00Z`–`2026-08-21T12:00:00Z`. HTTP timeout — 1 с; controller pass дольше 5,25 с запрещает продвижение. Это контроль завершения эксперимента, не измеренный latency SLO.

Чтобы принять решение, нужны разные сигналы — наблюдаемые признаки состояния. Следующая таблица задаёт их смысл и точку измерения.

| Сигнал | Где измеряется и population | Порог за окно | Решение владельца |
|---|---|---|---|
| Нарушение контракта | Проверка ответа клиентом, отдельно все 100 запросов каждой применимой когорты | 0 | При любом нарушении stop |
| Неожиданный сбой | Клиент: 5xx, timeout, транспортная ошибка; те же populations | 0 | Stop, затем recovery |
| Exposure и полнота | Response version + server receipt по каждому request ID, сверка с таблицей | Точное распределение, нет пропущенных запросов | При расхождении или отсутствии сигнала stop |

Владелец всех трёх решений — выполняющий rollout инженер. Он фиксирует результат окна до запуска следующей стадии. Stop запрещает дальнейшее расширение, прекращает генерацию между окнами и запускает заранее подготовленный путь восстановления. Лаборатория принимает решение на границе окна: это не обещание мгновенно прекратить каждый запрос при первой ошибке.

## Почему зелёной метрики ошибок недостаточно

Корректный POST должен вернуть 201 и `order_id`. Старый ошибочный запрос получает 422 и `{"error":"invalid order"}`. Для scheduled-запроса без end ожидается 422 с `Content-Type: application/problem+json`, `status=422`, `type=https://api.example.test/problems/invalid-delivery-window` и `errors`, содержащим `pointer=#/delivery/window/end`, `code=required`. Клиент отправляет `Accept: application/problem+json`.

Контролируемый дефект new в S2 сохраняет 422, но возвращает обычный JSON с `detail`. Счётчик 5xx остаётся нулевым, хотя клиент уже не может распознать машинный тип ошибки. Именно поэтому [S10 contract check](../../risk-based-service-verification/kata/detect-orders-error-contract-regression.md) используется как отдельное условие остановки. Формат Problem Details определён [RFC 9457 §3](https://www.rfc-editor.org/rfc/rfc9457.html#section-3); конкретный pointer — соглашение этого API, не универсальная форма всех ошибок.

В [авторском Gate 0](../../../../../../governance/work-packages/M1.8.15-safe-service-evolution-s11-slice.md#gate-0-record) degraded S2 дал 20/100 нарушений у scheduled, 0/100 у legacy и ноль 5xx. Если смотреть только на server errors, получится ложное go. Если смешать когорты, получится 20/200, что скроет, для кого нарушено ожидание. И раздельное 20/100, и смешанное 20/200 превышают нулевой порог, но только раздельное значение показывает, ожидание какой когорты нарушено.

## Восстановление до и после нового обязательства

До scheduled управление маршрутом проверяется возвратом legacy на old и контрольным R-окном: 100 legacy, scheduled 0, оба счётчика 0, exposure 100 old. Это rollback — возврат исполняемой версии и маршрута при сохранении нужного поведения. Дополнительный Gate 0 прогон с одним 503 в S1 проверил именно этот путь. Он не доказывает доступность заказов, которые до stop принял new: в лаборатории они остаются в общем словаре new/fixed в памяти. Непрерывность данных между раздельными хранилищами и проверочное чтение (readback) этих записей — отдельная production-забота вне Gate 0.

После 80 успешных scheduled-заказов S2 общий rollback запрещён. В этой модели заранее выбран roll-forward: остановить продвижение, направить обе когорты на исправленную совместимую fixed и повторить окно 100 legacy + 100 scheduled. Затем прочитать все 80 ранее принятых заказов и сравнить их данные, включая окна. Нулевые ошибки новых запросов без этой сверки могли бы скрыть потерю прежних обязательств.

Fixed в лаборатории использует то же состояние, что new. Проверка доказала сохранение записей при смене маршрута; она не проверяла аварийный перезапуск процесса или восстановление базы. Для production-переноса эти предположения потребовали бы собственных подтверждений.

Компенсация (compensation) — отдельное предметное действие, уменьшающее последствия уже выполненной операции. Отменить заказ или перенести окно без согласованного правила нельзя считать безопасной технической процедурой. Поэтому эта альтернатива отвергнута в текущей истории. Если fixed недоступна, правильный результат — сохранить stop, а не импровизировать с old или объявлять cleanup восстановлением.

## Завершение имеет наблюдаемые признаки

После healthy S3 обе когорты должны обслуживаться new. После degraded R обе обслуживаются fixed, прежние окна сохранены, дефект больше не участвует в маршруте. В журнале остаются последовательность стадий, populations, результаты проверок и решение инженера. Только после этого удаляются лабораторные данные и временные ресурсы.

Бесконечный переходный режим появляется, когда владелец не назначил условия выхода. Для упражнения выход проверяем: финальное окно успешно, state readback выполнен при необходимости, old не получает трафик после полного выпуска, журналы сохранены, процессы завершены, порты закрыты, временный каталог удалён. В production «пять секунд без обращений к old» не доказывают отсутствие редкого клиента; учебное условие ограничено известным генератором.

Частые ошибки связаны с потерей одной из этих границ: продвижение по таймеру подменяет go; возврат binary подменяет сохранение данных; общая метрика подменяет ожидания когорты; неназванный владелец оставляет stop без действия. Исправление начинается с конкретного отсутствующего факта, а не с добавления ещё одного инструмента мониторинга.

## Самопроверка

Почему new запущен, а scheduled в S1 отсутствует?

<details>
<summary>Ответ</summary>

Сначала проверяется старое поведение на новой версии без создания новых обязательств. Это сохраняет простой путь возврата на old. Запуск binary и разрешение новой семантики — разные решения.

</details>

В S2 все 201 корректны, 5xx нет, но 20 ответов 422 имеют неверный формат. Можно ли продолжить?

<details>
<summary>Ответ</summary>

Нет. Нарушена отдельная проверка контракта scheduled: 20 из 100 запросов не соответствуют ожиданиям. После stop нужны fixed и сверка уже принятых заказов; таймер и агрегированный успех не отменяют нарушение.

</details>

Можно ли назвать удаление словаря заказов компенсацией?

<details>
<summary>Ответ</summary>

Нет. Оно уничтожит наблюдаемые обязательства. В эксперименте словарь очищается только после доказанного восстановления, как cleanup; компенсация требует предметного основания и проверки последствий для клиента.

</details>

## Словарь и актуальность

- **Pre/postconditions** — условия допуска к стадии и факты, которые она должна оставить.
- **Когорта** — одна группа клиентских ожиданий.
- **Exposure** — фактические обращения к версии.
- **Measurement window** — интервал с заранее заданной population и порогами.
- **Incident path** — последовательность stop, фиксации причины, восстановления и проверки под ответственностью инженера.
- **Rollback / roll-forward / compensation** — возврат версии / совместимое исправление / предметное уменьшение последствий.
