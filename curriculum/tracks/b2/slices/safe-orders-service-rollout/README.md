# Поэтапный выпуск изменения Orders API

Команда Orders API уже подготовила совместимую поддержку доставки по временному окну. Старый operations script создаёт заказ без `delivery`, новый checkout передаёт `delivery.mode="scheduled"` и обе границы окна. Теперь инженеру нужно постепенно дать клиентам доступ к новой версии, заметить нарушение условий и восстановить работу. Главная опасность появляется после первого принятого scheduled-заказа: старый сервис не умеет обслуживать новую семантику, а обещанное клиенту окно уже существует.

Пакет предназначен для backend-инженера, который умеет проверять HTTP-контракт и хочет управлять выпуском одного изменения. Здесь проверяется безопасная доставка изменений — [Delivery capability](../../capabilities.md) в модуле [Safe Service Evolution](../../modules.md). Сценарий [S11](../../scenarios.md) использует результат S03, а не предлагает спроектировать ещё один API.

## Что нужно на входе

Прочитайте [контракт Orders S03](../evolvable-api-contracts/project-spec/evolvable-orders-api.md) и [проверку ошибки S10](../risk-based-service-verification/kata/detect-orders-error-contract-regression.md). Старый запрос без `delivery` сохраняет поведение; `pickup` не требует окна; `scheduled` требует `start < end`. Эти правила не меняются в S11. Обязательные [prerequisites](../../prerequisites.md) — классификация совместимого изменения, проверка поведения сервиса и совместимости клиентов.

Для практики нужна самостоятельно созданная минимальная система в отдельном репозитории. Готового стартового кода нет. Достаточны различимые версии сервиса, локальные HTTP-запросы, управление их адресатами и журнал измерений. Способность выполнить эти операции — входная готовность среды; она не подтверждает квалификацию в platform engineering или reliability engineering.

## Одна история и одна модель измерения

Группа запросов с одинаковыми клиентскими ожиданиями называется когортой (cohort). Legacy использует старый запрос; scheduled использует окно доставки. Фактическая доля обращений к версии (exposure) определяется по полученным запросам и ответам, а не по значению настройки «10%».

Лабораторные old, new и fixed — обозначения исполняемого поведения, не URL-версии. New поддерживает обе когорты, fixed сохраняет это поведение и устраняет внесённый дефект. Наличие процесса new ещё не означает, что к нему пошёл трафик или что клиентам разрешили scheduled.

Таблица задаёт совместимость и контрольные populations — количество запросов каждой когорты в одном окне. Scheduled → old запрещён во всех строках.

| Стадия | Legacy old/new | Scheduled old/new | Основание следующего действия |
|---|---:|---:|---|
| B: контрольный замер | 100/0 | 0/0 | Старое поведение исправно |
| S1: ограниченное включение | 90/10 | 0/0 | Legacy → old/new допустим по контракту; предел наблюдений указан ниже |
| S2: включение scheduled | 50/50 | 0/100 | Проверены обе когорты; уже есть новые обязательства |
| S3: полное включение | 0/100 | 0/100 | Новая версия обслуживает обе когорты |
| R до новых обязательств | 100/0 | 0/0 | Возврат на old проверен |
| R после новых обязательств | 0/100 fixed | 0/100 fixed | Исправление вперёд проверено, заказы сохранены |

Отсутствие scheduled в B/S1 означает, что новая возможность ещё не включена. Нельзя записывать для неё «проверка прошла». После S2 возврат всего трафика на old недопустим; в этом упражнении выбран выпуск совместимого исправления (roll-forward). Отмена последствий отдельным предметным действием (compensation) потребовала бы другого согласованного основания.

В каждом окне 5 секунд. Генератор выполняет запросы последовательно, без retry: 100 запросов со слотами 50 мс либо 200 со слотами 25 мс, сначала legacy, затем scheduled. В каждой применимой когорте 80 корректных и 20 ошибочных запросов, каждый пятый ошибочен. Legacy-ошибка — пустые `items`; scheduled-ошибка — отсутствие `window.end`. Полное окно доставки в fixtures: `2026-08-21T10:00:00Z`–`2026-08-21T12:00:00Z`, без зависимости от текущего времени.

Корректный POST возвращает 201 и `order_id`. Legacy-ошибка сохраняет 422 и `{"error":"invalid order"}`. Для scheduled клиент отправляет `Accept: application/problem+json` и проверяет 422, этот же media type, `status=422`, `type=https://api.example.test/problems/invalid-delivery-window` и расширение `errors` с `pointer=#/delivery/window/end`, `code=required`. Человекочитаемый `detail` не используется для ветвления клиента.

В конце окна выполняющий rollout инженер проверяет три условия отдельно по когортам: нарушений контракта 0; неожиданных 5xx или транспортных ошибок 0; наблюдаемое распределение точно совпало с таблицей и все запросы учтены. Ожидаемые 422 не являются серверными сбоями. Потеря журнала или неполная population означает stop. HTTP timeout равен 1 секунде; предохранитель длительности всего прохода — 5,25 секунды, а не норматив задержки ответа. Это учебные числа, не production defaults и не нагрузочный тест.

## Маршрут

1. [Разбор механизма](learn/staged-rollout-stop-recovery.md) помогает разделить выпуск версии, направление запросов и включение нового поведения; объясняет остановку и пределы восстановления.
2. [Развивающийся interview-кейс](interview/limited-reversibility-orders-change.md) проверяет рассуждение от заданного checklist до ограниченной обратимости. Ответ на интервью ещё не доказывает исполнение.
3. [Kata](kata/stop-unsafe-orders-rollout.md) даёт один checklist и один дефект процесса: он продолжает rollout после плохого окна. Результат — выполненная остановка и заданное восстановление.
4. [Проект](project-spec/evidence-driven-orders-rollout.md) требует самостоятельно связать подготовку, стадии, владельца решения и восстановление, затем защитить результат отдельными доказательствами планирования и работы при ограниченной обратимости.

## Что подтвердил авторский Gate 0

[Запись Gate 0](../../../../../governance/work-packages/M1.8.15-safe-service-evolution-s11-slice.md#gate-0-record) имеет итог `confirmed`. Одноразовая проверка на CPython 3.14.0 использовала один процесс, три локальных HTTP server threads, controller и общий словарь заказов new/fixed. Контроль адресата находился в генераторе. Когорта известна по его fixtures и сверяется с сервером по request ID; недоверенный заголовок клиента не предлагается как способ production-идентификации.

Healthy прошёл B–S3: 600 POST, ноль нарушений и ошибок. Degraded остановился на S2: 20/100 scheduled ответов имели неверный формат, хотя 5xx было 0. После перевода на fixed повторное окно 100+100 прошло, а чтение всех 80 ранее созданных scheduled-заказов подтвердило сохранность. Дополнительный 503 в S1 остановил продвижение и позволил вернуть 100 legacy-запросов на old. Переход на следующую rollout-стадию после каждого отказа отсутствовал.

В healthy и degraded профилях S1 подтвердил точное суммарное распределение запросов по версиям (aggregate exposure) и отсутствие зарегистрированных нарушений контракта и неожиданных серверных/транспортных ошибок; профиль с 503 проверял отдельный отказ. Порядок назначения форм запросов на old/new (interleave) не сохранён, поэтому эти результаты сами по себе не доказывают, что new в S1 наблюдался с каждой валидной и невалидной формой legacy-запроса. Таблица задаёт допустимость маршрутов по контракту; проект требует отдельные наблюдения сочетаний маршрута и формы.

Возврат legacy-трафика на old до первого scheduled-обязательства подтверждает управление маршрутом, но не доступность заказов, которые до stop принял new. В лаборатории эти записи остаются в общем словаре new/fixed в памяти; непрерывность данных между раздельными хранилищами и проверочное чтение (readback) этих записей — отдельная production-забота вне Gate 0.

Временные сервисы и журналы удалены после сохранения агрегатов; порты закрыты, потоки завершены, временный каталог отсутствует. Учащемуся этот стенд не передаётся. Эксперимент доказывает доступность локальной механики, а не полноту реализации S03, устойчивость хранения после аварии или готовность к production.

## Границы результата и актуальность

[Delivery L1–L3](../../level-outcomes.md) различаются действием: выполнить заданный checklist; самостоятельно составить план; провести изменение после появления ограниченно обратимых обязательств. L1 получает новое для принятых материалов покрытие. У L2/L3 уже есть supporting coverage в S03; собственная ценность S11 — измеренные стадии, stop и recovery, а не первое упоминание миграции. Delivery L4, межкомандный rollout, B6/B7, Evolution и Verification не получают новых relationships.

CPython 3.14.0 — проверенный baseline, не заявление о latest. Документация ветки 3.14 на дату 2026-09-06 отображала 3.14.7; при другой версии повторите readiness. [HTTPServer](https://docs.python.org/3.14/library/http.server.html) предоставляет локальную серверную примитиву; её применение здесь ограничено лабораторией. [RFC 9457 §3](https://www.rfc-editor.org/rfc/rfc9457.html#section-3) задаёт представление Problem Details, а конкретные `type` и `errors` взяты из S10.

## Самопроверка

Можно ли после успешного S1 удалить old?

<details>
<summary>Ответ</summary>

Нет: 90 из 100 legacy-запросов ещё обслуживает old, а scheduled вообще не проверен. S1 даёт основание перейти к следующему ограниченному окну, но не завершить rollout.

</details>

## Локальный словарь

- **Стадия** — фиксированное распределение запросов и отдельное окно принятия решения.
- **Когорта** — запросы с одним набором ожиданий клиента.
- **Exposure** — измеренные обращения к конкретной версии.
- **Stop/go** — решение запретить либо разрешить следующую стадию по данным окна.
- **Rollback** — возврат на прежнюю версию, допустимый только при сохранении обязательств.
- **Roll-forward** — восстановление совместимой следующей версией.
- **Compensation** — предметное действие над последствиями, не удаление лаборатории.
- **Cleanup** — освобождение ресурсов и удаление временных данных после проверки результата.
