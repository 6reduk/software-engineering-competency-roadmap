# Где запрос потерял диагностический контекст

Команда небольшого сервиса котировок перенесла часть обработки запроса при рефакторинге middleware и зависимостей. Пользователь по-прежнему получает котировку или понятный код отказа, но поддержка больше не может связать ответ с обработкой внутри сервиса: вместо серверного диагностического ID появляется `missing`. Тесты, сравнивающие только JSON, остаются зелёными.

Задача инженера — восстановить путь одного запроса, найти первое место расхождения с рабочей версией и исправить его причину. Начальный симптом не сообщает, был ли ID создан, потерялся ли позже или неверно прочитан при формировании ответа. Такой разбор составляет этот узкий вариант [сценария S01](../../scenarios.md). Остальные задачи HTTP Runtime, в частности shutdown и утечки ресурсов, здесь не выполняются.

## Что именно исследуем

Данные, принадлежащие одной обработке запроса, называются **контекстом запроса (request context)**. Здесь это один UUID, который создаёт сервер; он не подтверждает личность клиента и не даёт прав доступа. Клиентский `X-Request-ID` не является доверенным источником этого значения.

Передача значения между исполняющими компонентами — **распространение контекста (propagation)**. Проверяем его в нескольких именованных местах — **контрольных точках (checkpoints)**. Добавление таких наблюдений — **instrumentation**. Отдельная безопасная метка операции связывает записи (**correlation**), даже когда исследуемый контекст исчез. Эту метку нельзя использовать для подстановки отсутствующего ID в ответ: тогда наблюдатель сам скроет дефект.

Первая наблюдаемая потеря (**first-loss boundary**) — пара соседних существенных точек, между которыми значение было и исчезло. Она ещё не равна доказанной первопричине: между точками могли исполняться несколько действий. Причину устанавливают уточнением наблюдения и изменением одного фактора. Поздний `missing` — лишь внешнее последствие. **Регрессионная проверка (regression)** должна снова падать при возвращении причины, даже если кто-то вручную исправит конечный заголовок.

Лабораторный путь — `GET /quote?mode=ok|unavailable`; отдельный ошибочный ввод `mode=bad`. Контракт: `200 {"quote":42}`, `503 {"code":"quote_unavailable"}` либо `422 {"code":"invalid_query"}`, всегда `application/json` и `X-Request-ID` с созданным сервером UUID. Тела приведены полностью. Ошибка 422 требует исправить query; 503 означает недоступность котировки, а не пустой успешный результат. ID меняется между запросами, но сохраняется внутри одного пути.

## Маршрут от объяснения к самостоятельному результату

1. [Где возникает фактический HTTP-контракт — C1](../evolvable-api-contracts/learn/http-contract-execution-boundary.md). Прочитайте, чтобы различать декларацию модели и ответ собранного приложения. Это supporting learn другого модуля: здесь мы сохраняем контракт, а не проектируем новый API.
2. [Cancellation, deadlines и lifecycle ресурсов — R1](../runtime-concurrency-lifecycle/learn/cancellation-deadlines-resource-lifecycle.md). Это собственный learn HTTP Runtime, хотя расположен в соседнем slice. Для нашей задачи нужны понятия владельца и request scope: завершение endpoint ещё не означает завершение очистки. Fan-out, cancellation policy и pool limits из R1 не становятся заданием этого пакета.
3. [Интервью: восстановить путь по неполным признакам](interview/reconstruct-context-path.md). Сначала предскажите заданный порядок, затем выберите различающие наблюдения. Production follow-up проверяет ход рассуждения, а не наличие production-опыта.
4. [Kata: локализовать потерю контекста](kata/localize-context-loss.md). Создайте минимальный стенд, исследуйте один ограниченный посеянный дефект и предъявите исходный и исправленный traces с регрессией.
5. [Проект: сохранить контекст через собственный refactor](project-spec/preserve-context-through-refactor.md). Самостоятельно выберите диагностическое значение и границу изменения, соберите более широкую матрицу наблюдений и защитите решение в отдельном репозитории.

Нового learn нет: два перехода выше дают нужную исходную модель. Читать work package или review для понимания заданий не требуется. [S10](../risk-based-service-verification/kata/detect-orders-error-contract-regression.md) полезен как контраст: там заранее названа ошибка регистрации обработчика, а здесь требуется отличить конкурирующие причины по наблюдениям. [Fan-out project](../runtime-concurrency-lifecycle/project-spec/resilient-fanout-service.md) исследует длительность и ресурсы нескольких вызовов; здесь нет downstream-сервисов или нагрузочного tuning.

## Готовность и предел результата

Нужны async-функции, исключения и `finally`, различие task/thread из B1, а также HTTP method/status/headers/body из A3. [Prerequisites B2](../../prerequisites.md) оставляет tracing без внутренних hard prerequisites: порядок чтения выше — учебная рекомендация. Не нужны БД, auth, OpenTelemetry collector или готовая observability platform.

Закреплённая лаборатория использует один процесс и event-loop thread, асинхронную dependency с `yield` и request scope, FastAPI/Starlette и HTTPX ASGITransport. Этот transport вызывает приложение без сети. Участник сам создаёт стенд; готового scaffold и решения здесь нет. До эксперимента он проверяет успешный и оба ошибочных ответа через собранное приложение.

Kata требует три повтора: control/defect/fixed по 30 запросов (10 каждого исхода); concurrent — 12 одновременно (4 каждого исхода); recovery — три повтора, в каждом после конкурентной волны 20 последовательных операций: пять последовательностей `unavailable → ok → bad → ok`. Всего recovery `3 × 20 = 60`. Подробный порядок и пороги заданы в kata. Это 366 операций, отдельно 3 отрицательных проверки обхода pipeline. Размеры выбраны для различения причин и изоляции, а не для оценки производительности. Проект расширяет разнообразие проверок, сохраняя эти группы как минимум или обосновывая явное сопоставление.

Материалы готовят [трассировку выполнения запроса](../../capabilities.md): [L1 — заданный путь, L2 — самостоятельная локализация, L3 — production reconstruction](../../level-outcomes.md). Index даёт reference; interview — только probe L1–L3; kata — practice/assess L1/L2; project — integrate/assess L2. Исполнение локальной лаборатории не доказывает L3, lifecycle/cancellation, Verification или B7. Материалы в review не меняют accepted coverage и не принимают module gate.

## Частая ловушка и самопроверка

Плохая практика — скопировать ID в endpoint или строить корреляцию только по потерявшемуся значению. Первая скрывает дефект от клиента, вторая делает наблюдение слепым. Полезнее независимая метка операции и несколько точек вокруг подозреваемого перехода; после локализации лишнюю временную диагностику можно убрать, сохранив проверку инварианта.

## Словарь и актуальность

| Термин | Смысл в этом маршруте |
|---|---|
| Server-owned context | Диагностическое значение, которое создаёт и очищает сервер |
| Propagation | Сохранение этого значения при переходе между компонентами исполнения |
| Checkpoint / instrumentation | Именованное наблюдение / добавление наблюдений для проверки гипотезы |
| Correlation | Связывание записей одной операции безопасной меткой |
| First-loss boundary | Первый наблюдаемый переход от своего значения к отсутствующему |
| Regression | Исполняемая проверка возвращения обнаруженного дефекта |
