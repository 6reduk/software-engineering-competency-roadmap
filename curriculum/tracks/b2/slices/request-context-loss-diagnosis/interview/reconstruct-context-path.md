# Интервью: восстановить путь потерянного контекста

После рефакторинга middleware/dependency сервиса котировок поддержка получает ответы без пригодного диагностического ID. `GET /quote?mode=ok` по-прежнему возвращает `200 {"quote":42}`, `mode=unavailable` — `503 {"code":"quote_unavailable"}`, неизвестное `mode=bad` — `422 {"code":"invalid_query"}`. Все тела приведены полностью, тип содержимого — `application/json`. Но вместо созданного сервером UUID в `X-Request-ID` появляется `missing`. Тесты только тела не обнаружили изменения.

ID относится к данным одной обработки — **контексту запроса (request context)**. Сервер владеет этим значением: создаёт его и завершает его область жизни. Клиентский заголовок не является его источником, ID не доказывает права клиента. Кандидату пока неизвестно, не создался ли ID, потерялся ли по пути или был неправильно прочитан. Интервьюер выдаёт дополнительные наблюдения после того, как кандидат объяснит, зачем они нужны; ответы ниже открывают после собственного рассуждения.

## 1. Заданный путь: где возникает результат? — L1

Дано собранное FastAPI-приложение внутри внешнего ASGI middleware. Middleware создаёт контекст; далее вызываются routing, асинхронная зависимость с `yield` в request scope, endpoint и зарегистрированные error mappings. Middleware наблюдает начало ответа и в конце очищает свой контекст. Все компоненты работают в одном event-loop thread; transport — HTTPX ASGITransport, без сети.

Checkpoint `dependency-exit` наблюдается на success и error paths, потому что запись выхода размещена в `finally` вокруг `yield`. Код просто после `yield`, без `finally`, может не исполниться при вбросе исключения в генератор зависимости. Поэтому отсутствие этой записи само по себе не доказывает ошибку сборки приложения: сначала проверьте instrumentation. Это условие наблюдаемого trace, а не изменение фактического порядка разворачивания dependency stack закреплённой сборки.

Предскажите существенный порядок для success, исключения `quote_unavailable` в endpoint и ошибки query. Где нужно проверить ваше предсказание, и почему недостаточно вызвать endpoint как Python-функцию?

<details>
<summary>Ориентир ответа</summary>

Для закреплённой сборки success проходит dependency-enter, handler, response-start, dependency-exit. При domain error после handler сначала выходит dependency, затем вызываются error mapping и response-start. Для invalid query endpoint отсутствует, но в проверенной сборке dependency-enter/exit есть до validation mapping. После возврата downstream внешняя обёртка завершает ожидание и очищает контекст.

Это предсказание нужно сопоставить с наблюдениями собранного ASGI app: прямой endpoint call исключает routing, dependency resolution, error mapping и отправку ответа. Сильный кандидат называет ограничение версии и request scope. Утверждение «cleanup всегда после ответа» неверно даже для трёх заданных ветвей: исключение меняет выход из dependency.

</details>

## 2. Неполная информация: какой следующий факт нужен? — L2

Есть только исходный симптом `missing` при прежнем status/body и сообщение о refactor. Сформулируйте минимум две причины и выберите минимальные наблюдения, которые их различат. Как связать записи одного запроса, если сам исследуемый ID может исчезнуть?

<details>
<summary>Ориентир ответа</summary>

Гипотезы: создание не выполнилось; значение было создано, но не доступно последующему компоненту; значение доступно, однако reader строит неверный заголовок. Нужны контрольные точки (checkpoints) после создания, на входе следующего существенного компонента и перед формированием заголовка. Добавление этих наблюдений (instrumentation) отвечает на конкретные вопросы, а не записывает всё подряд.

Независимая серверная метка операции связывает записи (correlation) даже при пустом исследуемом ID. Она не передаётся как «исправление» в endpoint. Сравниваются порядок, наличие значения и task/thread identity, а не только timestamps разных запросов. Клиентский ID нельзя молча принять за доверенный ключ диагностики.

</details>

## 3. Первая потеря и причина — L2

После предложенных наблюдений для одной операции получено: `created` видит UUID в task A; `dispatch-enter`, dependency и reader ответа видят `None` в task B; после ожидания B родительская task A всё ещё видит UUID. Thread ID одинаковый. В контрольной версии все точки видели UUID. Какой вывод уже доказан и что ещё нужно проверить до исправления?

<details>
<summary>Ориентир ответа</summary>

Первая наблюдаемая потеря (first-loss boundary) находится между созданием в A и входом dispatch в B. Поздний `missing` — следствие, а не место первого сбоя. Это пока не доказывает конкретную строку причины: нужно проверить момент создания B, выбранный для неё context, а также отсутствие раннего reset. Один thread не означает один task context.

Сильный следующий опыт сохраняет app и error mappings, но меняет только передачу контекста на этой границе (propagation). Возврат значения в B при прежнем пути и ответах поддерживает причинную гипотезу. Смена одновременно middleware, validation и формата ответа не позволяет сделать такой вывод.

</details>

## 4. Как отличить исправление от маскировки? — L2

Коллега предлагает передать UUID отдельно в endpoint и проставить заголовок в готовом ответе. Какую проверку добавите, чтобы эта правка не создала ложный зелёный результат? Что проверите на error, concurrency и recovery?

<details>
<summary>Ориентир ответа</summary>

Регрессия (regression check) должна сравнивать свой ID в существенных точках и факт прохождения dependency/error path, а затем method, status, media type, полное тело и header ответа. Вручную исправленный endpoint не восстанавливает значение до него и не помогает validation error, где endpoint вообще не вызывается. Отрицательный контроль с правильным ответом, но пропущенной dependency, обязан быть отвергнут.

Для каждой группы control/defect/fixed задаются одинаковые входы. Отдельная конкурентная волна удерживает несколько запросов одновременно: каждый видит только свой ID. После success/error родительская контролируемая граница пуста, дочерняя задача завершена; последующая независимая операция начинает с пустого контекста. Нулевое число ошибок одной последовательной пары не подтверждает конкурентную изоляцию. Локальный cleanup также не обещает поведение при process kill или сетевом disconnect.

</details>

## 5. Путь в production неизвестен — L3 follow-up

Теперь известен только один неполный production-log и жалоба клиента. Неясны версии, состав middleware, workers и точка формирования ответа. Какие данные запросите, какую минимальную instrumentation предложите и какие выводы отложите?

<details>
<summary>Ориентир сильного рассуждения</summary>

Нужны версия и фактическая сборка нужного экземпляра, method/path и класс исхода, границы proxy/app, task/thread/process topology и безопасная корреляция. Затем — конкурирующие гипотезы и наблюдение с минимальным изменением: мог ли запрос завершиться раньше endpoint, изменился ли context на task boundary, не сформировал ли ответ другой компонент. Сырые token, credentials и полные payload не нужны.

Кандидат связывает потерю контекста с последствиями для состояния и владельца: какая работа ещё живёт, кто очистит значение, может ли следующий запрос увидеть чужие данные. Он отделяет отсутствие записи от отсутствия события и называет слепые зоны. Нельзя считать локальную пару A/B доказательством production-root-cause без подтверждения соответствия сборки и маршрута. Принятие решения о broader tracing policy относится к отдельному контексту.

</details>

## Как оценивать рассуждение

| Уровень | Наблюдаемое рассуждение | Недостаточный ответ |
|---|---|---|
| L1 | Восстанавливает заданные ветви, называет место ответа и способ проверки порядка | Перечисляет компоненты, но теряет ветвь validation или очистку |
| L2 | Сам выбирает различающие checkpoints, проверяет первую потерю и причинную правку без обхода | Угадывает context bug по слову refactor или проверяет только заголовок |
| L3 follow-up | Восстанавливает неизвестные production-границы как гипотезы, связывает состояние и ресурсы, ограничивает выводы | Переносит лабораторную топологию на неизвестный production или предлагает логи везде |

Интервью даёт только `probe` для [Trace L1–L3](../../../level-outcomes.md). Практическое действие L1/L2 проверяет [kata](../kata/localize-context-loss.md), самостоятельную интеграцию L2 — [проект](../project-spec/preserve-context-through-refactor.md). Ни правильный ответ L3, ни эта лаборатория не являются production execution evidence.

## Словарь и техническая применимость

| Термин | Значение |
|---|---|
| Request context | Данные, относящиеся к одной обработке запроса |
| Server-owned | Сервер создаёт и завершает область жизни значения |
| Propagation | Доступность значения при переходе между компонентами |
| Checkpoint / instrumentation | Точка наблюдения / добавление наблюдений |
| Correlation | Связывание записей одной операции независимо от потерянного значения |
| First-loss boundary | Первая наблюдаемая граница появления отсутствующего значения |
| Regression | Проверка, обнаруживающая возвращение причины отказа |
