# Kata: найти первую потерю контекста запроса

Сервис котировок сообщает клиенту цену либо причину отказа. Поддержка связывает ответ с обработкой по UUID из `X-Request-ID`. После рефакторинга middleware/dependency статус и JSON сохранились, но диагностический ID в ответе заменился на `missing`. Клиент видит привычную ошибку, а поддержка не может найти её путь. Новое требование — восстановить диагностику, сохранив HTTP-контракт и новый способ запуска обработки.

Пока неизвестно, не создаётся ли значение вообще, теряется ли между компонентами или неверно читается при отправке. Не начинайте с исправления заголовка. Ваша задача — получить данные, которые различат эти причины, затем доказать первую потерю и устранить её без обхода обработки.

**Scaffold не предоставляется.** Участник создаёт минимальную систему сам в отдельном рабочем каталоге либо использует собственную реализацию этого контракта. Код решения и готовый grader отсутствуют. Для диагностики с неполной информацией коллега может внести скрытый посев; при одиночной работе сначала сохраните гипотезы и план наблюдений, только потом откройте условие посева. Знание собственного посева ограничивает доказательство самостоятельности: сохраните исходные записи и сообщите reviewer, когда узнали условие.

## Контракт и минимальная сборка

Есть ровно один исследуемый путь: `GET /quote`. Query `mode` по умолчанию `ok`, разрешённые значения — `ok`, `unavailable`; `bad` используется как invalid input. Зафиксируйте следующие полные ответы:

| Вход | Status | Content-Type | JSON | Действие клиента |
|---|---:|---|---|---|
| `?mode=ok` | 200 | `application/json` | `{"quote":42}` | Использовать котировку |
| `?mode=unavailable` | 503 | `application/json` | `{"code":"quote_unavailable"}` | Различить недоступность; retry policy не проектируется |
| `?mode=bad` | 422 | `application/json` | `{"code":"invalid_query"}` | Исправить query |

В каждом ответе `X-Request-ID` содержит серверный UUID этой операции. Это часть контракта: правильные status/body не компенсируют `missing`. Входящий `X-Request-ID: untrusted-client` игнорируется. UUID нужен только для диагностики, не для authentication/authorization. Не сравнивайте UUID разных прогонов на равенство; сравнивайте ответ с созданным значением именно своего запроса.

Данные одной обработки — **контекст запроса (request context)**; здесь это единственный UUID в `ContextVar`. Внешний pure ASGI middleware вокруг FastAPI создаёт его и владеет окончательной очисткой. Затем исполняется dispatch собранного приложения: router, async dependency с `yield` в request scope, async endpoint, зарегистрированные mappings для domain exception и `RequestValidationError`. Обёртка читает контекст для заголовка на `http.response.start`. `unavailable` вызывает локальное исключение endpoint; никаких Pricing/БД/сетевых dependencies не нужно.

Один процесс, стандартный event loop и task factory, один thread; HTTPX ASGITransport, без socket server, proxy и TLS. Все пользовательские обработчики асинхронные. Сначала добейтесь рабочего контрольного пути с прямым ожиданием dispatch; посев допустим только после трёх верных ответов. Версии YAML обязательны для сравнения с авторским опытом; перенос на другую сборку требует отдельного подтверждения.

## Сначала наблюдение, затем посев

До расширенной диагностики сохраните минимум две гипотезы и для каждой — наблюдение, которое её опровергнет. Передача доступного значения между компонентами называется **propagation**. Проверять её нужно в именованных контрольных точках (**checkpoints**); добавление таких измерений — **instrumentation**. Выберите минимальный начальный набор: место после предполагаемого создания, вход следующего существенного компонента и место чтения для ответа. Если между двумя точками много действий, уточните их после первого результата.

Checkpoint `dependency-exit` наблюдается на success и error paths, потому что запись выхода размещена в `finally` вокруг `yield`. Код просто после `yield`, без `finally`, может не исполниться при вбросе исключения в генератор зависимости. Поэтому отсутствие этой записи само по себе не доказывает ошибку сборки приложения: сначала проверьте instrumentation. Это условие наблюдаемого trace, а не изменение фактического порядка разворачивания dependency stack закреплённой сборки.

Для связи записей (**correlation**) используйте независимую серверную метку операции в диагностическом scope и порядковое положение события. Сохраняйте только эту метку, имя точки, диагностическое значение и task/thread identity. Не записывайте headers, payload, token и персональные данные. Метка наблюдения не должна становиться резервным источником UUID для app или response.

<details>
<summary>Условие посева — открыть после записи гипотез; коллега может выполнить скрыто</summary>

Оставьте создание UUID во внешней обёртке. Перенесите тот же dispatch из прямого ожидания в новую дочернюю task и дождитесь её завершения. Единственный посеянный дефект — при запуске дочерней task выбран новый пустой execution context. Остальные компоненты, mapping registration, query validation и ответы не меняются. Не добавляйте ранний reset, подмену ContextVar или второй дефект.

Здесь задано изменение для воспроизводимости стенда, а не выдан диагностический trace или исправление. После сборки сначала предъявите исходный симптом. Далее подтвердите наблюдениями, какая именно граница потеряла значение и какие альтернативы отвергнуты. При оценке неизвестной причины reviewer учитывает, кто знал условие посева.

</details>

## Что требуется сделать

1. До инструментирования предскажите путь success, domain error и invalid query: где формируется ответ и кто завершает область контекста. Сопоставьте предсказание с исполнением; это результат L1.
2. Получите trace одной контрольной и одной дефектной операции с безопасной связью записей. Найдите **первую наблюдаемую потерю (first-loss boundary)** — значение присутствует в предыдущей точке и отсутствует в следующей. Отделите её от позднего `missing` и от ещё проверяемой причины.
3. Проведите различающий опыт с одним изменяемым фактором. Исправьте причину, сохранив task dispatch, dependency и error mappings. Ручное копирование UUID в endpoint или готовый response не принимается: оно не восстанавливает доступность контекста у предыдущих читателей.
4. Добавьте **регрессионную проверку (regression)**, которая падает при возврате дефекта и проходит после исправления. Проверяйте путь и полный ответ, а не отдельный mapper/endpoint call. Сохраните исходный запуск с ожидаемым нарушением как отдельный профиль; не смешивайте ожидаемое падение с ошибкой стенда.
5. Выполните группы ниже и защитите причинный вывод, альтернативу и предел доказательства; это результат самостоятельной локализации L2.

## Группы измерения и конечные пороги

Сделайте **три повтора** каждой строки. Между профилями меняется только конфигурация control/defect/fixed. Наблюдение начинается до установки контекста и заканчивается после возврата ASGI-вызова и очистки. Watchdog — 5 секунд на последовательный запрос или целую конкурентную волну; это лабораторный предел зависания, не SLO. Сохраните фактическую длительность каждой группы, не требуйте совпадения с чужими миллисекундами.

| Группа | Запросы в одном повторе | Критерий |
|---|---|---|
| control | 10 раз `ok → unavailable → bad`, последовательно | 0 потерь, правильные три ответа и порядок |
| defect | Те же 30 входов | 30 потерь на одной границе; status/media type/body сохранены, header нарушен |
| fixed | Те же 30 входов | 0 потерь; полный контракт и существенный путь сохранены |
| concurrent | 12 одновременно: 4 каждого исхода; общий barrier на входе dispatch | Все 12 одновременно достигли границы до продолжения; 0 чужих ID, 0 потерь и неверных ответов |
| recovery | После волны 5 раз `unavailable → ok → bad → ok`, последовательно, новый экземпляр той же fixed-сборки в том же процессе/event loop | 0 остатков на входе следующих операций, 0 потерь; чистая родительская граница |

Всего 366 запросов: 90/90/90/36/60 по группам. Для каждой операции сопоставляйте все её checkpoints и ответ с её UUID, а не с «каким-нибудь непустым ID». Проверяйте отсутствие значения до создания и после cleanup, завершение дочерней task до выхода родителя. Отдельно назовите границу: пустой родительский контекст и завершённая дочерняя task не означают физическое стирание памяти, проверку worker reuse или crash recovery.

Добавьте три отрицательных контроля, по одному на каждый исход: ответ сформирован с верными status/body/header, но dependency и endpoint/mapping обойдены. Проверка пути должна отвергнуть все три, хотя проверка ответа проходит. Итого с ними — 369 ASGI-вызовов. Они проверяют чувствительность регрессии к обходу, а не создают второй seeded defect для диагностики.

## Что предъявить на review

Одна команда воспроизводит группы в вашей реализации. К ней приложены версии, topology, исходные гипотезы с временем их фиксации, контрольный/дефектный/исправленный traces, матрица исходов, фактические длительности, результаты concurrent/recovery и отрицательных контролей. Decision note объясняет, почему исправлена причина, почему отвергнут ручной fallback и что остаётся вне наблюдения.

| Проверяемое действие | Достаточное подтверждение |
|---|---|
| L1: следовать заданному пути | Предсказание и trace всех трёх ветвей; места response/error и cleanup указаны |
| L2: локализовать | Минимум две исходные гипотезы, различающие наблюдения, первая потеря и причинное изменение одного фактора |
| Сохранить pipeline | Реальная сборка, существенные checkpoints, 3/3 bypass отвергнуты |
| Сохранить контракт | Method/path, status, media type, полное JSON-тело, серверный header invariant для каждой ветви |
| Изоляция и завершение | 36 конкурентных и 60 recovery операций без чужого ID/остатка; контекст очищен на каждом success/error path |

Критерии оценивают [Trace L1/L2](../../../level-outcomes.md). Они не начисляют самостоятельный production L3, lifecycle, Cancellation или Verification. Не нужны нагрузочный тест, fan-out, shutdown/cancellation policy, auth/tenant context, OpenTelemetry backend, изменение API, CI template и готовая эталонная реализация.

## Постепенные подсказки

<details>
<summary>Подсказка 1 — отделите создание от чтения</summary>

Наличие `missing` в конце не показывает, что было в начале. Получите два наблюдения одного и того же запроса по независимой метке; иначе записи разных запросов могут выглядеть как потеря.

</details>

<details>
<summary>Подсказка 2 — уточните область исполнения</summary>

Сравните task identity с обеих сторон подозреваемой границы. Одинаковый thread не доказывает общую область контекста. Проверьте также момент создания задачи относительно установки значения, прежде чем выбирать изменение.

</details>

<details>
<summary>Подсказка 3 — проверьте читателей, которые не являются endpoint</summary>

Invalid query может завершиться без endpoint. Исправление, которое полезно только после входа в endpoint, не объясняет сохранность контекста для остальных ветвей.

</details>

## Самопроверка и частые ошибки

Можно ли считать исчезновение значения в `dependency-exit` тем же дефектом, если в `dispatch-enter` оно ещё присутствует?

<details>
<summary>Ответ</summary>

Нет: это другая первая наблюдаемая граница. Ищите действие между последней точкой со значением и первым отсутствием; проверьте раннее завершение области. Не подгоняйте новый trace под ожидаемый посев. Если стенд не воспроизводит ровно заданный defect, сначала устраните ошибку сборки.

</details>

Почему хранить UUID в глобальной изменяемой переменной хуже, чем проверить передачу контекста?

<details>
<summary>Ответ</summary>

Последующий запрос может заменить значение, пока предыдущий ещё работает. Последовательный smoke test этого не покажет; barrier-wave с проверкой своего UUID покажет. Глобальный список разрешён как хранилище диагностических записей с отдельной корреляцией, но не как источник request context.

</details>

Почему нельзя объявить root cause только по паре checkpoints?

<details>
<summary>Ответ</summary>

Пара ограничивает участок поиска. Для причины нужен различающий опыт: между точками могли быть запуск другой task, ранний reset или неверный reader. Контроль и исправленная версия с одним изменённым фактором позволяют отвергнуть альтернативы. Поздний верный ответ без этого остаётся слабым подтверждением.

</details>

## Словарь и источники

| Термин | В этой kata |
|---|---|
| Request context / server-owned | UUID одной обработки, создаваемый и очищаемый сервером |
| Propagation | Доступность своего UUID после перехода между компонентами |
| Checkpoint / instrumentation | Наблюдаемая точка / добавление таких точек |
| Correlation | Независимое связывание записей одного запроса |
| First-loss boundary | Первый наблюдаемый переход к отсутствующему значению |
| Regression | Проверка возвращения причины; включает отрицательный контроль обхода |
| Recovery | Новые независимые операции после конкурентной волны и ошибок |
