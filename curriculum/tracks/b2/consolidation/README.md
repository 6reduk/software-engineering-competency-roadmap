# B2: от принятого материала к самостоятельному результату

Инженер открывает B2 перед изменением сервиса. Он видит принятые материалы по контрактам, данным, интеграциям и выпуску, но наличие задания ещё не отвечает на вопрос: «Что я должен сделать сам и чего будет достаточно для проверки?» Это досье связывает существующие маршруты с результатами самостоятельной работы и условиями отдельного решения о завершении модуля.

Основание — [G18: принятие досье](../../../../governance/reviews/M1.8.19-G18-b2-consolidation-acceptance.md) и [G19: принятие HTTP Runtime/S01](../../../../governance/reviews/M1.8.20-G19-http-runtime-acceptance.md). Snapshot 2026-09-08 включает 12 slices. Текущий refresh M1.8.21 находится в `review`; прошлое acceptance не принимает эти изменения или следующую рекомендацию. Однопрофильные исключения G18/G19 не отменяют профиль B нового review.

## Что уже есть

| Наблюдение после G19 | Что оно означает для читателя |
|---|---|
| `10/10 own content entry` | У каждого модуля есть собственный принятый содержательный вход. |
| `10/10 five-genre flow` | HTTP Runtime получил собственные index/interview/kata/project-spec; собственный R1 learn и supporting C1 включены в полный маршрут. Все десять модулей имеют пять жанров. |
| `0/10 module completion` | Ни один модуль не имеет принятого решения о завершении. Принятый slice и полный набор жанров не заменяют module gate. |

Числа учебных связей остаются в [каноническом аудите](../module-delivery-plan.md): 61 accepted artifact, 259 relationships, 58 из 69 outcomes со связями, 11 без связей и семь только с interview probe. Эти числа описывают материалы; они не измеряют умения читателя.

## Как выбрать работу

Начните с роли, найдите нужный модуль, откройте его существующий маршрут, выполните самостоятельную работу и предъявите результат для сопоставления с gate/debt. Не нужно читать все файлы подряд.

1. [Маршруты и переиспользование](routes-and-reuse.md) показывают десять входов, порядок жанров и два ролевых среза. Здесь находится единственная запись статуса каждого маршрута.
2. [Готовность самостоятельной реализации](implementation-readiness.md) помогает перейти от выбранного project-spec к своему репозиторию и проверяемому результату.
3. [Карточки module gates](module-gates.md) показывают требуемые действия, имеющиеся основания и недостающие подтверждения. Здесь находится единственная запись текущей готовности каждого gate.
4. [Реестр долга](debt-register.md) объясняет причину каждого ограничения, владельца concern, условие закрытия и повод выделить будущий пакет. Локальный debt ID определяется только в этом реестре.

Весь B2 baseline нужен тому, кто претендует на системное владение backend в одной из двух [RoleViews](../role-requirements.md): нужно уметь действовать на всех обязательных границах, даже если часть умений уже подтверждена другой работой. Для инженера, решающего одну локальную задачу, достаточно выбранного маршрута и его prerequisites. Это не отменяет остальных требований роли и не превращает список материалов в обязательный линейный курс. Архитектору с backend-специализацией тоже нужны действия L3; обязательные L4 определяются конкретными role requirements, а не заголовком трека.

## Словарь и границы доказательства

<a id="terms"></a>

- **Учебная связь (`coverage`)** связывает artifact с capability/outcome; она не является выполненной работой. В metadata досье такие связи отсутствуют.
- **Наблюдаемый результат (`evidence`)** — результат выполненной деятельности: например, журнал исходного отказа и исправленного прогона. Спецификация только требует получить его.
- **Подтверждённая способность (`proficiency`)** — вывод о способности конкретного участника по проверенным действиям и объяснению решений.
- **Входная готовность (`readiness`)** — выполненные условия допуска к конкретной работе и её среде. Авторский Gate 0 не подтверждает автоматически среду участника.
- **Module gate** — отдельное решение по совокупности подтверждений и scope модуля. Готовность к рассмотрению не означает принятия.
- **ImplementationReference** — зарегистрированная ссылка на самостоятельно выполненную и проверенную реализацию. Project-spec и удалённый авторский стенд такой ссылкой не являются.

Основные ограничения остаются видимыми: [исполнение HTTP tracing после закрытия content D19/D20](debt-register.md#d20), [11 uncovered](debt-register.md#outcome-debt), [семь probe-only](debt-register.md#probe-debt), реальное применение соглашений несколькими командами и [отсутствие ImplementationReference](debt-register.md#d26). Локальная лаборатория не даёт L4 adoption от количества названных в ней «команд».

## Проверка собственного выбора

Достаточно ли реализовать Pricing L2, чтобы заявить владение медленной зависимостью L3?

<details>
<summary>Ответ и следующий переход</summary>

Нет. Pricing сохраняет различие пустого успеха и сбоя одного HTTP-вызова. Для L3 нужны самостоятельные решения о деградации и проверяемые отказы, уже заданные runtime-проектом. Откройте [маршрут External](routes-and-reuse.md#external), затем предъявите результаты соответствующего проекта. Ни один из двух project-spec сам по себе не является выполнением или module gate.

</details>

## Одно следующее действие и выход из consolidation

Рекомендуется **один B3 boundary intake на границе application transaction и store isolation**. Каноническое [сравнение трёх вариантов и decision brief](../module-delivery-plan.md#сравнение-следующей-фазы) задаёт владельца concern, prerequisites, non-goals и exit trigger; досье не создаёт второй план выбора или coverage registry.

B2 completion-tail S12 (D21) полезен обеим ролям, но отдельный механизм относительно fan-out и применимая B7 readiness ещё не установлены. HTTP Runtime теперь имеет полный маршрут, однако пакет подготовки его gate не близок к решению: нет самостоятельных tracing/resource результатов, остаются production L3/S02 и conditional L4. B3 intake использует существующий track scope для одного следующего управленческого результата, сохраняя явный B2 debt.

S01 больше не будущий content package: [D19](debt-register.md#d19) content/navigation и [D20](debt-register.md#d20) content/exercise закрыты G19. Открыты исполнение участником, review и возможная ImplementationReference; для всех двенадцати проектов это [D26](debt-register.md#d26). Все десять [gate cards](module-gates.md) остаются not-ready-for-gate: задания и авторские Gate 0 не заменяют выполненные проекты и независимо проверенные реализации. Применимое L4 требует реального adoption/migration.

Выход следующего intake — один reviewable документ с границей B2/B3, одним будущим store-level действием, readiness-условиями, наблюдаемым результатом и разрешённым ownership. Новые semantic IDs, content, реализации и module-gate decisions не входят в него. Назначение и принятие — отдельные решения оркестратора после review. Возврат к B2 вызывается конкретным trigger D01–D27, а не числом partial; бесконечная consolidation-фаза не назначается.

Блокирующих вопросов для Handoff M1.8.21 нет. Для независимого review нужны пересчёт YAML и DAG, оба ролевых перехода к новому S01 маршруту, audit trail D19/D20, двенадцать readiness-карточек, десять gate cards и обоснованность единственного следующего выбора. G19 ограничения и отсутствие независимого профиля B в прошлом сохраняются; текущий авторский self-check не является acceptance.
