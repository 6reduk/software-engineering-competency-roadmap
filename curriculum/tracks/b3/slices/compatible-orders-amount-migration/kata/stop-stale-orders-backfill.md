# Сумма исправлена пользователем, но перенос ещё помнит старую

В Orders оператор исправляет суммы заказов через старое приложение. Новая версия принимает копейки, поэтому команда добавляет к рублям новое представление и переносит существующие строки. Пользователь должен увидеть своё подтверждённое изменение в обеих версиях. Перенос, который захватил 10000 до изменения на 12000, не имеет права вернуть старую сумму.

Вы самостоятельно создаёте минимальную SQL-среду и оснастку управляемых барьеров. Стартового приложения, готового trigger, преобразования на пути приложения (`adapter`) и fixed SQL нет. Задача ограничена одной таблицей и заданными контрактами: воспроизвести двухшаговый дефект, найти первое неверное решение, обеспечить корректный результат и безопасный повтор пачки. Полноценный migration framework не нужен.

## Заданный договор

`orders`: `order_id` — ключ, `amount_rub numeric(12,2)` — обязательные рубли; `amount_minor bigint` добавляется nullable. Одна валюта, без DELETE и других таблиц. Диапазон 0,00…9999999999,99, точное значение без округления. W-old передаёт только рубли; избыточная точность отвергается до SQL внешним входным договором, отрицательная сумма также запрещена store. W-new принимает только целые копейки того же диапазона и записывает оба представления одной атомарной операцией. Тип numeric сам по себе не доказывает отвержение лишней точности.

R-old читает явно названные рубли по ID. R-new получает оба поля, использует рубли только при NULL нового; заполненное расхождение — ошибка. Последняя подтверждённая W-old/W-new команда определяет правильную сумму. Подтверждение технической копии не меняет независимый ожидаемый набор из входных команд и подтверждений (`oracle`). Механизм совместимости должен сохранять старый INSERT/UPDATE, включая конечную обязательность копеек.

| Состояние | R-old/W-old | R-new/W-new | Условие |
|---|---|---|---|
| Только рубли | Допустимы | Отказ из-за отсутствующего столбца | Проверить старый доступ и отрицательный новый |
| Nullable-столбец | Допустимы | Выключены | Новый столбец не выдаётся за готовые данные |
| Сосуществование/backfill | Допустимы с совместимостью | Переходное чтение/атомарная пара | Совместимость включена раньше действия ограничения на запись (`enforcement`) |
| Сверка/validation | Защищены непрерывно | Договор сохранён | Все ключи и суммы сверены, ограничение проверено |
| Обязательные копейки, рубли сохранены | Всё ещё допустимы | Допустимы | Отказы неверных записей проверены, старый путь не удалён |

Ваша реализация проверяет заданную матрицу, а не меняет её ради прохождения. В плане перехода объясните условия входа и отмены каждого шага. Это самостоятельная ограниченная работа, хотя предметный договор уже задан.

## Заранее заданные строки (`fixtures`) и независимый результат

Создайте исходные ID 1–4 со значениями из второго столбца. Четыре текущих команды имеют фиксированный смысл и выполняются между барьерами прохода.

| ID | Исходные рубли | Текущая команда | Итоговые копейки |
|---|---:|---|---:|
| 1 | 0.00 | Нет | 0 |
| 2 | 100.00 | W-old UPDATE →120.00 | 12000 |
| 3 | 12.34 | W-new UPDATE →1300 копеек | 1300 |
| 4 | 9999999999.99 | Нет | 999999999999 |
| 5 | Строки нет | W-old INSERT →7.89 | 789 |
| 6 | Строки нет | W-new INSERT →2501 копейка | 2501 |

Этот набор плюс подтверждения команд, а не SELECT результата backfill, задаёт oracle. Для каждого подтверждённого write сохраните чтение после подтверждения (`readback`). Перед финальной сверкой дождитесь завершения текущих команд; сравните все ID в обе стороны, NULL и значения. Это короткое окно чтения не разрешает убрать конкурентную запись из опыта.

## Seeded defect: два разных шага

Ниже только ошибочное действие. Между командами обязателен барьер подтверждённого W-old; константа взята из результата первого шага, а не вычисляется заново.

```sql
-- Шаг 1, backfill: сохранить результат 10000 в оснастке.
SELECT (amount_rub * 100)::bigint
FROM orders WHERE order_id = 2;
-- Барьер: отдельный W-old подтвердил amount_rub = 120.00.
-- Шаг 2, backfill: попытаться применить сохранённые 10000.
UPDATE orders SET amount_minor = 10000 WHERE order_id = 2;
```

Первое неверное решение — считать захваченное значение пригодным для применения после нового подтверждения. При действующей защите эта попытка может быть отвергнута, а не применена. До полного запуска закрепите isolation backfill/W-old, объявите ожидаемый исход и подтвердите короткой пробой. Проверенная автором модель на Read Committed даёт `23514`. Если ваш механизм молча превращает эту попытку в исправленный прогон (`Fixed`), различающий дефект ещё не построен: остановитесь и исправьте постановку опыта, не объявляя воспроизведение.

## Что выполнить и передать

1. Запишите план пяти состояний и условия возврата. По заданной матрице объясните несовместимые клетки; затем проверьте чтение, INSERT и UPDATE всех разрешённых путей, отделив откатываемые диагностические пробы от предметных команд.
2. Выполните контрольный прогон (`Control`) на чистом наборе без конфликтующего захвата и применения. Между пачками идут те же четыре текущие записи. Он должен показать, что ваша защита не запрещает завершение всегда.
3. Выполните дефектный прогон (`Defect`): capture 10000 → подтверждение 12000 → отдельная попытка 10000. Сохраните реальный SQLSTATE/расхождение и отсутствие автоматического следующего этапа.
4. Выполните Fixed на чистом наборе с теми же барьерами и oracle. Самостоятельно защитите применение; нельзя убрать W-old UPDATE или заменить ожидаемые 12000 на 10000. Отдельно покажите, что список ID 1–4 не включает поздний ID 5, даже если новое поле уже заполнено механизмом совместимости.
5. После commit пачки остановите backfill, сохраните строки, закройте его соединение. Возобновите с новым соединением и повторите ту же пачку. Сверьте не счётчик, а неизменность правильных значений; затем завершите перенос и обязательность.

Повторите каждый профиль дважды. Приложите собственные команды, fixtures, параметры, журнал барьеров и readback, точные версии и хэши вместе с исходными файлами. Готового решения в скрытых ответах нет.

## Ограниченный контур измерений

Один PostgreSQL, шесть соединений: W-old, W-new, backfill, DDL/validation, observer, писатель приложения (`writer`) для lock-пробы. Чтения выполняются через соответствующую версию. Пачка ≤2 строки; 4 исходные строки и 4 текущих write. Измеряйте каждый SQL round-trip у клиента и весь профиль отдельно. Базовые лабораторные предохранители (`guardrails`): 2 с на SQL, 60 с на профиль; для воспроизведения авторской lock-пробы lock_timeout=1,5 с. Настройка/запуск среды в эти времена не входят. До запуска обоснуйте замену чисел, если ваша выделенная среда требует её; не меняйте их после неудачи, чтобы скрыть отказ.

Диагностическая lock-проба задана: удерживаемый UPDATE и SET NOT NULL. Покажите владельца RowExclusiveLock, ожидающий AccessExclusiveLock, `granted=false`, pg_blocking_pids и wait event, bounded отказ `55P03`, освобождение и отдельный повтор. Не переносите этот конфликт на VALIDATE без проверки режима. Эта заданная диагностика входит в L2 и не превращает kata в L3.

Stop обязателен при расхождении, неизвестном writer/подтверждении, нарушенном барьере, неожиданной ошибке или превышении лимита. После него следующая стадия не вызывается. Сначала установите судьбу последней операции; reset нельзя выдавать за resume.

## Критерии самопроверки

Результат пригоден к передаче, если полный набор содержит ровно ID 1–6 с заданными копейками, нет NULL, лишних/пропущенных ID, расхождений или потери подтверждённых write. Отдельные пробы неверной пары, NULL, отрицательной суммы, верхнего переполнения и избыточной точности проверяют разные части договора. Ноль и максимум должны успешно сохраняться. W-new не виден другим сеансам частично; W-old остаётся допустимым после обязательности. Старое поле не удалено.

L1 проверяется вашим объяснением несовместимого доступа, неполного списка и lock-следа. L2 — самостоятельным планом, исполнением, сверкой, прерыванием/продолжением и доказанным stop. Поясните, как вернуться к старому приложению, сохранив подтверждённые новые суммы в рублях. Качество рассказа не заменяет след исполнения.

<details>
<summary>Подсказка 1: что разделить в наблюдениях</summary>

Назовите отдельно момент захвата, подтверждение бизнес-команды и применение технической копии. Затем сравните каждый с readback. Один общий лог «обработан заказ» скрывает важный порядок.

</details>

<details>
<summary>Подсказка 2: где искать условие безопасности</summary>

Исследуйте, что должно оставаться истинным между чтением и применением, и кто поддерживает согласованность после следующего старого UPDATE. Это связанные, но разные обязанности переноса и совместимости текущих путей.

</details>

<details>
<summary>Подсказка 3: почему может не хватить списка ID</summary>

Список фиксирует прошлую популяцию. Сравните его с таблицей после позднего INSERT. Повтор пачки и обнаружение новых строк требуют отдельных наблюдений; «пачка прошла» не доказывает полноту.

</details>

После сохранения доказательств откатите открытые транзакции, закройте свои соединения, удалите только объекты выделенного опыта и подтвердите отсутствие их locks. Не нужны API, ORM, третья версия приложения, deployment, удаление рублей, BR01 или production migration.

## Термины и источники

Backfill — технический перенос; oracle — ожидаемые строки из входных команд; validation — проверка ограничения; readback — чтение после подтверждения; barrier — управляемая точка порядка; resume сохраняет незавершённое состояние, reset его заменяет.

Для работы psql с явными транзакциями: [psql](https://www.postgresql.org/docs/18/app-psql.html). Локальный опыт не доказывает production latency или proficiency участника.
