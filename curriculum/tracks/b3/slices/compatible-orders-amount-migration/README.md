# Перенести суммы заказов, пока старое приложение продолжает писать

Старая версия Orders хранит сумму в рублях. Новая работает с целыми копейками, а в таблице уже есть заказы, которые нужно перенести. Пользователь меняет 100,00 на 120,00 в тот момент, когда перенос ещё держит прочитанные 10000 копеек. Если применить эту техническую копию как новое бизнес-значение, новая версия покажет устаревшую сумму. Если ограничение отвергнет копию, подтверждённая сумма сохранена, но перенос всё ещё не завершён.

Этот маршрут учит связывать промежуточные состояния схемы с допустимым доступом, текущими записями и проверкой результата. Пакет принят после G26 и correction-pass M1.9.5a. Принятие материалов не означает выполнения заданий или принятия результатов участника.

## Что понадобится

Нужно уметь читать небольшую таблицу по ключу, выполнять SELECT/INSERT/UPDATE, отличать соединение от транзакции, commit от отправки команды и rollback от повторного запуска. Для практики требуется выделенный PostgreSQL с правами на свои объекты и наблюдение блокировок. Стартового приложения нет: минимальную SQL-среду участник создаёт самостоятельно; Python нужен только при выборе такой оснастки.

Маршрут развивает две [способности B3](../../capabilities.md): планировать совместимые переходы схемы и проводить ограниченное изменение данных. Сначала определите допустимые состояния, затем выполняйте перенос. В [каталоге prerequisites](../../prerequisites.md) это записано как зависимость `validate-online-data-change → plan-compatible-schema-transitions`; направление изучения обратное, `plan → validate`. Нового требования пройти весь SQL-модуль нет.

## Один договор во всех материалах

Таблица `orders` имеет `order_id`, обязательные рубли `amount_rub numeric(12,2)` и добавляемые копейки `amount_minor bigint`. Разрешены точные суммы 0,00…9999999999,99 без округления. Старое чтение/запись называются R-old/W-old; новые — R-new/W-new. Старый писатель приложения (`writer`) посылает только рубли, новый атомарно сохраняет пару. Новое чтение использует рубли только при NULL нового столбца; заполненное расхождение считается ошибкой.

Перенос существующих строк (backfill) не может отменить последнее подтверждённое изменение приложения. Независимый ожидаемый набор (oracle) после четырёх текущих записей: ID 1–6 → `0,12000,1300,999999999999,789,2501` копеек. Проверяются все ключи и значения, а не только процент прохода.

Пять состояний: только рубли → nullable-столбец → сосуществование с защитой текущих записей → полная сверка и проверка ограничения → обязательные копейки при сохранённом старом пути. Проверка ограничения хранилища (validation) и сверка с oracle отвечают на разные вопросы.

## Проверенная основа и предел результата

Авторский локальный опыт на PostgreSQL/psql 18.6 различил контрольный (`Control`), дефектный (`Defect`) и исправленный (`Fixed`) прогоны, каждый дважды. В Defect сохранённые 10000 отвергались с `23514`, сумма 12000 сохранялась; в Fixed перенос завершался. Проверены поздние INSERT, повтор пачки, восстановление после закрытия backfill-соединения и реальное ожидание DDL с `55P03`. Пределы малого опыта: ≤2 строки в пачке, 2 секунды на SQL-операцию, 60 секунд на профиль; это не эксплуатационные SLO. Источники и применимость разобраны в методичке.

B3 отвечает за данные, состояния, DDL и локальные блокировки. B2 подтверждает контракты приложения и состав потребителей, B6 предоставляет среду и оркестрацию развёртывания, B7 принимает production stop/go. Неизвестный writer требует остановки и выяснения его контракта. Удаление `amount_rub`, production cutover, BR01, L4/L5 и завершение всего модуля в маршрут не входят.
