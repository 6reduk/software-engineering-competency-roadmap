# Исправить финансовую сводку без потери пустых заказов

Финансовая команда пользуется Orders report для сверки покупок и платежей. После добавления платежей стоимость заказа 1 стала 400 вместо 200. Заказов по-прежнему четыре, поэтому проверка только числа строк ошибку не обнаружила. Новое требование — выдавать по каждому заказу точные суммы, остаток и ранг, сохраняя неоплаченные и пустые заказы.

Ваша ограниченная задача — воспроизвести ошибку, найти первый этап размножения строк и самостоятельно написать корректный SQL. Стартового приложения и стартового каркаса (scaffold) нет: минимальную SQL-среду, файлы запуска и проверки создаёт участник вне этого учебного каталога. Готовое исправление не предоставляется. Нужны PostgreSQL/psql 18.6 и умение запустить SQL в отдельной тестовой базе; Python необязателен.

## Фиксированный договор

Канонические данные: `orders = {1,2,3,4}`; строки `(line_id, order_id, amount)` — `(101,1,100)`, `(102,1,100)`, `(103,2,50)`, `(104,4,200)`; платежи `(payment_id, order_id, amount)` — `(201,1,60)`, `(202,1,40)`, `(203,4,200)`. Две строки по 100 — разные покупки, а не дубликат записи. Заказ 2 не оплачен, заказ 3 пуст, заказ 4 полностью оплачен и равен заказу 1 по стоимости.

Договор сводки: одна строка на каждый заказ, включая пустой. `line_count` и `payment_count` считают реальные дочерние записи; `line_total` и `paid_total` складывают их суммы. Все деньги — целые minor units (минимальные денежные единицы одной валюты). Отсутствие строк или платежей означает нулевые число и сумму; это локальное правило отчёта, а не общее равенство `NULL = 0`. Исходные суммы обязательны (`NOT NULL`): неизвестная сумма платежа не допускается. `NULL` в этом наборе возникает из отсутствующего совпадения при outer join.

`balance = line_total - paid_total`: положительное значение — недоплата, отрицательное — переплата; нулевой остаток пустого заказа не означает состоявшуюся оплату. `total_rank` ранжирует по `line_total` по убыванию без пропусков между различными суммами: равным суммам — одинаковый ранг. Выдача отдельно упорядочена по `line_total DESC, order_id ASC`; ID не входит в смысл равенства рангов.

Ожидаемые строки в порядке выдачи:

| order_id | line_count | line_total | payment_count | paid_total | balance | total_rank |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 2 | 200 | 2 | 100 | 100 | 1 |
| 4 | 1 | 200 | 1 | 200 | 0 | 1 |
| 2 | 1 | 50 | 0 | 0 | 50 | 2 |
| 3 | 0 | 0 | 0 | 0 | 0 | 3 |

## Схема и исходные данные

Эти временные таблицы позволяют повторять упражнение в новых psql-сессиях, не сохраняя учебные данные. Выполните схему, запросы и проверки в одной сессии; после её завершения TEMP-таблицы исчезнут. Данные намеренно небольшие, чтобы ожидаемые суммы можно было проверить вручную.

```sql
CREATE TEMP TABLE orders (order_id integer PRIMARY KEY);
CREATE TEMP TABLE order_lines (
  line_id integer PRIMARY KEY,
  order_id integer NOT NULL REFERENCES orders,
  amount bigint NOT NULL CHECK (amount >= 0)
);
CREATE TEMP TABLE payments (
  payment_id integer PRIMARY KEY,
  order_id integer NOT NULL REFERENCES orders,
  amount bigint NOT NULL CHECK (amount >= 0)
);
INSERT INTO orders VALUES (1), (2), (3), (4);
INSERT INTO order_lines VALUES (101,1,100), (102,1,100), (103,2,50), (104,4,200);
INSERT INTO payments VALUES (201,1,60), (202,1,40), (203,4,200);
```

Исходные ключи различают записи с равными суммами; FK задают принадлежность заказу. Общая нормализация и проектирование схемы здесь не оцениваются.

Ниже единственный дефектный запрос упражнения. Он возвращает базовые показатели; остаток и ранг участник добавляет в собственное решение по договору выше.

```sql
SELECT o.order_id,
       COUNT(l.line_id) AS line_count, COALESCE(SUM(l.amount),0) AS line_total,
       COUNT(p.payment_id) AS payment_count, COALESCE(SUM(p.amount),0) AS paid_total
FROM orders o
LEFT JOIN order_lines l ON l.order_id = o.order_id
LEFT JOIN payments p ON p.order_id = o.order_id
GROUP BY o.order_id
ORDER BY o.order_id;
```

У заказа 1 он возвращает `(1,4,400,4,200)`. У заказов 2,3,4 базовые показатели совпадут с ожидаемой таблицей. Это делает дефект опасным: проверка только пустых заказов или одного платежа его не обнаружит.

## Что предъявить на проверку

1. Команду воспроизведения на чистой базе и точные версии сервера/adapter. При psql используйте `-X -v ON_ERROR_STOP=1`: первый параметр исключает startup-файлы psql, второй завершает неинтерактивный запуск при SQL-ошибке с кодом 3 ([документация psql 18](https://www.postgresql.org/docs/18/app-psql.html), проверено 2026-09-10).
2. Вывод исходного запроса и четыре пары `(line_id,payment_id)` заказа 1. Подпишите гранулярность — смысл строки — до JOIN, после JOIN, после агрегации и на входе окна.
3. Собственный SQL и автоматическую сверку всех семи полей ожидаемых четырёх строк в договорном порядке. Ожидаемую таблицу задайте независимо от join решения; один общий checksum недостаточен.
4. Три чистых прогона с одинаковыми результатами. Перезапуск должен пересоздавать данные, а ошибка SQL или несовпадение строки завершать проверку неуспехом. Сохраните отчёт различий и удалите временную среду после работы.
5. Короткое объяснение, почему выбранная композиция считает каждую покупку и платёж один раз. Полный запрет платежей или исключение пустого заказа не считается исправлением.

## Матрица самопроверки

| Случай | Наблюдение, которое нужно получить | Почему проверяем |
|---|---|---|
| 2×2, заказ 1 | Четыре промежуточные пары, но в итоге counts 2/2 и суммы 200/100 | Находит размножение независимых отношений |
| Нет платежа, заказ 2 | Одна строка, paid_total=0, balance=50 | Не позволяет WHERE потерять заказ |
| Пустой заказ 3 | Одна строка с нулевыми counts/суммами, ранг 3 | Проверяет полный набор orders |
| NULL отсутствующего совпадения | На orders LEFT JOIN payments для 3: COUNT(*)=1, COUNT(payment_id)=0, SUM(amount)=NULL; amount > 50 не истинно | Отличает строку соединения от реального платежа |
| Равные реальные стоимости | Покупки 101/102 обе учитываются: 100+100=200 | Отвергает SUM(DISTINCT amount) |
| Равные итоги | 1 и 4 получают общий ранг 1, следующий ранг 2; выдача 1,4,2,3 | Разделяет peers и порядок отображения |
| Три новых сессии | Полная таблица каждый раз одинакова | Отделяет чистое воспроизведение от остаточного состояния |
| Пустой orders, дополнительный вход | Ноль строк отчёта | Не допускает синтетический «нулевой заказ» |

Также сравните диагностический фильтр `p.amount > 50` в ON и в WHERE: в первом случае остаются order_id 1,2,3,4, во втором 1,4. Не включайте этот фильтр в основной отчёт: его договор учитывает все платежи. PostgreSQL допускает UNKNOWN у сравнения с NULL; это не ошибка выполнения.

Для L1 проверяющий просит с поддержкой проследить пары, NULL и различие агрегации/окна, включая влияние равных значений порядка (ties). Для L2 участник самостоятельно получает и проверяет весь результат по фиксированному договору. Эти действия соответствуют [составлению запросов](../../../level-outcomes.md#compose-relational-queries) и [агрегатам/окнам](../../../level-outcomes.md#derive-grouped-window-results). Выполнение не начисляется по наличию файла SQL: нужны наблюдения и независимая сверка. L3 здесь не заявлен — разрешение неоднозначных требований вынесено в проект.

## Постепенные подсказки

<details>
<summary>1. От какой строки отталкиваться</summary>

Начните с фразы «одна строка представляет…» для каждого этапа. Сравните требуемую строку заказа с парами line_id/payment_id до SUM. Совпадение числа итоговых заказов не отвечает на вопрос, сколько раз учтён каждый amount.

</details>

<details>
<summary>2. Как отличить реальную запись от сохранённой строки</summary>

Для заказа 3 выведите правый идентификатор после LEFT JOIN и сопоставьте COUNT(*) с COUNT этого ID. Отдельно установите, какой бизнес-смысл позволяет получить ноль из отсутствия платежей. Неизвестная сумма существующей записи была бы другой задачей.

</details>

<details>
<summary>3. Какие классы решений сравнить</summary>

Проверьте независимые агрегаты каждого дочернего отношения, подзапросы и именованные промежуточные этапы. Для каждого докажите, что на стадии сборки заказа вклад покупки или платежа возникает один раз. Затем определите вход окна. Конкретную структуру SQL выберите сами.

</details>

Гранулярность — смысл строки; fan-out — размножение строк при соединении; peers — равные по оконному показателю строки; oracle — ожидаемые данные, рассчитанные отдельно от решения. Разбор механизма есть в [brief](../learn/join-cardinality-and-result-grain.md), развитие самостоятельности — в [проекте](../project-spec/orders-financial-summary.md). Планы, индексы, приложение, ORM, аналитический pipeline и изоляция транзакций не входят в kata.

## Источники и актуальность

Проверено 2026-09-09 на PostgreSQL/psql 18.6. [Таблица поддержки](https://www.postgresql.org/support/versioning/) подтверждает текущую stable-ветку 18 и minor 18.6 на эту дату; это воспроизводимый учебный baseline, а не автоматический выбор production-версии.

- [Соединения, фильтры и группировка](https://www.postgresql.org/docs/18/queries-table-expressions.html) задают состав промежуточных строк.
- [Aggregate expressions](https://www.postgresql.org/docs/18/sql-expressions.html#SYNTAX-AGGREGATES) различает COUNT(*)/COUNT(column) и DISTINCT над значениями; [aggregate functions](https://www.postgresql.org/docs/18/functions-aggregate.html) описывает NULL у SUM пустого входа.
- [Сравнения с NULL](https://www.postgresql.org/docs/18/functions-comparison.html) объясняют неизвестный результат предиката.
- [Оконные функции](https://www.postgresql.org/docs/18/functions-window.html) определяют равные ранги peers, а [ORDER BY](https://www.postgresql.org/docs/18/queries-order.html) — отдельный порядок выдачи.
- [Оконные функции в запросе](https://www.postgresql.org/docs/18/tutorial-window.html): оконная функция выполняет вычисление по связанным строкам, не сворачивая их в одну строку, и видит виртуальную таблицу после `WHERE`, `GROUP BY` и `HAVING`.

Правила о составе строк и вычислениях выше — семантика PostgreSQL. Сохранение всех заказов, нулевая сумма отсутствующих платежей и ранги без пропусков — локальные решения этого отчёта. Выбор раздельных этапов — инженерный вывод из кратности; превосходство по скорости не заявлено.
