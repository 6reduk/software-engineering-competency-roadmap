# Сумма выросла, данные не изменились

Финансовая команда сверяет заказы с поступившими платежами. Разработчик добавляет payments к запросу orders/order_lines и получает удвоенную стоимость заказа 1. SQL выполняется без ошибки, число итоговых заказов выглядит верно, но финансовый отчёт уже нельзя использовать. Проверять надо смысл строк, которые дошли до SUM, а не только синтаксис или количество строк после GROUP BY.

## Сначала договор результата

Канонические данные: `orders = {1,2,3,4}`; строки `(line_id, order_id, amount)` — `(101,1,100)`, `(102,1,100)`, `(103,2,50)`, `(104,4,200)`; платежи `(payment_id, order_id, amount)` — `(201,1,60)`, `(202,1,40)`, `(203,4,200)`. Две строки по 100 — разные покупки, а не дубликат записи. Заказ 2 не оплачен, заказ 3 пуст, заказ 4 полностью оплачен и равен заказу 1 по стоимости.

Договор сводки: одна строка на каждый заказ, включая пустой. `line_count` и `payment_count` считают реальные дочерние записи; `line_total` и `paid_total` складывают их суммы. Все деньги — целые minor units (минимальные денежные единицы одной валюты). Отсутствие строк или платежей означает нулевые число и сумму; это локальное правило отчёта, а не общее равенство `NULL = 0`. Исходные суммы обязательны (`NOT NULL`): неизвестная сумма платежа не допускается. `NULL` в этом наборе возникает из отсутствующего совпадения при outer join.

`balance = line_total - paid_total`: положительное значение — недоплата, отрицательное — переплата; нулевой остаток пустого заказа не означает состоявшуюся оплату. `total_rank` ранжирует по `line_total` по убыванию без пропусков между различными суммами: равным суммам — одинаковый ранг. Выдача отдельно упорядочена по `line_total DESC, order_id ASC`; ID не входит в смысл равенства рангов.

Ожидаемые строки в порядке выдачи:

| order_id | line_count | line_total | payment_count | paid_total | balance | total_rank |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 2 | 200 | 2 | 100 | 100 | 1 |
| 4 | 1 | 200 | 1 | 200 | 0 | 1 |
| 2 | 1 | 50 | 0 | 0 | 50 | 2 |
| 3 | 0 | 0 | 0 | 0 | 0 | 3 |

## Что именно размножилось

Гранулярность результата (grain) отвечает на вопрос «что представляет одна строка». У order_lines это отдельная покупка с line_id, у payments — отдельный платёж с payment_id. В сводке нужна строка заказа. Кратность соединения — число подходящих записей справа на одну запись слева; JOIN не знает, что суммы двух независимых отношений нельзя повторять.

Для заказа 1 можно проследить все строки до агрегирования:

| line_id | line amount | payment_id | payment amount |
|---:|---:|---:|---:|
| 101 | 100 | 201 | 60 |
| 101 | 100 | 202 | 40 |
| 102 | 100 | 201 | 60 |
| 102 | 100 | 202 | 40 |

Получилась гранулярность «пара строка заказа × платёж», а не строка покупки. Каждая стоимость встречается дважды; каждый платёж тоже дважды. Суммы становятся 400 и 200. GROUP BY order_id объединит эти четыре строки в одну, но не восстановит сведения о том, какие повторы внесло соединение. При двух независимых LEFT JOIN число промежуточных строк одного заказа равно `max(число строк заказа,1) × max(число платежей,1)`, если других условий соединения нет. Для заказов 1,2,3,4 это 4,1,1,1.

## Сохранённая строка ещё не является платежом

LEFT JOIN оставляет заказ без совпадения, дополняя правые поля NULL. Поэтому у заказа 3 COUNT(*) после соединения с payments равен 1, а COUNT(p.payment_id) — 0. Первый считает промежуточную строку, второй — ненулевые идентификаторы реальных платежей. SUM(p.amount) равен NULL; ноль в отчёте появляется из явно выбранного правила отсутствия платежей. Если бы сумма реального платежа могла быть неизвестна, её нельзя было бы молча трактовать как отсутствие денег.

NULL означает отсутствие значения, а сравнение с ним может дать UNKNOWN, то есть неизвестный результат. Например, `p.amount > 50` для отсутствующего платежа не истинно. WHERE оставляет только истинные условия. Чтобы увидеть практическое различие, сравните диагностические запросы:

```sql
SELECT o.order_id, p.payment_id
FROM orders o LEFT JOIN payments p
  ON p.order_id = o.order_id AND p.amount > 50
ORDER BY o.order_id, p.payment_id;

SELECT o.order_id, p.payment_id
FROM orders o LEFT JOIN payments p ON p.order_id = o.order_id
WHERE p.amount > 50
ORDER BY o.order_id, p.payment_id;
```

Первый оставляет `(1,201),(2,NULL),(3,NULL),(4,203)`: он выбирает подходящие платежи, сохраняя каждый заказ. Второй возвращает только `(1,201),(4,203)`: он отбирает строки уже соединённого набора. Оба запроса могут быть осмысленными для разных требований. Ни один не является полным финансовым отчётом нашего договора, где учитываются все платежи, включая 202 с суммой 40.

## Почему маскировка повторов не исправляет смысл

SELECT DISTINCT после группировки ничего не изменит: строки заказов уже различны. COUNT(DISTINCT line_id) способен восстановить число покупок, но не делает SUM(amount) корректной. SUM(DISTINCT amount) складывает различные стоимости: у заказа 1 получится 100 вместо 200, потому что две реальные покупки стоят одинаково. Дополнительный GROUP BY line_id/payment_id меняет гранулярность результата; это может быть полезным промежуточным этапом, но требует доказать последующее сведение к заказу. Случайный набор ключей не даёт такого доказательства.

Хорошая практика — перед каждым этапом подписать смысл строки и уникальный ключ, затем проверить их на данных. Плохая — добавлять DISTINCT, пока одно число не совпадёт, или делить сумму на наблюдаемое число платежей. Последнее скрывает проблему на 2×2 и ломается на заказах без платежа или при другой кратности.

## Варианты композиции и их цена

Чтобы суммы не повторялись, каждое независимое отношение должно дать свой вклад ровно один раз. Можно предварительно агрегировать строки и платежи по order_id, затем соединить две сводки с orders. Промежуточный договор прост: не более одной строки каждого вида на заказ. Можно вычислять скалярные агрегаты коррелированными подзапросами для каждого заказа: область входа каждой суммы видна рядом с выражением. Обычный подзапрос может оформить ту же предварительную сводку без CTE. Можно разделить вычисления на именованные этапы с проверяемыми промежуточными результатами.

У предварительной агрегации удобны проверки уникальности order_id; у коррелированных выражений — локальность смысла, но много показателей может дублировать условия и усложнить изменение. Раздельные этапы помогают диагностике, но требуют поддерживать договоры между ними. CTE — форма записи, а не автоматическая гарантия корректности или скорости. Для данного отчёта важнее показать, почему каждый вклад учтён один раз, чем выбрать универсально «лучший» синтаксис.

На L3 появляется неоднозначность: «показывать оплаченные заказы» может означать только заказы с платежом либо все заказы с показателем оплаты. До выбора ON/WHERE нужно записать оба смысла и различающую строку, например заказ 2. Подзапрос, проверяющий существование платежа, выражает условие включения заказа; агрегатный подзапрос вычисляет показатель. Эти задачи нельзя смешивать только ради короткого запроса. После согласования смысла сравнивают варианты композиции по ясности условий, сохранению пустых групп и удобству проверки; ускорение здесь не доказательство.

## Группа и окно решают разные задачи

GROUP BY сводит строки одной группы к итоговой строке. Оконная функция вычисляет значение для каждой строки своего входа, сохраняя их. Если окно получило размноженные пары, четыре строки заказа 1 останутся четырьмя строками; оконная сумма тоже может оказаться завышенной. Поэтому ранг нашего отчёта вычисляется на уровне уже готовых заказов.

Равные значения оконного порядка называют peers. Здесь 1 и 4 имеют стоимость 200 и общий ранг 1; следующая стоимость 50 получает 2. Это смысл dense_rank, тогда как rank дал бы следующей группе 3, а row_number назначил бы каждой строке отдельный номер. Добавление order_id внутрь порядка ранжирования разрушит равенство 1 и 4. Для стабильной выдачи ID нужен в отдельном внешнем ORDER BY. Повторение одного и того же случайного порядка три раза не заменяет такого договора.

## Диагностика и края

Начните с ожидаемой таблицы из четырёх строк. Посчитайте строки и платежи отдельно, выведите пары их идентификаторов после JOIN и найдите первый этап, где стоимость стала повторяться. Затем проверьте смысл GROUP BY и вход окна. Сравнивайте все столбцы и порядок; общий checksum способен скрыть две компенсирующие ошибки.

Минимальные края уже есть в наборе: две реальные равные стоимости, отсутствие платежа, отсутствие обоих дочерних наборов и равные итоги разных заказов. Отдельно полезно проверить полностью пустой orders: группировать будет нечего, и сводка должна быть пустой, а не содержать «нулевой заказ». Это дополнительный тест участника, не результат трёх канонических прогонов. Смена смысла неизвестной суммы или фильтра требует нового договора и различающих данных, а не только переноса COALESCE.

## Самопроверка

1. Почему одна итоговая строка заказа не гарантирует правильную сумму?

<details>
<summary>Ответ</summary>

GROUP BY может свернуть неправильный промежуточный набор в правильное число строк. У заказа 1 четыре пары дают одну строку с 400/200; проверка должна проследить вклад каждого исходного ID.

</details>

2. Что означают COUNT(*) = 1 и COUNT(payment_id) = 0 у пустого заказа?

<details>
<summary>Ответ</summary>

LEFT JOIN сохранил левую строку и поставил NULL в правые поля. Это одна строка результата соединения, но ноль платежей. Сравнение amount > 50 для неё неизвестно и не проходит WHERE.

</details>

3. Как сохранить одинаковый ранг и стабильный порядок у заказов 1 и 4?

<details>
<summary>Ответ</summary>

Равенство рангов определяется только стоимостью; dense_rank не оставляет пропусков. Порядок отображения дополнительно различает order_id во внешнем ORDER BY. Если добавить ID в окно, получится другой бизнес-смысл.

</details>

4. Как выбрать между предварительной агрегацией и подзапросами, если заказчик просит «только оплаченные»?

<details>
<summary>Ориентир сильного решения</summary>

Сначала различить условие включения заказа и показатель оплаты; согласовать ожидаемую строку заказа 2 и определение частичной оплаты. Затем сравнить варианты на одном договоре: где видны условия, уникальность строки заказа и независимость сумм. Правильность не выбирают по предполагаемой скорости.

</details>

## Локальный словарь

- Гранулярность (grain) — что означает одна строка на конкретном этапе.
- Размножение строк (fan-out) — появление нескольких пар на одну исходную запись.
- Агрегация — сведение входных значений группы к показателю.
- Окно — вычисление по связанным строкам с сохранением строки входа.
- Peers — строки, равные по выражениям оконного порядка.
- Oracle — независимо заданный ожидаемый результат, здесь таблица из исходных записей.

## Источники и актуальность

Проверено 2026-09-09 на PostgreSQL/psql 18.6. [Таблица поддержки](https://www.postgresql.org/support/versioning/) подтверждает текущую stable-ветку 18 и minor 18.6 на эту дату; это воспроизводимый учебный baseline, а не автоматический выбор production-версии.

- [Соединения, фильтры и группировка](https://www.postgresql.org/docs/18/queries-table-expressions.html) задают состав промежуточных строк.
- [Aggregate expressions](https://www.postgresql.org/docs/18/sql-expressions.html#SYNTAX-AGGREGATES) различает COUNT(*)/COUNT(column) и DISTINCT над значениями; [aggregate functions](https://www.postgresql.org/docs/18/functions-aggregate.html) описывает NULL у SUM пустого входа.
- [Сравнения с NULL](https://www.postgresql.org/docs/18/functions-comparison.html) объясняют неизвестный результат предиката.
- [Оконные функции](https://www.postgresql.org/docs/18/functions-window.html) определяют равные ранги peers, а [ORDER BY](https://www.postgresql.org/docs/18/queries-order.html) — отдельный порядок выдачи.
- [Оконные функции в запросе](https://www.postgresql.org/docs/18/tutorial-window.html): оконная функция выполняет вычисление по связанным строкам, не сворачивая их в одну строку, и видит виртуальную таблицу после `WHERE`, `GROUP BY` и `HAVING`.

Правила о составе строк и вычислениях выше — семантика PostgreSQL. Сохранение всех заказов, нулевая сумма отсутствующих платежей и ранги без пропусков — локальные решения этого отчёта. Выбор раздельных этапов — инженерный вывод из кратности; превосходство по скорости не заявлено.
