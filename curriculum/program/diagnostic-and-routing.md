# Опциональная диагностика читателя

Диагностика — необязательный инструмент читателя. Она не нужна для проектирования программы, не является входным условием и не влияет на полноту материалов. Ширину и глубину программы определяют ролевые competency views, модель уровней и редакционный стандарт.

Если читатель хочет выбрать собственную точку входа, диагностика отвечает на три практических вопроса:

1. С какого уровня начинать внутри каждого трека?
2. Какие темы можно быстро подтвердить и пропустить?
3. Какие 2–4 вертикали выбрать для глубокого прохождения?

## Шкала самооценки компетенции

Оценивается наблюдаемое действие, а не знакомство с термином.

| Балл | Наблюдаемое состояние |
|---|---|
| 0 | Не знаком или не могу объяснить. |
| 1 | Узнаю термин и могу дать неполное объяснение. |
| 2 | Могу решить типовую задачу с документацией или подсказкой. |
| 3 | Самостоятельно применяю в рабочих задачах и диагностирую обычные проблемы. |
| 4 | Проектирую подсистему, объясняю компромиссы и разбираю нетипичные отказы. |
| 5 | Определяю стандарты/направление для нескольких команд и обучаю других. |

## Что может сделать учащийся

### Шаг 1. Выбрать ролевое представление

Выбрать одно основное ролевое представление на ближайший цикл. Сейчас формализуются:

- Backend / Distributed Systems;
- Architecture / Technical Leadership.

Планируются после проверки первых двух views: Platform / SRE / Cloud, Data Engineering, ML Engineering / MLOps, LLM / AI Engineering и семейство Python Developer. Порядок их формализации остаётся открытым вопросом в [`governance/state/OPEN-QUESTIONS.md`](../../governance/state/OPEN-QUESTIONS.md).

Ролевое представление не удаляет остальные треки, а меняет их метку `core`, `depth` или `awareness`. До публикации подходящего RoleView читатель может использовать общую карту треков, но такая личная проекция не считается канонической role view программы.

### Шаг 2. Оценить вертикали

Для каждого трека A1–C1 записать:

- текущий балл 0–5;
- один проверяемый пример из практики;
- главные пробелы или неуверенность;
- желаемую роль трека: `core`, `depth`, `awareness`;
- целевой уровень L1–L5.

Если пример привести невозможно, оценка выше 2 преждевременна.

### Шаг 3. Подтвердить сильные области

Не нужно проходить весь материал заново. Для предполагаемо сильной области достаточно позднее выполнить один диагностический набор:

- объяснить несколько концепций;
- решить мини-задачу;
- разобрать failure/debugging scenario;
- принять и защитить design decision.

Успешное подтверждение позволяет перейти к следующему уровню или оставить тему как справочную.

### Шаг 4. Выбрать маршрут

- После определения состава обязательного core его компетенции рекомендуется доводить до baseline соответствующей RoleView; до закрытия [открытого вопроса о core](../../governance/state/OPEN-QUESTIONS.md) это не нормативное требование программы.
- Выбираются 2–4 depth-вертикали.
- Остальные поддерживаются на awareness-уровне, достаточном для архитектурного взаимодействия.
- C1 развивается параллельно на кейсах и проектах выбранных вертикалей.

## Ограничение самооценки

Число не считается доказательством уровня. Оно помогает выбрать точку входа, а затем корректируется по результатам задач, проектов, интервью и review. Для публичного курса диагностические наборы появятся после competency matrix.
